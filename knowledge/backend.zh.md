### 1. REST vs RPC vs GraphQL vs gRPC

**频率：** 高

**题目：** 请比较 REST、RPC/gRPC 与 GraphQL 三种 API 风格：它们各自如何为接口建模，分别最适合哪类受众？

**答案：** 四种风格的主要差异在于如何为接口建模，以及各自的强项在哪。

- **REST** 把领域建模为由 URL 寻址、用统一 HTTP 动词（`GET/POST/PUT/PATCH/DELETE`）操作的*资源*。它的最大优势是 HTTP 缓存（ETag、`Cache-Control`）、庞大的工具/代理生态以及可发现性——因此是**公开/第三方** API 的默认选择。缺点：弱类型（JSON 默认无 schema）、载荷冗长、以及过度/不足获取。
- **RPC（JSON-RPC）** 把接口建模为*动作/过程*（`createOrder`、`refund`）。它天然对应代码，但失去了 HTTP 缓存语义。
- **gRPC** 是基于 HTTP/2 + protobuf 的 RPC：二进制、schema 优先的代码生成、双向流、多路复用。它是**内部高吞吐**服务间调用的默认选项，但浏览器支持差（需 gRPC-Web），且载荷不透明、较难调试。
- **GraphQL** 暴露单一类型化端点，客户端精确查询所需字段——非常适合**移动端/BFF 聚合**（否则要串联多次 REST 调用）。代价是 N+1 解析器爆炸（需 DataLoader 批处理）、HTTP 缓存困难、以及更复杂的鉴权/限流（成本分析、深度限制）。

**要点：**
- REST：通过 HTTP 可缓存、弱类型、载荷冗长。
- gRPC：流式、代码生成、浏览器支持差（需要 gRPC-Web）。
- GraphQL：查询灵活、有 schema、鉴权与限流复杂。
- 按受众选：公开/第三方 = REST；内部高吞吐 = gRPC；移动端聚合 = GraphQL。

### 2. 幂等性：方法与 key

**频率：** 高

**题目：** 什么使得一个 HTTP 操作具备幂等性？`Idempotency-Key` 请求头如何让服务器安全地处理重试？

**答案：** 一个操作若执行一次或多次都产生相同的可观察服务端状态，就是**幂等**的。按 HTTP 契约，`GET`、`PUT`、`DELETE` 是幂等的（第二次 `DELETE` 只会返回 404/204），而 `POST` 不是——两次 `POST /payments` 会产生两笔扣款。

要让不安全的 `POST` 在重试下也安全，客户端生成一个唯一的 `Idempotency-Key`（通常是 UUID）作为请求头发送。服务器首次收到时处理请求，并存储一条记录 `(key → 请求指纹 + 状态 + 响应体)` 并附带 TTL（通常 24 小时，存于 Redis 或专用表）。之后任何携带相同 key 的重试都**回放已存响应**，而非重新执行。若相同 key 却携带*不同*的请求体，服务器应以 `409/422` 拒绝，以捕获客户端 bug。这能防御网络超时+重试、双击、webhook 重投以及至少一次的队列消费者。

注意幂等 ≠ 安全：`PUT` 会改变状态但幂等；而“安全”方法（`GET`、`HEAD`）完全不改变状态。

**要点：**
- 存储 `(key, request hash, response)`；同一 key 不同 body 时拒绝。
- TTL 通常 24 小时；持久化到 Redis 或专用表。
- 幂等 ≠ 安全：PUT 改变状态但是幂等的。
- 对 webhook、支付和队列消费者至关重要。

### 3. 分页：offset vs cursor

**频率：** 高

**题目：** 请比较 offset 与 cursor（keyset）分页。在大型、并发更新的集合上，两者各自表现如何？

**答案：** **Offset 分页**（`ORDER BY created_at LIMIT 20 OFFSET 10000`）实现极其简单，还能跳到任意页，但数据库必须扫描并丢弃全部 `OFFSET` 行——所以第 500 页远慢于第 1 页（O(offset)）。它还*不稳定*：若用户翻页期间有行被插入或删除，行会漂移，导致条目被跳过或重复显示。

**Cursor（keyset）分页**记住上一行的排序元组并从其后继续：`WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 20`。配上匹配的复合索引，无论翻多深都是 O(log n)，且因为锚定的是值而非位置，在并发写入下稳定。代价是：无法随机跳页——只能上一页/下一页。

最佳实践：在不透明的 base64 cursor 中编码**完整排序元组**（含 `id` 之类的决胜列），以便日后演进格式；返回 `next_cursor` 与 `has_more`；在超大表上避免 `COUNT(*)` 总数。对用户想要页码的小型、有界管理表，offset 仍然没问题。

**要点：**
- Cursor 必须编码完整排序元组以保稳定。
- 不透明的 base64 cursor 隐藏实现、便于演进。
- Offset 在无限滚动 UX 下崩溃。
- 返回 `next_cursor` 与 `has_more`；大表上避免总数统计。

### 4. 限流算法（token/leaky/sliding）

**频率：** 高

**题目：** 请比较令牌桶、漏桶、固定窗口与滑动窗口限流。各自如何处理爆发？你如何在集群范围内执行限流？

**答案：**

- **令牌桶**以稳定速率向桶内补充令牌（上限为容量）；每个请求消耗一个。它允许短时爆发（至桶大小），随后收敛到补充速率——最佳通用选择，也是大多数 API 网关采用的方案。
- **漏桶**以固定速率排空队列，把爆发式输入平滑成恒定输出流；超额被排队或丢弃。当下游需要稳定供给时很好用。
- **固定窗口**按日历窗口计数（对 `key:minute` 计数器做 `INCR`）。便宜简单，但在窗口边缘允许 **2 倍爆发**——00:59 的 100 个请求和 01:00 的 100 个在两秒内全通过。
- **滑窗日志**存储每个请求时间戳，精确但耗内存；**滑窗计数器**对当前与上一固定窗口加权来低成本近似，用极小状态修复边缘问题。

跨集群时在 **Redis** 中集中执行，让每个节点共享计数——`INCR` + `EXPIRE`，或用 Lua 脚本保证原子（避免 INCR 与 EXPIRE 之间的竞态）。返回 `429` 加 `Retry-After` 和 `X-RateLimit-Limit/Remaining/Reset` 头，按 API key + IP + 路由组合设限，并配合并发上限保护慢速下游。

**要点：**
- 返回 `429` 加 `Retry-After` 和 `X-RateLimit-*` 头。
- 按 API key、按 IP、按路由组合设上限。
- Redis `INCR` + EXPIRE 或 Lua 脚本保证原子。
- 与并发上限组合以保护下游服务。

### 5. 认证 vs 授权；OAuth 2.0 流程

**频率：** 高

**题目：** 请辨析认证与授权，并描述 OAuth 2.0 的主要流程。什么时候用 Authorization Code + PKCE，什么时候用 Client Credentials？

**答案：** **认证（AuthN）**证明*你是谁*；**授权（AuthZ）**决定*你能做什么*。OAuth 2.0 是一个**授权**框架：它颁发带 scope 的 access token，让客户端无需看到用户密码即可操作资源。**OIDC** 在其上叠加认证，增加 ID token（一段签名的身份声明 JWT）和 `userinfo` 端点。

主要流程：

- **Authorization Code + PKCE**——有用户在场的 Web 与移动/SPA 应用的默认。PKCE（code verifier/challenge）防止授权码被截获，正因如此它取代了已弃用的 **Implicit** 流。
- **Client Credentials**——机对机、无用户；服务用自己的 client ID/secret 认证换取 token。
- **Device Code**——输入受限设备（电视、CLI），用户在第二台设备上完成授权。
- **Resource Owner Password**——已弃用；它把密码交给客户端，违背了 OAuth 的初衷。

Token 卫生：access token 保持短命（5–15 分钟）并配可轮换的 refresh token；每个请求都校验 `aud`、`iss`、`exp` 与签名；用 scope 做粗粒度授予、用策略引擎（claim/ABAC）做细粒度控制。

**要点：**
- 不再使用 Implicit 流——PKCE 取代之。
- Access token 短命；refresh token 长命且可轮换。
- 每个请求都校验 `aud`、`iss`、`exp` 与签名。
- Scope 做粗权限，claim 做属性，策略引擎做细粒度。

### 6. JWT vs session cookie

**频率：** 高

**题目：** 请比较 JWT 与服务端 session cookie。各自最适合什么场景？用两者分别如何撤销访问？

**答案：** **session cookie** 持有一个不透明的随机 ID；所有状态都在服务端（Redis/DB）。校验请求需要一次查找，但**撤销极其简单**——删掉服务端记录，会话立即失效。对第一方 Web 应用，这是更简单更安全的默认选择。

**JWT** 是自包含的签名声明（`sub`、`exp`、角色）。任何服务都能用签发方的公钥本地校验——无需共享会话存储——因此在微服务间扩展性很好。代价：**过期前难以撤销**（需要黑名单，又把你想避免的查找带了回来）；token 比 cookie 大；而误配置如接受 `alg=none` 或混淆 HS256/RS256 密钥是经典漏洞。

经验法则：**第一方 Web 应用 → 会话**（配安全 cookie）；**API / 分布式服务 → 短命 JWT（5–15 分钟）+ 轮换 refresh token**。凡是放进 cookie 的都要设 `HttpOnly`、`Secure`、`SameSite=Lax/Strict`，并用非对称密钥（RS256/EdDSA）而非所有服务共享的密钥来验签 JWT。

**要点：**
- JWT 缺点：体积、没黑名单难撤销、易误用 `alg=none`。
- 会话 cookie 永远设 `HttpOnly`、`Secure`、`SameSite=Lax/Strict`。
- JWT 保持短（5-15 分钟）；通过轮换的 refresh token 刷新。
- 多服务下用非对称密钥（RS256/EdDSA）验签，而非共享密钥。

### 7. ACID

**频率：** 高

**题目：** 请解释事务的 ACID 特性。哪一个最“含糊”？是什么机制提供了原子性与持久性？

**答案：**

- **原子性（A）**——事务的写入要么全做要么全不做；中途崩溃会回滚一切。
- **一致性（C）**——已提交事务把数据库从一个合法状态搬到另一个，保持不变量（约束、外键）。这是最**含糊**的特性，因为大部分“一致性”是由*你的应用*规则定义的，而不仅是数据库。
- **隔离性（I）**——并发事务表现得（在隔离级别设定的程度上）像串行执行，从而不破坏彼此的视图。
- **持久性（D）**——一旦提交，数据在崩溃或断电后仍存在。

**A** 与 **D** 背后的机制是**预写日志（WAL）**：数据库在确认提交*之前*，先把预期改动追加到顺序日志并 `fsync`。恢复时重放已提交事务、丢弃未完成事务。这正是为什么持久性最终取决于 `fsync` 是否真的落到稳定存储——某些云盘或误配置的控制器会对刷盘“撒谎”，悄悄削弱 D。像 Postgres 这样的 RDBMS 四样全提供；许多 NoSQL 为横向扩展而放宽其中一项或多项（常是隔离性或即时持久性）。

**要点：**
- "C"最模糊——讲的是应用级不变量，不仅是数据库的。
- 持久性取决于 `fsync` 与存储；云盘可能撒谎。
- 隔离级别（下一题）决定你看到的异常。
- WAL 是 A 与 D 背后的机制。

### 8. 隔离级别与异常

**频率：** 高

**题目：** 请逐一讲解 SQL 隔离级别及各自允许的异常。Postgres 的 Serializable 与 Repeatable Read 有何不同？

**答案：** 从最弱到最强：

- **Read Uncommitted**——能看到另一事务未提交的写入（**脏读**）。Postgres 实际从不给你这个，它表现为 Read Committed。
- **Read Committed**（Postgres 默认）——无脏读，但同一查询执行两次可能返回不同结果（**不可重复读**），也可能出现新的匹配行（**幻读**）。
- **Repeatable Read**——整个事务一个稳定快照：无不可重复读。MySQL InnoDB（其默认）中间隙仍允许部分幻读；Postgres 基于快照的 RR 也阻止幻读，但仍允许**写偏斜**（两个事务各自读取一个共享不变量并独立违反它）。
- **Serializable**——结果等价于*某个*串行顺序，连写偏斜也消除。

关键区别：Postgres 的 **Serializable** 用 **SSI（可串行化快照隔离）**，它追踪读写依赖，并*中止*危险环中的某个事务——从而抓住 Repeatable Read 漏掉的写偏斜——而 MySQL 的 Serializable 则退化为在读上加共享锁。更高隔离用吞吐换正确性（更多中止或锁等待），所以**总要把事务包在重试循环里**以应对序列化失败，并对具体热行使用 `SELECT ... FOR UPDATE`，而不是提升整个事务的隔离级别。

**要点：**
- 异常：脏读、不可重复读、幻读、写偏斜、丢失更新。
- Postgres SSI 抓住 Repeatable Read 漏掉的写偏斜。
- 在应用代码中始终处理序列化失败重试。
- 对热行用显式 `SELECT ... FOR UPDATE`，而非提升隔离级别。

### 9. 索引：B-tree vs hash；覆盖

**频率：** 高

**题目：** 请比较 B-tree、hash 与覆盖索引。什么是最左前缀规则，覆盖索引何时有帮助？

**答案：** **B-tree** 是主力索引：它保持 key 有序，因此能服务等值（`=`）、范围（`<`、`BETWEEN`）、前缀（`LIKE 'foo%'`）和 `ORDER BY`——均为 O(log n)。**hash 索引**只支持等值查找，无法帮助范围或排序；很少值得选用（在 Postgres 中直到 v10 才崩溃安全）。

对于像 `(tenant_id, created_at)` 这样的**复合** B-tree，**最左前缀规则**说索引可用于过滤其列的左对齐前缀的查询——`tenant_id`，或 `tenant_id + created_at`，但*不*能单独用 `created_at`。所以列顺序必须匹配你的查询与排序模式。

**覆盖索引**包含查询读取的每一列（通过额外的复合列或 Postgres 的 `INCLUDE (...)`），因此引擎完全从索引作答、跳过回表——这种“纯索引扫描”在热读路径上可快几倍。相关手段：不要给低**选择性**列建索引（布尔列很少有用）；用**部分索引**（`WHERE deleted_at IS NULL`）只索引你查询的行；全文、数组、JSON、地理用 **GIN/GiST**。记住每个索引都增加写入与存储成本，所以加之前要度量。

**要点：**
- 索引选择性：低基数列很少受益。
- 部分索引用于过滤子集（`WHERE deleted_at IS NULL`）。
- 全文/数组/JSON/地理用 GIN/GiST。
- 每个索引都让写变慢——加之前要度量。

### 10. N+1 查询问题

**频率：** 高

**题目：** 什么是 N+1 查询问题，你如何修复和检测它？

**答案：** N+1 发生在：你用一个查询取回 N 个父行，然后懒地为**每个父行再发一个查询**去加载关联——1 + N 次往返。这是经典的 ORM 陷阱（Django 的懒属性、ActiveRecord 关联、GraphQL 解析器）：在开发环境的 10 项列表上一切正常，然后在生产环境列表增长到成千上万时吞吐崩溃，因为每个查询都要付网络 + 规划延迟。

按扇出量修复：

- **JOIN / 预加载** 用于 1:1 或小扇出（Django 的 `select_related`、EF Core 的 `Include`）——一个查询同时返回父与子。
- **`IN (...)` 批量** 用于大扇出（`prefetch_related`）——第二个查询用 `WHERE parent_id IN (...)` 加载所有子，无论 N 多大都共 2 个查询。
- **DataLoader**（GraphQL）——它把一个 tick 内的逐字段解析器调用合并成单个批量查询；GraphQL API 几乎普遍需要它。

检测：在开发期记录 SQL，并在测试中对热端点**断言查询数**（如 `assertNumQueries`），这样重新引入 N+1 的回归会让 CI 失败。N+1 是 ORM 重栈中慢 API 的头号成因。

**要点：**
- 在测试中始终记录 SQL，并对热路径断言查询计数。
- 1:1 或小扇出用 `JOIN`；大扇出用 `IN` 批量。
- GraphQL resolver 几乎总是需要 DataLoader。
- N+1 是 ORM 重栈中慢 API 的最常见原因。

### 11. Join；何时反规范化

**频率：** 高

**题目：** 什么时候应该反规范化而不依赖 join，反规范化又代价何在？

**答案：** **规范化**schema 把每个事实只存一次，从而写便宜、消除更新异常——在一行里改客户名，所有查询都看到。Join 让你在读时重新拼装数据，对大多数 OLTP 负载，一个建好索引的 join 完全够快。

Join 在下列情况不再“免费”：读延迟占主导且某热路径每秒重复执行成千上万次昂贵的 4–5 路 join；或者 join 必须**跨分片/分区**，把本地操作变成散列-聚集。这时就**反规范化**——把所需列复制到你读取的行上，或预计算结果。

代价是复制的数据会漂移，所以反规范化*总*需要**同步策略**：数据库触发器、CDC（变更数据捕获）把更新流到副本、或小心的双写。中间地带避免手写这些：**物化视图**（周期或增量刷新）与**计算/生成列**。经验法则：读多 → 倾向反规范化；写多 → 保持规范化。在 NoSQL 中你通常默认反规范化并从一开始就围绕访问模式建模。

**要点：**
- 内连 vs 左连 vs 全外连——按语义选，不要凭性能直觉。
- 反规范化需要同步策略（触发器、CDC、双写）。
- 读多 → 反规范化；写多 → 规范化。
- 周期刷新的物化视图常是最佳折中。

### 12. 范式 1NF-BCNF

**频率：** 高

**题目：** 请定义 1NF 到 BCNF 的范式。为什么大多数应用停在 3NF？

**答案：** 每一级范式通过收紧允许的函数依赖来消除一类冗余：

- **1NF**——每列只存单个原子值；无重复组或塞进一个字段的数组。
- **2NF**——1NF *加上*无**部分依赖**：在复合键下，任何非键列不得仅依赖该键的一部分。
- **3NF**——2NF *加上*无**传递依赖**：非键列不得依赖另一个非键列（如同时存 `zip` 和它推出的 `city`）。
- **BCNF**——更严格的 3NF：**每个决定因素都必须是候选键**，堵住表有重叠候选键时 3NF 允许的边界情况。

实际应用瞄准 **3NF**，因为它几乎消除了所有更新异常，同时保持 schema 可查询，而进到 BCNF 对典型设计很少改变什么。再往后就是刻意的权衡：过度规范化会迫使每次读都做过多 join，所以分析系统故意反规范化为**星型/雪花**schema，而 **JSON/JSONB 列**是面对稀疏或快变属性、你又不想建表时的实用逃生口。

**要点：**
- 规范化最小化更新异常和存储重复。
- 过度规范化导致过多 join。
- 分析中的星型/雪花 schema 故意反规范化。
- JSON 列是稀疏属性的实用逃生口。

### 13. 分片（范围/哈希/地理）

**频率：** 高

**题目：** 请比较范围、哈希与地理分片。如何选择分片 key，为何它日后很难改？

**答案：**

- **范围分片**按连续的 key 区间拆分（如 `A–M`、`N–Z`，或按日期）。范围扫描与“最近”查询保留在一个分片上，但单调递增的 key（时间戳、自增 id）会把每个新写都发到*同一*分片——形成热点。
- **哈希分片**按 `hash(key) % N` 安放行，均匀铺开负载、消除热点，代价是失去范围扫描（一个范围现在命中每个分片）。
- **地理分片**按区域路由，以获得低延迟和数据驻留/合规（欧盟数据留在欧盟）。

一个好的**分片 key** 既给均匀分布*又*给查询本地性——理想情况下你最常见的查询能从单个分片作答，且一个租户的数据住在一起，从而避免跨片 join 和分布式事务（能按租户路由就按租户）。分片 key **难以更改**，因为它决定了每一行的物理位置：改它意味着一边服务流量一边重新哈希并搬迁整个数据集，所以要按未来 3–5 年设计。用**一致性哈希**使增/删节点只重映射 ~1/N 的 key，并对范围方案**预先拆分**以避免初始热点。

**要点：**
- 分片 key 难改——按未来 3-5 年设计。
- 一致性哈希在节点变化时最小化再平衡。
- 范围方案预拆分避免初始热点。
- 避免分布式事务；可能时按租户路由。

### 14. 乐观 vs 悲观锁

**频率：** 高

**题目：** 请比较乐观锁与悲观锁。各自适用何时，在 API 层如何体现？

**答案：** **乐观锁**假设冲突罕见：你连同一个 `version`（或 `updated_at`/etag）一起读行，然后以 `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?` 写回。若**更新了 0 行**，说明别人先改了——你检测到冲突并重试（或报给用户）。读写之间不持锁，所以低争用下扩展性很好。

**悲观锁**假设冲突常见：`SELECT ... FOR UPDATE` 取一个行锁，其他写者阻塞直到你提交。这对热行（库存计数器、座位预订）给出可预测、串行化的行为，避免白费的重试开销，但降低并发并有死锁风险。

低争用或重试便宜时选乐观；高争用行或重新计算昂贵时选悲观。实践要点：总带专用的**版本列**；在 HTTP 层，`If-Match`/`ETag` *就是*乐观锁（服务器用 `412 Precondition Failed` 拒绝陈旧写）；绝不跨**用户思考时间**持悲观锁（表单编辑期间持锁会阻塞所有人）；用 `SELECT ... FOR UPDATE SKIP LOCKED` 构建无争用工作队列，让每个 worker 抓到不同的未锁定行。

**要点：**
- 乐观永远带整数/UUID 版本列。
- HTTP If-Match/ETag 是 API 层的乐观锁。
- 悲观锁跨用户思考时间持有 = 灾难。
- `SKIP LOCKED` 启用无争用的工作队列模式。

### 15. CAP 与 PACELC

**频率：** 高

**题目：** 请说明 CAP 定理及 PACELC 如何扩展它。CAP 中的“一致性”指什么？

**答案：** **CAP** 说当发生**网络分区**时，分布式系统必须在**一致性**（每次读都看到最新写）与**可用性**（每个请求仍得到非错误响应）之间二选一——分区时两者不可兼得。关键在于，CAP 描述的是*分区期间*的行为，而非稳态；其“C”指**线性化**，比 SQL 的 ACID “C” 更强。

**PACELC** 补全了图景：*若*分区（P），则在可用性与一致性间权衡（PA/PC）；**否则**（E，正常运行）你仍要在**延迟与一致性**间权衡（EL/EC）。这个 Else 分支才是你每天真正在做的权衡——更强一致性意味着协调（quorum、共识）因而更大延迟。

真实系统分类：Dynamo/Cassandra 是 **PA/EL**（保持可用与快速，接受最终一致），而 Spanner、etcd、ZooKeeper 是 **PC/EC**（偏向一致，接受更高延迟或不可用）。许多系统可按操作调节——Cassandra 允许你每次查询选 `ONE` vs `QUORUM`。不要仅凭 CAP 分类选数据库；日常的**可运维性**（备份、故障转移、可观测性）通常更重要。

**要点：**
- CAP 讲分区期间行为，不是稳态。
- CAP 的"一致性"= 线性化，强于 SQL 的"C"。
- 延迟 vs 一致性折衷（PACELC 的 LC）是日常那个。
- 不要只凭 CAP 选数据库——可运维性更重要。

### 16. cache-aside vs read-through vs write-through vs write-behind

**频率：** 高

**题目：** 请比较 cache-aside、read-through、write-through 与 write-behind 缓存。哪个是安全的默认，为什么？

**答案：**

- **Cache-aside（懒加载）**——应用检查缓存；miss 时读数据库、回填缓存并返回。失效由应用掌控。这是**默认**选择：简单、有弹性（缓存宕机只意味着更多数据库读），且只缓存真正被请求的数据。
- **Read-through**——应用总是问缓存，缓存库在 miss 时从数据库加载。应用代码更干净，但你被绑定到一个懂你数据源的缓存。
- **Write-through**——写同时进缓存并在返回前同步写数据库。缓存永不陈旧，代价是写延迟更高；配合 read-through 使读保持预热。
- **Write-behind（回写）**——缓存立即 ack 写，异步刷到数据库。写延迟最低、对写爆发很好，但刷盘前崩溃会**丢数据**，所以需要耐久队列/日志才安全。

除非有特定理由，否则选 cache-aside。无论选哪种，即便显式失效也要设 **TTL** 作为兜底，这样一次遗漏的失效不会永远提供陈旧数据。

**要点：**
- Cache-aside 把失效负担放到应用。
- Write-through 以写成本消除缓存/数据库偏差。
- Write-behind 需要耐久队列才能安全。
- 即便有显式失效也总要设 TTL。

### 17. 缓存失效策略

**频率：** 高

**题目：** 主要的缓存失效策略有哪些，为何要把 TTL 与显式失效结合？

**答案：** “计算机科学只有两件难事……”——各选项在陈旧与管道复杂度之间权衡：

- **TTL**——条目到期自动失效。极简且自愈，但允许有界的陈旧，也不会更快推送新数据。
- **写时显式失效**——源变更时删/改 key。正确且即时，但管道重：每条写路径都得知道自己影响的每个 key，漏掉一条就会无限期提供陈旧数据。
- **key 中嵌入 version/etag**——把版本写进 key（`user:42:v7`）；bump 版本就瞬间“失效”全部而无需删除，跨部署很好用。
- **pub/sub 扇出**——广播失效（如 Redis keyspace 通知），让每个节点丢掉该 key。

把 **TTL + 显式失效**组合做纵深防御：显式失效在正常路径上保鲜，TTL 则在遗漏一次失效时封顶损失。配套手段：**雪崩保护**（锁或 single-flight，使 miss 时只有一个请求重建热 key）、**负缓存**（短暂记住“未找到”以阻止重复打库）、**按查询形状命名 key**（`user:42:posts:page:1`），以及**软 TTL + 后台刷新**让热 key 保持预热、用户从不为 miss 买单。

**要点：**
- miss 时雪崩保护（锁、single-flight）。
- 负缓存——短暂记住"未找到"。
- 按查询形状的 key：`user:42:posts:page:1`。
- 软 TTL + 后台刷新让热 key 保持温。

### 18. 线程 vs 进程 vs 协程 vs 异步

**频率：** 高

**题目：** 请比较线程、进程、协程与异步事件循环。CPU 密集与 I/O 密集分别该怎么选？

**答案：**

- **线程**共享父进程的内存，由内核抢占式调度。通信便宜（共享数据）但也是隐患——你需要锁，并有竞态和死锁风险。上下文切换花微秒级，每线程占 MB 量级栈。
- **进程**完全隔离（独立地址空间），更安全、能独立用满所有 CPU 核，代价是创建更重、IPC（管道、共享内存、序列化）更贵。
- **协程**（goroutine、Java 虚拟线程、`asyncio` 任务）是用户态“线程”：KB 级栈，协作调度或调到小内核线程池上，能并发跑几十万个。
- **异步事件循环**是单线程通过就绪通知（epoll/kqueue）复用多个 I/O，在 `await` 点切换任务。

按瓶颈选择：**I/O 密集**（数据库调用、HTTP 扇出）→ 异步/协程以极小成本换巨大并发；**CPU 密集**→ 需真并行，用进程（Python 里绕开 GIL）或真并行线程的运行时（Go、Java）。经典陷阱是在异步路径中混入**阻塞调用**——一个同步的数据库或文件系统调用会卡住整个事件循环、静默拖垮吞吐。

**要点：**
- CPU 密集 → 进程（Python）或线程（Go/Java）。
- I/O 密集 → 异步/协程做最大并发。
- 异步混阻塞调用 = 静默停顿。
- 选与工作负载匹配的运行时。

### 19. Python GIL

**频率：** 高

**题目：** 什么是 Python 的 GIL，它如何影响你对 CPU 密集与 I/O 密集工作的选择？

**答案：** **全局解释器锁**是 CPython 中的一个互斥锁，令任何时刻只有**一个线程能执行 Python 字节码**。它存在是因为 CPython 的内存管理（引用计数）若无它就非线程安全，GIL 让解释器更简单、单线程代码更快。

实际后果：线程给不了你 **CPU 并行**——开 8 个线程算数仍只跑在一个核上。但 I/O 操作（socket、磁盘、`time.sleep`）在等待时**会释放 GIL**，所以线程*确实*对 **I/O 密集**负载有帮助（线程大多时间反正停在那里等网络）。

对 **CPU 密集**工作有三个选项：**`multiprocessing`**（独立进程，各自有解释器和 GIL，经 pickle/共享内存通信）；在重计算时**释放 GIL 的原生扩展**（NumPy、Cython `nogil` 块、Rust/C 扩展）；或新的**无 GIL 构建（PEP 703，3.13+ 实验性）**彻底移除 GIL。一个警告：GIL **不会**让你的代码免于竞态——它只保证一次一个字节码操作，多步操作（`x += 1`）在应用层仍需锁才能原子。

**要点：**
- 异步 + 线程 + 进程是互补工具。
- C 扩展可在数值计算中释放 GIL。
- PEP 703（无 GIL）是 opt-in 且实验性。
- GIL 不防止应用逻辑中的竞态。

### 20. 竞态 vs 死锁 vs 活锁

**频率：** 高

**题目：** 请区分竞态、死锁、活锁与饥饿。各自如何检测和预防？

**答案：** 四者都是并发失败模式，但特征不同：

- **竞态**——正确性取决于对共享状态并发访问的*时序/交错*。经典形态是 **check-then-act**：两个线程都读到 `balance == 100`、都减 100，于是双重花销。阴险之处在于它非确定——测试中可能百万次通过，只在生产负载下交错对上时才损坏数据。
- **死锁**——两个以上线程各持对方所需的锁，成环，无一能进。需同时满足 Coffman 四条件（互斥、持有并等待、不可抢占、循环等待）——破其一就不会死锁。
- **活锁**——线程*在*运行并相互响应而变状态，却无前进（两人在走廊里左右互让）。常见于朴素重试/退避不断碰撞。
- **饥饿**——某线程因其他线程持续抢赢而被永久剥夺资源（如写者被连续读者饿死）。

**预防：**用锁或原子/CAS 护共享状态；施加**全局锁顺序**使环不能形成；加**带抖动的随机退避**破活锁；用公平队列避免饥饿。最好是用**不可变性**与**消息传递**（Go channel、actor 模型）避开整个问题类。**检测：**Go 的 `-race`、C/C++ **ThreadSanitizer**、Java 的 `jcstress`、严格异步模式，加上猛撞并发路径的压力/模糊测试，因为普通单测很难暴露这些。

**要点：**
- 竞态常在生产负载下才可见。
- 检测：`-race`（Go）、TSan（C++）、`pytest-asyncio` 严格模式。
- 用压力 + 模糊测试并发路径。
- 优先不可变 / 消息传递而非共享可变状态。

### 21. 互斥锁 vs 信号量 vs 条件变量

**频率：** 高

**题目：** 请比较互斥锁、信号量与条件变量。为何必须在循环中重查条件变量的谓词？

**答案：**

- **互斥锁（Mutex）**——同时恰好**一个**持有者的互斥。它护住临界区，使只有一个线程碰共享状态。所有权重要：通常只有加锁者才能解锁。
- **信号量（Semaphore）**——**N 个许可**的计数器；最多 N 个线程可并发持有。`acquire()` 减一（到 0 时阻塞），`release()` 加一。用于限制资源池（“最多 10 个并发数据库连接”）或粗略限流。二元信号量（N=1）像互斥锁但无所有权，任何线程都能释放。
- **条件变量（Condition variable）**——让线程**等待一个谓词**为真而无需忙等。它总与互斥锁配对：加锁、检查谓词，若为假则 `wait()`（原子地释锁并休眠）；另一线程的 `signal()`/`notify()` 唤醒它重新拿锁并重查。

必须在 **`while` 循环而非 `if`** 中重查谓词，原因有二：（1）**伪唤醒**——操作系统可能无任何信号就唤醒等待者；（2）多等待者时，其他线程可能在唤醒与你重新拿锁之间消费了条件。读多数据用 **RWMutex**（共享读锁、独占写锁）提升并发。最佳实践：总在 `defer`/`finally` 释锁以异常安全；实时系统当心**优先级反转**（用优先级继承）；**自旋锁**仅用于多核上极短临界区；Go 中能用 channel 就优先于显式锁。

**要点：**
- 始终释放互斥锁（defer/finally）——异常安全。
- 实时系统当心优先级反转。
- 自旋锁仅用于多核上极短临界区。
- Go 中 channel 常更干净地替代显式锁。

### 22. Kafka vs RabbitMQ vs SQS

**频率：** 高

**题目：** 请比较 Kafka、RabbitMQ 与 SQS。各自何时选用，保留模型有何不同？

**答案：** 它们代表两种不同心智模型——**日志** vs **队列**。

- **Kafka** 是分布式、只追加的**提交日志**。消息按保留窗口（按时间或大小，如 7 天）持久且**可回放**——新消费者能倒到 offset 0 重新处理历史，这使它理想用于**事件溯源、流处理、向多个独立消费者扇出**。排序是每分区级；吞吐极高（百万/秒），因为实质上是顺序磁盘写 + 零拷贝读。代价是运维重（broker、分区、ZooKeeper/KRaft），除非用托管的 MSK/Confluent。
- **RabbitMQ** 是带丰富路由的经典 **broker**：生产者发到**交换机**，后者按绑定规则（direct、topic、fanout、headers）路由到队列。它提供按消息 ack、优先级、TTL、死信队列——对**工作队列、RPC、复杂路由**优秀。消息通常**ack 后删除**，吞吐低于 Kafka。
- **SQS** 是完全托管、零运维的 AWS 队列：**至少一次**投递，默认无序（可选 **FIFO** 变体以更低吞吐提供排序 + 去重）。完美适合 **AWS 原生后台 worker**，你想要一个队列又永不想跑 broker。

经验法则：需回放/流式/高扇出 → **Kafka**；需灵活路由/自建工作队列 → **RabbitMQ**；想要 AWS 上的托管队列 → **SQS**。

**要点：**
- Kafka = 日志；Rabbit/SQS = 队列。心智模型不同。
- Kafka 按时间/大小保留；Rabbit/SQS ack 时丢。
- 吞吐：Kafka >> Rabbit > SQS 标准。
- 运维：SQS 零，Rabbit 中，Kafka 重（或通过 MSK/Confluent 托管）。

### 23. Exactly-once vs at-least-once vs at-most-once

**频率：** 高

**题目：** 请解释 at-most-once、at-least-once 与 exactly-once 语义。为何真正的 exactly-once 如此困难，现实目标是什么？

**答案：** 三种保证在**丢失**与**重复**之间权衡：

- **At-most-once**——发完不管（发送不等 ack）。无重复，但崩溃或丢包会**丢失**消息。适合丢一个数据点也无所谓的一次性遥测。
- **At-least-once**——生产者重试到拿到 ack，消费者处理后才 ack。不丢，但慢 ack 后重试、或消费者*处理后提交前*崩溃会产生**重复**。
- **Exactly-once**——每个效果发生一次，既不丢也不重。难在需要跨*两个*系统（broker 和你的数据库）原子性，而“投递-处理-ack”在步骤间有无法避免的崩溃窗口。

关键区分：不可靠网络上的 **exactly-once 投递**基本不可能（两将军问题），但 **exactly-once 处理**可行——只要把*效果*做成幂等，重复投递就无害。靠**幂等键 + 去重表**，或把结果与 offset 写在**一个事务**里。Kafka 的 EOS（事务 + 幂等生产者）能做到 **Kafka 到 Kafka**，但一旦碰到外部系统（发邮件、刷卡）就需要**事务性 outbox** 或 2PC 模式。所以现实工程目标是**至少一次投递 + 幂等消费者**——总把消费者设计成能容忍看到同一消息两次。

**要点：**
- "Exactly-once 投递"多是营销；"exactly-once 处理"是真实的。
- 幂等键 + 去重表是你构建 exactly-once 的方式。
- Kafka 事务覆盖 Kafka 到 Kafka；桥接外部系统需要 outbox/2PC 模式。
- 始终设计消费者处理重复。

### 24. Kafka 分区/消费者组/offset

**频率：** 高

**题目：** 请解释 Kafka 的分区、消费者组与 offset。分区数与消费者并行度是什么关系？

**答案：** 一个 **topic** 拆为 **N 个分区**，每个都是独立、有序、只追加的日志。这种分区让 Kafka 能水平扩展——分区位于不同 broker、并行读取。

- **生产者路由：**带 key 的消息按 `hash(key) % partitions` 放置，所以**相同 key 落到相同分区**、保持相对有序（无 key 的轮询）。排序仅在分区*内*保证，绝不跨整个 topic。
- **消费者组：**共享 `group.id` 的消费者分摊分区，组内**每分区最多一个消费者**。所以 6 分区的 topic，一组内最多 6 个消费者做有效工作——**分区数是消费并行度的硬上限**。不同的组各自独立拿到完整流（扇出）。
- **offset：**每个分区跟踪每个消费者组的读位置（offset），提交回 Kafka（`__consumer_offsets` topic）。重启或再平衡时从上次提交的 offset 恢复。

运维含义：先预留足够分区，因为后加分区会破坏 key→分区映射（从而破坏排序）；**处理*后*提交 offset** 以得至少一次（先提交后处理会在崩溃时丢消息）；**再平衡**（消费者加入/离开）会短暂暂停消费，所以用**协作/增量再平衡**最小化 stop-the-world；谨慎选 key，因为它同时定义你的**排序边界**与**负载分布**（低基数 key 会造热分区）。

**要点：**
- 分区数决定了每组消费者并行度的上限。
- 再平衡暂停消费——协作式再平衡最小化干扰。
- 在处理后提交 offset，不是之前（至少一次）。
- key 选择 = 排序边界 AND 负载分布。

### 25. SQL 注入——参数化查询

**频率：** 高

**题目：** 如何防御 SQL 注入，为什么参数化查询是首要防线？

**答案：** SQL 注入发生在用户输入被拼进查询串、从而被**当作 SQL 代码解析**时——经典的 `"... WHERE name = '" + input + "'"`，当 `input = "' OR '1'='1"` 时把一次查找变成全表导出（或 `'; DROP TABLE users;--`）。

首要且近乎彻底的防线是**参数化查询 / 预编译语句**：你通过**独立通道**分别发送 SQL 模板和值——`db.query("SELECT * FROM users WHERE id = $1", id)`。数据库先编译查询计划，再把值纯粹作为*数据*绑定，所以任何输入都无法改变查询结构。无论攻击者输入什么都有效。**ORM** 默认参数化；危险区是手写原生 SQL 和动态查询构建器。注意参数绑定的是*值*而非标识符——表名/列名无法参数化，要用白名单校验。

**字符串转义**（给特殊字符加引号）只是脆弱的回退——跨编码/方言极易出错——绝不能当主防御。叠加纵深防御：把**所有**输入（含来自上游服务和消息队列的值）都当敌意；记住**存储过程并非自动安全**（内部仍可能拼接）；用**最小权限数据库用户**跑应用（无 DDL/`DROP`、只限所需表），使一次成功注入被限制；并在 CI 加静态分析（**semgrep、CodeQL**）在合并前抓出拼接查询。

**要点：**
- 把所有输入当敌意——包括来自上游服务的。
- 存储过程有助但非银弹。
- 用最小权限数据库用户（应用角色无 DDL）。
- 静态分析（semgrep、CodeQL）抓拼接式查询。

### 26. 密码存储（bcrypt/argon2、加盐、加胡椒）

**频率：** 高

**题目：** 如何安全存储密码，加盐与加胡椒分别防御什么？

**答案：** 绝不明文存储，也绝不用**快**哈希（MD5、SHA-1、SHA-256）——现代 GPU 每秒算数十亿次 SHA-256，泄漏的快哈希表几乎瞬间被破。要用刻意**慢、内存困难的密钥派生函数**：**Argon2id**（当今首选）、**scrypt** 或 **bcrypt**。

- **盐（Salt）**——每用户唯一的随机值，与哈希一起存（KDF 库替你生成并内嵌）。它使相同密码的两个用户得到不同哈希，从而**击败预计算彩虹表**、阻止攻击者一次破解多个账户。盐不是秘密。
- **胡椒（Pepper）**——单个应用级密钥，在哈希*之前*混入（或用它加密整个哈希），与数据库**分开存**（放在密钥管理器/HSM，而非 users 表）。它加一道防线：若只有**数据库**泄漏而胡椒没泄，哈希实际上不可破。

**调工作因子**（Argon2 内存/迭代、bcrypt cost），使一次哈希在生产硬件上约 **100–250 毫秒**——慢到瘫痪暴力破解，快到不影响登录体验。补充实践：选 Argon2id 是因为它同时抗 **GPU** 和**侧信道**攻击；bcrypt 会在 **72 字节**处静默截断，若允许长密码就先用 SHA-256（base64 编码）预哈希；提高 cost 参数后**在成功登录时重哈希**（此刻你短暂持有明文）；并**限流/锁定**认证尝试以钝化在线暴力破解。

**要点：**
- Argon2id 抗 GPU 与侧信道攻击。
- bcrypt 72 字节上限是脚枪——先用 SHA-256 预哈希。
- 成本参数提高时登录时重哈希。
- 限流认证尝试拖慢暴力破解。

### 27. PUT vs PATCH

**频率：** 中

**题目：** 请比较 PUT 与 PATCH。省略的字段会怎样，如何防止丢失更新？

**答案：** **PUT 用你发送的表示替换整个资源**——是完整覆盖，所以你*省略*的任何字段通常被当作“设为空/默认”，而非“保持不变”。**PATCH 应用部分更新**——只发要改的字段，其余原样保留。

PATCH 有两种标准报文格式：

- **JSON Merge Patch (RFC 7396)**——发一个部分对象；出现的 key 覆盖，`null` 表示“删除该字段”。简单可读，但*因为* `null` 被重载为删除，它**无法区分“设为 null”与“移除”**，也无法表达数组元素操作（必须重发整个数组）。
- **JSON Patch (RFC 6902)**——有序的操作列表（`{"op":"replace","path":"/email","value":...}`，外加 `add`/`remove`/`move`/`test`）。表达力强得多（定向数组编辑、条件 `test` 操作），但更冗长、更难手写。

当客户端天然持有整个文档、且你想要可预期的替换语义时选 **PUT**；稀疏编辑选 **PATCH**，尤其**并发写者触碰不相交字段**时（两个客户端 patch 不同字段不会互相覆盖）。幂等性不同：**PUT 幂等**（重复得到相同状态），而 **PATCH 仅当 patch 本身幂等时才幂等**（merge-patch 通常是；对数组 `add` 不是）。所有情况都配合 **`ETag` + `If-Match`**：客户端发它读到的版本，若资源在其下变了，服务器用 `412 Precondition Failed` 拒绝写入——防止丢失更新问题。

**要点：**
- PUT 幂等；PATCH 只有当 patch 本身幂等时才幂等。
- JSON Merge Patch：简单，无法表达数组操作或 null vs 缺失。
- JSON Patch：操作列表，更具表达力，写起来更难。
- 始终配合 ETag/If-Match 防止丢失更新。

### 28. API 版本化（URL/header/内容协商）

**频率：** 中

**题目：** 请比较 URL、header 与内容协商三种 API 版本化。什么样的版本化策略能压低维护成本？

**答案：** 三种放置方式在整洁与可运维间权衡：

- **URL 版本化**（`/v1/users`）——最**可发现**（日志、浏览器、curl 里都可见）、天然**缓存友好**（不同 URL 是不同缓存键）、在网关易路由。多数公开 API（Stripe、GitHub）实际都这么用。纯粹主义者不喜欢“同一”资源有多个 URL。
- **Header 版本化**（`API-Version: 2`）——保持 URL 干净、让一个 URL 演进，但版本在访问日志和浏览器测试里**不可见**，缓存必须被告知按该 header `Vary`。
- **内容协商**（`Accept: application/vnd.acme.v2+json`）——最“RESTful”（版本化*表示*而非资源），但冗长、手工测试别扭。

合理的**策略**比机制更重要：偏好**加法式、向后兼容**的变更（新可选字段、新端点、新枚举值），只在真正破坏性变更时升**大**版本；把自己限制在**约 2 个并存大版本**以免支持与测试爆炸；用 **`Deprecation` 与 `Sunset` 头**加书面时间表宣告移除；并给你的**错误契约与 webhook**（不只是正常路径载荷）也版本化。GraphQL 通过演进一套 schema、把字段标 `@deprecated` 让客户端迁移，从而完全绕开版本化。

**要点：**
- 偏好加法式、向后兼容的变更；只有破坏性变更才升大版本。
- 最多维护 2 个大版本以约束支持成本。
- 公布弃用时间表并发出 `Sunset` / `Deprecation` 头。
- GraphQL 通过字段弃用避免版本号。

### 29. API 网关职责

**频率：** 中

**题目：** API 网关做什么，它与服务网格有何不同？

**答案：** **API 网关**是所有外部客户端在流量到达服务前先命中的单一入口（“前门”）。它集中**横切关注点**，使每个后端服务不必各自重实现：

- **TLS 终止**与证书管理。
- **认证/授权**——校验 JWT 或 API key，使服务能信任一个内部身份 header。
- 按客户端/key 的**限流与配额**。
- **路由**到正确后端，加上**请求/响应变换**（协议转换、header 改写、响应塑形）。
- **韧性**——对不稳定后端的重试、超时、断路器。
- **可观测性**——统一的日志、指标、追踪传播，常还集成 **WAF** 应对 L7 攻击。

关键是它应保持**薄**：它处理管道，而**业务逻辑留在服务里**。把领域逻辑塞进网关，它就成了部署瓶颈和每个团队都要协调的单点。例子：Kong、Envoy、NGINX、AWS API Gateway、Apigee。

网关 vs 网格的区别在于**南北向 vs 东西向流量**。网关治理**南北向**——从集群外进入的流量。**服务网格**（Istio、Linkerd）治理**东西向**——集群*内*的服务间调用——通过 sidecar 代理处理 mTLS、重试和流量切换。二者互补：网关在边缘，网格在内部。

**要点：**
- 把横切关注点从服务卸载。
- 别把领域逻辑放进网关——会成为瓶颈。
- 用服务网格（Istio/Linkerd）处理东西向；网关处理南北向。
- 配合 WAF 处理 L7 攻击。

### 30. 长任务：202+轮询 vs webhooks vs SSE

**频率：** 中

**题目：** 处理长任务时，202+轮询、webhooks 与 SSE/WebSocket 各适合什么场景？

**答案：** 绝不要让请求线程阻塞在慢工作上——立即返回，结果带外投递。三种模式：

- **202 Accepted + 轮询**——接受任务，返回 `202` 和任务 URL，让客户端轮询 `GET /jobs/{id}` 直到完成。**最简单、对防火墙友好**（纯客户端发起的 HTTP，到处能用），客户端控制节奏。缺点：额外请求量及完成到下次轮询间的延迟——用 `Retry-After` 提示缓解。
- **Webhooks**——就绪时把结果推到客户端注册的回调 URL。**请求更少、几乎即时**，但客户端必须**托管一个公开端点**，而*你*现在拥有投递可靠性（签名、重试、DLQ）。最适合服务间集成。
- **SSE / WebSocket**——在活连接上流式推送进度。**对显示进度条的浏览器 UX 最佳**。单向服务端→客户端流用 **SSE**（更简单、自动重连、跑在普通 HTTP 上）；需**双向**实时（聊天、协同编辑）时用 **WebSocket**。

三种都应：**同步返回任务 ID** 使客户端总有句柄；**持久化任务状态**使重试提交返回同一任务而非重复启动；可行时**同时**提供轮询与 webhooks，简单客户端轮询、高级的订阅。

**要点：**
- 永远同步返回任务 ID；不要在长任务上阻塞。
- 可行时同时提供轮询与 webhooks。
- 持久化任务状态，让重试返回同样结果。
- 给出合理轮询建议（`Retry-After`）以避免猛击。

### 31. Webhook 设计：重试、签名、回放

**频率：** 中

**题目：** 如何设计一个健壮的 webhook 投递系统，涵盖签名、重试与回放防护？

**答案：** 生产级 webhook 系统得熍过不受信接收方、不稳定网络和恶意回放。

**签名（真实性 + 完整性）：**用共享密钥对*原始*请求 body 拼上时间戳计算 **HMAC-SHA256**，两者都放入 header（`X-Signature`、`X-Timestamp`）。接收方重算 HMAC 并用**恒时间**相等比较。签**原始字节**——若签一个解析后重序列化的对象，空白/key 顺序差异会破坏校验。

**回放防护：**把时间戳包含在签名载荷里，让接收方**拒绝早于小窗口（~5 分钟）的一切**，使捕获的请求无法稍后重发。配合接收方去重的**事件 ID**，因为重试意味着同一事件可能合法地到达多次（至少一次）。

**重试：**任何非 2xx 或超时时，在拓展窗口（数小时到几天）内用**指数退避 + 抖动**重试，然后把无法投递的事件停入**死信队列**供手动回放。快速响应——接收方应返 **`202`** 并异步处理而非内联重活。

**运维：**提供**回放/重发工具**和测试事件功能；支持**双活跃密钥的密钥轮换**（用新的签，重叠期仍接受旧的）；并**文档化**投递 SLA、最大重试窗口、载荷 schema 和你的**源 IP 段**以便接收方白名单。

**要点：**
- 对原始 body 签名——JSON 重新序列化会破坏签名。
- 提供回放工具与密钥轮换机制（两个活跃 key）。
- 文档化投递 SLA、最大重试窗口与 IP 段。
- 让接收方用 202 + 处理队列异步确认。

### 32. 向后兼容

**频率：** 中

**题目：** 哪些 API 变更是向后兼容的、哪些是破坏性的？如何安全地演进 schema？

**答案：** **加法式变更是安全的**，因为现有客户端会直接忽略它们不认识的东西：新增**可选**字段、新端点、新**可选**请求参数、新**枚举值**（仅当客户端能容忍未知值时才安全——很多并不能，所以对新枚举值要谨慎）。

**破坏性变更**迫使客户端同步更新：删除或**重命名**字段、**收紧校验**（把可选变必填、缩小最大长度）、**改字段类型**（string → number）或其**单位/含义**、改**默认行为**、或改客户端据之分支的**错误码/状态**。

首要铁律：**绝不重用现有字段**——若含义变了，就加一个*新*字段并弃用旧的。谨慎对待 **Postel 法则**（“接受时宽容”）：过宽松的输入解析会掩盖客户端 bug 并把你困住，因为别人依赖的行为日后无法收紧。**工具与灰度：**类型化 schema 用 protobuf 的**字段号**（绝不重用）和 GraphQL 的 **`@deprecated`** 使兼容性显式；在 CI 跑**消费者驱动的契约测试**（Pact），使会破坏真实消费者的生产者变更构建失败；公布带 `Sunset` 头与时间表的弃用策略；并把风险变更置于**特性开关**后，全局切换前对比新旧客户端行为的指标。

**要点：**
- 永远不要复用字段含义——加新字段。
- 类型化 schema 用 protobuf 字段号 / GraphQL `@deprecated`。
- 在消费者与生产者之间跑契约测试（Pact）。
- 用特性开关推出，并对新旧客户端做指标对比。

### 33. 错误模型（HTTP 状态码 + RFC 7807）

**频率：** 中

**题目：** 如何用 HTTP 状态码和 RFC 7807 设计一致的 API 错误模型？

**答案：** 先**正确使用 HTTP 状态码**——`4xx` 意味着*客户端*得改什么，`5xx` 意味着*服务器*出错。常见映射：

- **400** 报文/语法无效；**401** 缺失或无效凭证（认证）；**403** 已认证但无权（授权）；**404** 资源不存在；**409** 冲突（版本不匹配、重复）；**422** 请求格式良好但**语义**无效（校验失败）。

在状态码之上，返回**一致的、机器可读的 body**。**RFC 7807 Problem Details**（`application/problem+json`）用 `type`（标识错误类的 URI）、`title`、`status`、`detail`（人读细节）、`instance`（哪次发生），加上你自己的**扩展**成员（如 `validation_errors` 数组）标准化形状。总带一个**稳定的 `code`** 字符串供客户端编程分支（单靠状态码太粗），以及 **`request_id`/关联 ID** 使支持人员能在日志中追到确切失败。

护栏：**每个端点用同一错误格式**——无每团队雪花；**绝不向客户端泄露堆栈、内部 SQL 或主机名**（既混乱又是安全披露）——这些按 request ID 在服务端记录；若 API 面向用户则**本地化** `title`/`detail`，同时保持 `code` 稳定且与区域无关。

**要点：**
- `400` 校验、`401` 无/坏凭证、`403` 无权限、`404` 不存在、`409` 冲突、`422` 语义。
- 始终包含 `code` 和 `request_id` 便于支持排查。
- 所有端点统一错误格式——别有雪花。
- 面向用户的 API 本地化 `title`/`detail`。

### 34. EXPLAIN

**频率：** 中

**题目：** 如何用 EXPLAIN 诊断慢查询，要留意哪些警告信号？

**答案：** **`EXPLAIN`** 在不执行查询的情况下显示规划器*选中*的计划及其成本/行数**估算**；**`EXPLAIN ANALYZE`** 真正**执行**它，并在估算旁报告**实际**时间、循环次数和行数。总是**从里向外/自底向上**读计划：最深的（叶）节点先跑、馈给父节点。

要猎的警告信号：

- **大表上的 `Seq Scan`** 你本期待索引——要么索引缺失，要么谓词不可 sarg（被函数包裹、类型错、前导通配符）。
- **外层行数高的 `Nested Loop`**——几行时好，外侧返回成千上万时灾难性（常应是带更好索引的 hash/merge join）。
- **估算与实际行数差距大**——**统计陈旧**的铁证；规划器猜错、选了坏 join。用 `ANALYZE` 修。
- **`Rows Removed by Filter`**——引擎读的行远多于保留的，提示缺失或选择性差的索引。

通过加/调索引、重写查询或刷新统计修复。更深手段：加 **`BUFFERS`** 看缓存命中 vs 实际磁盘读（一个全磁盘 I/O 的"快"计划会在负载下垮）；批量加载后跑 **`ANALYZE`** 使规划器不从空表统计出发；当心看似便宜却选错索引、当匹配行稀疏时变慢的 **`LIMIT`** 计划；生产中用 **`auto_explain`** 和 **`pg_stat_statements`** 抓回归的和吃总时间最多的查询。

**要点：**
- `BUFFERS` 揭示缓存命中 vs 磁盘读。
- 批量加载后用 `ANALYZE` 更新统计。
- 当心 `LIMIT` 计划看起来便宜但选错索引。
- 用 auto_explain / pg_stat_statements 抓生产回归。

### 35. 只读副本与复制延迟

**频率：** 中

**题目：** 只读副本与复制延迟如何工作，如何处理"读自己的写"陈旧？

**答案：** 在**主/副本**拓扑中，**主**接所有写，并把变更日志（WAL/binlog）流式传给一个或多个**副本**，后者应用它并服务**读**流量。这水平扩展读，并给你故障切换用的热备。复制几乎总是**异步**的——主不等副本就 ack 提交——所以副本落后主**毫秒到秒级**（负载高时更多）。

那个延迟造成**读自己的写**问题：用户更新资料（写到主），下一页从尚未追上的副本读，看到陈旧数据——像写丢了。缓解：

- 写后短窗口内把**关键读路由到主**（或按会话"粘主"）。
- 用 **token 等追上**：捕获写的 **LSN/GTID**，让副本读阻塞到已应用到该位置（"读自己的写"一致性）。

写爆发、单个跟不上的复制流、或**副本上长查询**阻塞 WAL 应用时延迟会暴涨。运维关注：**监控延迟**（Postgres 的 `pg_stat_replication`、MySQL 的 `Seconds_Behind_Master`）并告警；**同步复制**消除故障切换时的数据丢失但增加提交延迟（主等副本 ack）——直接的延迟-耐久权衡；关注**序列/identity** 和缓存在故障切换中的行为；需只复制部分表或为大版本升级做低停机桥接时用**逻辑复制**。

**要点：**
- 监控延迟（`pg_stat_replication`、Seconds_Behind_Master）。
- 同步复制以延迟换故障切换零数据丢失。
- 注意序列/identity 在故障切换中的行为。
- 逻辑复制支持选择性表复制和版本升级。

### 36. 连接池

**频率：** 中

**题目：** 为何数据库连接池必不可少，如何确定池的大小？

**答案：** 数据库连接**开启昂贵**——TCP + TLS 握手、认证，在 Postgres 里还是一个自带内存的完整**后端进程**。每请求开一个会增加数十毫秒并耗尽服务器。**连接池**保持一小把已打开的连接，在查询/事务期间发出、完了后收回——把那份建立成本摊派到成千上万请求上。

**定大小**反直觉：更多*不*是更好。好起点是*每应用实例*约 **`核数 * 2`** 连接，且**所有实例之和必须低于数据库的 `max_connections`**。一旦活跃查询超过 CPU/磁盘并行度，多余连接只会造成**上下文切换风暴**和内存压力而*拖慢数据库*（这就是为何 PgBouncer 常胜过巨大应用池）。Postgres 的标准外部池是 **PgBouncer** 的**事务池**模式——它把多客户多路复用到少量真实连接，仅在一个事务时长内分配连接。坑：事务池**破坏会话级特性**——服务器端预编译语句、`SET`/会话变量、建议锁、`LISTEN/NOTIFY`——因为连续语句可能落在不同后端。

其他：常**分层**应用端池与代理池；设**空闲超时**使泄漏连接不永久占槽；**serverless** 函数（扩到成千并发实例、各自想要连接）基本*需要* **RDS Proxy** 或 **PgBouncer** 这样的代理合并，否则瞬间冲破 `max_connections`。

**要点：**
- 应用池 ≠ 代理池；分层。
- 太多连接 = 上下文切换风暴和数据库 OOM。
- 空闲超时防止泄漏占住宝贵槽位。
- Serverless 函数需要代理（RDS Proxy、PgBouncer）合并连接。

### 37. 死锁

**频率：** 中

**题目：** 数据库死锁由什么导致，如何避免和处理？

**答案：** 当两个事务各持对方所需的锁、形成环时发生**死锁**：T1 锁行 A 然后想要 B，而 T2 锁行 B 然后想要 A——无一能进。数据库跑一个**死锁检测器**发现环，并以错误**中止其中一个事务**（"受害者"，`deadlock_detected`/`ER_LOCK_DEADLOCK`），让另一个继续。

**避免**策略：

- **一致的锁顺序**——总以相同全局顺序取锁（如更新前先按 ID 排序你要碰的行/key），使环永不能形成。这是最有效的单一修复。
- **保持事务短**——尽量短时间持锁；绝不在事务内等用户输入或外部 HTTP 调用。
- **安全时降隔离**——高隔离取更多/更宽的锁。
- **给外键加索引**——未索引的外键会迫使子插入/更新对父取更宽锁，造成意外争用。

**处理：**死锁在并发下是正常、预期的情况，所以**总把事务包在重试循环**里（带点退避重试受害者）。Postgres 会记录*两条*冲突语句——读日志找出胇病对。当心**热行争用**（大家都更新同一计数器）伪装成死锁；对**队列式**访问，`SELECT ... FOR UPDATE SKIP LOCKED` 让 worker 不阻塞地抓不同行；重排或**按排序键批量**从源头打破环。

**要点：**
- Postgres 同时记录两个查询——仔细读日志。
- 热行争用常伪装成死锁。
- `SELECT ... FOR UPDATE SKIP LOCKED` 非常适合队列式模式。
- 重排操作或按排序键批量打破环。

### 38. 窗口函数

**频率：** 中

**题目：** 什么是 SQL 窗口函数，它与 GROUP BY 有何不同？

**答案：** **窗口函数**在一**帧**相关行上计算值而*不折叠它们*——不像 `GROUP BY` 把多行聚合成一行，窗口函数保留每一输入行并在旁加上计算列。所以你能在同一结果集里同时展示每笔订单*和*它的运行总计。

主力函数：

- **排名：**`ROW_NUMBER()`（唯一递增）、`RANK()`/`DENSE_RANK()`（并列共享名次）。
- **偏移：**`LAG()`/`LEAD()` 取前/后一行——完美用于**同期对比**增量（本月 vs 上月）。
- **窗口上的聚合：**`SUM(...) OVER (PARTITION BY ... ORDER BY ...)` 用于**运行总计**、移动平均、累计计数。

`OVER` 子句有三部分：**`PARTITION BY`** 把行分成独立组（每组重置），**`ORDER BY`** 在每个分区内排序，**`ROWS`/`RANGE`** 定义帧边界（如 `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` 做 7 行移动平均）。

经典的**组内 top-N** 模式是在子查询里 `ROW_NUMBER() OVER (PARTITION BY group ORDER BY score DESC)`，再 `WHERE rn <= N` 过滤。两个细节：窗口函数在 `WHERE`/`GROUP BY` **之后**、在最终 `ORDER BY`/`LIMIT` **之前**求值（所以不能在同一查询的 `WHERE` 里过滤窗口结果——要包一层）；它们通常比所替代的相关子查询或自连接**更对索引友好、快很多**。

**要点：**
- `PARTITION BY` 分组；`ORDER BY` 排序；`ROWS/RANGE` 设帧。
- 组内 top-N：`ROW_NUMBER() OVER (PARTITION BY g ORDER BY x)` + 过滤。
- 在 WHERE/GROUP BY 之后但在 ORDER BY/LIMIT 之前计算。
- 通常比子查询更对索引友好。

### 39. 分区

**频率：** 中

**题目：** 什么是表分区，何时划算？如何选择分区键？

**答案：** **分区**按一个键把一张逻辑表拆成多个物理**子表（分区）**，而查询仍针对父表。三种方案：**范围**（按日期——最常见）、**列表**（按区域等离散值）、**哈希**（无自然范围时均匀铺开）。

**好处：**

- **分区裁剪**——`WHERE created_at >= '2026-01-01'` 的查询只扫相关分区、跳过其余，每查询的有效表大小骤降。
- **便宜的大批删除**——删旧数据是 `DROP PARTITION`（瞬时元数据操作）而非产生膨胀的巨大 `DELETE`——完美适合滞动保留窗口。
- **按分区维护**——`VACUUM`/`ANALYZE` 和索引重建按分区进行，每个保持小而快。

**代价：**额外的查询规划开销（数千分区时规划器变慢），以及**全局唯一性难**——不含分区键的 `UNIQUE` 约束无法便宜地跨所有分区强制。

**指引：**经典用例是按时间分区的**时序**（日志、事件、指标）。用 Postgres **声明式分区**（v10+），它取代了旧的继承/触发器黑魔法。关键是**选一个出现在多数查询 `WHERE` 子句里的分区键**——否则得不到裁剪、只付代价。并**自动化分区创建**（如 `pg_partman`），使新时间范围在数据到达前就有分区；手动创建必被遗漏、插入失败。

**要点：**
- 时序日志/事件是经典用例。
- Postgres 声明式分区（10+）取代继承技巧。
- 选与多数查询 WHERE 子句匹配的分区键。
- 自动化分区创建（pg_partman）——手动易出错。

### 40. 在线 schema 迁移

**频率：** 中

**题目：** 如何在不锁住忙碌表的情况下在线迁移 schema？请解释扩展/收缩模式。

**答案：** 危险在于朴素 DDL 会取**强表锁**并在整个期间阻塞读写：重写每行以加一个带默认值的 `NOT NULL` 列、建索引（阻塞写）、或改列类型都可能把忙碌表冻住几分钟——一次故障。

安全做法把一个风险变更拆成**小、不锁的步骤**，绝不一次重写整表。加一个必填列：

1. **加可空列**（快、仅元数据）。
2. **分限速批回填**（如每次 1k 行并暂停），从不持长事务或尰负载。
3. **加 `NOT NULL` 约束**（Postgres 中先 `NOT VALID` 再 `VALIDATE` 分开校验，避免全表锁）。
4. 等无人读时**删旧列**。

现代 Postgres 帮忙：**`CREATE INDEX CONCURRENTLY`** 不阻塞写地建索引，自 v11 起 **`ADD COLUMN ... DEFAULT`**（常量默认）是仅元数据操作（无重写）。MySQL 或更重变更用在线 DDL 工具——**`gh-ost`**、**`pt-online-schema-change`**（建影子表、回填、交换）或 **`pg_repack`**。

总体原则是**扩展/收缩（并行变更）**模式：先**扩展** schema 同时支持*新旧两种*形态，部署兼容读写的应用代码，迁移数据，再**收缩**移除旧形态——每步都可独立回滚，且每次迁移都**与上一已部署应用版本前向兼容**，回滚永不破坏。

**要点：**
- 永远不要在生产忙表上盲跑 `ALTER TABLE`。
- 回填要分批 + 限速。
- 扩展/收缩模式：在迁移前部署能处理两种形态的代码。
- 让迁移与上一应用版本前向兼容。

### 41. 数据库约束 vs 应用校验

**频率：** 中

**题目：** 为何要同时强制数据库约束和应用校验？各自能捕获对方遗漏的什么？

**答案：** 它们在不同层运作、防御不同失败，所以健壮系统**两者都用**。

**数据库约束**（`NOT NULL`、`FOREIGN KEY`、`UNIQUE`、`CHECK`）是**最后一道防线**，也是唯一*绝对*被强制的。无论什么接触数据都保护它——有 bug 的部署、第二个服务、临时 `psql` 会话、数据迁移脚本。只有 DB 能可靠做两件事：`FOREIGN KEY` 即使 ORM 级联逻辑错也防止**孤儿行**；`UNIQUE` 捕获应用级"先检查再插入"无法防的**竞态**——两个并发请求可同时通过应用端"email 被占了吗"检查然后都插入，只有 DB 的唯一索引能挡住重复。

**应用校验**提供 DB 做不到的：给用户**友好的字段级错误信息**；DB 无法表达或跨多资源/服务的**业务规则**（如"免费套餐用户最多 3 个项目"）；并在押数据库前就拒绝明显无效的输入而**避免往返**。

铁律：**绝不只靠应用校验**——数据库不应信任应用，因为总有一天你已校验的代码路径之外的东西会写入。把校验逻辑放在模型层附近使其在每个端点共享，并**把约束违反映射为清晰的 API 错误码**（唯一冲突 → `409 Conflict` 带具体 `code`，而非裸 500）。

**要点：**
- 即便 ORM 出错，FK 约束也防止孤儿行。
- UNIQUE 抓住应用级检查漏掉的竞态。
- 把校验逻辑放在模型层附近；端点共享。
- 约束违反应映射到清晰的 API 错误码。

### 42. 软删除 vs 硬删除

**频率：** 中

**题目：** 比较软删除与硬删除。软删除会造成哪些问题，如何缓解？

**答案：** **硬删除**物理移除行（`DELETE FROM ...`）。**软删除**保留行但标记它，通常设 `deleted_at` 时间戳（或 `is_deleted` 标志），并在读时过滤掉。

软删除买来**审计迹、易撤销、引用安全**（指向它的行不悬空）——对误删代价高的面向用户数据很有价值。但它带来真实摩擦：

- **查询污染**——*每个*查询都得记得 `WHERE deleted_at IS NULL`，一个遗忘的过滤就泄露"已删"数据。
- **破坏唯一性**——`UNIQUE(email)` 约束现在拒绝一个*新*注册，因为软删用户仍占用那个 email。
- **表无限增长**——死行永远累积，膨胀索引、拖慢扫描。

缓解：

- 用**部分唯一索引**（`UNIQUE(email) WHERE deleted_at IS NULL`），使唯一性只对活行生效。
- 应用**默认作用域/视图**（很多 ORM 支持全局"仅活行"作用域），使开发者不会忘过滤。
- 跑**后台清理作业**把过了保留窗口的行硬删，封顶增长。

一个关键告讫：**GDPR/CCPA 删除权**通常无法用软删满足——数据仍存在——所以那些请求需真正的**硬删或匿名化**。常见混合是先软删供撤销，再在保留或法律截止日硬删/匿名化。

**要点：**
- 部分唯一索引绕开软删唯一问题。
- GDPR 删除权通常强制硬删或匿名化。
- 默认视图/作用域隐藏已删行防泄漏。
- 后台作业在保留窗口后清理软删行。

### 43. UUID vs 自增主键

**频率：** 中

**题目：** 比较 UUID 与自增整型主键。为何随机 UUID 伤写性能，UUIDv7 如何帮忙？

**答案：** **自增整型**（`BIGSERIAL`）紧凑（8 字节）、天然**有序**、对缓存友好——新行追加到 B-tree 的"右边缘"，插入快、索引保持稠密。它们是插入和 join 最快的选项。缺点：**泄露业务指标**（`id=5023` 告诉竞对你的用户数、让攻击者**枚举** `/users/5024`），且需中心序列，在分布式写入方和离线客户端下尴尬。

**UUID** 是 128 位、**全局唯一**、可**客户端生成**而无需与 DB 协调——理想用于分布式系统、易合并数据、不泄露计数的公开标识符。坑在性能：随机 **UUIDv4** 每次插入 B-tree 的*随机*位置，造成**页分裂与碎片**（写放大）、缓存命中率差、索引膨胀——大表上插入可测得地变慢。

**UUIDv7**（和 **ULID**）把高位做成**时间戳**修复了这一点，新 ID **按时间有序**、像整型一样在右边缘附近插入——你保持全局唯一与不泄露*又*重获插入本地性。这使 **UUIDv7/ULID 成为新系统的现代默认**。

指引：绝不在 URL 里暴露顺序整型 ID（枚举）；分布式系统和公开 API 用 UUID，而纯内部表用整型仍好；并总以原生 **`uuid`** 类型（16 字节）而非 `text`（36 字节）存储 UUID——错的类型三倍存储并拖慢每次比较。

**要点：**
- 永远不要在 URL 中暴露顺序 ID（枚举攻击）。
- UUIDv4 随机 ≠ 插入有序 → 写放大。
- UUIDv7 / ULID 是现代默认。
- Postgres `uuid` 类型 16 字节 vs `text` 36——始终用原生类型。

### 44. 文档存储：嵌入 vs 引用

**频率：** 中

**题目：** 在文档存储中，何时嵌入子数据、何时引用？权衡是什么？

**答案：** 决定取决于子数据相对父的**生命周期与访问模式**。

当子数据具备以下情况时**嵌入**（把子嵌在父文档里）：

- **有界**——不会无限增长（订单行项、帖子的地址）。
- **随父访问**——几乎总是一起读。
- **属于父/随父变化**——无独立生命。

嵌入使读变成**单次查找无 join**——整个聚合一次返回，这是文档模型的核心性能优势。

当子数据具备以下情况时**引用**（存子的 ID 单独查）：

- **被多个父共享**（一个 `user` 被成千上万 `post` 引用）。
- **无界**（聊天的消息、账户的事件——可长到百万）。
- **独立变更**——常单独更新它。

权衡：嵌入优化读但**文档膨胀**且**数据重复**，所以对嵌入数据的更新必须在每个复制处都应用。引用保持数据规范化但需**应用端 join**（`$lookup` 或 N 次后续查）。具体约束推动决定：MongoDB 的 **16 MB 文档上限**迫使任何无界增长物改用引用。常见**混合**是嵌入一个*摘要*（供显示的作者名 + 头像）并引用完整记录取详情。NoSQL 一如既往——**为主导查询设计**，建你读得最多的形状。

**要点：**
- MongoDB 16MB 文档上限强制对无界增长改用引用。
- 嵌入子文档避免 join 但更新时重复。
- 混合：嵌入摘要 + 详情用引用。
- 按主导查询模式设计。

### 45. 键值存储（Redis、DynamoDB）

**频率：** 中

**题目：** 把 Redis 与 DynamoDB 作为键值存储比较。它们的甜蜜点和运维坑是什么？

**答案：** 两者都是键值存储，**用查询灵活性换原始速度与水平扩展**——都不能跑临时 join 或过滤，所以你预先**围绕访问模式建模**。

**Redis** 是**内存**存储（每分片单线程，所以命令原子、无锁竞争），带**丰富数据类型**——字符串、哈希、列表、集合、有序集合、流、HyperLogLog、bitmap。因为在内存，快得惊人（亚毫秒）但受 RAM 限制，耐久可选（RDB 快照/AOF）。甜蜜点：**缓存、会话、排行榜（有序集合）、限流、实时计数器、轻量队列/流**。

**DynamoDB** 是**完全托管**、多 AZ、磁盘支撑的存储，在无限规模下以**个位数毫秒**延迟、**零运维**交付。查询模型故意狭窄：按**分区键**（或分区键 + **排序键**范围）取；其他都需**全局二级索引（GSI）**。甜蜜点：想要可预测延迟且无服务器管理的 **serverless 与高规模**应用。

运维坑：DynamoDB 中选错分区键造成**热分区**（限流），且 **GSI 是最终一致**（传播滞后），写后立刻读可能漏。Redis 中避免生产环境 `KEYS *`（阻塞单线程——用 `SCAN`）；**集群模式**下 key 跨节点分片，多 key 操作（`MGET`、事务、跨多 key 的 Lua）需 **hash tag**（`{user123}:...`）把 key 共位到一个分片。

**要点：**
- Redis 用于缓存、会话、排行榜、限流、队列。
- DynamoDB 用于想要零运维 + 可预测延迟的 serverless 应用。
- 注意 DDB 热 key 与 GSI 传播延迟。
- Redis 集群模式分片 key；多 key 操作需要 hash tag。

### 46. 最终一致性模式

**频率：** 中

**题目：** 什么是最终一致性，哪些模式让它在真实应用中可用？

**答案：** **最终一致性**意味着若写停止，所有副本*最终*收敛到同一值——但写后的某个窗口内，不同副本可能返回不同（陈旧）结果。这是 AP 系统在分区时保持可用与快速的代价，对点赞/浏览数无所谓，但对看不到自己变更的用户很刺眼。

使其可用的是**以客户为中心的一致性保证**：

- **读自己的写**——用户总看到自己的更新；短窗口内把该用户的读路由到主（或已追上的副本）或会话亲和。
- **单调读**——用户不会看到时间倒退（看到的值又消失）；把会话钉到**同一副本**使其不从更滞后的副本读。
- **有界陈旧**——保证副本最多落后 *X* 秒，应用可推理最坏情况。
- **因果一致**——保留因果次序（先看到评论再看到回复）；用**矢量时钟**/版本向量追踪。

当陈旧不可避免时，**在 UI 中暴露**（"更新中…"、乐观渲染）而非显示自信而错的值。

保障：除非加对账，否则**钱和库存避免最终一致**；用**补偿动作**（saga）修无法预防的冲突；优选 **CRDT 或显式合并函数**而非朴素的**最后写入获胜**（后者静默丢弃并发更新）；并在 staging **注入故意副本延迟**测试，因为这类 bug 在单个快节点上隐形。

**要点：**
- 钱/库存避免使用，除非协调。
- 补偿动作处理无法防止的冲突。
- 最后写入获胜简单但丢数据；CRDT 或合并函数更安全。
- 在 staging 故意延迟副本测试。

### 47. Redis 数据类型与用例

**频率：** 中

**题目：** 请遍历 Redis 主要数据类型及各自的一个用例。关键的生产实践有哪些？

**答案：** Redis 的威力在于每个数据类型都专为某种用途而建，你选匹配负载的结构：

- **字符串**——缓存、JSON blob、原子**计数器**（`INCR` 计页面浏览、限流计数）。
- **哈希**——存对象字段并**部分更新**（`HSET user:42 name ...`）而无需重序列化整个对象。
- **列表**——有序序列，做简单**队列**（`LPUSH`/`BRPOP`）和"最近 N"feed。
- **集合**——无序唯一成员，做**标签、去重、成员测试**，加集合运算（交集做"共同好友"）。
- **有序集合（ZSET）**——成员按分数排名：**排行榜**、时间范围查询、**滑动窗口限流器**（分数=时间戳）的首选。
- **流**——带**消费者组**的追加日志（带 ack 与回放的"Kafka-lite"）。
- **HyperLogLog**——概率型**基数估算**（唯一访客），不论数量均约 12 KB。
- **Bitmap**——紧凑的**存在/活动**追踪（每用户一位日活）。

生产实践：**绝不在活服务器 `KEYS *`**——它扫一切并阻塞单线程；用 **`SCAN`** 游标迭代。用**流水线**批量往返，用 **Lua 脚本**（或 `MULTI`）做**原子多操作**序列（无竞态的读-改-写）。设**每 key TTL** 和合理**淘汰策略**（`allkeys-lru` 是好的缓存默认）使内存有界。需文档访问或超出核心类型的全文/二级索引查询时用模块——**RedisJSON** 和 **RediSearch**。

**要点：**
- 生产避免 `KEYS *`——用 `SCAN`。
- 流水线和 Lua 脚本做原子多操作批量。
- 每 key TTL；淘汰策略（`allkeys-lru` 是合理默认）。
- RedisJSON/Search 模块加文档和全文功能。

### 48. 缓存雪崩缓解

**频率：** 中

**题目：** 什么是缓存雪崩（stampede），当热 key 过期时如何预防？

**答案：** **缓存雪崩**（或"dogpile"）发生在一个热门 key 过期、在重新填前的极短窗口内，**数百上千并发请求全部同时 miss** 并同时扬向源数据库。数据库（缓存本是为保护它而存在）瞬间被全未缓存负载击中而可能垮掉，在流量高峰时尤其危险。

缓解：

- **single-flight/请求合并**——只有*第一个* miss 的请求真正重算值，并发调用者等那一个结果而非各自报 DB。常用重建 key 上的**短命锁**实现。
- **概率早过期**——在真实 TTL *之前*以随过期临近上升的概率把值视为过期（XFetch 算法），使单个请求提前刷新而旧值仍服务其他人——无同步悬崖。
- **后台刷新**——作业在热 key 临近过期时主动刷新，用户永不碰 miss。
- **stale-while-revalidate**——一个 worker 后台重建时继续服务旧值，用一点陈旧换零源峰值。

配套实践：绝不让大扇出 key 在硬、共享的瞬间过期——**给 TTL 加抖动**（如 `300s ± random`）使 key 不齐过期；事件中**同时监控缓存命中率*和*源压力**，因为下降的命中率是雪崩将至的先行指标。

**要点：**
- 别让大扇出 key 在同一瞬间同步过期。
- TTL 加抖动避免同步过期。
- "Stale-while-revalidate"模式在重建时服务陈旧。
- 事件中同时监控缓存命中率与源压力。

### 49. CDN 缓存 API 响应

**频率：** 中

**题目：** 如何在 CDN 缓存 API 响应，什么绝不能在那里缓存？

**答案：** CDN 在**靠近用户**的边缘 POP 缓存你的 `GET` 响应，相同公开数据的重复请求几毫秒内就服务、根本不碰源站——对汇率、商品目录、公开配置等是巨大的延迟与负载收益。

用 **HTTP 缓存头**控制：

- **`Cache-Control: public, max-age=N`**——任何人可缓存 N 秒；加 **`s-maxage`** 给*共享*缓存（CDN）设与浏览器不同（通常更长）的寿命。
- **`Vary`**——告诉 CDN 哪些请求头（如 `Accept-Encoding`、`Accept-Language`）产生不同响应，以便分开缓存。缺失或过宽的 `Vary` 造成错版本 bug。

**失效**：给响应打 **surrogate key/缓存标签**，写时能精确清除受影响对象（"清除所有标为 `product:42` 的"）而非整个缓存。把**写时事件驱动清除**与 **TTL 上限**兼作兼底，错过的清除也能自愈。

关键铁律：**绝不在共享缓存缓存用户特定或敏感响应**——标为 `public` 但含用户 A 数据的响应可能被发给用户 B（严重数据泄露）。个性化响应必须 `private`（仅浏览器）或按用户/分段作键。效率加项：**`ETag` + `If-None-Match`** 让源站在重验时返回廉价的 **`304 Not Modified`** 而不重发 body；**`stale-while-revalidate`**/**`stale-if-error`** 让边缘在刷新（或源站宕机）时服务略陈旧内容，同时提升延迟与韧性。

**要点：**
- ETag + `If-None-Match` 廉价返回 304 做重验证。
- Stale-while-revalidate / stale-if-error 提升韧性。
- 写时清除（事件驱动）加 TTL 上限。
- 没合适分段时避免 CDN 缓存敏感个性化数据。

### 50. Goroutine 与 M:N 调度器

**频率：** 中

**题目：** goroutine 和 Go 的 M:N 调度器如何工作，goroutine 泄漏怎么发生？

**答案：** **goroutine** 是 Go 运行时（非 OS）管理的轻量用户态任务。调度器是 **M:N**：把 **N** 个 goroutine 多路复用到 **M** 个 OS 线程（大致每核一线程），所以百万 goroutine 可跑在少数线程上。每个 goroutine 以小小的 **~2 KB 栈**起步、**动态伸缩**，所以生成一个几乎免费——`go func()` 是任何主流语言中最便宜的并发原语。

调度器是**工作窃取**的（空闲线程从忙线程队列窃取可运行 goroutine 做负载均衡）且**抢占**的（自 Go 1.14 可中断卡在紧循环的 goroutine，所以一个 CPU 密集 goroutine 不会饿死其他）。**`GOMAXPROCS`** 控制同时跑 Go 代码的 OS 线程数，默认 `runtime.NumCPU()`。

goroutine 通过 **channel** 与 **`select`** 以 CSP 风格协调——惯用法是*"不要通过共享内存通信；通过通信共享内存"*，把数据所有权通过 channel 传递从而绕开很多锁 bug。

**泄漏**发生在 goroutine 永远阻塞且无退出路径——如等待向无人接收的 channel 发送，或等一个永不到来的接收。因 goroutine 廉价，泄漏的会静默累积、占着内存与资源直到进程 OOM。修法是总给 goroutine 一个**退出路径**：穿一个 **`context.Context`** 并 `select` `ctx.Done()`、用超时、确保 channel 被关闭——使 goroutine 总能被告知停止。

**要点：**
- `go func()` 是任何主流语言中最便宜的并发原语。
- 别共享内存；通过 channel 通信（惯用法）。
- `GOMAXPROCS` 默认 `runtime.NumCPU()`。
- 遗忘的 goroutine = 泄漏；总要有退出路径（context）。

### 51. 异步 I/O 事件循环陷阱

**频率：** 中

**题目：** 面向异步事件循环编程的主要陷阱有哪些，如何避免？

**答案：** 事件循环跑**一个线程**，在 `await` 点快速切换任务。头号铁律：**绝不阻塞循环**。若一个任务做 CPU 重活、调**同步** I/O 库、或用阻塞 `sleep`，*整个*循环冻住——*每个*并发请求都停顿，不只那一个。症状阴险：吞吐崩塌、**尾延迟（p99）爆炸**，健康检查超时而 CPU 看似空闲（它停在阻塞调用里）。

关键陷阱与修法：

- **阻塞调用**——用线程/进程池（`asyncio.to_thread`、`loop.run_in_executor`）把 CPU 活或同步库推出循环，使循环空出来服务其他任务。
- **无界 `gather`**——`gather(*数千任务)` 一下开数千连接，可耗尽 DB 池、套接字或内存。用**信号量**（有界 worker 池）限并发。
- **缺超时**——对挂死远程调用的 `await` 永远等，占着任务及其持有的资源。总把 await 包在**超时**（`asyncio.wait_for`）里。
- **取消**——任务被取消时在当前 `await` 抛 `CancelledError`；若正在变更状态或持锁/连接，可能泄资源或损坏状态。在 `finally` 里清理并**测试取消路径**（常有 bug）。

用事件循环监控（如 `aiodebug`、`uvloop` 统计）抓被阻塞的循环，并端到端优选全异步驱动使无同步调用潜入。

**要点：**
- 用事件循环监控做剖析（如 `aiodebug`、`uvloop` 统计）。
- 用 `asyncio.to_thread` / `run_in_executor` 包装同步库。
- 始终对 await 设超时。
- 测试取消路径——它们常有 bug。

### 52. 背压

**频率：** 中

**题目：** 什么是背压，哪些机制能让系统端到端施加背压？

**答案：** **背压**是慢消费者向上游发出**"慢点"**信号以免被淡没。无背压时，快生产者喂慢消费者，中间队列无限增长——延迟随队长上升、内存填满，最终进程 **OOM 崩溃**，常拖垮上游服务级联。所以背压本质是**过载下的稳定性**：优雅降级而非崩塌。

在不同层携带"慢点"信号的机制：

- **有界队列**——固定容量队列在满时**阻塞**生产者（或**丢弃**），把"无限内存增长"变成"生产者等待"。
- **HTTP `429 Too Many Requests`/`503 Service Unavailable`**（带 `Retry-After`）——过载服务告诉客户退避。
- **Reactive Streams `request(n)`**——消费者显式拉取它能处理的个数，生产者从不多发。
- **TCP 流控**——接收窗口是内置于传输层的背压：慢读者缩小窗口，发送方自动限速。
- **带 `await` 的异步迭代**——`async for` 自然把生产者节奏到消费者速度。

两条原则：**无界队列是伪装的 bug**——总给它上界并显式决定满时**阻塞、丢弃、限速还是泄洪**；并**端到端传播背压**（网关 → 服务 → 队列 → DB），因为一跳缓解而下一跳仍无界只是把失败挪位。在负载下度量**队列深度**并**早拒**而非接下完不成的工作。

**要点：**
- 永远给队列上界——无界队列是伪装的 bug。
- 过载时丢弃、限速或泄洪。
- 端到端传播背压（网关 → 服务 → 数据库）。
- 度量队列深度并在负载下早拒。

### 53. Saga 模式

**频率：** 中

**题目：** 什么是 saga 模式，编舞与编排有何不同？

**答案：** **saga** 协调跨多服务的业务事务而**不用分布式（2PC）事务**——你避开它因为跨服务长时间锁行杀可用性且不可扩展。saga 是一串**局部事务**，每服务一个（预留库存、扣卡、预定发货），各自独立提交。若后续步骤失败，saga 跑**补偿事务**逆序语义**撤销**已完成步骤（退卡、释放库存）。注意补偿是*语义*的而非回滚——发出的邮件收不回，只能再发一封取消。

两种协调风格：

- **编舞（choreography）**——无中心控制器；每服务**对上一个发出的事件反应**（`OrderCreated` → 支付服务扣款 → 发 `PaymentCompleted` → 发货服务反应…）。短流程解耦且简单，但多步时逻辑涂抹在各服务里，难以跟踪、调试或可视化（"整体状态是什么？"）。
- **编排（orchestration）**——中心**编排器**显式驱动步骤并决定失败时怎么办。更易推理、监控、修改，代价是多一个组件且有变成 god-service 的风险。把它建模为显式**状态机**使进展与补偿可见。

关键设计：**提前设计补偿**（每个前向步骤需定义好撤销），并使**前向步骤与补偿都幂等**，因为至少一次投递意味着任何步骤可能被重试。常见编排器：**Temporal、Camunda、AWS Step Functions**。

**要点：**
- 补偿必须提前设计且幂等。
- 用于跨服务流如订机票 + 订酒店 + 扣卡。
- 用状态机可视化状态。
- Temporal、Camunda、AWS Step Functions 是常见编排器。

### 54. 幂等消费者

**频率：** 中

**题目：** 什么使消息消费者幂等，为何在至少一次投递下它必不可少？

**答案：** **幂等消费者**无论把一条消息处理一次还是五次，都产生**相同的终态**。这必不可少，因为几乎所有耐久消息（Kafka、SQS、RabbitMQ）都保证**至少一次**投递——消费者在做完工作但 ack 前崩溃，或慢 ack 后重投，都使**重复是常态而非例外**。若消费者非幂等，一个重复就重复扣卡或重复发货。

技术大致按偏好排序：

- **天然幂等操作**——把写设计成重复无害：**`UPSERT`**（按键插入或更新）、**条件更新**（`SET status='paid' WHERE status='pending'`）、或设绝对值而非自增。无需记账。
- **按消息 ID 去重**——在**`processed_ids` 表（或 Redis 集合）带 TTL** 里记录每条已处理消息 ID，跳过已见的。需**生产者提供的稳定 ID**（别在消费端生成，否则重试看似新的）。
- **事务性 outbox + 已处理 ID 表**——在**一个局部事务**里同时写业务变更*和*"我处理了消息 X"记录，使你不可能做了工作却不记录。

关键细节：**去重窗口必须覆盖最大重试时限**——若消息可重投 3 天，1 小时的去重 TTL 会放旧重复溦过。**离开数据库的副作用**（发邮件、调支付 API）需额外小心，因为本地去重表无法撤销它们——把幂等性推入外部调用本身的**幂等键**。最后，**用故意重放测试**——幂等性 bug 只在重复下暴露。

**要点：**
- 始终包含来自生产者的稳定消息 ID。
- 去重窗口必须覆盖最大重试时限。
- 副作用（邮件、支付）要额外小心——用幂等键。
- 用故意重放测试消费者。

### 55. 死信队列

**频率：** 中

**题目：** 什么是死信队列，为何它对健康的消息管道至关重要？

**答案：** **死信队列（DLQ）**是一个单独队列，把**反复处理失败**的消息停放在那里，而非永远重试或静默丢弃。消息超过阈值后——SQS 的 **`maxReceiveCount`**、RabbitMQ 的最大重试/拒绝、Kafka 配置的重试限——broker 把它移到 DLQ，主流程得以继续。

为何关键：无 DLQ 时，一条**毒消息**（总抛异常——报文畸形、被引用记录被删）会被无休止重试。在 Kafka 分区这类有序系统里，那毒消息卡在队首并**阻塞其后每一条**，停滞整个分区。DLQ 是释放阀，让好流量前行而把坏消息隔离待查。

运维必备：

- **对 DLQ 深度告警**——上升的 DLQ 是真事件信号；无人看的 DLQ 只是静默黑洞。
- **建检查/修复/回放工具**——需能检查死消息、纠正根因（部署修复、补数据）、并**回放**回主队列。
- **转移时附带失败元数据**——原始头、异常/原因、时间戳，使排查不用猜。
- **绝不静默丢弃**——丢失败消息会丢数据；DLQ 使失败可见且可恢复。
- **周期清理** DLQ，使其在问题解决后不无界增长。

**要点：**
- 带指标和仪表板的默认 DLQ 是基本要求。
- 没 DLQ 时毒消息可让分区停滞。
- 转移时包含原始头与失败原因。
- 周期清理 DLQ 防无界增长。

### 56. 事件溯源 & CQRS

**频率：** 中

**题目：** 请解释事件溯源和 CQRS。它们的好处是什么，真实成本又是什么？

**答案：** **事件溯源**把状态存为**不可变事件的追加日志**（`OrderPlaced`、`ItemAdded`、`OrderShipped`）而非可变的当前状态行。当前状态通过**回放**事件推导。因为保留每次变更，你得到**完美审计轨迹**、**时间旅行**（重建任一历史时刻的状态）、以及从未预料的历史构建**新投影**的自由。

**CQRS（命令查询职责分离）**把**写模型**与**读模型**分开。命令校验业务规则并发出事件（写侧）；这些事件更新一个或多个**反规范化读模型（投影）**，每个针对特定查询塑形。两侧独立扩展与演化。CQRS 常与事件溯源配对（事件是天然桥梁）但不强制。

**真实成本**是你不到处套用它的原因：

- **事件/schema 演化**——事件不可变且永久存储，改事件形状意味着给事件版本化并写 upcaster；事件实际成了你必须维护的长寿 API。
- **回放性能**——重建有长历史的聚合很慢；你加**快照**（周期物化状态）使回放从最新快照而非事件 0 起步。
- **投影重建**——改读模型意味着回放历史来重填，规模化时运维很重。
- **最终一致性**——读模型落后写模型，UI 必须容忍"你的变更处理中"。

用于有**强审计/合规或时间分析需求**的领域（金融、账本、订单生命周期），并只套用到**定向聚合**而非整个系统。

**要点：**
- 快照加速长历史聚合的回放。
- 事件是你 API 的一部分——小心版本化。
- 用于强审计/合规需求的领域。
- 不要事件溯源一切——挑定向聚合。

### 57. Python：GIL/asyncio/multiprocessing

**频率：** 中

**题目：** 在 Python 中如何针对给定负载在 asyncio、threading、multiprocessing 之间选择？

**答案：** 选择直接取决于 **GIL**（一时只允一个线程跑 Python 字节码）和你的负载是 **I/O 密集还是 CPU 密集**。

- **`asyncio`**——单线程**协作**并发。一个线程杂耆海量 `await` 任务，在每个 `await` 处切换。理想用于**高并发 I/O 密集**（成千同时网络/DB 调用），每任务开销极小。因为单线程无 GIL 争用，但一个阻塞调用冻住全部。
- **`threading`**——真 OS 线程，但 GIL 串行化它们的 Python 执行，所以**无 CPU 加速**。它们*确*帮 **I/O 密集**代码，因为阻塞 I/O（套接字、磁盘）等待时**释放 GIL**，让其他线程跑。当你必须用**同步**库又不想重写为异步时好。
- **`multiprocessing`**——独立**进程**，各自解释器和 GIL，所以对 **CPU 密集**（图像处理、数值计算）实现**真并行**。代价是更重的启动和**通过 pickle 的 IPC**，跨边界的数据必须可 pickle 且拷贝不免费。

实用指引：按负载选——I/O 并发 → asyncio；阻塞库 I/O → 线程；CPU 并行 → 进程。要在 asyncio 内用**同步库**，用 **`asyncio.to_thread`**/`run_in_executor` 卸载以免阻塞循环。**`concurrent.futures`**（`ThreadPoolExecutor`/`ProcessPoolExecutor`）给两者统一 API。注意格局在变：**子解释器（3.12+）**与 **free-threaded（无 GIL）构建（3.13+）**开始允许无 multiprocessing IPC 开销的真线程并行。

**要点：**
- 别不带 `to_thread` 把 asyncio 与同步库混。
- `concurrent.futures` 提供线程/进程的统一 API。
- 子解释器（3.12+）和 free-threading（3.13+）重塑格局。
- pickle 约束折磨 `multiprocessing` 用户。

### 58. Python：类型提示，mypy

**频率：** 中

**题目：** Python 的可选静态类型给你什么，如何增量采用？

**答案：** **PEP 484** 加了可选**类型提示**（`def f(x: int) -> str:`），**mypy** 和 **pyright/Pylance** 这样的检查器在代码运行前**静态**验证。回报：提示在签名级**记录意图**，不执行代码就**抓一类 bug**（在需值处传 `None`、拼错属性、错参数类型），并驱动丰富的 **IDE 智能**（自动补全、重构、跳转定义）——都是**零运行时成本**，因为解释器忽略它们。

现代类型特性（3.10+）很表达：

- **`X | None`**——简洁的可选/联合语法（替 `Optional[X]`）。
- **`Protocol`**——**结构**类型（"带静态检查的鸭子类型"）：任何有对应方法的对象都满足它，无需继承。
- **泛型**（3.12 的 `class Stack[T]:`）、**`TypeAlias`**、**`Self`**、**`TypedDict`**（给 dict/JSON 载荷的形状标类型）。

**增量采用**是关键卖点——不必一次全标。从无类型起步，逐模块加提示，用 **`# type: ignore`** 静默已知缺口，并按模块棘轮严格度（如在清理过的文件启 `disallow_untyped_defs`），使覆盖只增不减。

一个关键告讫：**提示不在运行时强制**——没什么阻止在边界传错类型。对外部输入（API body、配置）的**运行时校验**需 **Pydantic** 或 **attrs**，它们读注解并真正检查/强转值。实践中，**pyright** 比 mypy 更快更严，**`from __future__ import annotations`** 使注解成惰性字符串，支持前向引用与更便宜的导入。

**要点：**
- `pyright`（Pylance）比 `mypy` 更快更严。
- 运行时校验需要 Pydantic/attrs——类型不强制。
- `Protocol` 启用带静态检查的鸭子类型。
- 用 `from __future__ import annotations` 做前向引用。

### 59. Go：channel vs 互斥锁

**频率：** 中

**题目：** 在 Go 中何时用 channel、何时用互斥锁来协调 goroutine？

**答案：** Go 的口号是*"不要通过共享内存通信；通过通信共享内存。"*想法：与其多个 goroutine 锁定并变更同一变量，不如把数据本身通过 **channel** 传递，转移**所有权**使一时只一个 goroutine 碰它。这往往产生更清晰的设计——流水线、worker 池、fan-in/fan-out——数据流动*就是*同步。

但口号是指引而非教条。诚实的划分：

- **用 channel** 做**交接与协调**——在 goroutine 间传工作、信号完成、汇入结果、编排流水线阶段。channel 表达*"接下来谁拥有它。"*
- **用互斥锁**保护**少量共享状态**——计数器、map 缓存、多 goroutine 读的配置结构。围几行的 `sync.Mutex` 比把每次访问都路由过 channel 和管理 goroutine **更简单更快**。这里用 channel 是过度工程。

配套工具：**`sync.RWMutex`** 用于读远多于写（多并发读、独占写）；**`sync.Once`** 做线程安全惰初始；**`sync/atomic`** 做无锁计数器/标志。channel 方面，**缓冲 channel** 加容量但过大缓冲常**掩盖设计缺陷**（用糊慢消费者而非施背压）；**关闭 channel** 是惯用的"无更多值"信号，接收方用 comma-ok（`v, ok := <-ch`）检测，`ok == false` 即已关。无论哪种方法都跑**竞态检测器**（`go test -race`）。

**要点：**
- 缓冲 channel 加容量但过大会掩盖设计缺陷。
- `sync.RWMutex` 用于读多状态。
- `sync.Once` 做懒初始；`sync/atomic` 做计数器。
- 关闭 channel 信号完成；接收方用 `, ok` 检测。

### 60. Go：context 取消

**频率：** 中

**题目：** Go 的 `context.Context` 做什么用，最佳实践有哪些？

**答案：** **`context.Context`** 沿调用链向下传三样：**取消信号**、**截止时间/超时**、**请求级值**。它主职是让你**取消不再需要的工作**——客户断开或请求超时时，取消流向该请求下生的每个 goroutine、DB 查询、HTTP 调用，使它们及时停而非跑完浪费资源。

机制：把 `ctx` 作为**第一参数**传给任何做 I/O 或生 goroutine 的函数。用 **`WithCancel`**、**`WithTimeout`**、**`WithDeadline`** 派生子 context；父取消（或超时触发）时子自动取消，形成一起拆毁的树。在长循环或 select 中监视 **`ctx.Done()`**（取消时关闭的 channel）并返回 `ctx.Err()`；context 感知的标准库调用（`db.QueryContext`、`http.NewRequestWithContext`）已为你做了——优选那些重载。

最佳实践：

- **绝不把 Context 存进结构体**——显式通过函数调用传；存储的 context 活得比其请求长，造微妙 bug。
- **用于请求生命周期而非通用依赖注入**——`context.Value` 用于 trace ID、认证主体等请求级数据，*非*传服务/配置（那会隐藏依赖且无类型）。
- **创建可取消 context 后总 `defer cancel()`**，即使正常完成——否则泄漏 context 的资源（timer/goroutine）。
- 把忽略所给 context 的函数视为 bug——取消只有在每层都尊重时才生效。

**要点：**
- 永远别把 context 存在结构体里——通过函数传。
- 用于请求生命周期，不用于通用 DI。
- 始终 `defer cancel()` 释放资源。
- 多数标准库接受 context；用那些重载。

### 61. Go：错误处理

**频率：** 中

**题目：** Go 如何处理错误，如何惯用地包装和检查它们？

**答案：** 在 Go 中，**错误是普通值**而非异常。任何可能失败的函数把 `error` 作为最后一个结果返回，调用方用 `if err != nil` 显式检查。这使每条失败路径在代码里可见（无隐形控制流跳转），代价是啰嗦。Go 故意对预期失败**无异常**；**`panic`** 只留给**不可恢复的程序员 bug**（nil 解引用、不可能状态），若捕获也是在边界用 `recover`。

**包装与检查：**

- 用 **`fmt.Errorf("loading user %d: %w", id, err)`** 加上上下文**包装**——**`%w`** 动词把原错误保留在链中以便日后解包（普通 `%v` 把它压成字符串失去此能力）。
- 用 **`errors.Is(err, target)`** 对**哨兵**（`io.EOF`、`sql.ErrNoRows` 这类包级值）测试，用 **`errors.As(err, &target)`** 提取**类型化**错误并读其结构化字段（如 `*PathError` 的 path）。

风格与安全：

- **每层包装一次**，在错误跨抽象边界时加点上下文——而非每行，那会产生喀杂冗余的链。
- 用 **`errors.Join`**（Go 1.20+）把多个错误（如批量中的）聚合成一个。
- **别忽略错误**——即便显式 `_ = f()` 也应是有意识、有理由的选择而非条件反射。
- **自定义错误类型**实现 `Error() string`，可选实现**行为接口**（如 `Temporary() bool` 或 `Timeout() bool`），使调用方按行为而非具体类型分支。

**要点：**
- 在每层包装一次，不是每行。
- `errors.Join` 做多错误聚合（1.20+）。
- 别忽略错误——即便 `_ = ...` 也要刻意。
- 自定义错误类型实现 `Error() string` + 行为接口。

### 62. Java GC（G1、ZGC、Shenandoah）

**频率：** 中

**题目：** 比较主要的 JVM 垃圾回收器。如何根据延迟、吞吐和堆大小选择？

**答案：** JVM 自带多个回收器，沿**延迟 vs 吞吐**轴针对不同目标调优：

- **G1 GC**（JDK 9 起**默认**）——把堆分成**区域**并多并发，目标**可预测的低暂停**（可配目标，如 `-XX:MaxGCPauseMillis=200`）。是堆至约 **32 GB** 的均衡全能选手，典型服务的正确默认。
- **ZGC** 与 **Shenandoah**——**超低暂停**回收器，**亚毫秒且即使堆长到 TB 暂停仍平坪**。它们把**压缩与应用并发**做，用**读/加载屏障**在对象移动时保引用有效。用于大堆、延迟关键服务（交易、低延迟 API）。**分代 ZGC**（JDK 21+）加年轻代，使短命对象廉价回收，提吞吐。
- **Parallel GC**——用多线程做 stop-the-world 回收来最大化**原始吞吐**，接受更长暂停。适合**批处理/分析**作业，总完成时间比单次暂停更重要。

**如何选：**延迟敏感 + 大堆 → ZGC/Shenandoah；均衡交互服务 → G1；批吞吐 → Parallel。实用调优：把 **`-Xms` 与 `-Xmx` 设相等**免 JVM 花时间缩堆；总捕捉 **GC 日志**（`-Xlog:gc*`）——它们是暂停与分配问题的首要诊断；并**避免过早调优**——默认选得好，只在测到暂停或吞吐问题时才换回收器/标志。

**要点：**
- ZGC 分代（JDK 21+）更快回收年轻对象。
- 用 `-Xms = -Xmx` 调堆大小避免缩放。
- GC 日志（`-Xlog:gc*`）对诊断必备。
- 避免过早调优——默认对多数应用合理。

### 63. Node.js 事件循环、libuv、worker

**频率：** 中

**题目：** Node.js 事件循环如何工作，如何防止 CPU 密集工作阻塞它？

**答案：** Node 在**单线程**上跑你的 JS，底层 **libuv** 驱动异步 I/O。**事件循环**每刻循环固定**阶段**：

1. **timers**——到期的 `setTimeout`/`setInterval` 回调。
2. **pending callbacks**——延迟的系统回调。
3. **idle/prepare**——内部。
4. **poll**——取新 I/O 事件并跑其回调（大多工作在此）。
5. **check**——`setImmediate` 回调。
6. **close**——`close` 事件（如套接字拆毁）。

阶段间（及每回调后）Node 排空**微任务队列**——已 resolve 的 **Promise**、`queueMicrotask`、`process.nextTick`（它抢在其他微任务之前）——使微任务总在循环推进到下阶段前跑。

因 JS 单线程，**任何 CPU 重同步工作阻塞整个循环**——巨大载荷的 `JSON.parse`、同步 crypto/压缩、紧密计算——它跑时**无其他请求被服务**。卸载它：用 **`worker_threads`** 做进程内 CPU 并行（通过 `SharedArrayBuffer` 共内存），或 **`child_process`** 做更重隔离。注意异步 I/O 本身不阻塞，因 libuv 在**线程池**（由 **`UV_THREADPOOL_SIZE`** 定大小，默认 4）上处理文件系统及部分 crypto/DNS。

值得知：**`setImmediate`** 在 check 阶段（poll 后）触发，**`setTimeout(fn, 0)`** 在 timers 阶段（下刻），**`process.nextTick`** 在循环继续前——对排序重要的不同时机。用 **`clinic.js`**、**`--inspect`**、**`--prof`** 剖析循环卡顿。

**要点：**
- 别用大载荷 `JSON.parse`、同步 crypto 等阻塞循环。
- `setImmediate` vs `setTimeout(0)` vs `process.nextTick`——不同阶段。
- 原生模块可通过 libuv 线程池做循环外工作（`UV_THREADPOOL_SIZE`）。
- 用 `clinic.js`、`--inspect`、`--prof` 剖析。

### 64. Django vs Flask vs FastAPI

**频率：** 中

**题目：** 比较 Django、Flask 和 FastAPI。何时选择各自？

**答案：** 三者处在**电池全包 ↔ 极简**光谱上：

- **Django**——**电池全包**：成熟 ORM、自动生成的 **admin** 界面、内置 **auth**、迁移、表单、安全默认，全在一个有主见的包里。是交付 **CRUD 应用、内容站、全栈产品**最快的方式，因为太多东西免费。配 **Django REST Framework（DRF）**，它仍是有复杂模型和 admin 需求的全功能 API 的主导选择。代价是更重、更有主见。
- **Flask**——**微框架**：给你路由和请求处理，其余（ORM、校验、auth）由*你*选。最大灵活与极小内核，代价是**更多样板与接线**，质量取决于你拼装的扩展。想要**完全控制**或小型定制服务时选它。
- **FastAPI**——**现代异步、类型驱动**框架：用 **Pydantic** 类型提示校验/序列化请求与响应体，并从这些类型**自动生成 OpenAPI 文档**（Swagger UI）。基于 ASGI，擅长**高并发 JSON API**，是**新 API 服务**尤其 I/O 密集型的默认选择。

如何选：需要 admin + 丰富 ORM + 快速全栈 CRUD → **Django（+DRF）**；想要极简与完全控制 → **Flask**；构建新的、高并发、良好类型化的 API → **FastAPI**。注意 Django 的**异步支持**（3.0+）在视图/中间件层稳固，但 **ORM 的异步故事仍滞后**，所以重异步 DB 工作在 FastAPI + 异步驱动上更顺。

**要点：**
- 高并发 JSON API 用 FastAPI。
- 需要 admin 和 ORM 开箱用 Django。
- "我要完全控制"用 Flask。
- Django 异步支持（3.0+）很扎实，但 ORM 异步滞后。

### 65. TLS 握手与证书钉

**频率：** 中

**题目：** 走一遍 TLS 1.3 握手，并解释证书钉及其风险。

**答案：** **TLS 1.3** 把握手精简到**一个往返（1-RTT）**：

1. **ClientHello**——客户预先发支持的 cipher 套件*和*一个 **key share**（临时 Diffie-Hellman 公值），猜服务器偏爱的群。
2. **ServerHello**——服务器选 cipher，发自己的 **key share** 和**证书**（加签名）。两方现能推导共享会话密钥。
3. **Finished**——对握手的 MAC 确认完整性，加密应用数据开始流动。

客户通过验证证书**链至受信根 CA**（签名、过期、主机名匹配、吐销）**验证服务端身份**。TLS 1.3 还支持 **0-RTT 恢复**，回访客户用预共享密钥在首飞发数据——更快但可重放，所以只对幂等请求安全。

**证书钉（pinning）**把客户绑到**特定证书或公钥**而非信任*任何* CA 为该域签发的证书。这防御**流氓或被披 CA** 签发欺诈证书做中间人。严重风险：若钉确切证书然后**轮换**它（续签、换密钥），每个未更新的钉定客户都**变砖**——所以钉主要用于**移动应用**（受控发布周期），后端少见。

最佳实践：TLS 1.3 **丢了 RSA 密钥交换**并强制通过临时 DH 的**前向保密（PFS）**；**弃用 TLS 1.0/1.1** 和弱 cipher；**自动证书续期**（Let's Encrypt/ACM），因为过期证书是经典的自残故障；若钉，则**钉 SPKI（公钥哈希）**而非整证书，并留**备用钉**，使你能轮换证书而不轮换密钥变砖客户。

**要点：**
- TLS 1.3 丢 RSA 密钥交换，要求 PFS。
- 用现代 cipher 套件；弃用 TLS 1.0/1.1。
- 自动证书续期（Let's Encrypt、ACM）；过期引发故障。
- 钉公钥 SPKI 而非证书，更安全轮换。

### 66. 密钥管理（Vault、KMS）

**频率：** 中

**题目：** 如何正确管理密钥，什么是信封加密？

**答案：** 基线规则：**密钥绝不活在代码、git 历史或提交的 `.env` 文件**——密钥一碰仓库就等于泄露（仓被克隆、fork、泄漏），从历史里轮掉它很痛苦。改用专用**密钥管理器**——**HashiCorp Vault**、**AWS Secrets Manager**、**GCP Secret Manager**——它们提供**版本化、轮换、访问控制和每次读的审计日志**。最强特性是**动态密钥**：Vault 可铸**短命、按需数据库凭证**自动过期，无长命密码可偷。

**KMS 与信封加密**处理*加密密钥*而非任意密钥。与其把所有数据送 KMS 加密（慢、限尺寸），你用**信封加密**：

1. KMS 生一个**数据加密密钥（DEK）**，同时返回明文和 KMS 加密形式。
2. 你在**本地**用明文 DEK 加密实际数据（快、任意尺寸），然后**丢弃明文 DEK**，把 **KMS 加密的 DEK** 与密文一同存。
3. 解密时请 KMS 解密 DEK，再本地用它。

主密钥**从不离开 KMS/HSM**，你可集中轮换或吐销访问。

运维实践：**按时间表并在人员变动时立即轮换密钥**；**审计每次访问**以检测异常读；**运行时注入密钥**（sidecar、init container、挂载卷、启动时 env）而非烤进镜像（镜像会推仓库并缓存）；并尽可能优先**工作负载身份 / IAM 角色**而非长命 API key，使服务用轮换、限域的凭证而非静态密钥认证。

**要点：**
- 按时间表和人员变动轮换密钥。
- 审计每次访问。
- 运行时注入（sidecar、init container），不烤进镜像。
- 尽可能 IAM 角色 > 长命 API key。

### 67. OWASP Top 10

**频率：** 中

**题目：** 什么是 OWASP Top 10，应如何使用它？为何访问控制失效排 #1？

**答案：** **OWASP Top 10** 是周期更新、社区排名的**最关键 Web 应用安全风险**清单，作为**意识基线与检查清单**——"我们想过这些了吗"的下限，**而非上限**或完整安全方案。当前分类：

1. **访问控制失效**——用户越权行事。
2. **加密失效**——弱/缺加密、敏感数据暴露。
3. **注入**——SQL/NoSQL/命令/LDAP 注入。
4. **不安全设计**——架构层的缺陷而非仅仅 bug。
5. **安全配置错误**——默认凭证、啰嗦错误、开放的存储桶。
6. **易受攻击与过时组件**——已知 CVE 依赖。
7. **识别/认证失效**——弱登录、会话问题。
8. **软件/数据完整性失效**——未签名更新、不安全反序列化、供应链。
9. **安全日志/监控失效**——无法检测或调查入侵。
10. **SSRF**——服务器被骗发攻击者控制的请求。

**访问控制失效排 #1** 因为它既**最普遍又最具破坏性**：它持续以 **IDOR**（不安全直接对象引用——把 `/orders/123` 改成 `/orders/124` 就看到他人订单）和只在 UI 藏了按钮的端点上**缺失授权检查**出现。强制必须**每请求在服务端**做，默认拒绝并校验已认证用户确实拥有/可访问该具体资源。

如何使用：当**纵深防御**清单——自动**打依赖补丁**（Dependabot/Renovate）因易受攻击组件无所不在；防 **SSRF** 通过拒绝到内部/元数据 IP（`169.254.169.254`）的请求、限出站、校验/白名单 URL；并叠 **WAF + 安全框架默认 + 代码评审 + SAST/DAST 扫描**而非依赖单一控制。

**要点：**
- 访问控制失效是 #1——IDOR 和缺检查到处都是。
- 打依赖补丁（Dependabot/Renovate）——易受攻击组件常见。
- SSRF 防御：拒绝元数据 IP、限出站、校验 URL。
- 纵深防御：WAF + 框架默认 + 代码评审 + 扫描。

### 68. API vs 表单的 CSRF

**频率：** 中

**题目：** 什么是 CSRF，为何基于 cookie 的会话易受攻击而 bearer token API 通常不会？

**答案：** **CSRF（跨站请求伪造）**骗已登录用户的**浏览器**向其已认证的站发意外的变更状态请求。攻击者页面（或邮件）触发到 `bank.com/transfer` 的请求，因请求去 `bank.com`，浏览器**自动附上用户的 `bank.com` cookie**——所以服务器看到一个用户从未意图的合法认证请求。关键洞见：CSRF 利用**浏览器自动发送的凭证**。

这正是漏洞取决于认证机制的原因：

- **基于 cookie 的会话认证易受攻击**，因 cookie 在任何到该域的请求上自动附上。它需显式防御：**CSRF token**（同步器模式——服务器在表单/页面嵌随机 token，提交时校验；攻击者跨站页读不到它）和/或 **`SameSite=Lax/Strict`** cookie（告诉浏览器跨站请求**不**发 cookie）。
- **Bearer token API 不易受 CSRF**，因 token 住在 **`Authorization` 头**，浏览器**不**自动附上——应用 JS 必须刻意加，而恶意跨源页做不到。（把 token 存 `localStorage` 则用 CSRF 风险换 XSS 风险，另一回事。）
- **混合认证**（同时接受会话 cookie *和* bearer token）仍可经 cookie 路径受攻击，所以仍需 CSRF 保护。

支撑点：**`SameSite=Lax`** 是现代浏览器默认，单独就阻大多 CSRF；**双提交 cookie** 模式给无状态保护（token 同时作 cookie 和头发并比较）；**绝不用 `GET` 做状态变更**（GET 可被 `<img>` 标签轻易触发）；记住 **CORS 不是 CSRF 防御**——它管 JS 能否*读*跨源*响应*，而非请求是否被*发送*，请求到达服务器那刻伤害已造成。

**要点：**
- `SameSite=Lax` 是现代默认，阻止大多数 CSRF。
- 无状态 CSRF 保护用双提交 cookie 模式。
- 别接受通过 GET 的状态变更请求。
- CORS 防止读响应，不防止发请求——不是单独的 CSRF 防御。

### 69. 限流与滥用检测

**频率：** 中

**题目：** 如何设计分层限流与滥用检测？"速率"与"并发"有何不同？

**答案：** 有效保护在**多层**施限，每层抓一种滥用模式：

- **边缘/网关按 IP**——最便宜、最粗的一层；在洪流到应用前钝住它（IP 共享/可伪造，所以是过滤器而非全部）。
- **应用按 API key**——每客户/租户的公平使用强制。
- **昂贵端点按路由**——对高成本操作（搜索、报表生成、导出）的紧限，全局限会错过。
- **敏感操作按用户**——对**登录、改密、OTP** 的严限，这里攻击是凭证填充而非量。

叠上**滥用检测**（异常信号）：**失败登录激增**、**新见 IP** 突发流量、异常 **user agent** 或地域、或一账号命中多账号数据。按比例响应——可疑时上 **CAPTCHA**，重复失败上**指数退避**，明确凭证填充上临时**账号锁定**。

关键区分：**速率**（单位时间请求数，如 100/分）不同于**并发**（同时在途请求数，如最多 5 个导出在跑）。用户可能在速率限之下却因同时持多请求而打垮慢下游，所以昂贵端点常**两者都需**。

实践：总返回 **`X-RateLimit-Limit/Remaining/Reset`**（及 `429` + `Retry-After`）使良好客户自限；**记录被拒请求**做取证与调优；并提供**配额提升路径**，使真实爆发的合法客户不被永久限流。

**要点：**
- 区分"速率"（每秒）与"并发"（在途）。
- 始终在错误响应里包含上限信息（`X-RateLimit-*`）。
- 记录被拒请求做取证。
- 考虑合法爆发流量并提供配额提升路径。

### 70. 结构化日志与关联 ID

**频率：** 中

**题目：** 什么是结构化日志，关联 ID 如何让你跨服务追踪一个请求？

**答案：** **结构化日志**把每条日志发为**机器可解数据**——带**一致键值字段**（`timestamp`、`level`、`service`、`trace_id`、`span_id`、`user_id`、`request_id` 加事件特定字段）的 JSON 或 logfmt——而非自由形式的 `printf` 字符串。回报是日志后端能对字段**过滤、聚合、告警**（"显示过去一小时 `user_id=42` 的所有 `level=error`"），这是 grep 散文无法可靠做到的。

**关联 ID**（即 request ID）解微服务调试难题：单个用户动作扇出到多个服务，无共享标识符时它们的日志无法对齐。所以在**边缘生一个 ID**（网关/首服务）并**通过每个下游调用传播**（HTTP 头、消息元数据），给每行日志标上它。现在你能按该 ID 过滤拉出*一个*请求跨所有服务的完整旅程。理想地**复用 OpenTelemetry `trace_id`** 作关联 ID，使日志、trace、指标全基于同一值可相互跳转。

实践：每个有意义事件发**一行结构化**（非散落 `printf`）；**绝不记密钥或 PII**——在源头洗 token、密码、卡号、邮箱（既是合规又是泄露风险）；**诚实用日志等级**——`error` 应意味"需人看/可能 page 人"，以免真事件沉在噪声里；并**集中化**日志（ELK、Loki、Datadog）配**保留策略**平衡调查价值与存储成本（热近期日志、便宜冷归档）。

**要点：**
- 每个重要事件一行日志；避免非结构 `printf`。
- 别记密钥/PII；源头清洗。
- 诚实用等级：`error` 应当 page 谁。
- 集中（ELK、Loki、Datadog）并按合适成本折衷保留。

### 71. 链路追踪：OTel span 与采样

**频率：** 中

**题目：** 用 OpenTelemetry 解释分布式追踪，并比较基于头 vs 基于尾的采样。

**答案：** 一个 **trace** 把单个请求的端到端旅程表为 **span 树**。每个 **span** 是单个操作（HTTP handler、DB 查询、队列发布），带**开始/结束时间戳**、父链接和**属性**（状态、路由、行数）。span 合起精确展示请求在哪花时间、在哪失败。**OpenTelemetry（OTel）**是**供应商中立标准**，使你能换后端（Jaeger、Tempo、Datadog）而无需重新埋点。

**采样**存在是因为规模化追踪**每个**请求存储成本极高，所以你留一个代表性子集：

- **基于头采样**——在**根 span** 处、在你知道结果前决定，通常保留固定百分比。它**便宜简单**（决定传播，整条 trace 一致保留或丢弃），但**盲**——你可能采样掉恰好报错或变慢的那 1%。
- **基于尾采样**——缓存所有 span 并在**完整 trace 完成后**决定，使你能**保留每个错误和每个慢 trace**而丢掉无聊的快成功。对调试有用得多，但更贵更复杂（需 collector 持 span 至 trace 完成）。

常见生产配置是 **1-5% 头采样基线量加错误/高延迟总采样**（常通过尾采样）以保证捕获重要 trace。

细节：上下文通过 **W3C `traceparent`** 头跨服务传播；**自动埋点**开箱覆盖常见库（HTTP、DB、队列）——在重要业务逻辑上**补自定义 span**；保持 **span 属性低基数**（别把原始用户 ID 或带 ID 的完整 URL 做属性键）避免后端索引爆炸；并把 trace 与日志（共享 `trace_id`）和指标（exemplar 把峰值链到具体 trace）**关联**。

**要点：**
- W3C `traceparent` 头跨服务传播上下文。
- 自动埋点覆盖 HTTP、数据库、队列；在热路径补充自定义 span。
- Span 属性：保持低基数避免后端爆炸。
- 配对追踪与日志（共享 trace_id）和指标（exemplar）。

### 72. 健康检查：liveness/readiness/startup

**频率：** 中

**题目：** 解释 Kubernetes 的 liveness、readiness、startup 探针。为何 liveness 不应检查下游依赖？

**答案：** 三种探针回答**不同问题**，混淆它们会造故障：

- **Liveness**——*"进程还活/未卡死吗？"*失败则 Kubernetes **重启容器**。用于从挂起进程（死锁、卡死事件循环）恢复。
- **Readiness**——*"这 pod 现在该接流量吗？"*失败则 Kubernetes **从 Service/LB 移除 pod**（但**不**重启）。用于瞬时"未就绪"（暂时依赖不可达、正暖缓存）。
- **Startup**——*"慢初始化完成了吗？"*它在启动期间**闸**住 liveness/readiness，使慢启动应用（大缓存暖机、迁移）不被 liveness 在起来前杀。

关键设计规则：**保持 liveness 浅**——只确认进程本身响应（一个返回 200 的琐碎 `/healthz`），而 **readiness 检查真实依赖**（DB、队列可达），理想通过**断路器**而非每探针全扇出到每个依赖。

为何 **liveness 不得依赖下游**：若你的 liveness 在**数据库**宕时失败，那么 DB 故障期间 Kubernetes **反复重启每个 pod**——一场重启风暴加载、丢在途工作、阻恢复，却什么也不修（重启应用不修好 DB）。改把 **readiness** 绑依赖，使无法服务的 pod 流量**排空**，而 liveness 保绿、pod 存活待依赖回来时恢复。**Startup** 探针专防合法慢启动应用被提前杀。

**要点：**
- Liveness 失败引起重启——保持笨避免级联。
- Readiness 在数据库/队列故障时翻转让流量排空。
- 别把 liveness 绑到下游——故障期会重启循环。
- Startup 探针防慢启动应用过早被杀。

### 73. 优雅关停

**频率：** 中

**题目：** 如何实现优雅关停，它如何与 Kubernetes 和负载均衡协调？

**答案：** 优雅关停意味在进程退出**前**排空工作，使部署或缩容不丢在途请求。触发是 **`SIGTERM`**。Kubernetes 序列：发 **`SIGTERM`**，等至 **`terminationGracePeriodSeconds`**，进程未退则 **`SIGKILL`**——所以你的 handler 必须在该窗口内完成。

正确的 `SIGTERM` 关停序列：

1. **先把 readiness 翻为 `false`**。这是微妙但关键的一步：告诉 Kubernetes 从 Service endpoints 移除 pod，使 **LB 停路由新流量**。然后**短睡**（几秒）——因 endpoint 移除异步传播，在途 LB 可能在注意到前再发几个请求。
2. **停接受新连接/作业**（关 HTTP 监听、停从队列拉）。
3. **完成在途工作**——让活跃请求完成；worker 完成当前作业并**提交 offset/ack** 使不丢不重处理。
4. **关资源**——排空并关 DB 池、刷缓冲/日志。
5. **干净退出**。

实现注意：HTTP 服务器通常停监听并**等 `WaitGroup`/追踪连接并带超时回退**（Go 的 `http.Server.Shutdown(ctx)`）。总设**比 `terminationGracePeriodSeconds` 短的最大排空超时**——一个挂起等待卡住请求的关停拖垮整个部署并最终仍被 `SIGKILL`（丢了优雅部分）。并**测它**：在 staging 发 `SIGTERM` 验证干净及时退出且无丢请求——坏的关停逻辑直到生产部署造错误峰前都隐形。

**要点：**
- HTTP 服务器：停监听、等 wait group、超时回退。
- Worker：停拉新作业、完成当前、提交 offset/ack。
- 始终设最大排空超时——挂起的关停伤部署。
- 在 staging 发 SIGTERM 测试干净退出。

### 74. CI/CD 中的数据库迁移

**频率：** 中

**题目：** 如何在 CI/CD 中安全跑数据库迁移？解释扩展/收缩模式。

**答案：** 核心问题：滚动部署期间**新旧应用版本同时跑**一段时间，所以 schema 必须一时对**两者**兼容。一个新代码需要但旧代码容不下的迁移会护掉旧 pod 仍服务的每个请求。方案是**扩展/收缩（并行变更）模式**，跨**多个发布**：

1. **扩展**——做**加法、向后兼容**的 schema 变更（加新可空列/表、加索引）。旧代码忽略它；新代码可开始用。
2. **迁移/回填**——部署**双写**新旧的代码，并回填现有行。
3. **收缩**——只在所有实例用新形状且无旧代码后，在**后续**发布中删旧列/约束。

随之而出的铁律：**绝不在部署依赖它的代码的同一发布中做破坏性变更（删/改名列）**——改名 = 加新 + 回填 + 切读 + 删旧，分散在多发布。

运维上：把迁移作为**专用预部署作业/步骤**跑，**与应用 pod 分开**——若每副本启动时都跑迁移会**竞争**。迁移要**版本化、在 PR 评审、对 prod 形状数据集测试**（小 dev DB 掩锅/超时问题）。大表的**长/锁迁移**用**在线 schema 变更工具**（`pt-online-schema-change`、`gh-ost`、`pg_repack`）免持阻塞锁数分钟。优先**向前滚**（写新纠正迁移）而非回滚——down 迁移易错且常无法恢复已删数据。工具：**Flyway、Liquibase、Alembic、Django 迁移、golang-migrate、Atlas**。

**要点：**
- 永远别在部署需要旧形状代码的同一版本里破坏性。
- 长迁移需要在线工具（pt-osc、gh-ost、pg_repack）。
- 向前滚——回滚迁移很痛苦。
- 迁移作业与应用 pod 分开跑避免竞态。

### 75. 特性开关与暗发布

**频率：** 中

**题目：** 什么是特性开关和暗发布，它们如何把部署与发布解耦？

**答案：** **特性开关**是一个运行时条件，**无需重部**就开/关一条代码路径。这把**部署与发布解耦**：你可以**发"暗"代码**（已合并部署但禁用），然后任选时机**独立启用**——按用户、按段、或按百分比。这一分离从一个机制解锁多实践：**金丝雀/百分比推出**（1%→10%→100%，盯指标）、**A/B 实验**、**kill switch**（瞬间禁用失常特性无需回滚部署）、**权限门控**（特性仅对某些套餐可用）。

**暗发布**更进一步：你把**真实生产流量**路由到新代码路径但**丢弃其结果**（或影子对比），使你能在任何用户看到输出前在真实负载下验证**性能与正确性**——如新排序服务与旧并行跑、记录差异，只在匹配后才翻上线。它用生产规模数据先测新路径来降风险。

好实践：按意图**分级开关**——**发布**（短命，推出后删）、**实验**（A/B）、**运维/kill switch**（长命控制）、**权限**（门控）——因为它们命期和业主不同。**积极清理陈旧开关**："开关债"（死条件乱代码）成真实维护与测试负担。使**默认状态安全**（关/旧行为），使配置服务宕时 fail closed 到已知良好。并**每个开关配一个指标仪表板**，使你翻它那刻能看到爆炸半径。工具：LaunchDarkly、Unleash、ConfigCat 或自研。

**要点：**
- 分级开关：发布（短命）、实验、运维（kill switch）、权限。
- 清理陈旧开关——开关债真实。
- 默认状态应安全（关 / 旧行为）。
- 与指标组合：每个开关一个爆炸半径检测仪表板。

### 76. 过滤/排序/稀疏字段集

**频率：** 低

**题目：** 如何为 API 设计过滤、排序和稀疏字段集而不开安全或性能漏洞？

**答案：** 三者的主题都是**显式白名单**——暴露查询灵活而不暴露数据库：

**过滤**——定义**标准、文档化语法**（如 `?status=active&created_at[gte]=2024-01-01&tag[in]=a,b`）带固定的**允许字段与操作符**（等值、范围、`IN`、全文）。铁律：**绝不让任意 SQL 渗出**。每个 API 字段通过**白名单**映射到列，把操作符译为**参数化/预编译语句**，并对未知字段**高调用 400 拒绝**而非静默忽略（静默忽略掩 bug 且可绕过约束）。把过滤值拼进 SQL 是直接的 **SQL 注入**路径——总绑定它们。

**排序**——把 `sort` 限为**有索引列的白名单**。对无索引列排序强迫昂贵的全扫 + filesort；让客户任意排序既是性能隱窗又是滥用向量。另**限页大小和总查询复杂度**，使单请求无法触发巨扫。

**稀疏字段集**——让客户只请需要的字段（`?fields=id,name`）来**缩小载荷**并跳过计算昂贵子资源。这本质是手动字段选择；**GraphQL** 天然具备。配白名单使 `fields` 不能探不该暴露的列。

**要点：**
- 白名单过滤/排序字段；未知字段高调拒绝。
- 给页大小和复杂度设上限以防滥用。
- 文档化操作符语义：等值、范围、IN、全文。
- 用预编译语句；永远不要插入过滤值。

### 77. HATEOAS——何时值得

**频率：** 低

**题目：** 什么是 HATEOAS，它什么时候真值得采用？

**答案：** **HATEOAS**（超媒体作为应用状态引擎）是 REST 约束，响应**嵌入到下一可用操作的链接**，使客户**动态发现能做什么**而非硬编码 URL。一个订单响应可能包含 `{"status":"pending", "_links":{"cancel":"/orders/5/cancel", "pay":"/orders/5/pay"}}`——一旦付款，`cancel` 链接消失而 `refund` 链接出现。客户只跟随当前存在的链接。

**实践中它很少回本**，因为大多客户**针对固定、文档化 URL 手写**并完全忽略嵌入链接——你承担了生成无人消费的超媒体成本，而客户在语义变时仍会坏。对**单团队或内部 API**，它通常是过度工程；跳过。

它**确实公至**的地方：**生命周期长、客户多样且独立演进的公开 API**（PayPal、部分 AWS API），服务器需加/移能力而不护调用方；以及**状态机资源**，允许转换**真正随状态变化**，把"现在允许什么"编入链接（而非每客户重实现状态规则）降耦合。用 **HAL** 或 **JSON:API** 标准化链接格式而非自创。注意语义鸿沟：Roy Fielding 认为 HATEOAS 是称 API 为 "RESTful" 的**必需**，但**业界压倒性地用 "REST" 指无超媒体的面向资源 JSON over HTTP**——别纠结纯洁之争。

**要点：**
- 当客户端/服务端独立演进且客户端通用时使用。
- 内部服务或单团队 API 跳过。
- HAL 与 JSON:API 标准化链接格式。
- 别把"REST"与"HATEOAS"混为一谈——Roy Fielding 会，业界多数不会。

### 78. CTE 与递归查询

**频率：** 低

**题目：** 什么是 CTE 和递归查询，关键性能告讫有哪些？

**答案：** **公共表达式（CTE）**用 `WITH` 给子查询命名，使你能**按名引用**它，提升**可读性**并在一语句内复用同一中间结果而非嵌套子查询。**Postgres** 的关键性能细微处：**v12 前，CTE 是优化屏障**——总单独物化且 planner 无法把谓词推进去（有时有意有用，常是意外变慢）；**v12 起 CTE 默认内联**（当子查询规划），**除非**你写 `WITH x AS MATERIALIZED (...)` 强制旧行为。

**递归 CTE**（`WITH RECURSIVE`）让 SQL **走树和图**——组织层级、评论线程、物料清单、分类树。形状是**基础情况 `UNION ALL` 递归引用** CTE 自身：
```sql
WITH RECURSIVE subs AS (
  SELECT id, manager_id FROM emp WHERE id = 1       -- base
  UNION ALL
  SELECT e.id, e.manager_id
  FROM emp e JOIN subs ON e.manager_id = subs.id    -- recursive
)
SELECT * FROM subs;
```
主要危险是环图上的**无限循环**——用**深度计数/上限**（或 `CYCLE` 检测）防守。其他指导：重子查询多次复用时用 **`MATERIALIZED`**（算一次）；对运行总和/排名，**窗口函数**常能更高效地替自连接 CTE；对大图的**深遍历**，递归 CTE 变慢——改用**图数据库**。

**要点：**
- 递归 CTE：`WITH RECURSIVE t AS (base UNION ALL recursive ref)`。
- 多次复用重子查询时用 `MATERIALIZED`。
- 窗口函数常更高效地替代 CTE。
- 不要在巨图上深递归——用图数据库。

### 79. Postgres 的 JSON 列

**频率：** 低

**题目：** 何时该在 Postgres 用 JSON 列，如何索引和查询 `jsonb`？

**答案：** **`jsonb`** 以**分解二进制格式**（key 去重、无无意义空白）存 JSON，支持**索引**和丰富**操作符**——`->`（取 JSON）、`->>`（取文本）、`@>`（包含）、`?`（key 存在）加 JSONPath。优于 **`json`**（存原始文本、保留重复 key/空白、操作符更少）；`json` 只在需保留确切原文时胜。

**好用例**：**稀疏、schema 灵活属性**——每项设置、特性异的产品属性、标签、外部 API 载荷、审计/事件 blob——列会多为 null 或形状逐行变。关键**告讫**：别把 `jsonb` 当**主建模工具**。塞入 JSON 的数据失**外键、类型/NOT-NULL 约束、高效 join**，查询也难优化——有清晰结构与关系的数据属于真列/表。

索引与查询技术：
- **GIN 索引**用于**包含/存在**查询：`CREATE INDEX ON t USING gin (data jsonb_path_ops)` 加速 `data @> '{"status":"active"}'`（`jsonb_path_ops` 变体更小更快但只支 `@>`）。
- **表达式（B-tree）索引**用于**特定抽取字段的等值**：`CREATE INDEX ON t ((data->>'email'))`。
- **部分更新**用 `jsonb_set(data, '{a,b}', '1')` 和 `||` 合并操作符——但两者都**重写整个值**（MVCC 创新行版本），所以很大 JSON blob 频繁更新昂贵。
- 在边界用 `CHECK` 约束**验证形状**，如 `CHECK (jsonb_typeof(data->'count') = 'number')`，因列本身不强结构。

**要点：**
- 包含查询用 `jsonb_path_ops` 上的 GIN 索引。
- 抽取字段的表达式索引用于等值查找。
- `jsonb_set`、`||` 做部分更新——整个值会被重写。
- 用 `CHECK (jsonb_typeof(col->'x') = 'number')` 验证形状。

### 80. 宽列分区键

**频率：** 低

**题目：** 如何在 Cassandra、DynamoDB 这类宽列存储中设计分区键，什么导致热分区？

**答案：** Cassandra/DynamoDB 中，**分区键**决定**哪个节点拥有数据**（通过哈希）并**约束一起读的行集**——单分区是存储与访问单位。所以分区键必须同时满足两件事：**高基数/均匀分布**（数据与负载散到多节点）**且与查询模式对齐**（一起取的行住同分区）。**聚簇键（Cassandra）/排序键（DynamoDB）**再**在分区内排行**，使高效**范围扫**（如"此聊天消息，最新在前"）。

**热分区**是典型失败：若键**顺序**（时间戳或自增）或**低基数**（`status`、`country`），不成比例的读/写落在**一节点**，它成瓶颈而其他空闲——摧毁横向扩展益处。

建模指导（与关系思维相反）：
- **"查询第一，建模第二"**——按**访问模式设一表**并**反规范/复制**数据跨它们，而非规范化后 join（无 join）。
- **复合分区键**散负载并限分区大小，如 `(tenant_id, day)` 使一租户数据按天拆而非一巨分区。
- 尊重**分区大小上限**——Cassandra 每分区 ~100 MB；DynamoDB 每分区键 10 GB item-collection 限——否则性能降。
- **次要索引昂贵**（GSI 额外写/存储；Cassandra 次索引扩展差），所以访问模式通常用**反规范重复表**服务。

**要点：**
- "查询第一，建模第二"——按访问模式设计表。
- 复合分区键分散负载（`(tenant_id, day)`）。
- 分区大小上限（Cassandra ~100MB，DDB 项目集合 10GB）。
- 次要索引昂贵，常被反规范化掉。

### 81. 搜索引擎作为非主数据库

**频率：** 低

**题目：** 为何把 Elasticsearch 这类搜索引擎用作次级存储而非真相源？

**答案：** **Elasticsearch/OpenSearch** 为**全文搜索、faceted/聚合、分析**查询而建——相关性排序的文本匹配、多字段过滤、日志分析——关系库处理得差的负载。但它们是差的**记录系统**：**最终一致**（写不立即可搜——refresh 间隔）、**耐久性较弱**（比 WAL 支撑的 RDBMS 更易丢数据）、**无多文档事务**。所以标准模式是保**主数据库作真相源**，把 ES 当**派生次级索引**，通过**变更数据捕获（CDC）**或**消息队列**把写从主库流入 ES 保同步。

铁律：**绝不让 ES 成为写入的唯一副本**——若它派生，你总能在損坏或映射变更后从主库**重建**索引。零停机重建用**别名切换**（建新索引、回填、原子切别名）。按语言调 **analyzer**（默认词干粗糙）。注意**分片规模**（10-50GB/分片）——分片太多杀集群性能。

**要点：**
- 永远别把 ES 作写入的唯一副本。
- 重建索引策略：通过别名切换做零停机映射变更。
- 按语言调 analyzer；默认词干粗糙。
- 注意分片规模（10-50GB/分片）；分片太多杀集群性能。

### 82. 时序数据库（InfluxDB/Timescale）

**频率：** 低

**题目：** 请讲解时序数据库（InfluxDB/Timescale）：(1) 时序工作负载的特征（追加密集写、按时间有序读、保留策略、降采样）；(2) 专用存储如何压缩时间戳并游程编码值以节省空间、提供连续聚合；(3) Timescale 作为 Postgres 扩展在想要 SQL 时的优势。请一并说明高写吞吐加便宜的按时间范围扫描、连续聚合/降采样降存储、内置 TTL/保留策略，以及数百万点 Postgres 单独就够、数十亿点才用专用。

**答案：** 时序工作负载有追加密集写、按时间有序读、保留策略和降采样。专用存储（InfluxDB、Timescale、Prometheus）压缩时间戳和游程编码值以巨幅节省空间，并提供连续聚合。Timescale 是 Postgres 扩展——想要 SQL 时很好。

**要点：**
- 高写吞吐 + 便宜的按时间范围扫描。
- 连续聚合 / 降采样降存储。
- 内置 TTL/保留策略。
- 数百万点 Postgres 单独就够；数十亿点用专用。

### 83. 图数据库（Neo4j）

**频率：** 低

**题目：** Neo4j 这类图数据库何时胜过关系数据库，何时应避免？

**答案：** 图数据库把**节点和边作为一等公民**存储，**连接记录间直接指针**（"无索引邻接"）。结果是遍历关系是 **O(邻居数)**——你直接从节点跳到其邻居——而非关系方式中每"跳"是**成本随表大小扩张的 JOIN**，多跳查询意味叠自连接而组合爆炸。所以对**多跳深**的查询，图数据库可快数量级。

**它们发光处**：关系**本身就是查询**的负载——**欺诈检测**（账号/设备环）、**推荐**（"买了 X 的朋友的朋友"）、**社交图**、**知识图**、**依赖/影响分析**。经验法则：若查询常规遍历**深于 ~3 跳**，或关系比实体重要，考虑图数据库。查询语言：**Cypher**（Neo4j）、**Gremlin**（TinkerPop）、**SPARQL**（RDF）。

**何时避免**：对**简单查找和浅关系**，关系库**更快、更简单、更成熟、更广为人知**——别因数据"有关系"就采图数据库（及其运维/招人成本）；所有数据都有关系。是*遍历的形状与深度*才证它合理，且**原生图存储**（非 RDBMS 上的图层）才交付遍历速度。替代：**AWS Neptune、JanusGraph、ArangoDB、Memgraph**。

**要点：**
- 关系主导查询时（深度 > 3 跳）最好。
- 简单查找别用——关系型更快更简单。
- 原生图存储对遍历速度重要。
- AWS Neptune、JanusGraph、ArangoDB、Memgraph 是替代。

### 84. Redis 持久化：RDB vs AOF

**频率：** 低

**题目：** 比较 Redis 持久化选项 RDB 与 AOF。为何生产常两者都跑？

**答案：** Redis 在内存，持久化关乎活过重启/崩溃，它提供两个取舍相反的机制：

- **RDB（快照）**——周期把**整个数据集倒到紧凑二进制文件**（`.rdb`）。优：**文件小、重启快**（加一个二进制），理想作**备份**。缺：**丢上次快照后的每个写**——若每 5 分快照而 4:59 崩，那 5 分没了。快照 **fork** 进程且依**写时复制**，所以快照时写重负载可致**内存峰值**（页分岖被拷）。
- **AOF（追加文件）**——把**每条写命令**记到文件，重启时回放。耐久由 **`fsync` 策略**界定：`appendfsync everysec`（默认甜点）最多丢 ~1 秒；`always` 完全耐久但慢；`no` 交给 OS。缺：**文件更大**、**重启更慢**（回放所有命令）——由周期**后台 AOF 重写**把日志压到最小命令集缓解。

**生产常两者都跑**：**AOF 做耐久**（小丢数据窗）加 **RDB 做快速恢复与备份**——配**副本**，就是耐久三剑客（复制做可用、AOF 做近期写、RDB 做快照）。反之，当 Redis 是**纯缓存**（数据可从真相源重建）时，**完全禁用持久化**以最大吐吐且无 fork 相关延迟。

**要点：**
- `appendfsync everysec` 是默认甜点。
- 快照 fork 进程——内存写时复制飙升。
- 纯缓存完全禁用持久化。
- 副本 + AOF + RDB 是耐久三剑客。

### 85. 缓存中的 Bloom 过滤器

**频率：** 低

**题目：** 什么是 Bloom 过滤器，它如何加速缓存和数据库？为何它可能假阳但从不假阴？

**答案：** **Bloom 过滤器**是由**微型位图**和 `k` 个哈希函数支撑的**概率集合**。加元素时置其哈希指向的 `k` 位；测成员时检查是否**全部** `k` 位都置。两种可能答案：**"肯定不在集中"**（任一位为 0 则从未加）或 **"可能在集中"**（全位置——但可能是*其他*元素置的）。故**假阳可能**（位碰撞），而**假阴不可能**（加元素总置其位，所以存在元素从不读为缺席）。假阳率可通过位图大小和 `k` 选择**调节**。

缓存回报：把 Bloom 过滤器**放在昂贵缓存/DB 查找前**做存在性检查。先问过滤器——若说"肯定不在"，你**完全跳过查找**；仅"可能在"才真查。因假阳仅致**偶尔白费查找**（从不给错结果）且假阴不可能，它是安全优化。经典用：**"此用户名占了吗"**、**"这 URL 爬过吗"**、避免对缺失 key 磁盘读。

特性与告诫：
- **极空间高效**——**每元素几位**而非完整 key，数十亿项占 MB 级。
- **不能从**标准 Bloom 过滤器**删**（清位会损其他元素）——需删除时用**计数 Bloom** 或 **cuckoo 过滤器**。
- **Cassandra 和 RocksDB** 内部用 Bloom 过滤器**跳过不可能含 key 的 SSTable**。
- 按预期 `n` 和可接受假阳概率 `p` **刻意定大小**——偏小会飙假阳。

**要点：**
- 空间高效——每元素几位，不存完整 key。
- 不能删除（用计数 Bloom 或 cuckoo 过滤器）。
- Cassandra/RocksDB 内部用 Bloom 做 SSTable 查找。
- 按预期 n 和可接受假阳性 p 设大小。

### 86. 无锁 / CAS

**频率：** 低

**题目：** 什么是 compare-and-swap（CAS），为何写正确的无锁代码如此之难？

**答案：** **Compare-and-swap** 是原子 CPU 原语：`CAS(addr, expected, new)` **仅当 `addr` 当前等于 `expected` 时把它更新为 `new`**，返回是否成功——全作一条不可分指令。它是**无锁数据结构**的基础：不取锁，而是读当前值、算新值、**CAS**；若其间其他线程改了（CAS 失败）则**重试循环**。好处是避**锁争用**及持锁线程被调度开的风险（优先级反转、护送）。

它**极难写对**，主因二：
- **ABA 问题**——CAS 仅查值*等于* `expected`，非它从未变。若值在你读与 CAS 间 A→B→A，CAS **尽管世界变了仍成功**（如节点被释放并在同地址重分配），损坏结构。修复加**版本/tag 计数**（双宽 CAS）或用危险指针/纪元回收。
- **内存序**——在弱序架构（ARM、POWER）上必须正确指定 **acquire/release/seq_cst** 语义，否则其他线程见重排写。推理此点臭名易错。

其他现实：**无锁 ≠ 无等待**——无锁仅保*某*线程进展；单线程可**饥饿**地重试。高争用下，CAS 可能因大家不断失败重试（缓存行 ping-pong）而比锁**更慢**。实用要领：用**库提供的原子**（`atomic.Int64`、`AtomicReference`）和**证明过的并发结构**（并发 map/队列）；只在极端谨慎与重测下才自滚——且**先剖析**，因普通互斥锁通常已够快。

**要点：**
- 无锁 ≠ 无等待；某些线程仍可停顿。
- 弱架构上内存模型规则（acquire/release/seq_cst）重要。
- 高争用下 CAS 可能比锁慢（重试）。
- 优化前剖析——锁通常没问题。

### 87. Outbox 模式

**频率：** 低

**题目：** 什么是 outbox 模式，它解决哪个双写问题？

**答案：** **双写问题**：服务常需**更新数据库并发布消息**（到 Kafka/RabbitMQ）回应同一业务事件。两者作独立操作无原子性——任一可独立失败，给你**"数据库提交但消息丢"**（下游永不知）或**"消息发了但数据库回滚"**（下游对不存在的数据行动）。实践中无跨 DB 与 broker 的分布式事务。

**outbox 模式**把发消息变为**本地 DB 写**：在更新业务状态的**同一事务**内，**向 `outbox` 表插一行**描述事件。因是一事务，状态变更与 outbox 行**一同提交或回滚**——原子。然后一个**独立中继**——轮询未发 outbox 行的**轮询器**，或尾随 DB 事务日志的 **CDC 工具（如 Debezium）**——读那些行、**发布到 broker**、**标记已发**。这保证消息**当且仅当** DB 变更提交时发布，使投递与事务对齐。

后果与实践：
- 投递是**至少一次**（中继可能发布、标记前崩、重发），所以**消费者必须幂等**——重复是预期而非例外。
- **基于 CDC 的中继比轮询扩展更好**（无查询负载、延迟低）但加基础设施。
- 保 outbox 表**小**——置 `processed_at` 并周期**归档/删**已发行，免无限长而拖慢中继。

**要点：**
- 消除"数据库提交但消息丢"/"消息发了但数据库回滚"。
- 与幂等消费者配对（重复是预期的）。
- 基于 CDC 的中继比轮询扩展更好。
- 加 `processed_at` 或归档保持 outbox 小。

### 88. 2PC——为什么被避免

**频率：** 低

**题目：** 两阶段提交（2PC）如何工作，为何现代分布式系统普遍避免它？

**答案：** **两阶段提交**通过**协调器**提供跨多参与者（数据库/服务）的原子事务：
1. **准备阶段**——协调器问每个参与者"能提交吗？"。各自做完工作、**锁资源**、写日志、**投 yes/no**（yes = 承诺若被告知就*能*提交）。
2. **提交阶段**——若**全**投 yes，协调器告知大家**提交**；若任一投 no（或超时），告知大家**中止**。参与者遵从并释锁。

它确交付原子性，但**普遍被避免**，因：
- **协调器故障时阻塞**——若协调器在参与者投 yes **后**但发提交/中止决定**前**崩，参与者**无限持锁**，不知提交还是回滚。这是致命缺陷：整系统可卡死。
- **扩展差**——同步往返加跨所有参与者**持锁**事务全程，串行吐吐并拉高延迟。
- **可用性耦合**——事务只能在**每个**参与者都在时提交；总可用性是各参与者可用性的*乘积*，随服务增多而降。

**3PC** 加一阶段减阻塞，但更复杂且**假设同步网络**（有界延迟），真网络违反——很少用。且实际上**2PC 在异构数据库和 broker 间支持差**。**跨服务**一致性的现代答案是 **saga + outbox**：以严格 ACID 换**可用、最终一致**的工作流加失败时**补偿动作**。告讫：当数据在**一个数据库**内，普通**单 DB 事务**仍是正确、远更简单的答案——别不必要地用分布式事务。

**要点：**
- 3PC 减阻塞但加复杂度并假设同步。
- 跨异构数据库/broker，2PC 支持很差。
- 可能时单数据库事务仍是正确答案。
- Saga 以 ACID 换可用的最终一致性。

### 89. Paxos/Raft 基础

**频率：** 低

**题目：** Paxos、Raft 这类共识算法解决什么问题，Raft 的基于领导者方法如何工作？

**答案：** **共识算法**让集群**在故障（崩溃、重启、网延）下对单一值（或有序日志）达成一致**，使复制系统表现得像一台一致机器。这支撑**复制状态机**：分布式数据库、配置存、协调服务。

**Raft** 为**易理解**（vs Paxos）而设，通过**强领导者**工作：
- **领导者选举**——节点分 follower/candidate/leader。若 follower 在选举超时内未听到领导者，candidate 请求投票；得**多数**者成为该**任期**的领导者。
- **日志复制**——**所有写过领导者**，它追加到日志并复制条目到 follower。条目**一旦多数 ack 即提交**，然后应用到状态机。这多数要求使它安全。
- **N 节点容 `(N-1)/2` 故障**——五节点集群能存活 2 故障而保多数。

用于 **etcd、Consul、CockroachDB、TiKV、Kafka KRaft**。关键特性：**奇数集群（3、5、7）**标准，保**干净多数**避免分票（4 节点与 3 节点容同样 1 故障却更贵）；**法定人数读/写**（触多数）提供**线性化**；**领导者是写瓶颈**（所有写汇入它），通过**分片**成多 Raft 组扩展；**Paxos** 是更老、形式化证明的基础但**臭名难正确实现**，Multi-Paxos 和 Raft 是实用后裔。

**要点：**
- 始终用奇数集群（3、5、7）以干净多数。
- 法定人数读/写保证线性化。
- 写的领导者瓶颈；分片分担负载。
- Paxos 更老、形式化证明、更难实现。

### 90. 矢量时钟与 CRDT

**频率：** 低

**题目：** 什么是矢量时钟和 CRDT，它们如何无需协调地处理冲突？

**答案：** 两者都处理**分布式系统中无中心协调器的排序与冲突解决**。

**矢量时钟**跟踪**因果**。每节点持**一个计数器矢量**（每节点一项）；每事件自增自己那项并**把整矢量附到每条消息**。收到时按**逐元素 max 合并**并撞自己那项。比两矢量知关系：一方**严格主导**→**因果（happened-before）序**；**互不主导**→更新**并发**且真冲突。这让系统**检测冲突**（两客户独立改同一 key）而非静默丢写，再解（last-writer-wins、合并或交应用）。缺点：矢量时钟**随集群规模长**（每见过节点一项），故用**版本矢量/点版本矢量**裁陈旧项。

**CRDT（无冲突复制数据类型）**更进一步——合并函数**交换、结合、幂等**的数据类型（**计数器、集合、map、序列**），使**任意顺序**收更新的副本**确定性收敛到同一状态**，无需协调、构造上无冲突。如 G-Counter 求每节点计数和；OR-Set 跟踪 add/remove tag 使并发 add+remove 可预测解决。分**基于状态（CvRDT）**——副本发送并合并全状态——和**基于操作（CmRDT）**——副本广播操作（需可靠投递）。理想用于**离线优先应用、协作编辑（Figma、Yjs、Automerge）、多主复制（Riak）**，要**无协调延迟的最终一致**。取舍是元数据开销，且非每种结构都有自然 CRDT 化。

**要点：**
- 矢量时钟随集群规模增长——版本矢量 / 点版本矢量裁剪。
- CRDT 分基于状态（CvRDT）与基于操作（CmRDT）。
- 无协调开销的最终一致性。
- 非常适合离线优先应用与多主设置。

### 91. 时钟偏差、NTP、逻辑时钟

**频率：** 低

**题目：** 为何不能信任墙上时钟给分布式事件排序，逻辑时钟和 TrueTime 提供什么替代？

**答案：** 每机器的**物理时钟漂移**（石英振荡器随温度/年龄变），两服务器时钟差毫秒到秒。**NTP** 把它们纠向参考（典型几毫秒内），但**不能完美或完美同步**——甚至可把时钟**向后**跳。所以用**墙时钟时间戳跨节点排序不安全**：服务器 1 亊件 A 可带比服务器 2 亊件 B 晚的时间戳，即使 B 真在 A 后，而按墙钟的"last-writer-wins"可静默丢新写。

正确工具是**逻辑时钟**，按**因果而非时间**排序：
- **Lamport 时间戳**——单计数器，每事件自增，收消息时推到 `max(local, received)+1`。给**与 happened-before 一致的全序**，但**分不清并发与因果**（只单向蕴含）。
- **矢量时钟**——每节点计数器，捕获完整**因果/并发**关系（代价是尺寸）。

真需**绝对跨区域排序**的系统，**Google 的 TrueTime**（Spanner 用）反其道：不装时钟精确，而用 **GPS + 原子钟**把时间暴为**带有界不确定度的区间 `[earliest, latest]`**。Spanner 随后**"commit-wait"**——故意等完不确定窗再提交——使两事务时间戳反映真实序，产外部一致的全局排序。其他：**闰秒**破朴素时间戳数学（重复/缺失一秒）——smear；**混合逻辑时钟（HLC）**结合墙钟与逻辑计数做"够好"、基本单调且人可读的排序；**每服务器始终跑 NTP/chrony**；**关键正确性决策绝不跨节点比时间戳**——用逻辑时钟或协调服务。

**要点：**
- 闰秒破坏朴素时间戳逻辑。
- 混合逻辑时钟结合墙 + 逻辑做"够好"排序。
- 服务器始终跑 NTP/chrony。
- 别跨节点比较时间戳做关键正确性决策。

### 92. Python：pip vs poetry vs uv；锁文件

**频率：** 低

**题目：** pip、Poetry、uv 在 Python 依赖管理上有何不同，为何提交锁文件很重要？

**答案：** 这些工具处于递增的能力层级：
- **pip**——基线安装器；从 PyPI 取包但本身**不**产锁文件或确定性解完整依赖图。**`pip-tools`** 加锁：把松散 `requirements.in` 编译为**完全钉死的 `requirements.txt`**（每个传递依赖都钉确切版本）。
- **Poetry**——一体化：**依赖解析**（真求解器）、**`poetry.lock`**、**虚拟环境管理**、**打包/发布**，均由 `pyproject.toml` 驱动。成熟广采，但历史上解析慢。
- **uv**（Astral，Ruff 作者）——**基于 Rust** 的替代，做 pip/pip-tools/Poetry 所做但**快 10-100×**，带 **`uv.lock`** 和 `pyproject.toml`，加快速 venv 创建和 Python 版本管理。正迅速成**事实默认**。

**为何提交锁文件**：锁把**每个依赖（含传递）钉到确切版本和哈希**，使 `install` 在每台开发机、CI runner、生产构建上复现*相同*环境。无它，新装可静默拉新子依赖补丁引入回退或供应链变更——"我机器上能跑"。**`pyproject.toml`**（**PEP 621** 标准化）持你声明/抽象依赖和项目元数据，锁文件持解析/具体钉——两者都提交。实用：**CI 中绝不跑裸 `pip install package`**而无约束/锁文件——不可复现。今日选择：新项目用 **uv** 求速；团队/生态已投入 **Poetry** 则沿用。

**要点：**
- 始终提交锁文件以可复现。
- `pyproject.toml`（PEP 621）是标准项目元数据。
- CI 中避免不带约束文件的 `pip install`。
- `uv` 在 2026 年迅速成为事实选择。

### 93. Python：WSGI vs ASGI；gunicorn vs uvicorn

**频率：** 低

**题目：** Python 中 WSGI 与 ASGI 有何区别，它如何对应 gunicorn 与 uvicorn？

**答案：** **WSGI** 和 **ASGI** 是 Python web 应用与运行它的服务器间的**接口契约**：
- **WSGI** 是**同步**——单个可调用体每 worker 一时**处理一请求**，阻塞到返回。是 **Flask** 和 **Django（前 3）** 背后的模型。简单、经验考验，但 worker 等 I/O 时空闲，且**不能做 websocket 或流/SSE**。
- **ASGI** 是**异步**后继——`async` 接口让**单 worker 处理多并发请求**（在 `await` 点交织），支持 **websocket、SSE、长连接**。是 **FastAPI、Starlette、Django 3+** 背后的模型。

服务器对应：**gunicorn** 是用**预-fork** 模型（master 督多 worker 进程）的 **WSGI** 服务器——进程管理睚固但自身仅 WSGI；**uvicorn** 是 **ASGI** 服务器（建在 `uvloop`/libuv）跑异步应用。常见**生产组合**：**gunicorn 作进程督导跑 uvicorn worker**（`gunicorn -k uvicorn.workers.UvicornWorker`），兼得 gunicorn 健壮 worker 管理与 ASGI 能力。

运维：**worker 数**——同步 WSGI 约 `2×cores + 1`（worker 阻塞，故超配），异步**更少**（每 worker 已复用多请求，受 CPU 限）。**Hypercorn** 是另一 ASGI 服务器，还说 **HTTP/2 和 HTTP/3**。且**绝不在生产跑开发服务器**（`flask run`、`uvicorn --reload`、Django `runserver`）——它们单进程、未加固、非为负载而建。

**要点：**
- WebSocket/SSE/HTTP/2 需要 ASGI。
- 规模：同步 `workers = 2*cores+1`；异步少些。
- Hypercorn 支持 HTTP/2 和 HTTP/3。
- 别在生产跑开发服务器（`flask run`、`uvicorn --reload`）。

### 94. Java 虚拟线程（Loom）

**频率：** 低

**题目：** 什么是 Java 虚拟线程（Project Loom），为何它们让"线程对应请求"代码扩到百万连接？

**答案：** **虚拟线程**（Project Loom，**JDK 21 GA**）是 **JVM 管理的轻量线程**而非 OS 线程。平台（OS）线程耗 ~1 MB 栈且是稀缺资源，所以只能数千个。虚拟线程耗 **KB 级**，JVM 把**多个调度到小池"carrier"（平台）线程**。魔力在**阻塞**：当虚拟线程碰阻塞调用（`Thread.sleep`、阻塞 socket/DB I/O），JVM 把它从 carrier **卸载**并停靠，释 carrier 跑另一虚拟线程——阻塞虚拟线程**不阻 OS 线程**。

回报：你可继续写**简单、顺序、阻塞代码**——servlet、Spring MVC、JDBC 熟悉的**线程对应请求**风格——并扩到**百万并发请求**，**无需**重写成回调/响应式（`CompletableFuture`、Reactor）仅为避耗尽 OS 线程。你得到异步般扩展性加同步代码的可读可调试（真实栈迹）。

用法与告诫：
- 用 `Thread.ofVirtual().start(runnable)` 或 `Executors.newVirtualThreadPerTaskExecutor()` 创建。
- **钉住**：`synchronized` 块内的虚拟线程**钉住** carrier（不能卸载），在那阻塞会浪费 carrier——热路径优先 **`ReentrantLock`**（此钉住限制在后续 JDK 被移除）。
- **别池化虚拟线程**——它们便宜且一次性；每任务**创一个**，不同于昂贵的平台线程。池化事与愿违。

**要点：**
- `Thread.ofVirtual().start(...)` 或 `Executors.newVirtualThreadPerTaskExecutor()`。
- `synchronized` 块钉住 carrier——热路径优先 `ReentrantLock`（钉住正在修复）。
- 别池化虚拟线程——它们便宜，按任务创建。
- "线程对应请求"服务器的游戏改变者。

### 95. JVM 调优基础

**频率：** 低

**题目：** JVM 调优的要领有哪些，为何应先度量再动 GC 标志？

**答案：** 最重要原则：**先度量——默认很好**。现代 HotSpot 加 **G1** 对多数负载已调好；盲设 GC 标志通常更糟。改任何东西前用 **JFR（Java Flight Recorder）+ Mission Control** 或 **async-profiler** 剖析真瓶颈。

真正重要的少数设置：
- **堆大小**——把 **`-Xms = -Xmx`** 设同值免 JVM 启动时调堆大小，选契合负载**且给原生/堆外留余地**的值（堆非全部占用）。
- **按目标选 GC**——**G1**（默认）平衡吞吐与暂停；仅当需**极低可预测暂停**（亚毫秒）的延迟敏感服务才换 **ZGC**（或 Shenandoah）。
- **诊断常开**——启 **GC 日志**和 **`-XX:+HeapDumpOnOutOfMemoryError`**，使 OOM 或 GC 病态发生时你有证据诊断而非猜。
- **容器感知**——**`-XX:+UseContainerSupport`**（8u191 起默认）让 JVM 读 **cgroup 上限**，按容器而非宿主定堆和 CPU 数。无它，512 MB 容器里的 JVM 可能以为有整节点 RAM 而被 OOM 杀。

最常见现实坑是**堆外内存**：**DirectByteBuffer**（NIO、Netty）、**Metaspace**（类元数据）、线程栈、JIT 代码缓存都住在 `-Xmx` *之外*。"我 RAM 去哪了"通常是堆外增长。故**容器内存必须超 `-Xmx` + 原生 + 余地**（约 **`-Xmx` 上浮 ~25%**）否则内核 OOM 杀进程，即便 Java 堆看起来没事。

**答案：** 把 `-Xms = -Xmx` 设到契合工作负载的值，给原生/堆外留余地。按目标选 GC（G1 默认、ZGC 低暂停）。启用 GC 日志和 OOM 时堆转储（`-XX:+HeapDumpOnOutOfMemoryError`）。容器中用 `-XX:+UseContainerSupport`（8u191 起默认）让 JVM 看到 cgroup 上限。

**要点：**
- 调前度量；默认很好。
- JFR + Mission Control / async-profiler 做真诊断。
- 看堆外（DirectByteBuffer、metaspace）找"我 RAM 去哪了"。
- 容器内存必须超过 `-Xmx` + 原生 + 余地（~25%）。

### 96. Node.js 流与背压

**频率：** 低

**题目：** Node.js 流如何处理背压，为何优先 `pipeline()` 而非 `pipe()`？

**答案：** **流**将数据**增量**处理而非全加载进内存。四类：**可读**（源——文件读、HTTP 请求）、**可写**（汇——文件写、HTTP 响应）、**双工**（两者，如 socket）、**变换**（改数据的双工，如 gzip）。这让你处理大于 RAM 的数据。

**背压**是阻快生产者淹没慢消费者的机制。每可写流有带 **`highWaterMark`** 阈值的内部缓冲。`write()` 时若缓冲**超 `highWaterMark`**，`write()` 返回 **`false`** 信号"我满了、停"。良好读者随后**暂停**直到可写发 **`drain`** 事件再恢。`pipe()` 和 `pipeline()` **自动**接它——传播暂停/恢复使内存有界，无论速度多不匹配。无背压处理，慢磁盘配快源会膨胀内存至进程崩。

**优先 `pipeline()`** 因**错误处理与清理**。手动 `pipe()` 时若一流出错，其他**不自动销毁**——你泄露文件描述符和 socket，并得自己给每流接错误监听。**`pipeline(src, transform, dest, cb)`**（及其 promise 形）传播错误、**失败时销毁所有流**、给单个完成回调——正确、无泄露默认。现代实践：**异步迭代器**（`for await (const chunk of readable)`）是人体工学消费方式；**Web Streams API**（WHATWG）给浏览器/Worker/Deno/Bun 跨运行时代码；**流式处理文件而非全缓冲**；**对象模式**流传 JS 对象而非字节。

**要点：**
- 异步迭代器（`for await`）是现代流消费者。
- Web Streams API 镜像 WHATWG 做跨运行时代码。
- 别在内存里缓冲整个文件——流式处理。
- 对象模式流传对象，不传字节。

### 97. Spring Boot vs Quarkus vs Micronaut

**频率：** 低

**题目：** Spring Boot、Quarkus、Micronaut 有何不同，你如何在它们间选择？

**答案：** 核心区别是**何时装配依赖注入和 AOP**——运行时 vs 编译时——连带影响启动时间和内存：
- **Spring Boot**——**现任**，生态巨大成熟（Spring Data、Security、Cloud、各种集成）。传统上**通过反射和代理在运行时做 DI/AOP**，意味**启动较慢**（扫 classpath、生代理）和**内存较重**——历史上不适 serverless 冷启。
- **Quarkus** 和 **Micronaut**——新框架，把 **DI/AOP 移到编译时**（注解处理在构建生成装配）。结果是**启动快**（十几 ms）和**低内存**，为**serverless 函数和密集容器部署**而建。
- 三者都支 **GraalVM native image** 实现**毫秒启动**和小内存；**Spring Boot 3** 加 **AOT 处理**补了大部分差距。

选择：
- 选 **Spring Boot** 求**生态成熟**、集成广度和团队熟悉——多数企业后端的安全默认。
- 选 **Quarkus/Micronaut** 求**云原生**：serverless、函数、启动/内存主导成本的高密容器。
- **Native image** 买小内存与即时启动但付**慢构建**和**反射注意事项**（必须显式注册反射访问、动态代理、资源，或用框架 hint）。
- 三者都提供**反应式**栈（Quarkus **Mutiny**、Spring **Reactor**、加 RxJava），且**相互迁移非小事**——DI/配置/注解模型差得够多，实际上是重写装配层。

**要点：**
- 选 Spring 求生态成熟，选 Quarkus/Micronaut 求云原生。
- Native image：极小内存、慢构建、反射注意事项。
- 三者都支持反应式（Mutiny、Reactor、RxJava）。
- 在它们间迁移非平凡。

### 98. Express vs Fastify vs NestJS

**频率：** 低

**题目：** Express、Fastify、NestJS 如何对比，你如何在它们间选择？

**答案：** 它们处于**极简 ↔ 结构**和**速度**谱的不同点：
- **Express**——**极简、无处不在、成熟**，拥 Node 最大中间件生态。无主张（你自拼结构），是安全熟悉默认，但比新选项**慢**且回调时代设计显老。
- **Fastify**——**schema 优先、比 Express 快约 2×**。招牌特性是 **基于 JSON-Schema 的校验与序列化**：你声明请求/响应 schema，Fastify **校验输入**并为输出**编译快序列器**。有良好**插件/封装模型**和一等异步支持。
- **NestJS**——**有主张、结构化**，把 **Angular 风格模块、装饰器、依赖注入**带到后端。它跑在 **Express 或 Fastify 之上**（可插适配器），是架构层而非裸 HTTP 框架。最适**想要强制结构、可测、一致性的大型代码库与团队**。

选择：按**团队与规模**。**Fastify** 要性能与 schema 校验；**Express** 重熟悉、生态、简单；**NestJS** 当大团队需强制架构和 DI（接受更重学习曲线和更多样板）。三者都支 **async/await** 和**中间件/钩子**管线。更新选项是 **Hono**——小而快、**跨运行时**，跑在 **Cloudflare Workers、Bun、Deno、Node**，适合边缘/serverless 目标。

**要点：**
- Fastify 赢基准；Express 赢熟悉度。
- NestJS 加结构但学习曲线更重。
- 三者都支持 async/await 与中间件/钩子。
- Hono 是更新的跨运行时替代（Workers、Bun、Deno、Node）。

### 99. mTLS

**频率：** 低

**题目：** 什么是双向 TLS（mTLS），为何它对服务间认证比 bearer token 更强？

**答案：** 普通 TLS 只把**服务端**认证给客户（浏览器查站点证书）。**mTLS** 使其**双向**：**双方都提供 X.509 证书且各自向可信 CA 校验对方**。所以服务器密码学确认*哪个客户*在调，而非仅*某*客户连了。这使 mTLS 成为**零信任网络中服务对服务认证**的骨干，你不信任网络、每调用必证身份——替代或增强共享 API key。

它**比 bearer token 强**因**持有绑定**。bearer token（JWT/API key）是"谁持有谁就是"——若泄（日志、代理、SSRF、复粘）任人可重放。mTLS 客户证绑定到**从不离主机的私钥**，通过 TLS 握手挑战证明，所以**无静态可盗重放**——截流也不给攻击者私钥。

难点是**证书生命周期**——跨多服务的签发、分发、**轮换**、**撤销**。手工不扩展，故：
- **服务网格**（**Istio、Linkerd**）透明**自动化**签发与轮换，典型经 **SPIFFE/SPIRE**，应用代码不管证书。
- **短命证书**（小时级、自动轮换）**限爆炸半径**——被拔证书很快过期，减少撤销基设需求。
- **SPIFFE ID** 给每工作负载**稳定密码身份**（`spiffe://cluster/ns/sa`），独立于 IP/pod。
- **TLS 终止器/sidecar**（**Envoy**）**处理 mTLS 握手**，应用无需自实现证书逻辑。

**要点：**
- 证书生命周期（签发、轮换、撤销）是难点——自动化。
- 短命证书（小时级）限制爆炸半径。
- 配对 SPIFFE ID 做稳定工作负载身份。
- TLS 终止器（Envoy）处理 mTLS 让应用不必。

### 100. 指标：RED vs USE

**频率：** 低

**题目：** 比较指标的 RED 与 USE 方法，为何跟踪百分位而非平均？

**答案：** RED 和 USE 是两个互补的**监控框架**，告诉你*测什么*，面向不同对象：
- **RED**——为**请求驱动服务**（API、端点）：**Rate**（请求/秒）、**Errors**（错误/秒或错率）、**Duration**（延迟分布）。答"此服务服务请求好吗"，直映用户体验。
- **USE**——为**资源**（CPU、盘、内存、队列、连接池）：**Utilization**（忙%）、**Saturation**（多少工作排队/等）、**Errors**（设备/资源错）。答"此资源是瓶颈吗"。

用 **RED 监 API**、**USE 监其下基设**——一同覆盖需求端与供给端，当 API 的 RED 显延迟升你查其资源 USE 找因。

**跟直方图/百分位而非平均**，因平均掩尾延迟。若 99% 请求 20 ms、1% 要 5 s，**平均**可能看似没事（~70 ms）而**每 100 个用户有 1 个**体验极差——规模下那 1% 是巨量请求，常是超时并级联的。**p99（及 p99.9）**恰揭那尾。把延迟记为**直方图**以事后算任意百分位。

实践：
- **直方图支下游百分位查询**——如 Prometheus **`histogram_quantile(0.99, ...)`** 从分桶数据算 p99。
- **避高基数 label**（用户 ID、请求 ID、完整 URL）——每唯一 label 组合是一条单独时序，炸监控后端内存/存储。
- **对 SLO 燃烧率告警**（多快耗错误预算）而非原始静态阈值——更有意义且远不那么吵。
- 建**每服务黄金信号仪表盘**，使 on-call 到处有一致 RED 视图。

**答案：** RED 用于请求驱动服务：Rate（req/s）、Errors（err/s 或 %）、Duration（延迟分布）。USE 用于资源：Utilization、Saturation、Errors。API 用 RED，CPU/盘/队列用 USE。始终跟踪直方图/百分位，不只平均——p99 揭示意味着捕火的尾延迟。

**要点：**
- 直方图启用下游百分位查询（Prometheus `histogram_quantile`）。
- 高基数 label（用户 ID）炸基数——避免。
- 对 SLO 燃烧率告警，不是原始阈值。
- 每服务仪表板：黄金信号（RED + 饱和度）。
