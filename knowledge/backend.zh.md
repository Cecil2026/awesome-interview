### 1. REST vs RPC vs GraphQL vs gRPC

**频率：** 高

**题目：** 请比较 REST、RPC、GraphQL 和 gRPC 四种 API 风格：(1) REST 如何用 HTTP 动词对资源建模，为何适合公开、可缓存、面向资源的 API；(2) RPC（含 JSON-RPC、gRPC）以动作/过程建模的特点及适用的内部服务调用场景；(3) GraphQL 单端点加类型化 schema 的按需查询能力及其在移动端/BFF 聚合层的优势与 N+1、缓存难题；(4) gRPC 基于 HTTP/2 + protobuf 的二进制、流式、多路复用特性。请结合受众说明各自的选型依据。

**答案：** REST 用统一的 HTTP 动词对资源建模，非常适合公开、可缓存、面向资源的 API。RPC（JSON-RPC、gRPC）以动作/过程建模，适合内部服务对服务调用，强类型与低延迟更重要。GraphQL 暴露单一端点 + 类型化 schema，让客户端按需查询字段——非常适合移动端/聚合 BFF 层，但带来 N+1 与缓存难题。gRPC 用 HTTP/2 + protobuf 做二进制、流式、多路复用调用，是内部微服务的默认选项。

**要点：**
- REST：通过 HTTP 可缓存、弱类型、载荷冗长。
- gRPC：流式、代码生成、浏览器支持差（需要 gRPC-Web）。
- GraphQL：查询灵活、有 schema、鉴权与限流复杂。
- 按受众选：公开/第三方 = REST；内部高吞吐 = gRPC；移动端聚合 = GraphQL。

### 2. 幂等性：方法与 key

**频率：** 高

**题目：** 请解释什么是幂等性：(1) 幂等操作的定义，以及 GET/PUT/DELETE 与 POST 在 HTTP 契约下的幂等性差异；(2) 对支付这类不安全操作，客户端如何用 `Idempotency-Key` 请求头、服务器又如何按 key 存储首次响应并在重试时返回缓存；(3) 存储结构、TTL、以及同一 key 不同 body 时的处理；(4) 它能防御哪些问题（网络重试、双击、至少一次投递），并说明幂等与安全的区别。

**答案：** 一个操作如果重复执行产生相同的可观察结果，就是幂等的。GET/PUT/DELETE 按 HTTP 契约是幂等的；POST 不是。对支付这类不安全操作，客户端发送 `Idempotency-Key` 请求头；服务器按其存储首次响应一段 TTL，并在重试时返回缓存响应。这能防御网络重试、双击和至少一次消息投递。

**要点：**
- 存储 `(key, request hash, response)`；同一 key 不同 body 时拒绝。
- TTL 通常 24 小时；持久化到 Redis 或专用表。
- 幂等 ≠ 安全：PUT 改变状态但是幂等的。
- 对 webhook、支付和队列消费者至关重要。

### 3. 分页：offset vs cursor

**频率：** 高

**题目：** 请对比 offset 分页与 cursor（keyset）分页：(1) offset 分页（`LIMIT N OFFSET M`）的简单性，以及大 offset 时的性能问题和并发插入下的不稳定（条目漂移）；(2) cursor 分页如何用最后看到的排序键实现有索引下的高效且稳定的翻页；(3) cursor 为何要编码完整排序元组、以及使用不透明 base64 cursor 的好处；(4) 各自适用的数据规模，以及返回 `next_cursor`/`has_more` 与避免总数统计的建议。

**答案：** Offset 分页（`LIMIT N OFFSET M`）简单，但大 offset 时很慢，且在并发插入下不稳定（条目在页之间漂移）。Cursor（keyset）分页用最后看到的排序键（`WHERE (created_at, id) < (?, ?) ORDER BY ... LIMIT N`），有索引时是 O(log n)，对插入也稳定。大或增长中的集合一定用 cursor 分页；小管理表用 offset 没问题。

**要点：**
- Cursor 必须编码完整排序元组以保稳定。
- 不透明的 base64 cursor 隐藏实现、便于演进。
- Offset 在无限滚动 UX 下崩溃。
- 返回 `next_cursor` 与 `has_more`；大表上避免总数统计。

### 4. 限流算法（token/leaky/sliding）

**频率：** 高

**题目：** 请比较常见的限流算法：(1) 令牌桶如何允许爆发并稳定补充；(2) 漏桶如何以固定速率平滑输出；(3) 固定窗口的低成本与窗口边缘 2 倍爆发问题；(4) 滑窗日志的精确与内存代价，以及滑窗计数器的近似。请说明如何用 Redis 做集中式分布式执行，返回 `429` 加 `Retry-After` 和 `X-RateLimit-*` 头，按维度组合设限，并配合并发上限保护下游。

**答案：** 令牌桶允许爆发到桶大小、以稳定速率补充——最佳通用选择。漏桶以固定速率平滑输出，丢弃或排队超额。固定窗口便宜但窗口边缘允许 2 倍爆发。滑窗日志精确但耗内存；滑窗计数器以低成本近似。集中实现（Redis）做分布式执行。

**要点：**
- 返回 `429` 加 `Retry-After` 和 `X-RateLimit-*` 头。
- 按 API key、按 IP、按路由组合设上限。
- Redis `INCR` + EXPIRE 或 Lua 脚本保证原子。
- 与并发上限组合以保护下游服务。

### 5. 认证 vs 授权；OAuth 2.0 流程

**频率：** 高

**题目：** 请辨析认证与授权的区别，并讲解 OAuth 2.0：(1) 认证（你是谁）与授权（能做什么）的差别；(2) OAuth 2.0 作为授权框架的角色，以及 Authorization Code + PKCE、Client Credentials、Device Code 等各自适用场景，和为何 Resource Owner Password 已弃用；(3) OIDC 如何在 OAuth 之上叠加身份（ID token、userinfo）。请一并说明 access/refresh token 生命周期、每请求校验 `aud`/`iss`/`exp` 与签名、以及 scope、claim 与策略引擎的分工。

**答案：** 认证证明身份（"你是谁"）；授权决定权限（"能做什么"）。OAuth 2.0 是颁发 access token 的授权框架。Authorization Code + PKCE 是 Web 与移动应用的默认。Client Credentials 用于机对机。Device Code 用于电视/CLI。Resource Owner Password 已弃用。OIDC 在 OAuth 之上叠加身份（ID token、userinfo）。

**要点：**
- 不再使用 Implicit 流——PKCE 取代之。
- Access token 短命；refresh token 长命且可轮换。
- 每个请求都校验 `aud`、`iss`、`exp` 与签名。
- Scope 做粗权限，claim 做属性，策略引擎做细粒度。

### 6. JWT vs session cookie

**频率：** 高

**题目：** 请比较 JWT 与 session cookie：(1) session cookie 持有不透明 ID、状态在服务端因而撤销简单；(2) JWT 自包含签名声明、无需查找即可校验因而适合分布式系统但过期前难撤销；(3) 第一方 Web 应用与 API/微服务各自更适合哪种。请说明 JWT 的缺点（体积、难撤销、`alg=none` 误用）、cookie 应设的 `HttpOnly`/`Secure`/`SameSite` 属性、JWT 保持短命并用轮换 refresh token 刷新、以及多服务下用非对称密钥验签。

**答案：** Session cookie 持有不透明 ID；状态在服务端，所以撤销简单。JWT 是自包含的签名声明，任何服务无需查找即可校验——对分布式系统好但过期前难撤销。第一方 Web 应用，带 Secure HttpOnly cookie 的会话更简单更安全。API 与微服务里常用短命 JWT + refresh token。

**要点：**
- JWT 缺点：体积、没黑名单难撤销、易误用 `alg=none`。
- 会话 cookie 永远设 `HttpOnly`、`Secure`、`SameSite=Lax/Strict`。
- JWT 保持短（5-15 分钟）；通过轮换的 refresh token 刷新。
- 多服务下用非对称密钥（RS256/EdDSA）验签，而非共享密钥。

### 7. ACID

**频率：** 高

**题目：** 请解释 ACID 四大特性：(1) 原子性（写入全提交或全不提交）；(2) 一致性（把数据库从一个合法状态搬到另一个、保持约束）；(3) 隔离性（并发事务在某种程度上表现得像串行）；(4) 持久性（已提交数据崩溃后仍存在，通常靠 WAL fsync）。请一并说明为何 C 最模糊（应用级不变量）、持久性对 fsync 与存储的依赖、隔离级别决定看到的异常、以及 WAL 是 A 与 D 背后的机制。

**答案：** 原子性：事务的写入要么全提交要么全不。一致性：事务把数据库从一个合法状态搬到另一个（约束保持）。隔离性：并发事务在某种程度上表现得像串行。持久性：已提交数据在崩溃后仍存在（通常通过 WAL fsync）。Postgres 这类 RDBMS 四样都提供；NoSQL 常为规模放宽一项或多项。

**要点：**
- "C"最模糊——讲的是应用级不变量，不仅是数据库的。
- 持久性取决于 `fsync` 与存储；云盘可能撒谎。
- 隔离级别（下一题）决定你看到的异常。
- WAL 是 A 与 D 背后的机制。

### 8. 隔离级别与异常

**频率：** 高

**题目：** 请讲解数据库隔离级别及其异常：(1) Read Uncommitted 的脏读；(2) Read Committed（Postgres 默认）无脏读但仍可能不可重复读与幻读；(3) Repeatable Read（MySQL 默认，Postgres 的 RR 也防幻读）；(4) Serializable 完全串行（Postgres 用 SSI 中止冲突事务）。请一并列举脏读、不可重复读、幻读、写偏斜、丢失更新等异常，说明 SSI 如何抓写偏斜、应用代码为何要处理序列化失败重试、以及热行用 `SELECT ... FOR UPDATE`。

**答案：** Read Uncommitted：能看到脏读。Read Committed（Postgres 默认）：无脏读，但可能不可重复读和幻读。Repeatable Read（MySQL 默认）：无不可重复读；Postgres 的 RR 也通过快照防止幻读。Serializable：表现得完全串行——Postgres 用 SSI，会中止冲突事务。隔离越高 = 中止/重试越多。

**要点：**
- 异常：脏读、不可重复读、幻读、写偏斜、丢失更新。
- Postgres SSI 抓住 Repeatable Read 漏掉的写偏斜。
- 在应用代码中始终处理序列化失败重试。
- 热行用显式 `SELECT ... FOR UPDATE`，而不是抬高隔离。

### 9. 索引：B-tree vs hash；覆盖

**频率：** 高

**题目：** 请比较数据库索引类型并解释覆盖索引：(1) B-tree 作为主力支持等值、范围、前缀与 ORDER BY；(2) hash 索引只支持等值、为何很少值得；(3) 覆盖索引（INCLUDE 或复合）如何让引擎只读索引跳过堆；(4) 复合索引顺序与最左前缀规则。请一并说明索引选择性、部分索引、GIN/GiST 用于全文/数组/JSON/地理，以及每个索引都让写变慢、加之前要度量。

**答案：** B-tree 是主力——有序、支持等值、范围、前缀和 ORDER BY。Hash 索引只支持等值，很少值得（Postgres 有，但 10 之后才崩溃安全）。覆盖索引包含查询所需的全部列（通过 INCLUDE 或复合），引擎只读索引、跳过堆。复合索引顺序重要：最左前缀规则。

**要点：**
- 索引选择性：低基数列很少受益。
- 部分索引用于过滤子集（`WHERE deleted_at IS NULL`）。
- 全文/数组/JSON/地理用 GIN/GiST。
- 每个索引都让写变慢——加之前要度量。

### 10. N+1 查询问题

**频率：** 高

**题目：** 请讲解 N+1 查询问题：(1) 它如何产生（取 N 个父记录后发 N 个子查询，常见于朴素 ORM 和懒加载）及其症状（吞吐随列表大小骤降）；(2) 如何修复（预加载 JOIN 或 IN 批量、GraphQL 的 DataLoader、显式预取如 `select_related`/`prefetch_related`、EF 的 `Include`）；(3) 何时用 JOIN、何时用 IN 批量。请一并说明在测试中记录 SQL 并断言查询计数、GraphQL resolver 几乎总需 DataLoader，以及它为何是 ORM 重栈中慢 API 的最常见原因。

**答案：** 取 N 个父记录列表然后发 N 个子查询——朴素 ORM 和懒加载常见。症状：吞吐随列表大小骤降。修复：预加载（`JOIN` 或带批量的 `IN (...)`)、GraphQL 中的 DataLoader 风格批量、显式预取（Django 的 `select_related`/`prefetch_related`、EF 的 `Include`）。在开发期观察 ORM 生成的 SQL。

**要点：**
- 在测试中始终记录 SQL，并对热路径断言查询计数。
- 1:1 或小扇出用 `JOIN`；大扇出用 `IN` 批量。
- GraphQL resolver 几乎总是需要 DataLoader。
- N+1 是 ORM 重栈中慢 API 的最常见原因。

### 11. Join；何时反规范化

**频率：** 高

**题目：** 请讨论 join 与何时反规范化：(1) 规范化 schema 如何保持数据一致、写便宜；(2) 何时应反规范化（读延迟占主导、join 跨越分区/分片、热读模式重复执行多路 join）；(3) 物化视图与计算列作为中间地带、以及 NoSQL 默认反规范化按查询设计。请一并说明内连/左连/全外连按语义选择、反规范化需要的同步策略（触发器、CDC、双写）、读多与写多的权衡，以及周期刷新物化视图常是最佳折中。

**答案：** 规范化 schema 保持数据一致、写便宜。Join 没问题，直到它有问题——当读延迟占主导、join 跨越分区/分片，或某个热读模式重复执行 5 路 join 时反规范化。物化视图与计算列是中间地带。NoSQL 默认反规范化，并按查询设计。

**要点：**
- 内连 vs 左连 vs 全外连——按语义选，不要凭性能直觉。
- 反规范化需要同步策略（触发器、CDC、双写）。
- 读多 → 反规范化；写多 → 规范化。
- 周期刷新的物化视图常是最佳折中。

### 12. 范式 1NF-BCNF

**频率：** 高

**题目：** 请讲解从 1NF 到 BCNF 的范式：(1) 1NF（列原子、无重复组）；(2) 2NF（无对复合键的部分依赖）；(3) 3NF（无传递依赖）；(4) BCNF（每个决定因素都是候选键，比 3NF 更严）。请说明实际应用为何瞄准 3NF 并按性能选择性反规范化、规范化如何最小化更新异常与存储重复、过度规范化导致过多 join、分析中的星型/雪花 schema 故意反规范化，以及 JSON 列作为稀疏属性的逃生口。

**答案：** 1NF：列原子、无重复组。2NF：1NF + 无对复合键的部分依赖。3NF：2NF + 无传递依赖（非键 → 非键）。BCNF：每个决定因素都是候选键——比 3NF 更严。实际应用瞄准 3NF，按性能选择性反规范化。

**要点：**
- 规范化最小化更新异常和存储重复。
- 过度规范化导致过多 join。
- 分析中的星型/雪花 schema 故意反规范化。
- JSON 列是稀疏属性的实用逃生口。

### 13. 分片（范围/哈希/地理）

**频率：** 高

**题目：** 请比较分片策略：(1) 范围分片按 key 区间拆分的范围扫描优势与单调 key 热点风险；(2) 哈希分片的均匀分布与无范围扫描、再平衡难；(3) 地理分片按区域路由获得延迟与合规。请说明如何选择兼顾均匀分布与查询本地性的分片 key、跨片 join/事务的代价、分片 key 难改要按未来 3-5 年设计、一致性哈希最小化再平衡、范围方案预拆分避免初始热点，以及尽量按租户路由避免分布式事务。

**答案：** 范围分片按 key 区间拆分——范围扫描容易但单调 key 有热点风险。哈希分片均匀分布——无范围扫描、再平衡更难。地理分片按区域路由获得延迟和合规。选择分片 key 兼顾均匀分布和查询本地性；跨片 join/事务贵。

**要点：**
- 分片 key 难改——按未来 3-5 年设计。
- 一致性哈希在节点变化时最小化再平衡。
- 范围方案预拆分避免初始热点。
- 避免分布式事务；可能时按租户路由。

### 14. 乐观 vs 悲观锁

**频率：** 高

**题目：** 请比较乐观锁与悲观锁：(1) 乐观锁如何用版本/etag 在写时 `WHERE version = ?` 检测冲突并重试，及其适用的低争用场景；(2) 悲观锁如何用 `SELECT ... FOR UPDATE` 锁行直到提交，及其适用的高争用或重试昂贵场景；(3) 两者在扩展性与延迟可预测性上的差异。请一并说明乐观锁的版本列、HTTP If-Match/ETag 作为 API 层乐观锁、悲观锁跨用户思考时间持有的危害，以及 `SKIP LOCKED` 启用无争用工作队列。

**答案：** 乐观：读时带版本/etag，写时 `WHERE version = ?`；若 0 行更新则冲突，重试。最适合低争用工作负载。悲观：`SELECT ... FOR UPDATE` 锁住行直到提交。最适合高争用或重试昂贵时。乐观扩展更好；悲观在争用下延迟更可预测。

**要点：**
- 乐观永远带整数/UUID 版本列。
- HTTP If-Match/ETag 是 API 层的乐观锁。
- 悲观锁跨用户思考时间持有 = 灾难。
- `SKIP LOCKED` 启用无争用的工作队列模式。

### 15. CAP 与 PACELC

**频率：** 高

**题目：** 请讲解 CAP 与 PACELC：(1) CAP 为何说在网络分区下必须以一致性换可用性；(2) PACELC 如何扩展——即便无分区也要以延迟换一致性（PA/EL vs PC/EC）；(3) 常见分布式数据库如何归类为 AP（Dynamo、Cassandra）或 CP（Spanner、etcd、ZooKeeper），以及可调一致性。请一并说明 CAP 讲的是分区期间行为而非稳态、CAP 的一致性等于线性化（强于 SQL 的 C）、延迟 vs 一致性折衷是日常那个，以及选数据库不应只凭 CAP。

**答案：** CAP 说在网络分区下必须以一致性换可用性。PACELC 扩展：即便没分区，也要以延迟换一致性（PA/EL vs PC/EC）。多数分布式数据库是 AP（Dynamo、Cassandra）或 CP（Spanner、etcd、ZooKeeper）。真实系统可调：Cassandra 让你按查询挑一致性。

**要点：**
- CAP 讲分区期间行为，不是稳态。

### 16. cache-aside vs read-through vs write-through vs write-behind

**频率：** 高

- Cache-aside 把失效负担放到应用。
- Write-through 以写成本消除缓存/数据库偏差。
- Write-behind 需要耐久队列才能安全。
- 即便有显式失效也总要设 TTL。

### 23. Exactly-once vs at-least-once vs at-most-once

**频率：** 高

**答案：** 至多一次：发完不管；消息可能丢。至少一次：重试到 ack；可能重复。Exactly-once：每个效果发生一次——只能通过幂等消费者或事务写入端到端实现（Kafka 内 EOS）。实际上至少一次 + 幂等消费者是现实目标。

**要点：**
- "Exactly-once 投递"多是营销；"exactly-once 处理"是真实的。
- 幂等键 + 去重表是你构建 exactly-once 的方式。
- Kafka 事务覆盖 Kafka 到 Kafka；桥接外部系统需要 outbox/2PC 模式。
- 始终设计消费者处理重复。

### 24. Kafka 分区/消费者组/offset

**答案：** Topic 有 N 个分区，每个是有序日志。生产者按 key 路由（同 key → 同分区 → 有序）。消费者组成员分担分区——每分区最多一个消费者。Offset 跟踪每分区读位置，提交回 Kafka。通过加分区扩展消费者。

- 在处理后提交 offset，不是之前（至少一次）。

- 别接受通过 GET 的状态变更请求。

- Readiness 在数据库/队列故障时翻转让流量排空。
- 别把 liveness 绑到下游——故障期会重启循环。
- Startup 探针防慢启动应用过早被杀。

**题目：** 请介绍 Java 虚拟线程（Project Loom）：虚拟线程为什么轻量、JVM 如何把它们调度到少量 carrier 线程上，以及为什么可以写阻塞式代码（如 Thread.sleep、阻塞 I/O）而 JVM 会卸载虚拟线程而非阻塞 OS 线程，从而让 servlet/Spring 风格代码扩展到百万并发请求。同时说明 (1) 如何创建虚拟线程；(2) 为什么 synchronized 会钉住 carrier、热路径应优先 ReentrantLock；(3) 为什么不应池化虚拟线程。

**答案：** JDK 21 GA。虚拟线程轻量（KB 级），由 JVM 调度到少量 carrier 线程上。写阻塞代码（`Thread.sleep`、阻塞 I/O），JVM 卸载虚拟线程而非阻塞 OS 线程。让 servlet/Spring 风格代码扩展到百万并发请求而无需异步重写。

**要点：**
- `Thread.ofVirtual().start(...)` 或 `Executors.newVirtualThreadPerTaskExecutor()`。
- `synchronized` 块钉住 carrier——热路径优先 `ReentrantLock`（钉住正在修复）。
- 别池化虚拟线程——它们便宜，按任务创建。
- "线程对应请求"服务器的游戏改变者。

### 95. JVM 调优基础

**频率：** 低

**题目：** 请谈谈 JVM 调优基础：如何设置 -Xms 和 -Xmx（并为原生/堆外留余地）、如何按目标选择 GC、如何启用 GC 日志和 OOM 时堆转储，以及容器中如何用 UseContainerSupport 让 JVM 看到 cgroup 上限。同时说明 (1) 为什么应先度量再调优；(2) JFR 加 Mission Control 或 async-profiler 的作用；(3) 排查内存去向时为什么要看堆外（DirectByteBuffer、metaspace）；(4) 容器内存与 -Xmx 的关系。

**答案：** 把 `-Xms = -Xmx` 设到契合工作负载的值，给原生/堆外留余地。按目标选 GC（G1 默认、ZGC 低暂停）。启用 GC 日志和 OOM 时堆转储（`-XX:+HeapDumpOnOutOfMemoryError`）。容器中用 `-XX:+UseContainerSupport`（8u191 起默认）让 JVM 看到 cgroup 上限。

**要点：**
- 调前度量；默认很好。
- JFR + Mission Control / async-profiler 做真诊断。
- 看堆外（DirectByteBuffer、metaspace）找"我 RAM 去哪了"。
- 容器内存必须超过 `-Xmx` + 原生 + 余地（~25%）。

### 96. Node.js 流与背压

**频率：** 低

**题目：** 请介绍 Node.js 的流和背压：流的四种类型（可读、可写、双工、变换），以及 pipe() 和 pipeline() 如何传播背压（当可写缓冲超过 highWaterMark 时 write() 返回 false、读者暂停），并说明为什么应优先用 pipeline() 而非手动 pipe()。同时说明 (1) 异步迭代器作为现代流消费者；(2) Web Streams API 的跨运行时意义；(3) 为什么不应在内存里缓冲整个文件；(4) 对象模式流的用途。

**答案：** 流增量处理数据——可读、可写、双工、变换。`pipe()` 和 `pipeline()` 传播背压：当可写的内部缓冲超过 `highWaterMark`，`write()` 返回 false，读者暂停。用 `pipeline()`（带错误清理）而非手动 `pipe()`。

**要点：**
- 异步迭代器（`for await`）是现代流消费者。
- Web Streams API 镜像 WHATWG 做跨运行时代码。
- 别在内存里缓冲整个文件——流式处理。
- 对象模式流传对象，不传字节。

### 97. Spring Boot vs Quarkus vs Micronaut

**频率：** 低

**题目：** 请比较 Spring Boot、Quarkus 和 Micronaut 三个 Java 框架：说明 Spring Boot 作为现任的生态优势与运行时反射 DI/AOP 带来的启动慢和内存重，以及 Quarkus 和 Micronaut 的编译时 DI/AOP 如何砍启动与内存、适合 serverless 和容器。同时说明 (1) 如何在生态成熟与云原生之间选择；(2) GraalVM native image 的取舍（内存、构建速度、反射注意事项）；(3) 它们的反应式支持；(4) 相互迁移的难度。

**答案：** Spring Boot 是现任——巨大生态、通过反射做运行时 DI/AOP、启动较慢、内存较重。Quarkus 与 Micronaut 做编译时 DI/AOP，狂砍启动与内存——非常适合 serverless 和容器。两者都支持 GraalVM native image 实现毫秒启动。Spring Boot 3 + AOT 也带来 native 支持。

**要点：**
- 选 Spring 求生态成熟，选 Quarkus/Micronaut 求云原生。
- Native image：极小内存、慢构建、反射注意事项。
- 三者都支持反应式（Mutiny、Reactor、RxJava）。
- 在它们间迁移非平凡。

### 99. mTLS

**频率：** 低

**题目：** 请介绍 mTLS（双向 TLS）：客户端与服务端如何互相提供并校验证书、它如何用于零信任网络中的服务对服务认证（替代或增强 API key），以及服务网格（Istio、Linkerd）如何通过 SPIFFE/SPIRE 自动化证书签发与轮换。同时说明 (1) 为什么它比 bearer token 更强（持有绑定到主机私钥）；(2) 证书生命周期管理为什么是难点；(3) 短命证书如何限制爆炸半径；(4) TLS 终止器如何代应用处理 mTLS。

**答案：** 双向 TLS——客户端与服务端都提供证书，互相校验。用于零信任网络中的服务对服务认证，替代或增强 API key。服务网格（Istio、Linkerd）通过 SPIFFE/SPIRE 自动化证书签发与轮换。比 bearer token 更强因为持有绑定到主机私钥。

### 100. 指标：RED vs USE

**频率：** 低

**题目：** 请比较监控指标的 RED 与 USE 两种方法论：RED 用于请求驱动服务（Rate、Errors、Duration），USE 用于资源（Utilization、Saturation、Errors），并说明 API 与 CPU/盘/队列各自适用哪种。请说明为什么要跟踪直方图/百分位而不只是平均（p99 揭示尾延迟），以及 (1) 直方图如何支持下游百分位查询；(2) 高基数 label 的危害；(3) 为什么应对 SLO 燃烧率而非原始阈值告警；(4) 每服务仪表板的黄金信号。

**答案：** RED 用于请求驱动服务：Rate（req/s）、Errors（err/s 或 %）、Duration（延迟分布）。USE 用于资源：Utilization、Saturation、Errors。API 用 RED，CPU/盘/队列用 USE。始终跟踪直方图/百分位，不只平均——p99 揭示意味着捕火的尾延迟。

**要点：**
- 直方图启用下游百分位查询（Prometheus `histogram_quantile`）。
- 高基数 label（用户 ID）炸基数——避免。
- 对 SLO 燃烧率告警，不是原始阈值。
- 每服务仪表板：黄金信号（RED + 饱和度）。
