# 系统设计（场景实战）

经典的"设计某系统"面试场景，端到端走一遍：需求澄清、容量估算、API、数据模型，以及面试官真正打分的那两三个关键决策。这是一份起步集——一个小而精、可持续扩充的样本。它与 [architecture.md](architecture.md) 互补：后者单独讲底层模式（CQRS、事件驱动、一致性模型）。

每道题都带 `**Difficulty:**` 与 `**Topics:**` 元数据，便于选题器像对待公司题库那样做筛选和加权。

### 1. 设计短链接服务（TinyURL / bit.ly）

**难度：** 中等
**主题：** system-design, hashing, caching, sharding, read-heavy

**答案：** 先划范围：为长 URL 生成短码、查询时重定向、读写比约 100:1、短码永不过期（或可选 TTL）、v1 不做分析统计。容量：每天新增 1 亿 URL ≈ 1.2k 写/秒、100:1 下约 12 万读/秒——这是一个读多写少、低写入的系统，因此要优化重定向路径。短码生成是核心决策：(a) 对 URL 做哈希（MD5/SHA）取前 7 位 base62——冲突需"检查后重试"；(b) 分布式计数器（或按区间租约的 ID 服务）base62 编码——无冲突，但顺序码可被猜测并泄露业务量。折中方案——计数器喂入 base62 并加上每分片偏移——同时规避热点计数器争用与可猜测性。存储就是简单 KV：`code -> {long_url, created_at, owner}`；每天 1 亿量级需按短码哈希分片。重定向必须快：把短码放到缓存（Redis/CDN）后命中率极高，因为分布头部很小；301 可被浏览器缓存但会隐藏分析，若要按次计数就用 302。写路径要防重复提交（对长 URL 做幂等）和滥用（限流 + 恶意/URL 黑名单）。

**要点：**
- 读多写少：给重定向加缓存/CDN，写路径按远小的流量来设计。
- 短码生成才是真问题——计数器（无冲突、可猜）vs 哈希（有冲突、不可读）；要讲清权衡。
- 7 位 base62 = 62^7 ≈ 3.5 万亿个码——从容量推导长度，别拍脑袋。
- 301（可缓存、丢分析）vs 302（按次计数）是一个刻意选择。

### 2. 设计社交信息流（Twitter / Facebook 时间线）

**难度：** 困难
**主题：** system-design, fan-out, caching, sharding, consistency

**答案：** 核心矛盾是写扩散（push）vs 读扩散（pull）。Push：用户发帖时，把帖子 ID 写入每个粉丝预计算好的 feed 列表（放 Redis）。读取因而是 O(1)——直接读自己的列表——这很棒，因为读占主导。但拥有 1 亿粉丝的大 V 每发一条就触发 1 亿次写（"热点用户"/惊群问题），还会为不活跃粉丝浪费存储。Pull：按作者存帖子；读时聚合你关注的所有人的最新帖并按时间归并。写便宜，但读昂贵、高延迟，且猛击数据库。生产答案是混合：普通用户用 push，大 V 用 pull——一个粉丝的 feed = （其预计算的 push feed）在读时归并（其关注的少数大 V 的近期帖）。数据模型：帖子按帖子 ID（或作者）分片、关注/被关注图、每用户 feed 缓存。排序（时间序 vs ML 打分）叠加在检索之上。Feed 是最终一致的——新帖晚几秒出现没关系，所以可以用异步扩散 worker 并容忍延迟。

**要点：**
- 说出两种策略以及逼出混合方案的大 V 问题。
- Push = 读快/大 V 写贵；pull = 写便宜/读贵。
- 读占主导所以预计算；feed 容忍最终一致所以异步扩散。
- 把检索（取候选帖）与排序（排序它们）分开——二者扩展方式不同。

### 3. 设计限流器

**难度：** 中等
**主题：** system-design, rate-limiting, concurrency, caching, distributed-systems

**答案：** 先澄清：按用户还是按 IP？跑在哪——客户端、网关还是各服务内？限额是多少（如 100 次/分钟）、超限怎么办（429 + `Retry-After`，还是排队）？算法选择是重点：固定窗口（每时间桶一个计数器）极简，但在边界允许 2 倍突发；滑动窗口日志（存每次请求时间戳）精确但耗内存；滑动窗口计数器（当前与上一窗口的加权混合）是常见折中；令牌桶（令牌按稳定速率补充、每请求花一个）天然允许受控突发，是通常默认；漏桶把输出平滑到固定速率。在分布式部署里计数器必须共享，因此放 Redis 并让"检查并递减"原子化（Lua 脚本或带过期的 `INCR`），以避免多个网关节点间的竞态；否则两个节点各放行一个请求、合起来就超限了。注意单个热门用户的热点键问题——分片，或用本地近似计数配合周期性对账。失败开放还是关闭？为可用性通常失败开放（限流器挂了就放行），除非是安全敏感端点。

**要点：**
- 令牌桶是合理默认（稳定补充 + 受控突发）；要懂固定窗口为何在边界突发。
- 分布式正确性需要原子"检查并递减"（Redis Lua / INCR+EXPIRE），不是读后写。
- 返回 429 带 `Retry-After`；明确失败开放 vs 失败关闭。
- 热门用户的热点键需要分片或本地近似计数。

### 4. 设计分布式键值存储（Dynamo 风格）

**难度：** 困难
**主题：** system-design, distributed-systems, consistency, replication, sharding

**答案：** 需求：按 key 做 get/put、水平扩展、高可用、可调一致性。分区：一致性哈希把 key 放到环上，增删节点只移动约 1/N 的 key；虚拟节点均衡负载与热点。复制：每个 key 写到环上顺时针接下来的 N 个节点（偏好列表），并在物理主机/机架间跳过重复。一致性通过法定人数可调：N 个副本时，选 R（读）和 W（写）使 R + W > N 得到读己所写的一致性；更小的 R/W 用一致性换延迟/可用性（这就是 CAP 旋钮——Dynamo 选 AP 加最终一致）。对同一 key 的并发写会产生冲突；用向量时钟解决（检测因果、把兄弟版本抛给应用）或最后写入者胜（更简单、可能丢数据）。故障处理：提示移交让健康节点临时替宕机对等接受写、恢复后回放；用 Merkle 树的反熵通过自顶向下比对哈希高效地重新同步分歧副本。成员与故障探测用 gossip 协议，因此没有中心协调者。

**要点：**
- 一致性哈希 + 虚拟节点做分区、最小化重排。
- R + W > N 是较强读的法定人数规则；更小的值买可用性（CAP 权衡）。
- 冲突解决：向量时钟（因果、保留兄弟）vs 最后写入者胜（有损、简单）。
- 提示移交 + Merkle 树反熵 + gossip = 无协调者的高可用。

### 5. 设计即时通讯/聊天系统（WhatsApp、Messenger）

**难度：** 困难
**主题：** system-design, websockets, message-queue, consistency, fan-out

**答案：** 需求：1:1 和群聊、在线/离线送达、送达 + 已读回执、会话内有序、媒体附件。连接层：客户端与有状态网关保持长连接（WebSocket / 长轮询）；会话注册表（谁连到哪个网关）让你能把消息路由到接收方所在的网关。接收方离线时，持久化到每用户消息存储/队列并在重连时送达（外加推送通知）。有序：分配每会话序列号（或逻辑时钟），让客户端能排序并检测缺口，而不是依赖跨服务器的墙上时钟。送达语义：至少一次 + 客户端按消息 ID 去重，就得到"已发 → 已达 → 已读"的勾选状态；存储 ack 以驱动回执。群聊是扇出：小群写入每个成员的队列；大群用共享的每群日志供成员读取，扩展性更好。数据模型：消息按会话 ID 分片，让一个会话的历史共置。媒体进对象存储/CDN，消息只带 URL。无状态的路由逻辑水平扩展；有状态的部分是连接网关和会话注册表。

**要点：**
- 长连接 + 会话注册表路由到正确网关；离线 → 存储转发 + 推送。
- 每会话序列号做有序与缺口检测，别用服务器时钟。
- 至少一次 + 按消息 ID 去重；ack 驱动已达/已读回执。
- 按会话 ID 分片；媒体按引用进 CDN、不内联。

### 6. 设计网络爬虫

**难度：** 中等
**主题：** system-design, distributed-systems, message-queue, bloom-filter, politeness

**答案：** 需求：抓取数十亿页面、抽取链接、周期性刷新、遵守礼貌规则（robots.txt、每主机限速）、避开陷阱。核心循环：URL 前沿（一组队列）喂给抓取 worker → 解析/抽取 → 去重 → 入队新 URL。前沿是有意思的部分：它必须实施礼貌（别猛击一个主机——按主机分区队列，使每个主机由一个 worker 以受控速率服务）和优先级（先抓重要/新鲜页面）。海量去重：无法把数十亿 URL 的哈希集放内存，所以用布隆过滤器（快、小、容忍误判——误判只是跳过少数页面），后端配持久存储作为真相。内容去重（同页面不同 URL）用内容哈希 / simhash 处理近重复。礼貌：按主机缓存并遵守 robots.txt、加抓取延迟、用深度/模式限制检测蜘蛛陷阱（无限日历、会话 ID URL）。新鲜度：重抓频率随页面实际变化频率自适应。一切都分布式且幂等——已抓取但未处理的 URL 应可安全重试。

**要点：**
- URL 前沿同时编码礼貌（按主机分区 + 延迟）与优先级。
- 布隆过滤器做海量"已见 URL"去重；内容哈希 / simhash 处理重复页面。
- 遵守 robots.txt，用深度限制检测陷阱（无限/带参 URL）。
- 各阶段幂等、可重试，让 worker 崩溃不破坏抓取。

### 7. 设计通知服务（推送 / 邮件 / 短信扇出）

**难度：** 中等
**主题：** system-design, message-queue, fan-out, idempotency, reliability

**答案：** 需求：跨渠道发通知（推送、邮件、短信、站内）、处理高扇出（"突发新闻"广播）、遵守用户偏好与免打扰时段、保证不重复发送。架构：生产者发布通知事件 → 队列/broker → worker 解析收件人、应用偏好/去重过滤、按渠道套模板、再交给渠道专用提供商（APNs/FCM、邮件服务、短信网关）。通过队列解耦可吸收突发，并把慢/故障的提供商与其余隔离。可靠性：提供商会失败重试，所以让发送幂等——每（用户，通知）一个幂等键，使重试不重复发；对耗尽重试的消息用死信队列。按提供商限流（它们会限你）和按用户限流（别刷屏）。偏好与模板是分发前的查询 + 渲染步骤。对超大扇出，异步分批展开收件人列表，而不是一个巨大的同步循环。按渠道跟踪送达状态，用于可观测性和回执。

**要点：**
- 按渠道的队列解耦 worker 吸收突发并隔离提供商故障。
- 每（用户，通知）幂等键 + 死信队列就是"不重复、不丢发"的方案。
- 分发前应用用户偏好、免打扰时段、每用户/每提供商限流。
- 大扇出异步分批展开，而非一个同步循环。

### 8. 设计前缀补全 / 自动补全服务

**难度：** 中等
**主题：** system-design, trie, caching, read-heavy, ranking

**答案：** 需求：<100ms 内为一个前缀给出 top-k 补全、按热度排序、随趋势更新。这极其读多且有延迟 SLO，所以预计算。数据结构：一棵前缀树（trie），每个节点存储经过它的最热 top-k 补全，于是查询就是"走到前缀节点、返回其缓存的 top-k"——无需每请求排序。构建/刷新 trie 是对查询日志的离线批处理作业（统计查询频率、把 top-k 沿 trie 上推）；你周期性重建而不是每次击键都改。服务：trie 分片（如按首字母）并大量缓存；查询分布头部很小、可在边缘缓存。客户端对击键做防抖并缓存近期结果以削减请求量。排序数据的规模处理：对长尾用采样或近似频率计数（count-min sketch）而非精确计数。个性化和容错（编辑距离 / 模糊匹配）是热度基线之上的 v2 层。

**要点：**
- 在每个 trie 节点预计算 top-k，使服务是"走 + 返回"而非排序查询。
- 按计划从查询日志频率离线重建 trie；别每次击键就改。
- 读多 → 分片 trie 并大量缓存；客户端防抖。
- Count-min sketch / 采样处理长尾频率；模糊匹配与个性化是后续层。

### 9. 设计分布式唯一 ID 生成器

**难度：** 中等
**主题：** system-design, distributed-systems, sharding, clock

**答案：** 需求：64 位 ID、跨众多机器唯一、最好大致按时间可排序、高吞吐、无单点争用。选项：(a) 中心自增数据库——简单、有序，但是瓶颈和单点故障；(b) UUIDv4——易分布、实践中无冲突，但 128 位且不可排序，作为数据库主键很伤（随机插入会使 B 树碎片化）；(c) 数据库票据服务器给每个节点发放区间/段——减少协调但仍中心化；(d) Snowflake——标准面试答案：一个 64 位 ID = 时间戳（自定义 epoch 起的毫秒）+ 机器/worker ID + 每毫秒序列计数器。Snowflake 给出按时间有序、可排序、无需协调的 ID；每个节点只需一个唯一 worker ID（通过配置或 ZooKeeper 之类的协调服务分配）。经典失败模式是时钟偏移 / NTP 回拨——若时钟回退，你可能生成重复，所以必须检测并要么等待、要么在时钟追上前拒发 ID。位分配（时间戳 vs 机器 vs 序列各占多少位）是你应能论证的容量权衡。

**要点：**
- Snowflake：时间戳 + worker ID + 序列，共 64 位——可排序且无需协调。
- 对比自增（单点/瓶颈）与 UUIDv4（可分布但不可排序、做主键差）。
- 时钟回退是关键失败模式——检测偏移并停发，而非生成重复。
- 位分配是刻意的容量决策（时间戳可用年数 vs 节点数 vs 每毫秒 ID 数）。

### 10. 设计视频流媒体平台（YouTube / Netflix）

**难度：** 困难
**主题：** system-design, cdn, storage, encoding, read-heavy

**答案：** 把问题拆成上传/入库、存储/处理、播放——规模都在播放侧。上传：客户端把原始文件（可断点续传、分块）上传到对象存储；转码流水线再把它重新编码成多种分辨率和码率（240p→4K），并把每个切成小分片（HLS/DASH），产出一份清单（manifest）。这套自适应码率让播放器能按测得带宽逐分片切换清晰度，是流畅播放的核心。转码是易并行的——由队列驱动、跨 worker 集群按分片扇出。存储：原始文件加每个转码版本体量巨大，所以分层（热版本放快速存储/CDN，冷原始放廉价对象存储）。播放：这是巨大的读多、带宽受限问题，所以 CDN 不可或缺——分片在靠近用户的边缘 PoP 缓存，只有未命中才回源。热门内容预热到边缘。元数据（标题、播放量、推荐）是单独的、相对很小的服务。播放量与推荐作为异步分析跑在播放路径之外，而非同步。

**要点：**
- 自适应码率：转码成多版本、分片 + 清单（HLS/DASH），让播放器逐分片切换。
- 转码是按分片并行扇出、经 worker 队列。
- 播放以 CDN 为先——边缘缓存分片、预热热门内容、未命中才回源。
- 把很小的元数据/分析服务与巨大的带宽受限视频路径分开。
