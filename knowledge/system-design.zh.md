# 系统设计（场景实战）

经典的"设计某系统"面试场景，端到端走一遍：需求澄清、容量估算、API、数据模型，以及面试官真正打分的那两三个关键决策。这是一份起步集——一个小而精、可持续扩充的样本。它与 [architecture.md](architecture.md) 互补：后者单独讲底层模式（CQRS、事件驱动、一致性模型）。

每道题都带 `**Difficulty:**` 与 `**Topics:**` 元数据，便于选题器像对待公司题库那样做筛选和加权。

### 1. 设计短链接服务（TinyURL / bit.ly）

**频率：** 高

**难度：** 中等
**主题：** system-design, hashing, caching, sharding, read-heavy

**答案：** 按面试官期待的顺序一步步走：先定范围、再估规模、然后画设计，最后重点讲清真正打分的那一两个决策。

**第 1 步——先问清楚要做什么。** 核心就两个操作：给一条长 URL、返回一个短码；拿短码来时、重定向到原始 URL。把不确定的点大声澄清出来：读写比是不是很悬殊（是——一条链接创建一次却被点很多次，约 100:1）？短码会过期吗（假设不过期，或可选 TTL）？要不要点击分析、自定义别名（就说"v1 不做"，免得过度设计）？这一步就把"读占主导"摆上台面，而后面每个决策都由这个结论驱动。

**第 2 步——做个餐巾纸估算。** 假设每天新增 1 亿条 URL。那就是 1 亿 ÷ 86,400 秒 ≈ 1,200 写/秒，按 100:1 约 12 万读/秒。关键不是精确数字，而是它的*形状*：写不多、读很重。所以工程预算要花在把重定向路径做快上，写这一侧当成简单的一边处理。

**第 3 步——摆出各个部件。** 写入就存一行；读取就查一次然后返回 HTTP 重定向。存储就是一个键值映射：`code -> {long_url, created_at, owner}`。每天 1 亿条，单机远远放不下，所以要分片——按短码的哈希切分，查询直接落到对应分片。

**第 4 步——真正的问题：短码怎么生成？** 这是面试官在打分的点，所以放慢节奏，把各方案连同*权衡*讲清楚：
- *对 URL 做哈希*（如 MD5/SHA，取前 7 位 base62）。简单，但两条不同 URL 可能撞到同一个码——冲突——所以每次写都得"检查这个码占了没"，占了就换一段重试。写路径有额外开销。
- *分布式计数器*（0、1、2……再 base62 编码）。永不冲突，而且快。缺点是码是顺序出的，别人把你最新的码 +1 就能猜到别的码、还能估出你建了多少链接——这是业务数据泄露。
- *混合方案*——把计数器喂进 base62，但给每个分片一个偏移（或把位交错打散）。既保证写入无冲突，*又*把序列打乱到不再能轻易猜测，还避免每次写都去争抢同一个全局计数器。

为什么是 7 位？62^7 ≈ 3.5 万亿个码——按每天 1 亿也够用很多年。这就是从容量去*论证*长度，而不是拍脑袋。

**第 5 步——把重定向做快。** 因为热门链接只占全部链接的一小撮，在数据库前放一层缓存（Redis 或 CDN）命中率会非常高。重定向状态码也要刻意选：**301** 会被浏览器缓存（打到你这儿的请求更少，但你丢了逐次点击的分析），而 **302** 每次都会回到你这儿、于是你*能*统计点击。按"要不要分析"来选。

**第 6 步——守住写入路径。** 让创建幂等（同一用户提交同一条长 URL 返回同一个码，而不是堆一堆重复），并用限流 + 恶意/URL 黑名单防滥用，免得你的服务被拿去给坏链接打掩护。

**要点：**
- 读多写少：给重定向加缓存/CDN，写路径按远小的流量来设计。
- 短码生成才是真问题——计数器（无冲突、可猜）vs 哈希（有冲突、不可读）；混合方案两头的好处都占。
- 7 位 base62 = 62^7 ≈ 3.5 万亿个码——从容量推导长度，别拍脑袋。
- 301（可缓存、丢分析）vs 302（按次计数）是一个刻意选择。

### 2. 设计社交信息流（Twitter / Facebook 时间线）

**频率：** 高

**难度：** 困难
**主题：** system-design, fan-out, caching, sharding, consistency

**答案：** 整个问题就落在一个决策上——组装 feed 这件苦活，你放在写入时做，还是读取时做？分几步递进讲。

**第 1 步——澄清产品。** feed 就是把你关注的所有人的帖子归并、排序后的一条流。问清楚：普通用户有多少粉丝、极端情况又有多少（大多数人几百，大 V 上千万）？feed 必须实时吗，还是几秒延迟也行（几乎总是行）？按时间还是按排序？这些答案决定一切，尤其是大 V 那道坎。

**第 2 步——看清规模形状。** 读远远压倒写——人们刷的次数远多于发帖。所以和大多数消费级系统一样，我们要让读便宜，哪怕代价是写要多干活。

**第 3 步——核心选择：写扩散 vs 读扩散。**
- *写扩散（push）。* 有人一发帖，就把这条帖子的 ID 复制进每个粉丝预算好的 feed 列表（放 Redis）。读 feed 因而是 O(1)——直接返回你现成的列表。对读极好。麻烦在于：一个有 1 亿粉丝的大 V 发一条帖就触发 1 亿次写（"热点用户"/惊群问题），而且你还为那些从不登录的粉丝白白预算 feed、浪费存储。
- *读扩散（pull）。* 按作者存帖子，写入时什么都不做。有人打开 feed 时，再去把他关注的所有人的最新帖取来、按时间归并。写便宜，但读变得昂贵、高延迟，还猛击数据库。

**第 4 步——把两者结合（生产答案）。** 普通用户用 push，大 V 用 pull。一个粉丝的 feed = 他预算好的 push feed，在读时再和他关注的那少数几个大 V 的近期帖归并。这样没有哪条帖子会扩散到 1 亿个列表，普通读取又保持 O(1)。

**第 5 步——数据模型。** 帖子按帖子 ID（或作者）分片、一张关注/被关注图、每用户一份 feed 缓存。把检索（哪些帖子是候选）与排序（按时间还是按 ML 打分）分开——两者扩展方式不同，你也会想独立演进排序。

**第 6 步——善用最终一致。** 新帖晚几秒出现完全可以接受，所以扩散可以交给异步 worker 跑。正是这种对延迟的容忍，才让整套东西扩得起来。

**要点：**
- 说出两种策略以及逼出混合方案的大 V 问题。
- Push = 读快/大 V 写贵；pull = 写便宜/读贵。
- 读占主导所以预计算；feed 容忍最终一致所以异步扩散。
- 把检索（取候选帖）与排序（排序它们）分开——二者扩展方式不同。

### 3. 设计限流器

**频率：** 高

**难度：** 中等
**主题：** system-design, rate-limiting, concurrency, caching, distributed-systems

**答案：** 限流器看着简单，直到你追问"到底怎么计数？"以及"跨很多台服务器怎么算对？"——一步步逼近这两点。

**第 1 步——澄清规则。** 按什么限——用户、IP、还是 API key？跑在哪——客户端、API 网关、还是各服务内部（网关通常是最佳落点）？限额多少（比如 100 次/分钟），超限怎么办——用 `429 Too Many Requests` + `Retry-After` 头拒绝，还是排队？先定这些，再碰算法。

**第 2 步——选计数算法（重头戏）。** 按"精度 vs 开销"来比：
- *固定窗口*——每个时间桶一个计数器（比如每分钟）。极简，但跨边界会放 2 倍突发（这一分钟结尾 + 下一分钟开头）。
- *滑动窗口日志*——每次请求存一个时间戳，数最近 60 秒内的。精确，但内存随流量增长。
- *滑动窗口计数器*——把当前窗口与上一窗口按权重混合。常见折中：近乎精确、又便宜。
- *令牌桶*——令牌按稳定速率补充，每请求花一个；桶空了就被限。天然允许受控突发，是通常的默认答案。
- *漏桶*——以固定速率漏出，把突发输入平滑成稳定输出。

**第 3 步——跨服务器算对。** 有很多网关节点时计数器必须共享，所以放 Redis。陷阱在于："读计数、判断、写计数+1"是竞态——两个节点都读到 99、都放行，于是你放了 101 个。要让"检查并递减"原子化——用 Lua 脚本，或 `INCR` 配 `EXPIRE`——让"计数 + 决定"作为一步完成。

**第 4 步——处理热点键。** 一个超热门用户（或一个全局限额）会把它的计数器变成人人来砸的热点键。把计数器分片，或让每个节点各留一份本地近似计数、周期性对账，用一点精度换大量吞吐。

**第 5 步——定失败模式。** 如果限流器（或 Redis）挂了，你是失败开放（放行）还是失败关闭（拦截）？为可用性通常失败开放——但在安全敏感端点（登录、支付）上要失败关闭。

**要点：**
- 令牌桶是合理默认（稳定补充 + 受控突发）；要懂固定窗口为何在边界突发。
- 分布式正确性需要原子"检查并递减"（Redis Lua / INCR+EXPIRE），不是读后写。
- 返回 429 带 `Retry-After`；明确失败开放 vs 失败关闭。
- 热门用户的热点键需要分片或本地近似计数。

### 4. 设计即时通讯/聊天系统（WhatsApp、Messenger）

**频率：** 高

**难度：** 困难
**主题：** system-design, websockets, message-queue, consistency, fan-out

**答案：** 聊天本质上是个"路由 + 送达"问题：把一条消息从一个已连接的客户端送到另一个（可能离线的）客户端，保持有序，并且在用户看来恰好一次。分层往上搭。

**第 1 步——需求。** 1:1 和群聊、接收方在线或离线都要能送达、送达 + 已读回执、会话内正确有序、以及媒体附件。这些几乎一一对应到下面的设计决策。

**第 2 步——连接层。** 和请求/响应式 API 不同，聊天需要服务端主动推。所以客户端与一个有状态网关保持长连接（WebSocket，退化时用长轮询）。维护一张会话注册表——谁连在哪个网关上——这样 A 给 B 发消息时，你能查出 B 的网关并路由过去。

**第 3 步——离线送达。** 如果 B 没连着，别把消息丢了：持久化到每用户的消息存储/队列，等重连时再送，并发一条推送通知。"存储转发"正是让聊天感觉可靠的关键。

**第 4 步——有序。** 别信跨服务器的墙上时钟——时钟会漂。分配每会话的序列号（或逻辑时钟），让每个客户端都能排序、并检测缺口（"我有 1、2、4——3 呢？"）去补取。

**第 5 步——送达语义与回执。** 保证至少一次送达，并在客户端按消息 ID 去重——这个组合在用户看来就是恰好一次。在每个阶段记录确认（ack），用来驱动"已发 → 已达 → 已读"的勾选状态。

**第 6 步——群聊就是扇出。** 小群：把消息写进每个成员的队列（简单）。大群（上千人）：用一份共享的每群日志供成员来读，比向上千个队列扇出扩展性好得多。

**第 7 步——数据模型与扩展。** 按会话 ID 分片消息，让一个会话的历史共置、翻页便宜。媒体进对象存储/CDN，消息只带一个 URL、绝不带字节本身。路由逻辑无状态、可水平扩展；真正有状态的是连接网关和会话注册表。

**要点：**
- 长连接 + 会话注册表路由到正确网关；离线 → 存储转发 + 推送。
- 每会话序列号做有序与缺口检测，别用服务器时钟。
- 至少一次 + 按消息 ID 去重；ack 驱动已达/已读回执。
- 按会话 ID 分片；媒体按引用进 CDN、不内联。

### 5. 设计网络爬虫

**频率：** 中

**难度：** 中等
**主题：** system-design, distributed-systems, message-queue, bloom-filter, politeness

**答案：** 爬虫就是一个大循环——抓取、抽链接、入队、重复——但规模和礼貌把每一步都变成了各自的难题。先走一遍循环，再讲难点。

**第 1 步——需求。** 抓取数十亿页面、抽出链接、周期性刷新、遵守礼貌（robots.txt、每主机限速）、避开陷阱。"数十亿"和"礼貌"这两个词决定了整套设计的形状。

**第 2 步——核心循环。** 一个 URL 前沿（一组队列）喂给抓取 worker → 它们下载并解析页面 → 抽出新链接 → 去重 → 把新 URL 入队回前沿。其余一切都挂在这个循环上。

**第 3 步——前沿是最有意思的部分。** 它同时编码两件事：礼貌——别猛砸某一个主机，所以按主机分区队列、让一个 worker 以受控速率服务每个主机；以及优先级——先抓重要或新鲜的页面，再抓冷门的。把前沿做对，就完成了设计的大半。

**第 4 步——海量去重。** 你没法把数十亿 URL 的哈希集放内存。用布隆过滤器做"这个 URL 见过没？"的判断——又小又快，它唯一的错误（误判）也不过是跳过一个页面、可以接受——后端配一个持久存储作为真相来源。对*同一页面在不同 URL 下出现*的情况，比对内容哈希 / simhash 来抓近重复。

**第 5 步——礼貌与陷阱。** 抓取并缓存每个主机的 robots.txt 并遵守，加抓取延迟，用深度和 URL 模式限制去检测蜘蛛陷阱——无限日历、会话 ID URL 这类会源源不断生成链接的东西——免得爬虫掉进无底洞。

**第 6 步——新鲜度与健壮性。** 重抓频率应随页面实际变化的快慢自适应（新闻首页勤抓，归档旧文少抓）。让每个阶段都分布式且幂等：一个抓过但没处理完的 URL 必须能安全重试，这样 worker 崩了也不会破坏整次抓取。

**要点：**
- URL 前沿同时编码礼貌（按主机分区 + 延迟）与优先级。
- 布隆过滤器做海量"已见 URL"去重；内容哈希 / simhash 处理重复页面。
- 遵守 robots.txt，用深度限制检测陷阱（无限/带参 URL）。
- 各阶段幂等、可重试，让 worker 崩溃不破坏抓取。

### 6. 设计通知服务（推送 / 邮件 / 短信扇出）

**频率：** 中

**难度：** 中等
**主题：** system-design, message-queue, fan-out, idempotency, reliability

**答案：** 通知服务是一条流水线：一个事件进来，必须送到对的人、对的渠道、每人一次——而且在广播下不能烧穿。跟着事件走一遍。

**第 1 步——需求。** 跨渠道发送（推送、邮件、短信、站内），扛住高扇出（一条"突发新闻"广播给数百万人），遵守用户偏好与免打扰时段，保证不重复发送。"扇出"和"不重复"是硬约束。

**第 2 步——流水线的形状。** 生产者发布一个通知事件 → 队列/broker → worker 池。队列是关键的架构动作：它吸收突发（一次广播不会压垮下游任何一处），并隔离慢或故障的提供商、不让它把其余部分堵住。

**第 3 步——一个 worker 干什么。** 对每个事件，worker 解析收件人、套用偏好与去重过滤（剔掉退订的、处于免打扰时段的、或已经通知过的），按渠道套模板，再交给渠道专用提供商——推送用 APNs/FCM、邮件用邮件服务、短信用短信网关。

**第 4 步——可靠性与不重复。** 提供商会失败并被重试，而重复正是从重试来的。给每个（用户，通知）挂一个幂等键，让重试被识别、不重复发。把耗尽重试的消息送进死信队列去排查，而不是丢掉或让它打转。

**第 5 步——两个方向的限流。** 按提供商限流，因为它们会限你（超了就丢你的流量）；也按用户限流，免得一个有 bug 的触发器给某人刷 100 条推送。

**第 6 步——处理超大扇出。** "通知全部 1000 万用户"这种事件，应把收件人列表异步分批展开——入队一块块交给 worker 领取——而不是一个把 worker 占用一小时的巨型同步循环。按渠道跟踪送达状态，用于可观测性和回执。

**要点：**
- 按渠道的队列解耦 worker 吸收突发并隔离提供商故障。
- 每（用户，通知）幂等键 + 死信队列就是"不重复、不丢发"的方案。
- 分发前应用用户偏好、免打扰时段、每用户/每提供商限流。
- 大扇出异步分批展开，而非一个同步循环。

### 7. 设计前缀补全 / 自动补全服务

**频率：** 中

**难度：** 中等
**主题：** system-design, trie, caching, read-heavy, ranking

**答案：** 整套设计被一个数字主导：每次击键 100 毫秒以内。这个延迟预算逼着你把答案预算好，而不是每次请求现算。围绕它来搭。

**第 1 步——需求。** 对给定前缀，在 100 毫秒内返回 top-k 补全，按热度排序，并随趋势变化保持最新。它极其读多（每次击键都是一次查询）又带硬性延迟 SLO——这个组合就是在喊"预算"。

**第 2 步——数据结构。** 用前缀树（trie），但加个花样：在每个节点上，存下经过它的 top-k 最热补全。这样一次查询就是"沿树走到前缀节点、返回它缓存好的 top-k"——请求时不做排序，这正是你达标延迟的办法。

**第 3 步——构建 trie（离线）。** 别每次击键就改 trie。而是周期性地跑一个对查询日志的批处理作业：统计每个查询被输入的频率，再把每个节点的 top-k 沿树上推。你按计划（比如每小时）重建/刷新，这样既保持最新、又不碰服务路径。

**第 4 步——规模化服务。** 把 trie 分片（比如按首字母）分布到多台服务器，并大量缓存——查询分布的头部（"fac…" → "facebook"）很小、可直接在边缘缓存。在客户端，对击键做防抖（别每个字符都发），并缓存近期结果，大幅削减请求量。

**第 5 步——驯服排序数据。** 你没法为长尾里每个查询都保精确计数。用采样或像 count-min sketch 这样的近似计数器——它会把稀有项略微多算，但又小又快，对热度排序来说是划算的取舍。

**第 6 步——后续层。** 个性化（偏向这个用户的历史）和容错（编辑距离 / 模糊匹配）是叠在热度基线之上的 v2 功能——作为扩展点提一句就行，别让它们把核心搞复杂。

**要点：**
- 在每个 trie 节点预计算 top-k，使服务是"走 + 返回"而非排序查询。
- 按计划从查询日志频率离线重建 trie；别每次击键就改。
- 读多 → 分片 trie 并大量缓存；客户端防抖。
- Count-min sketch / 采样处理长尾频率；模糊匹配与个性化是后续层。

### 8. 设计视频流媒体平台（YouTube / Netflix）

**频率：** 中

**难度：** 困难
**主题：** system-design, cdn, storage, encoding, read-heavy

**答案：** 把系统拆成三段——上传/入库、存储/处理、播放——并且一上来就意识到：规模（和钱）都在播放这一侧。按顺序来。

**第 1 步——上传/入库。** 客户端把原始文件上传到对象存储。要可断点续传、分块——视频文件很大，一次断线不该让 4GB 的上传从零重来。

**第 2 步——处理（转码）。** 一条流水线把每个原始上传重新编码成多种分辨率和码率（240p → 4K），并把每个切成小分片（每片几秒，HLS/DASH），产出一份列出这些分片的清单（manifest）。这是为自适应码率做的铺垫——也就是流畅播放的核心（下一步）。转码是易并行的，所以按分片扇出到由队列驱动的 worker 集群。

**第 3 步——自适应码率播放。** 因为已经按多种清晰度预先切好片，播放器可以测量观众当前的带宽、并逐分片切换清晰度——网络一抖就降到 480p，恢复了再爬回 1080p——而不是卡顿缓冲。这正是第 2 步做那么多转码的*唯一*理由。

**第 4 步——存储分层。** 原始文件加上每一种转码版本是海量数据。分层：把热版本放在快速存储 / CDN，把冷的原始文件推到廉价对象存储。别为没人看的片子付高价存储。

**第 5 步——播放是个 CDN 问题。** 这是极其读多、受带宽限制的场景，所以 CDN 不可或缺：在靠近用户的边缘 PoP 缓存分片，只有未命中才回源。把热门内容（一部大新片）在流量高峰前预热到边缘。

**第 6 步——让元数据远离视频路径。** 标题、播放量、推荐是一个单独的、相对很小的服务。关键是：把播放量更新和推荐作为异步分析跑在播放路径之外——绝不能让"看视频"去等一次同步的计数写入。

**要点：**
- 自适应码率：转码成多版本、分片 + 清单（HLS/DASH），让播放器逐分片切换。
- 转码是按分片并行扇出、经 worker 队列。
- 播放以 CDN 为先——边缘缓存分片、预热热门内容、未命中才回源。
- 把很小的元数据/分析服务与巨大的带宽受限视频路径分开。

### 9. 设计分布式键值存储（Dynamo 风格）

**频率：** 低

**难度：** 困难
**主题：** system-design, distributed-systems, consistency, replication, sharding

**答案：** 这就是把 Dynamo 论文当面试题。主线是：没有中心协调者、保持可用、并把一致性交给调用方来调。按能力一层层往上搭。

**第 1 步——需求。** 按 key 做 get/put（没有查询、没有 join），通过加普通机器水平扩展，故障下仍高可用，并提供可调一致性。最后这点是主题——我们会*刻意*用严格一致性去换可用性。

**第 2 步——分区：一个 key 落在哪？** 朴素的 `hash(key) % N` 一旦 N 变几乎要全体重排。改用一致性哈希：把节点放到环上，一个 key 归它顺时针的下一个节点。增删节点现在只移动约 1/N 的 key。再给每个物理节点在环上放很多虚拟节点，让负载与热点摊平。

**第 3 步——复制。** 把每个 key 写到环上顺时针接下来的 N 个节点（它的"偏好列表"），跳过重复，让副本落到不同的物理主机/机架上。这样丢一个节点也不丢数据。

**第 4 步——用法定人数做可调一致性。** N 个副本时，让调用方选 R（一次读需多少节点确认）和 W（一次写需多少节点确认）。若 R + W > N，任何一次读都至少与一个见过最新写的节点重叠——读己所写一致性。R/W 更小则操作更快、更可用，但读到的可能更旧。这就是把 CAP 旋钮交到你手里；Dynamo 默认选 AP 加最终一致。

**第 5 步——解决写冲突。** 法定人数放松后，两个客户端可能并发写同一个 key。选择：向量时钟能判断一个写是不是因果地跟在另一个之后（并把真正的冲突作为"兄弟版本"抛给应用去合并），或按时间戳最后写入者胜——更简单，但会悄悄丢掉一个写。把这个权衡讲出来。

**第 6 步——扛住故障。** 提示移交：目标节点宕了，就让一个健康节点临时接下这个写、等对端回来再回放，于是写永不阻塞。用 Merkle 树做反熵：副本自顶向下比对树的哈希，精确找出到底哪些 key 分歧了、只重新同步那些，很省。成员管理与故障探测走 gossip 协议，于是没有一个会成为单点的中心协调者。

**要点：**
- 一致性哈希 + 虚拟节点做分区、最小化重排。
- R + W > N 是较强读的法定人数规则；更小的值买可用性（CAP 权衡）。
- 冲突解决：向量时钟（因果、保留兄弟）vs 最后写入者胜（有损、简单）。
- 提示移交 + Merkle 树反熵 + gossip = 无协调者的高可用。

### 10. 设计分布式唯一 ID 生成器

**频率：** 低

**难度：** 中等
**主题：** system-design, distributed-systems, sharding, clock

**答案：** 目标是：在很多机器间唯一、热路径上无需协调、最好还能按时间排序的 ID。把各选项推演一遍，Snowflake 自然就浮出来当答案。

**第 1 步——需求。** 64 位 ID（紧凑、适合当数据库主键）、跨众多机器唯一、最好大致按时间可排序、高吞吐、且无单点争用。"每个 ID 都不协调"这条约束会淘汰掉那些显而易见的做法。

**第 2 步——逐个过选项，看各自差在哪。**
- *中心自增数据库。* 简单又有序，但每次生成 ID 都要打一个数据库——瓶颈加单点故障。
- *UUIDv4（随机）。* 易分布、实践中无冲突，但它 128 位、且不按时间排序，做主键很伤：随机插入会散落在 B 树各处、把它搞碎。
- *数据库票据服务器。* 给每个节点发一段 ID 区间用完再来要——减少了协调，但仍有一个中心分配器。

**第 3 步——Snowflake（标准答案）。** 用三个字段拼一个 64 位 ID：时间戳（自定义 epoch 起的毫秒）+ 机器/worker ID + 每毫秒序列计数器。时间戳让 ID 可按时间排序，worker ID 让它跨机器唯一，序列计数器允许同一毫秒内出很多个 ID——而生成一个 ID 时全程无需协调。

**第 4 步——唯一需要协调的一处。** 每个节点仍需一个唯一的 worker ID。用静态配置分配，或启动时用 ZooKeeper 之类的协调服务分配——这是每个节点做一次，不是每个 ID 做一次。

**第 5 步——经典失败模式：时钟。** Snowflake 信任时钟，所以 NTP 往回拨很危险——时钟一旦回退，你可能重新发出已经用过的时间戳、生成重复。要检测它，然后要么等时钟追上、要么在追上之前拒绝发 ID。这一点务必主动讲出来。

**第 6 步——位分配是个真决策。** 时间戳、worker、序列各占多少位，是个容量权衡：时间戳位越多 = 溢出前的年数越多，worker 位越多 = 支持的机器越多，序列位越多 = 每毫秒能出的 ID 越多。要能从数字上论证这个划分。

**要点：**
- Snowflake：时间戳 + worker ID + 序列，共 64 位——可排序且无需协调。
- 对比自增（单点/瓶颈）与 UUIDv4（可分布但不可排序、做主键差）。
- 时钟回退是关键失败模式——检测偏移并停发，而非生成重复。
- 位分配是刻意的容量决策（时间戳可用年数 vs 节点数 vs 每毫秒 ID 数）。
