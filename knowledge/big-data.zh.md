# 大数据面试题

高频大数据题，覆盖存储（HDFS）、批处理计算（MapReduce/Spark）、流处理（Kafka/Flink）、数仓/湖仓、文件格式，以及面试官真正会追问的性能问题（数据倾斜、shuffle）。这是一个起步集——小而精，用于逐步扩充。

### 1. 4V 与批处理 vs 流处理

**频率：** 高

**题目：** 什么样的问题算「大数据」问题？如何在批处理与流处理之间做选择？

**方案：**

1. **4V 定义**：「大数据」通常用 **4V** 来界定：*Volume*（体量大到单机放不下）、*Velocity*（数据到达快/持续）、*Variety*（结构化、半结构化、非结构化并存）、*Veracity*（质量/不确定性）。
2. **真正触发点**：实际的触发点更简单：当数据在单机上再也放不下或跑不完时，你就需要横向扩展，以及一个替你处理分区、并行和故障恢复的框架。
3. **批处理特征**：**批处理**按计划处理一份有界、完整的数据集——吞吐高、延迟高（分钟到小时），正确性更简单（能看到全量数据）。
4. **流处理特征**：**流处理**在事件到达时处理无界数据流——延迟低（毫秒到秒），但你必须面对不完整/乱序数据（事件时间、水位线、窗口）。
5. **选型指引**：报表、ETL、训练数据用批处理；欺诈检测、监控、实时特征用流处理。
6. **两者兼用**：很多系统两者兼用，这正是 Lambda/Kappa 架构要解决的。

**演进：**

1. **Lambda 架构**：批层保证最终正确性，速度层补低延迟近似结果，服务层合并两者——代价是两套代码双份维护。
2. **Kappa 架构**：只保留流处理一条链路，用可重放的日志（如 Kafka）回放历史数据来替代批层，简化维护。
3. **流批一体**：Flink、Spark Structured Streaming 等把批视为流的特例，用同一套 API 覆盖两种场景，是当前主流收敛方向。

**面试追问：**

1. **延迟 vs 正确性权衡**：流处理追求低延迟，但面对迟到数据如何在「尽早出结果」与「结果准确」之间取舍（水位线 + 允许迟到）。
2. **什么时候不该上大数据**：若单机/单库能放得下跑得完，引入分布式框架只会徒增复杂度与运维成本。
3. **Veracity 如何落地**：数据质量/不确定性在流水线里靠什么保障（校验、去重、schema 管控、监控）。

**要点：**

1. **4V 与触发点**：4V：Volume、Velocity、Variety、Veracity——真正的触发点是「单机放不下/跑不完」。
2. **批 vs 流**：批 = 有界数据、高吞吐、高延迟；流 = 无界、低延迟、正确性更难。
3. **迟到乱序**：流处理强制你显式处理迟到/乱序数据。

### 2. HDFS 架构

**频率：** 高

**题目：** 请解释 HDFS 架构。NameNode 和 DataNode 各自扮演什么角色？副本机制如何工作？

**方案：**

1. **设计目标**：HDFS 是为大文件、高吞吐、跑在廉价机器上而设计的分布式文件系统。
2. **分块存储**：文件被切成大**块**（默认 128 MB），分散在众多 **DataNode** 上。
3. **NameNode 职责**：单一 **NameNode** 在内存中保存全部元数据——目录树和块→DataNode 的映射——但从不接触真实数据。客户端向 NameNode 询问文件的块在哪，然后直接与 DataNode 收发数据。
4. **副本与放置策略**：每个块都会**复制**（默认副本因子 3）以保证持久性和本地性；默认放置策略把一个副本放在本机架、两个放在远端机架，从而在扛住机架故障的同时避免每次写都跨机架付出代价。
5. **心跳与重新复制**：DataNode 定期发送**心跳**和块报告；某个节点宕机后，NameNode 会把它的块在别处重新复制。
6. **HA 与单点故障**：NameNode 历来是单点故障，在 HA 部署中用活/备双节点配合 ZooKeeper 和共享编辑日志（JournalNode）解决。
7. **适用边界**：HDFS 为*大文件顺序读写和追加*优化，而非小文件或随机写——数百万小文件会耗尽 NameNode 内存（「小文件问题」）。

**演进：**

1. **NameNode Federation**：用多个 NameNode 各管一部分命名空间，突破单 NameNode 的内存/吞吐瓶颈，缓解元数据扩展问题。
2. **Erasure Coding（纠删码）**：用纠删码替代 3 副本，把存储开销从 200% 降到约 50%，牺牲部分重建成本换容量，适合冷数据。
3. **对象存储替代**：云上以 S3/对象存储 + 外部元数据取代 HDFS，计算存储分离，弹性更好。

**面试追问：**

1. **小文件问题怎么治**：合并（CombineFileInputFormat、HAR 归档）、压实成大文件、或改用更适合的存储格式。
2. **写入一致性**：HDFS 写流程（pipeline 复制、ack）如何保证副本一致，写入中途节点挂了怎么办。
3. **NameNode 内存估算**：每个文件/块约占多少元数据内存，如何据此规划集群规模。

**要点：**

1. **角色划分**：NameNode = 元数据（在内存）；DataNode = 真实块存储。
2. **块与副本**：块默认 128 MB，副本因子 3，机架感知放置。
3. **故障恢复**：心跳检测宕机节点 → 自动重新复制。
4. **擅长与不擅长**：不擅长小文件（NameNode 内存）和随机写；擅长大文件顺序 I/O。

### 3. MapReduce 模型

**频率：** 高

**题目：** 请讲解 MapReduce 的执行模型。map、shuffle、reduce 三个阶段各发生什么？

**方案：**

1. **编程模型**：MapReduce 把计算表达为对键值对的两个用户函数。
2. **Map 阶段**：**Map** 在输入分片（通常一个分片对应一个 HDFS 块，以获得数据本地性）上并行运行，产出中间 `(k, v)` 对。
3. **Shuffle 阶段**：框架的 **shuffle** 阶段随后跨集群按 key 分组：map 输出被分区（按 `hash(key) % reduce 数`）、排序，并通过网络传给对应的 reducer。
4. **Reduce 阶段**：**Reduce** 收到每个 key 及其排好序的值列表，产出最终输出。
5. **瓶颈与 combiner**：shuffle 是中间那段昂贵的、重网络重磁盘的阶段，通常是瓶颈。当 reduce 满足结合律/交换律时（如求和、计数），**combiner**（map 端的本地小 reduce）可减少 shuffle 数据量。
6. **容错与局限**：这个模型简单且容错——失败的任务直接重跑，因为输入不可变——但它在每个阶段之间都把中间结果落盘，这就是多步作业慢、以及 Spark 的内存模型基本取代它的原因。

**演进：**

1. **走向内存计算**：Spark 用内存中间数据与 DAG 执行取代逐阶段落盘，迭代/多阶段作业提速 10–100 倍。
2. **自定义 Partitioner / 二次排序**：通过自定义分区器和排序比较器，控制 key 分布与 value 排序，支撑更复杂的聚合与去倾斜。
3. **SQL on MapReduce**：Hive 把 SQL 编译为 MapReduce 作业链，降低使用门槛，之后又演进到 Tez/Spark 引擎以减少落盘。

**面试追问：**

1. **combiner 何时不能用**：非结合律/交换律的聚合（如求平均，若直接 combine 会出错）不能简单套用 combiner，需改写中间状态。
2. **reduce 数怎么定**：reduce 数影响并行度与小文件数，过多过少各有什么代价，如何结合数据量设置。
3. **数据倾斜在 MR 里的表现**：个别 reducer 拿到热点 key 拖垮整个作业，如何通过加盐/两阶段聚合缓解。

**要点：**

1. **三阶段**：Map（按分片并行）→ shuffle（按 key 分区+排序+网络传输）→ reduce（按 key 聚合）。
2. **瓶颈与优化**：shuffle 是瓶颈；combiner 可为满足结合律的聚合减少其数据量。
3. **容错机制**：靠在不可变输入上重跑任务实现容错。
4. **性能短板**：阶段间落盘使迭代类作业变慢。

### 4. Spark vs MapReduce

**频率：** 高

**题目：** 为什么 Spark 比 MapReduce 快？什么是 RDD 和 DAG 调度器？

**方案：**

1. **内存 vs 落盘**：Spark 把中间数据保留在**内存**里、需要时才溢写磁盘，而 MapReduce 把每个阶段的输出都写到 HDFS。
2. **加速幅度**：对于迭代型负载（机器学习、图算法）和多阶段流水线，这往往快 10–100 倍，因为省掉了反复的磁盘往返。
3. **RDD 抽象**：**RDD**（弹性分布式数据集）是 Spark 的核心抽象：一个不可变、分区的集合，并记录了构建它的转换的**血缘**。
4. **血缘容错**：Spark 不靠复制数据来容错，而是根据血缘重算丢失的分区。
5. **DAG 调度器**：Spark 构建转换的 **DAG**，遇到 action 时，**DAG 调度器**在 shuffle 边界把它切成若干**阶段（stage）**；同一阶段内的窄转换会流水线成一趟扫描。
6. **上层 API 优化**：更上层的 API（DataFrame/Dataset + Catalyst 优化器 + Tungsten 执行）在 RDD 之上增加了查询优化和代码生成。

**演进：**

1. **DataFrame / Dataset 化**：从裸 RDD 转向结构化 API，交给 Catalyst 优化器做谓词下推、列裁剪与物理计划选择。
2. **AQE 自适应查询执行**：运行时根据真实统计动态调整分区数、切分倾斜分区、转换 join 策略。
3. **Structured Streaming**：把同一套 DataFrame API 延伸到流处理，实现流批一体编程模型。

**面试追问：**

1. **Spark 一定比 MR 快吗**：内存不足频繁溢写、或单遍扫描的简单作业，Spark 优势可能被抵消，甚至因 JVM/调度开销更慢。
2. **血缘太长怎么办**：超长血缘导致恢复成本高，用 `checkpoint` 截断血缘落盘，或用 `cache/persist` 复用中间结果。
3. **窄宽依赖对性能的影响**：宽依赖触发 shuffle 决定 stage 边界，是调优重点（见下一题）。

**要点：**

1. **核心加速原因**：内存中间数据 vs MapReduce 每阶段落盘 → 迭代/多阶段作业大幅加速。
2. **RDD 本质**：RDD = 不可变、分区、靠血缘容错（重算而非复制）。
3. **调度机制**：DAG 调度器在 shuffle 边界切分阶段；窄操作流水线化。
4. **上层优化**：DataFrame API + Catalyst/Tungsten 在裸 RDD 之上做优化。

### 5. Spark 的转换 vs 动作、窄依赖 vs 宽依赖

**频率：** 高

**题目：** Spark 中转换（transformation）与动作（action）有何区别？窄依赖与宽依赖有何区别？

**方案：**

1. **转换是惰性的**：**转换**（`map`、`filter`、`join`、`groupBy`）是**惰性**的——它们只构建血缘/DAG，直到某个**动作**（`count`、`collect`、`save`）才真正触发执行。
2. **惰性带来的优化**：惰性让 Spark 能在运行前对整个计划做优化（流水线、谓词下推）。
3. **依赖定义**：依赖描述子分区与父分区的关系。
4. **窄依赖**：**窄依赖**指每个父分区最多喂给一个子分区（`map`、`filter`、`union`）——它们在同一阶段内流水线执行、无数据移动。
5. **宽依赖**：**宽依赖**（`groupByKey`、`join`、`reduceByKey`）需要来自多个父分区的数据跨网络重分区——这就是一次 **shuffle**，也定义了阶段边界。
6. **减少宽依赖**：尽量减少宽依赖（例如优先用 `reduceByKey` 而非 `groupByKey`，因为前者在 map 端先合并；或在 join 时广播小表）是 Spark 性能调优的核心。

**演进：**

1. **reduceByKey 取代 groupByKey**：对可聚合场景优先 map 端预聚合，大幅削减 shuffle 数据量。
2. **广播 join 消除 shuffle**：小表广播到每个 executor，把宽依赖 join 退化为窄依赖的本地 join。
3. **AQE 动态合并/切分分区**：运行时根据 shuffle 后真实数据量合并小分区、切分倾斜分区，减少无谓的宽依赖代价。

**面试追问：**

1. **为什么 reduceByKey 更优**：它在 map 端先做局部合并再 shuffle，而 groupByKey 把所有原始值都传过网络，内存与网络压力大。
2. **stage 个数怎么数**：一个 action 的 DAG 中每遇到一个宽依赖就切一个 stage，能据此估算 shuffle 次数。
3. **缓存的时机**：被多个 action 复用的 RDD/DataFrame 该不该 `cache`，以及缓存级别（内存/磁盘/序列化）如何选。

**要点：**

1. **转换与动作**：转换惰性；动作触发执行 → 支持整计划优化。
2. **窄依赖**：窄依赖 = 1 父 → 1 子，无 shuffle，阶段内流水线。
3. **宽依赖**：宽依赖 = shuffle，定义阶段边界，代价高。
4. **调优方向**：优先 `reduceByKey`/广播 join 以减少 shuffle。

### 6. 数据倾斜

**频率：** 高

**题目：** 什么是数据倾斜？如何发现和解决？

**方案：**

1. **定义**：**倾斜**是指数据在分区/key 上分布不均，导致个别任务处理的数据远多于其他任务。
2. **症状**：作业的整体耗时由最慢的任务决定，所以典型症状是 99% 的任务已完成、却有一个「拖尾」任务跑了几小时——在 Spark UI 中表现为某个任务的输入/shuffle 读取量巨大、时长很长。
3. **成因**：常见成因：热点 key（如 `null`、默认值、大 V 用户），或倾斜的 join key。
4. **加盐**：**加盐（salting）**——给热点 key 追加随机后缀把它打散到 N 个分区，先聚合再合并（join 场景下把小表按盐值复制多份）。
5. **广播 join**：**广播 join**——若一侧很小，把它广播到每个 executor，彻底避免 shuffle。
6. **分离热点 key 与过滤**：**分离热点 key**——用单独路径处理它们。尽早过滤掉垃圾 key（null）。
7. **AQE 自动处理**：较新的 Spark **AQE**（自适应查询执行）能在运行时自动检测并切分倾斜分区。

**演进：**

1. **两阶段聚合**：先对加盐后的 key 做局部聚合，再去盐做全局聚合，是加盐思路在聚合场景的标准落地。
2. **AQE Skew Join 优化**：开启 AQE 后自动识别倾斜分区并拆成多个子任务并行处理，无需手工加盐。
3. **预处理打散**：在数据入仓/建模阶段就对已知热点（大 V、默认值）做分桶或单独建表，从源头避免倾斜。

**面试追问：**

1. **怎么定位倾斜 key**：对 key 采样统计分布、或看 Spark UI 各 task 的 shuffle read，找出体量异常的 key。
2. **加盐的盐粒度**：盐值 N 太小打散不够、太大增加 shuffle 分区与合并成本，如何权衡。
3. **广播 join 的边界**：小表到底多大才适合广播（driver/executor 内存限制），超出后如何回退。

**要点：**

1. **本质**：倾斜 = key 分布不均 → 拖尾任务主导整体耗时。
2. **发现方法**：通过 Spark UI 发现：某任务 shuffle 读取/时长异常大。
3. **解决手段**：解决：加盐、广播 join、隔离热点 key、丢弃 null/垃圾 key。
4. **自动化**：Spark AQE 可在运行时自动处理倾斜 join。

### 7. 列式文件格式

**频率：** 高

**题目：** 分析型系统为什么用 Parquet/ORC 这类列式格式，而不是 CSV/Avro 这类行式格式？

**方案：**

1. **查询特征**：分析型查询通常是在很多行上只扫描少数几列（`SELECT avg(price) ... WHERE date = ...`）。
2. **列裁剪**：**列式**存储把同一列的所有值连续排布，因此引擎只读查询需要的列（**列裁剪**）、跳过其余——对宽表能省下巨量 I/O。
3. **压缩优势**：把同类型的值放在一起也让压缩效果好得多（游程、字典、增量编码）。
4. **谓词下推 / 数据跳过**：格式会为**每个行组保存 min/max 统计**，读取端可跳过整块无法匹配谓词的数据（**谓词下推/数据跳过**）。
5. **行式格式的适用场景**：**行式**格式（CSV、JSON、Avro）更适合写多、整行访问的场景——流式摄入，或需要读整条记录的 Kafka 消息。
6. **常见分层做法**：常见做法：原始数据先以 Avro/JSON 落地，再压实成 Parquet/ORC 供分析层使用。
7. **生态选型**：Parquet 是 Spark/Python 生态的事实标准；ORC 在 Hive 世界里常见。

**演进：**

1. **湖仓表格式**：Delta Lake / Iceberg / Hudi 在 Parquet/ORC 之上加事务、时间旅行、schema 演进与小文件压实，补齐分析存储的可更新能力。
2. **Z-Order / 数据聚簇**：按多列排序聚簇数据，增强 min/max 统计的剪枝效果，进一步减少扫描。
3. **向量化读取**：引擎按列批量向量化读取与计算，配合列式布局榨干 CPU 缓存与 SIMD 性能。

**面试追问：**

1. **列式为何压缩更好**：同列同类型值相邻，字典/游程/增量编码命中率高，而行式混排不同类型难以高效压缩。
2. **行组大小怎么选**：行组过大内存压力高、剪枝粒度粗；过小则统计/元数据开销大，如何平衡。
3. **什么时候别用列式**：需要频繁按整行写入/点查、或强实时摄入的场景，行式或专门的存储更合适。

**要点：**

1. **核心优势**：列式 → 只读所需列（裁剪）+ 更好压缩（同类值相邻）。
2. **剪枝能力**：行组 min/max 统计支持谓词下推/数据跳过。
3. **行式场景**：行式（Avro/JSON/CSV）适合写多、整行访问。
4. **生态标准**：Parquet（Spark 生态）/ORC（Hive）是分析标准。

### 8. YARN 资源管理

**频率：** 中

**题目：** YARN 解决什么问题？它的主要组件有哪些？

**方案：**

1. **解决的问题**：YARN（Yet Another Resource Negotiator）把集群资源管理与计算框架解耦，使 Spark、MapReduce、Flink 等能共享一个集群。
2. **ResourceManager**：**ResourceManager** 是全局调度器，在各应用间仲裁资源（内存/CPU）。
3. **ApplicationMaster**：每个应用有一个 **ApplicationMaster**，向 RM 协商**容器（container）**并协调自己的任务。
4. **NodeManager**：**NodeManager** 运行在每个工作节点上，负责启动/监控容器并向上汇报资源。
5. **提交流程**：流程：客户端提交应用 → RM 为 AM 分配一个容器 → AM 为实际工作请求更多容器 → NodeManager 启动它们。
6. **调度器与隔离**：调度器（Capacity、Fair）决定相互竞争的应用/队列如何共享资源。正是这种解耦，让同一集群能带隔离和配额地同时跑批处理与交互式负载。

**演进：**

1. **容器化 / Kubernetes**：计算框架逐渐转向以 Kubernetes 做资源编排，Spark on K8s 取代部分 YARN 场景，统一云原生调度。
2. **细粒度资源 / GPU 调度**：YARN 扩展支持 GPU、FPGA 等异构资源与更细粒度的容器请求，服务 AI/ML 负载。
3. **多租户队列治理**：用 Capacity/Fair 调度器配合队列配额、抢占、标签，支撑大规模多团队共享集群。

**面试追问：**

1. **Capacity vs Fair**：两种调度器在资源保证、抢占、延迟上的差异，分别适合什么组织/负载。
2. **AM 挂了会怎样**：ApplicationMaster 故障后 RM 如何重启它、已运行的容器与进度是否保留。
3. **资源碎片与超分**：容器内存/CPU 请求不合理导致的碎片，以及是否开启资源超分（oversubscription）的权衡。

**要点：**

1. **核心价值**：把资源管理与计算引擎解耦（多框架共享集群）。
2. **组件链路**：ResourceManager（全局）→ ApplicationMaster（每应用）→ NodeManager 上的容器。
3. **调度仲裁**：Capacity/Fair 调度器在队列/用户间仲裁。

### 9. Kafka 架构

**频率：** 高

**题目：** 请解释 Kafka 的核心架构：topic、分区、offset 和消费者组。

**方案：**

1. **提交日志本质**：Kafka 是一个分布式、只追加的**提交日志**。
2. **topic 与分区**：一个 **topic** 被切成若干**分区**，每个分区是一段有序、不可变的记录序列；顺序**仅在分区内**有保证，跨 topic 不保证。
3. **offset**：每条记录有一个 **offset**（在分区中的位置）。
4. **生产者分区选择**：生产者选择分区（轮询，或按 key 哈希，使同一 key 的所有记录落到同一分区并保持有序）。
5. **复制与 ISR**：每个分区在多个 broker 间复制，有一个**leader**和若干**follower**；生产者/消费者与 leader 通信，follower 复制以便故障切换（通过 **ISR** 即同步副本集跟踪）。
6. **消费者组与并行度**：**消费者组**提供可扩展、负载均衡的消费：一个分区在组内只被恰好一个消费者消费，所以并行度上限就是分区数。
7. **offset 提交与保留**：消费者自己记录已提交的 offset，这正是重放和不同投递语义的基础。Kafka 按时间/大小保留数据，与是否被消费无关，因此多个独立消费者可读同一份日志。

**演进：**

1. **去 ZooKeeper（KRaft）**：Kafka 用内置的 KRaft 共识取代 ZooKeeper 管理元数据，简化部署、提升可扩展性。
2. **分层存储（Tiered Storage）**：把历史日志卸载到对象存储，让 broker 本地只留热数据，实现近乎无限的保留与更低成本。
3. **Streams / Connect 生态**：Kafka Streams 做流处理、Kafka Connect 做源/汇集成，把 Kafka 从消息总线扩展为流处理平台。

**面试追问：**

1. **分区数怎么定**：分区数决定并行度上限，过多会增加元数据/选主开销与端到端延迟，如何权衡。
2. **rebalance 的代价**：消费者组扩缩容/故障触发 rebalance 导致短暂停顿，如何用静态成员、增量再平衡缓解。
3. **顺序性保证边界**：为什么只能保证分区内有序，业务需要全局有序时该如何设计（单分区 vs key 路由）。

**要点：**

1. **结构模型**：topic → 分区；顺序仅在分区内保证；offset = 位置。
2. **key 分区**：按 key 分区使同一 key 的记录在一个分区内有序。
3. **复制容错**：leader + ISR follower 复制以容错。
4. **消费并行度**：消费者组：每分区一个消费者 → 并行度受分区数限制。
5. **重放与解耦**：消费者记录 offset 支持重放；保留基于时间/大小，与消费解耦。

### 10. Kafka 精确一次与投递语义

**频率：** 高

**题目：** Kafka 提供哪些投递保证？它如何实现精确一次（exactly-once）？

**方案：**

1. **至少一次（默认）**：默认情况下 Kafka 提供**至少一次**：生产者对未确认的发送会重试，可能产生重复；消费者若先处理再提交 offset，崩溃后会重复处理。
2. **至多一次**：**至多一次**来自处理前就提交 offset（崩溃丢数据，但不重复）。
3. **精确一次（EOS）的两部分**：**精确一次（EOS）**由两部分构成。
4. **幂等生产者**：**幂等生产者**给每个生产者分配 PID 和每分区的序列号，broker 据此对重试的发送去重——消除生产者重试造成的重复。
5. **事务**：**事务**让生产者原子地向多个分区写入并提交消费者 offset（「消费—转换—生产」闭环），使下游看到要么全有要么全无。
6. **read_committed 隔离**：以 `read_committed` 隔离级别读取的消费者只看到已提交的记录。
7. **EOS 的边界**：关键注意点：EOS 只在 *Kafka 边界内*成立；端到端到外部系统的精确一次，仍要求该 sink 是幂等或事务性的。

**演进：**

1. **端到端幂等 sink**：在下游数据库/存储用主键 upsert 或去重表，把「至少一次」+ 幂等写等价成端到端精确一次，常比纯事务更简单。
2. **流处理框架集成 EOS**：Kafka Streams、Flink 的两阶段提交 sink 把源 offset、状态与输出绑定为一个事务，提供端到端精确一次。
3. **外部事务协调**：通过事务性 outbox、或 sink 自带事务（如支持事务的 DB/数据湖表格式）把 Kafka 事务延伸到外部系统。

**面试追问：**

1. **EOS 的性能代价**：事务与幂等带来额外的协调、刷盘与延迟，吞吐敏感场景是否值得，如何权衡。
2. **为什么端到端不自动成立**：Kafka 事务只覆盖写 Kafka 与提交 offset，写外部系统不在事务内，必须靠 sink 幂等/事务补齐。
3. **消费者 offset 提交时机**：先提交还是后提交 offset 决定了至多一次还是至少一次，EOS 下为何要把 offset 纳入事务。

**要点：**

1. **默认语义**：默认至少一次（重试 → 重复）；至多一次 = 处理前提交。
2. **幂等生产者**：幂等生产者（PID + 序列号）对重试发送去重。
3. **事务机制**：事务 = 原子的多分区写 + offset 提交；消费者用 `read_committed`。
4. **边界约束**：EOS 限于 Kafka 内部；真正端到端需幂等/事务性 sink。

### 11. 流处理：Flink vs Spark Streaming

**频率：** 高

**题目：** 比较 Flink 与 Spark Streaming。事件时间与处理时间有何区别？

**方案：**

1. **Spark Streaming（微批）**：经典的 **Spark Streaming** 用**微批（micro-batch）**——把流切成小时间片，对每片跑一个批作业，吞吐高但延迟受批间隔限制（Structured Streaming 的连续模式缩小了这一点）。
2. **Flink（真流式）**：**Flink** 是**真正的流式**引擎，逐条记录处理，毫秒级延迟，一等公民的事件时间处理和细粒度状态管理，因此在低延迟、有状态的流处理上更强。
3. **处理时间**：是事件被处理时的墙钟时间；简单，但结果不确定，因为它取决于系统速度和延迟。
4. **事件时间**：是事件实际发生的时间戳（嵌在数据里）；无论到达延迟如何都能产生正确、可复现的结果，但迫使你处理**乱序与迟到**事件。
5. **水位线（watermark）**：这正是**水位线（watermark）**的作用——水位线断言「不会再有早于时间 T 的事件到达」，让引擎决定何时窗口足够完整可以输出，同时限定等待拖尾的时长。

**演进：**

1. **吞吐优先**：吞吐优先、可容忍较高延迟时，微批足够。
2. **低延迟优先**：低延迟、有状态场景选真流式引擎（Flink）。
3. **语义选择**：从处理时间转向事件时间以获得正确、可复现的结果，代价是引入水位线处理乱序。

**面试追问：**

1. **水位线延迟**：水位线等待太久会放大延迟、太短会丢迟到数据，如何权衡？
2. **连续模式**：Structured Streaming 的连续处理模式能把延迟降到何种量级，适用边界在哪？
3. **状态规模**：Flink 的细粒度状态管理如何支撑超大状态？

**要点：**

1. **引擎对比**：Spark Streaming = 微批（吞吐高、延迟≈批间隔）；Flink = 真流式（毫秒延迟、状态丰富）。
2. **时间语义**：处理时间 = 何时被处理（简单、不确定）；事件时间 = 何时发生（正确、可复现）。
3. **迟到处理**：事件时间需通过水位线处理迟到/乱序数据。
4. **水位线含义**：水位线 = 「T 之后不再有更早事件」→ 决定何时关闭窗口。

### 12. 流处理中的窗口

**频率：** 中

**题目：** 请解释滚动窗口、滑动窗口和会话窗口。

**方案：**

1. **为何需要窗口**：因为流是无界的，聚合发生在**窗口**——流的有限切片上。
2. **滚动（tumbling）窗口**：是固定大小、不重叠的（如每 1 分钟一桶计数）；每个事件恰好属于一个窗口。
3. **滑动（sliding）窗口**：固定大小但按更小步长推进，因此窗口相互重叠，一个事件可属于多个（如每 1 分钟更新一次的 5 分钟平均值）——适合平滑的移动指标。
4. **会话（session）窗口**：是动态的：把间隔小于某个「不活跃间隙」的事件归为一组，当在间隙时长内没有事件到达时关闭——非常适合建模长度可变的用户会话。
5. **触发与收尾**：窗口基于水位线（事件时间）触发/收尾，因此迟到数据按既定策略处理（丢弃，或允许迟到并更新结果）。

**演进：**

1. **固定到重叠**：需要平滑移动指标时，从滚动窗口演进到带步长的滑动窗口。
2. **固定到动态**：建模变长活动突发时，用会话窗口替代固定窗口。
3. **迟到策略**：从直接丢弃迟到数据，演进到允许迟到并更新结果。

**面试追问：**

1. **会话间隙**：不活跃间隙设多大合适，如何由业务决定？
2. **重复计算**：滑动窗口重叠会带来多少重复聚合开销？
3. **迟到更新**：允许迟到更新结果时，下游如何处理已输出的旧结果？

**要点：**

1. **滚动**：固定、不重叠，每事件属一个窗口。
2. **滑动**：固定大小、重叠（步长 < 大小），事件可属多个窗口。
3. **会话**：基于间隙、长度动态，建模活动突发。
4. **触发时机**：水位线决定窗口何时触发；允许迟到处理拖尾。

### 13. Lambda vs Kappa 架构

**频率：** 中

**题目：** 对比 Lambda 与 Kappa 架构。分别在什么时候选用？

**方案：**

1. **Lambda 双路径**：**Lambda** 并行跑两条路径：**批处理层**在全量历史数据上重算准确视图（慢但正确/完整），**速度层**对近期数据给出低延迟的近似结果；服务层把两者合并。
2. **Lambda 代价**：它同时提供低延迟与最终正确，但代价是维护**两套代码库**实现同一逻辑，二者会漂移、难以保持一致。
3. **Kappa 纯流**：**Kappa** 去掉批处理层：一切皆流，「重处理」就是把日志（如从 Kafka 保留中）用同一套流式代码重放一遍新作业，再切换输出。
4. **Kappa 优势**：一套代码、运维更简单——在流引擎足够强大、日志可重放的今天是可行的。
5. **选型取舍**：新系统默认选 Kappa；在繁重历史批计算（复杂 ML 训练、超大回填）确实不同于实时路径时，Lambda 仍会出现。

**演进：**

1. **去批化**：从 Lambda 双层演进到 Kappa 纯流，消除双代码库漂移。
2. **重放能力**：依托可重放日志（Kafka 保留），把「重处理」收敛为重放同一套流式代码。
3. **保留 Lambda**：当批与实时逻辑确实分叉时，回退保留 Lambda。

**面试追问：**

1. **重放成本**：Kappa 重放超大历史日志的耗时与资源如何控制？
2. **代码漂移**：Lambda 两套代码库一致性如何保障？
3. **日志保留**：Kafka 保留期多长才能支撑完整重处理？

**要点：**

1. **Lambda 构成**：Lambda = 批（准确）+ 速度（快）+ 服务层合并；缺点是双代码库。
2. **Kappa 构成**：Kappa = 纯流；通过重放日志、用同一代码重处理。
3. **选型默认**：Kappa 是现代默认；批与实时逻辑确实分叉时保留 Lambda。

### 14. 数据仓库 vs 数据湖 vs 湖仓

**频率：** 高

**题目：** 比较数据仓库、数据湖和湖仓一体。

**方案：**

1. **数据仓库**：**数据仓库**以为分析优化的 schema 存储清洗后的结构化数据——**写时 schema**（先建模再加载）、治理强、SQL 快（Snowflake、BigQuery、Redshift）。适合 BI，但对原始/非结构化数据昂贵且不灵活。
2. **数据湖**：**数据湖**在对象存储（S3/HDFS）中廉价地存储任意类型的原始数据——**读时 schema**（查询时才施加结构），对 ML 和探索灵活。
3. **数据沼泽风险**：但缺乏治理时会退化成「数据沼泽」：无 ACID、schema 不可靠、查询性能差。
4. **湖仓（lakehouse）**：**湖仓（lakehouse）**在廉价湖存储之上加一层事务性表层（Delta Lake、Apache Iceberg、Hudi），在保留开放列式格式和接近数仓的 SQL 性能的同时，增加 **ACID 事务、schema 强制/演进、时间旅行、upsert**。
5. **统一目标**：它意在用一份数据同时服务 BI 和 ML，避免数仓/数据湖的割裂。

**演进：**

1. **成本与灵活**：从昂贵僵化的数仓演进到廉价灵活的数据湖以支撑 ML/探索。
2. **治理回补**：为避免数据湖退化成沼泽，在湖存储上加事务表层得到湖仓。
3. **一份数据**：从数仓/数据湖割裂演进到湖仓一份数据兼顾 BI 与 ML。

**面试追问：**

1. **表格式选型**：Delta、Iceberg、Hudi 三者在时间旅行与 upsert 上有何差异？
2. **性能逼近**：湖仓 SQL 性能能否真正逼近数仓？瓶颈在哪？
3. **治理落地**：读时 schema 场景如何施加 schema 强制与演进？

**要点：**

1. **仓库**：结构化、写时 schema、治理、SQL 快、贵/僵化。
2. **湖**：原始/任意格式、读时 schema、便宜/灵活、有变沼泽风险（无 ACID）。
3. **湖仓**：湖仓（Delta/Iceberg/Hudi）：在开放湖存储上加 ACID + schema + 时间旅行——一份数据兼顾 BI 与 ML。

### 15. OLAP vs OLTP

**频率：** 高

**题目：** OLAP 与 OLTP 系统有何区别？ClickHouse/Druid 这类引擎为什么分析快？

**方案：**

1. **OLTP**：**OLTP**（联机事务处理）处理大量小型、并发的读写事务，强一致——是应用背后的业务数据库（Postgres、MySQL）。它为点查和行级写优化，通常行式存储、重索引。
2. **OLAP**：**OLAP**（联机分析处理）处理对历史数据的大型聚合/扫描查询用于分析——用户少、扫描量大、以只读为主。它为聚合吞吐优化，而非逐行事务。
3. **列式与向量化**：像 **ClickHouse**、**Druid** 这样的分析引擎通过以下手段获得速度：**列式存储**（只读需要的列）、**向量化执行**（每条 CPU 指令处理一批值）。
4. **压缩与跳过**：激进**压缩**、通过每块 min/max 索引做**数据跳过**，以及预聚合/物化汇总。
5. **数据灌入**：通常经 CDC/ETL 把数据从 OLTP 灌入 OLAP，而非直接查业务库，以免分析扫描影响线上流量。

**演进：**

1. **职责分离**：从单库承载演进到 OLTP/OLAP 分离，保护线上事务。
2. **存储换速度**：从行存演进到列存 + 向量化 + 压缩以加速扫描聚合。
3. **数据链路**：通过 CDC/ETL 建立 OLTP → OLAP 的灌入链路。

**面试追问：**

1. **数据新鲜度**：CDC/ETL 链路会引入多少延迟，如何满足近实时分析？
2. **汇总粒度**：预聚合/物化汇总如何在灵活性与速度间取舍？
3. **行存索引**：OLTP 重索引为什么反而拖慢大扫描？

**要点：**

1. **OLTP**：大量小事务、强一致、行存、点访问（Postgres/MySQL）。
2. **OLAP**：大扫描/聚合、以读为主、列存、面向吞吐。
3. **提速手段**：ClickHouse/Druid 快在列式 + 向量化执行 + 压缩 + 数据跳过 + 汇总。
4. **数据链路**：经 CDC/ETL 把数据 OLTP → OLAP 以保护线上。

### 16. 维度建模：星型 vs 雪花

**频率：** 中

**题目：** 请解释星型和雪花模式，各自何时使用。

**方案：**

1. **维度建模基础**：维度建模把数仓组织为**事实表**（可度量的事件——销售、点击，含外键和数值度量）和**维度表**（描述性上下文——客户、产品、日期）。
2. **星型模式**：**星型模式**把每个维度反规范化成一张扁平表，直接与事实表 join。简单、join 少、查询快——是 BI 的默认。
3. **雪花模式**：**雪花模式**把维度规范化成子表（如 产品 → 类别 → 部门），省一些存储、减少更新异常，代价是更多 join、查询更慢更复杂。
4. **实践取舍**：实践中分析场景多用星型，因为存储便宜、查询的简单与速度更重要；雪花仅在大而频繁变化的维度上有选择地使用。

**演进：**

1. **规范到反规范**：从追求省存储的雪花规范化演进到查询更快的星型反规范化。
2. **选择性规范化**：仅对大而频繁变化的维度有选择地引入雪花规范化。
3. **以查询为先**：在存储便宜前提下，演进为优先查询速度与简单性。

**面试追问：**

1. **缓慢变化维**：SCD（缓慢变化维度）在星型/雪花中如何处理？
2. **更新异常**：反规范化带来的更新异常如何控制？
3. **桥接表**：多对多维度关系用什么结构建模？

**要点：**

1. **结构**：事实表（度量 + 外键）被维度表（上下文）环绕。
2. **星型**：星型 = 反规范化维度、join 少、更快——分析默认。
3. **雪花**：雪花 = 规范化维度、冗余少、join 多/更慢。
4. **优先级**：优先星型；存储便宜，查询速度与简单性占主导。

### 17. 有状态流处理中的精确一次

**频率：** 中

**题目：** Flink 这类流处理器如何保证精确一次的状态语义？

**方案：**

1. **核心机制**：核心机制是**检查点（checkpoint）**配合 **Chandy–Lamport 分布式快照**算法。
2. **屏障快照**：Flink 周期性地向流中注入**屏障（barrier）**；当屏障流经各算子时，每个算子把自己的状态（已消费的 offset、窗口内容、聚合值）快照到持久存储（如 S3/HDFS/RocksDB 上的状态后端）。当某个屏障对应的所有算子都完成快照时，该检查点就是完整且一致的。
3. **故障恢复**：故障时，Flink 把每个算子从最近一个完整检查点恢复，并把 source（如 Kafka offset）回退到相符位置——于是每条记录对状态的影响恰好一次。
4. **输出端保证**：这保证的是*内部状态*的精确一次。对外部 sink 的精确一次*输出*还需要 sink 是**幂等的**，或者是**两阶段提交**式 sink（仅在检查点完成时才提交写入）。
5. **语义澄清**：注意「精确一次」指每个事件对*状态的影响*发生一次，并非事件在物理上只被处理一次。

**演进：**

1. **状态到输出**：从保证内部状态精确一次，演进到端到端输出精确一次。
2. **sink 升级**：为端到端保证，把 sink 从普通写入升级为幂等或两阶段提交。
3. **恢复点推进**：随检查点周期推进，故障恢复点不断前移以减少重算。

**面试追问：**

1. **检查点开销**：检查点频率如何在恢复代价与运行开销间权衡？
2. **状态后端**：RocksDB 状态后端相比内存后端有何取舍？
3. **2PC 阻塞**：两阶段提交 sink 在提交阶段故障会怎样？

**要点：**

1. **快照机制**：用屏障做检查点（Chandy–Lamport）快照一致的全局状态。
2. **恢复语义**：故障时：恢复状态 + 回退 source offset → 每条记录只计一次。
3. **输出条件**：精确一次输出需幂等或 2PC（事务性）sink。
4. **语义澄清**：是精确一次的*影响*，而非物理上处理一次。

### 18. 面向扩展的分区与分片

**频率：** 高

**题目：** 分布大规模数据集有哪些分区策略？各有什么权衡？

**方案：**

1. **分区目的**：分区把数据切散到各节点以并行化工作。
2. **哈希分区**：**哈希分区**（`hash(key) % N`）分布均匀、点查直达，但破坏范围查询，且 N 变化时会引发大规模重排——用**一致性哈希**缓解，它在扩缩容时只搬动一小部分 key。
3. **范围分区**：**范围分区**（按 key 区间，如日期）保持范围扫描高效、可读性好，但若负载集中在某个区间会造成**热点**（如所有写都落在「今天」）。
4. **列表/目录分区**：**列表/目录分区**用一张显式查找表把 key 分配到分区——灵活但增加一层元数据。
5. **核心权衡**：反复出现的权衡是**均匀分布 vs 查询本地性**：哈希均衡负载但打散相关数据；范围保持本地性但有倾斜风险。好的分区键要避免热点（别用单调递增 ID 或低基数字段），而不停机地重平衡/重分片是运维上的难点。

**演进：**

1. **缓解重排**：从朴素 `hash(key) % N` 演进到一致性哈希，限制扩缩容抖动。
2. **本地性取舍**：按查询模式在哈希（均匀）与范围（本地性）间选择。
3. **在线重平衡**：从停机重分片演进到不停机的在线重平衡。

**面试追问：**

1. **热点消解**：范围分区出现时间热点时如何打散（如加盐）？
2. **虚拟节点**：一致性哈希用虚拟节点解决什么问题？
3. **分区键选择**：为何单调递增 ID 和低基数字段不宜做分区键？

**要点：**

1. **哈希**：均匀、点查直达、不利范围；一致性哈希限制扩缩容抖动。
2. **范围**：扫描高效、可读，但易热点（如按时间写入）。
3. **列表/目录**：靠映射灵活，多一层元数据。
4. **核心权衡**：均匀分布 vs 本地性；选能避开热点的键。

### 19. Spark 集群架构

**频率：** 高

**题目：** 请讲解 Spark 的运行时架构——driver、executor 以及 job/stage/task 层级是如何协同工作的？

**方案：**

1. **driver**：一个 Spark 应用运行一个 **driver** 和多个 **executor**。driver 持有 `SparkContext`，构建逻辑 DAG，与**集群管理器**（YARN、Kubernetes、Standalone、Mesos）协商资源，调度任务并收集结果——它是协调者，也是整个应用的单点故障。
2. **executor**：**executor** 是工作节点上的 JVM 进程，负责运行 task 和缓存数据；每个 executor 拥有固定数量的核数和内存预算。
3. **工作层级**：工作按层级分解：**Job**——由一个 action（`collect`、`save`、`count`）触发。**Stage**——在 **shuffle 边界**（宽依赖）处切分出的一组 task；窄转换在同一个 stage 内流水线执行。**Task**——最小执行单元，每个分区一个，在一个核上执行。
4. **调度与本地性**：DAG 调度器创建 stage；task 调度器将 task 分发到 executor，并优先考虑**数据本地性**。
5. **并行与恢复**：分区数多于核数可以让 executor 保持繁忙，并支持掉队任务的恢复。

**演进：**

1. **逻辑到物理**：从逻辑 DAG 演进到按 shuffle 边界切分的 stage/task 物理执行计划。
2. **本地性优化**：task 调度从随机分发演进到优先数据本地性。
3. **弹性恢复**：通过多于核数的分区支持掉队任务恢复与负载均衡。

**面试追问：**

1. **driver 单点**：driver 作为单点故障如何缓解（如 HA）？
2. **宽窄依赖**：宽依赖为何必然触发 shuffle 边界？
3. **本地性级别**：Spark 的数据本地性级别有哪些，降级如何发生？

**要点：**

1. **角色分工**：driver 负责协调（DAG、调度、结果）；executor 运行 task 并保存缓存数据。
2. **资源分配**：集群管理器（YARN/K8s/Standalone）为应用分配 executor。
3. **执行层级**：层级：action → job → stage（在 shuffle 处切分）→ task（每个分区一个）。
4. **task 数量**：task 数量 = 分区数量；应保持为总核数的倍数。

### 20. 分区、并行度、repartition 与 coalesce

**频率：** 高

**题目：** 如何在 Spark 中调优并行度？repartition 和 coalesce 分别在什么时候使用？

**方案：**

1. **并行度约束**：并行度受**分区**数量约束——每个分区对应一个 task，因此分区太少会让核空闲并有 OOM 风险，而分区太多则带来调度开销和过小的 task。
2. **经验法则**：常见经验法则是每个核 2–4 个分区；shuffle 输出由 `spark.sql.shuffle.partitions` 控制（默认 200，对小数据往往过大，对超大数据往往过小）。
3. **`repartition(n)`**：**`repartition(n)`**——完整 shuffle，产生大小大致相等的分区；可以*增加或减少*分区数并重新平衡数据倾斜。适用于宽操作之前，或需要写出大小均匀的文件时。
4. **`coalesce(n)`**：**`coalesce(n)`**——**不做完整 shuffle**（窄依赖）合并现有分区，只能减少分区数，且可能导致大小不均。适用于廉价地缩减分区，例如写出前避免产生大量小文件。
5. **选用策略**：在过滤后仅需减少分区数时优先用 `coalesce`；需要平衡或提升并行度时用 `repartition`。

**演进：**

1. **默认到调优**：从 `spark.sql.shuffle.partitions` 默认 200 演进到按数据量调优分区数。
2. **减少代价**：缩减分区时从昂贵的 `repartition` 演进到无 shuffle 的 `coalesce`。
3. **倾斜修复**：数据倾斜时用 `repartition` 完整 shuffle 重新平衡。

**面试追问：**

1. **小文件问题**：写出前如何用 `coalesce` 避免大量小文件？
2. **倾斜检测**：如何识别分区倾斜并选择重分区策略？
3. **AQE**：自适应查询执行（AQE）如何自动调整 shuffle 分区数？

**要点：**

1. **分区与 task**：每个分区一个 task；目标约为每个核 2–4 个分区。
2. **shuffle 分区**：`spark.sql.shuffle.partitions`（默认 200）决定 shuffle 后的分区数。
3. **两者差异**：`repartition` = 完整 shuffle，可增可减并重新平衡；`coalesce` = 无完整 shuffle，只能减少，可能不均。
4. **选用策略**：用 coalesce 廉价地减少小文件数量；用 repartition 修复倾斜或提升并行度。

### 21. persist/cache 与存储级别

**频率：** 高

**题目：** Spark 中的 cache 和 persist 有什么作用？各存储级别有何区别？

**方案：**

1. **复用动机**：由于 RDD/DataFrame 是惰性求值的，并且每次 action 都会根据 lineage 重新计算，因此在多个 action 之间复用某个数据集会导致每次都重算。**`cache()`** 和 **`persist()`** 将数据集标记为在首次计算后被存储，以便后续 action 复用。
2. **默认级别**：对于 RDD，`cache()` 是 `persist(MEMORY_ONLY)` 的简写；对于 DataFrame 则是 `MEMORY_AND_DISK`。存储级别在内存、CPU 和容错之间权衡。
3. **MEMORY_ONLY**：以反序列化形式存于 JVM 堆；最快，但放不下的分区会被重算。
4. **MEMORY_AND_DISK**：将放不下的分区溢写到磁盘，而非重算。
5. **SER 变体**：**MEMORY_ONLY_SER / MEMORY_AND_DISK_SER**——序列化字节；占用内存更少，CPU 更多。
6. **DISK_ONLY**：仅磁盘，适用于重算代价高但占内存大的数据。**_2 变体**将每个分区在两个节点上复制以实现容错。
7. **释放策略**：缓存是惰性的（在下一个 action 时才物化）；用完后调用 `unpersist()` 释放存储，并且只缓存被复用到足以抵消内存代价的数据集。

**演进：**

1. **不缓存**：每个 action 沿 lineage 从头重算，重复数据集反复计算。
2. **cache()**：首次计算后以默认级别存储，后续 action 直接复用。
3. **选择级别**：按内存/CPU/容错权衡选 `persist(级别)`，用 `unpersist()` 回收。

**面试追问：**

1. **惰性物化**：`cache()` 调用后何时真正物化？（下一个 action 时）。
2. **RDD vs DataFrame 默认**：为什么两者默认级别不同？
3. **SER 取舍**：序列化级别省内存但增加 CPU，何时值得？

**要点：**

1. **避免重算**：cache/persist 避免在多个 action 之间根据 lineage 重算被复用的数据集。
2. **默认级别**：`cache()` = MEMORY_ONLY（RDD）/ MEMORY_AND_DISK（DataFrame）。
3. **级别权衡**：各级别在内存与 CPU（SER）与容错（DISK、_2 复制）之间权衡。
4. **惰性与释放**：缓存是惰性的；用 `unpersist()` 释放；只缓存真正会复用的数据。

### 22. 广播变量与累加器

**频率：** 中

**题目：** 广播变量（broadcast variable）和累加器（accumulator）分别解决什么问题？两者有何区别？

**方案：**

1. **共享变量**：两者都是 Spark 的**共享变量**，但数据流动方向相反。
2. **广播变量**：将一个较大的只读值（查找表、ML 模型、配置 map）**一次性**发送到每个 executor 并在其上缓存，使该 executor 上的所有 task 复用同一份副本。
3. **不用广播的代价**：若不使用它，闭包中捕获的变量会被序列化并随*每个 task*一起发送，对大对象而言非常浪费；广播使用高效的点对点（类似 torrent）分发。这正是 broadcast hash join 的基础。
4. **累加器**：是面向 driver 端可观测性的只写聚合器：task 向其 `add`（计数、求和），而只有 driver 读取总值——适用于统计坏记录数等指标。
5. **容错注意**：由于失败或推测执行的 task 可能重跑，累加器更新**仅在 action 内部保证精确一次**，而在转换中不保证——重跑的 task 可能重复计数。转换中的累加器应视为尽力而为的诊断信息。
6. **方向对比**：**广播**——driver → executor，只读，每个 executor 缓存一份；**累加器**——executor → driver，只写（add），在 driver 端读取。

**演进：**

1. **闭包捕获**：直接在闭包引用大对象，每个 task 序列化一份，浪费网络与内存。
2. **广播变量**：每 executor 缓存一份只读副本，task 复用。
3. **累加器**：将 executor 端指标聚合回 driver，注意精确一次仅限 action 内。

**面试追问：**

1. **精确一次边界**：为什么转换中的累加器可能重复计数？（task 重跑/推测执行）。
2. **分发机制**：广播为何用 torrent 式 P2P 而非 driver 逐个推送？
3. **与 broadcast join 关系**：广播变量如何支撑 broadcast hash join？

**要点：**

1. **广播节省**：广播将较大的只读值每个 executor 发送一次，而非每个 task 发送一次。
2. **分发方式**：广播使用类 torrent 分发；是 broadcast hash join 的基础。
3. **累加器作用**：累加器将值聚合回 driver（计数器/指标）。
4. **精确一次**：仅在 action 内使用的累加器保证精确一次；转换中重跑可能重复计数。

### 23. Spark join 策略

**频率：** 高

**题目：** Spark 使用哪些 join 策略？它如何在 broadcast hash、shuffle hash 和 sort-merge join 之间进行选择？

**方案：**

1. **选择依据**：Spark 的物理计划器根据表大小、join 键和配置来选择 join。
2. **Broadcast hash join**：如果一侧小于 `spark.sql.autoBroadcastJoinThreshold`（默认 10 MB），Spark 会将其广播到每个 executor 并在本地构建哈希表，从而在**不做 shuffle** 的情况下连接大表。适用时远快于其他策略；但只适用于等值连接，且当"小"表被错误估计时有 driver/executor OOM 的风险。
3. **Shuffle hash join**：两侧都按键 shuffle；将某个分区中较小的一侧构建为哈希表，由另一侧探测。避免排序，但要求构建侧能放入内存；适用于一侧为中等大小且不希望排序的情形。
4. **Sort-merge join**：两侧都 shuffle，每个分区按键排序，然后归并。这是大表对大表等值连接的默认策略；扩展性好，并能优雅地溢写到磁盘，代价是排序开销。
5. **非等值回退**：非等值连接会回退到 broadcast/shuffle 嵌套循环连接。准确的统计信息和提示（`broadcast()`）有助于做出好的选择。

**演进：**

1. **大表对大表**：默认 sort-merge join，shuffle + 排序 + 归并，可溢写。
2. **一侧较小**：shuffle hash join 对较小侧建哈希表，省去排序。
3. **一侧极小**：broadcast hash join 广播小表，彻底消除 shuffle。

**面试追问：**

1. **阈值调优**：`spark.sql.autoBroadcastJoinThreshold` 调太大的风险？（OOM）。
2. **估计错误**：小表统计被低估导致误广播，如何排查与规避？
3. **非等值连接**：为什么 hash/merge 不能用于非等值连接？

**要点：**

1. **Broadcast hash**：广播小表，无 shuffle——最快但有内存风险（阈值默认 10 MB）。
2. **Shuffle hash**：两侧 shuffle，对较小侧建哈希表；无排序，构建侧须放入内存。
3. **Sort-merge**：shuffle + 排序 + 归并；大表对大表的默认策略，能优雅溢写。
4. **适用范围**：只有等值连接可用 hash/merge；非等值使用嵌套循环；统计信息和提示引导计划器。

### 24. 自适应查询执行（AQE）

**频率：** 高

**题目：** 什么是自适应查询执行（Adaptive Query Execution）？它执行哪些运行时优化？

**方案：**

1. **背景**：**AQE** 于 Spark 3.0 引入（3.2+ 默认开启），它利用实际的 shuffle 统计信息而非可能过时的编译期估计，在**运行时**重新优化物理计划。每个 shuffle stage 完成后，Spark 便掌握了精确的分区大小，并据此重新规划下一个 stage。
2. **动态分区合并**：将大量过小的 shuffle 后分区合并为更少、大小合适的分区，解决因 `spark.sql.shuffle.partitions` 过高导致的"过多小 task"问题。
3. **倾斜 join 处理**：检测异常大的分区并将其**拆分**为子分区（同时复制匹配的一侧），使单个掉队 task 不至于主导整体运行时间。
4. **动态 join 策略切换**：如果某一侧在运行时被证实比估计的更小，AQE 会将原计划的 sort-merge join 转换为 **broadcast hash join**，从而消除一次 shuffle。
5. **启用与收益**：AQE 减少了对手动调优 shuffle 分区数和手工修复倾斜的需求，通过 `spark.sql.adaptive.enabled` 启用。

**演进：**

1. **静态计划**：依赖编译期估计，统计过时则计划不优，需手工调参/修倾斜。
2. **运行时统计**：每个 shuffle stage 完成后掌握真实分区大小。
3. **自适应重规划**：逐 stage 合并分区、拆分倾斜、降级 join，减少人工调优。

**面试追问：**

1. **触发时机**：AQE 为什么必须在 shuffle stage 边界重新优化？
2. **倾斜检测阈值**：如何判断一个分区"异常大"？拆分后为何要复制另一侧？
3. **与手动调参关系**：开启 AQE 后 `spark.sql.shuffle.partitions` 还重要吗？

**要点：**

1. **运行时重优化**：逐 stage 地根据真实 shuffle 统计信息在运行时重新优化计划。
2. **分区合并**：动态分区合并将过小的分区合并为均衡的分区。
3. **倾斜处理**：倾斜 join 处理拆分超大分区以消除掉队者。
4. **join 降级**：当某一侧实际很小时，可将 sort-merge 降级为 broadcast join。

### 25. Catalyst 优化器与 Tungsten

**频率：** 高

**题目：** Catalyst 和 Tungsten 如何优化并执行 Spark SQL/DataFrame 查询？

**方案：**

1. **Catalyst 定位**：**Catalyst** 是 Spark SQL 基于规则和基于代价的查询优化器。
2. **转换阶段**：它将查询经过多个阶段进行转换：解析为**未解析的逻辑计划**，对照 catalog 进行解析，应用**逻辑优化**，生成**物理计划**，并按代价选择其一。
3. **逻辑重写**：关键的逻辑重写包括**谓词下推**（将过滤器移到靠近数据源处，使 Parquet 等格式可跳过 row group，JDBC 可将 `WHERE` 下推到数据库）、**投影下推**（只从列式存储读取所需列）、常量折叠以及 join 重排序。
4. **Tungsten 执行引擎**：**Tungsten** 是让所选计划高速执行的执行引擎：它以**堆外**方式管理内存，采用对缓存友好的二进制布局（避免 JVM 对象开销和 GC 压力），并执行**全阶段代码生成**，将一整条算子链融合为单个紧凑循环的 JVM 函数，取代缓慢的逐算子迭代器（Volcano）模型。
5. **协同效应**：二者结合下，Catalyst 决定*要*高效计算什么，Tungsten 让*如何*计算在 CPU 和内存上都高效——这正是 DataFrame 通常胜过手写 RDD 代码的原因。

**演进：**

1. **手写 RDD**：逐算子迭代器模型，JVM 对象开销大、GC 压力高。
2. **Catalyst**：规则 + 代价优化逻辑/物理计划，下推削减 I/O。
3. **Tungsten**：堆外二进制布局 + 全阶段代码生成，让执行贴近硬件。

**面试追问：**

1. **下推效果**：谓词/投影下推分别在哪些数据源上收益最大？
2. **全阶段代码生成**：为什么融合算子比迭代器模型快？
3. **DataFrame vs RDD**：为什么 DataFrame 常胜过手写 RDD？

**要点：**

1. **Catalyst 流程**：未解析 → 已解析 → 优化后的逻辑计划 → 物理计划 → 基于代价的选择。
2. **下推削减 I/O**：谓词下推和投影下推在数据源处削减 I/O（尤其是列式格式/JDBC）。
3. **Tungsten 内存**：Tungsten 使用堆外二进制内存布局，大幅降低 GC 和对象开销。
4. **代码生成**：全阶段代码生成将算子融合为一个函数，胜过迭代器模型。

### 26. 检查点与缓存及 lineage 截断

**频率：** 中

**题目：** Spark 的检查点（checkpointing）与缓存有何区别？它为什么要截断 lineage？

**方案：**

1. **缓存特性**：**缓存/持久化**将数据集的分区存于内存或本地磁盘以供复用，但它**保留 lineage**——若某个缓存分区丢失，Spark 会根据 DAG 重算它。
2. **检查点机制**：**检查点**则将 RDD/DataFrame 写入**可靠存储**（通常是 HDFS/S3），随后**截断 lineage**，用指向检查点文件的指针取而代之。
3. **为何重要**：非常长的 lineage（迭代算法，或长时间运行的结构化流状态）重算代价高昂，并可能导致栈溢出或巨大的 DAG；而纯缓存的数据集在 executor 及其缓存副本双双丢失时毫无保护。通过持久化到持久存储并切断依赖链，检查点限定了恢复代价。
4. **权衡**：它会触发一个额外的 job 来写出数据（因此更慢，通常应先 `cache()` 以避免重算），且文件会在 job 结束后依然存在。流式检查点还会额外存储偏移量和算子状态以实现精确一次恢复。
5. **对比**：**缓存**——快速，位于内存/磁盘，保留 lineage，executor 故障时丢失，不写入可靠存储；**检查点**——写入持久存储，截断 lineage，故障后仍存活，代价是一次额外写出。

**演进：**

1. **纯缓存**：内存/磁盘复用，保留 lineage，副本全丢则重算，长 lineage 代价高。
2. **cache + checkpoint**：先 cache 避免重算，再 checkpoint 写可靠存储并截断依赖。
3. **流式检查点**：额外持久化偏移量 + 算子状态以实现精确一次恢复。

**面试追问：**

1. **为何先 cache**：为什么检查点前建议先 `cache()`？（避免额外 job 重算）。
2. **lineage 截断动机**：长 lineage 会带来哪些具体问题？（栈溢出/巨大 DAG）。
3. **流式状态**：结构化流检查点存了什么以保证精确一次？

**要点：**

1. **核心区别**：缓存保留 lineage（丢失时重算）；检查点写入可靠存储并截断 lineage。
2. **截断价值**：截断可限定长/迭代 lineage 及巨大 DAG 的恢复代价。
3. **额外 job**：检查点会触发一个额外 job——应先 cache 以避免重算。
4. **流式恢复**：流式检查点持久化偏移量 + 状态以实现精确一次恢复。

### 27. Parquet 内部结构

**频率：** 高

**题目：** 请讲解 Parquet 文件的内部布局——row group、column chunk、page、编码方式以及 footer 统计信息。

**方案：**

1. **层级结构**：Parquet 文件是为列式扫描优化的层级结构。文件被切分为 **row group**（行的水平切片，通常约 128 MB），在每个 row group 内部，每一列以连续的 **column chunk** 存储。
2. **page 单元**：column chunk 又进一步划分为 **page**（通常约 1 MB），page 是编码和压缩的最小单元。
3. **编码方式**：数值在压缩前会先编码：**字典编码（dictionary encoding）** 用较小的整数索引替换重复值（对低基数列非常有效），而 **RLE/bit-packing** 则压缩这些索引以及编码嵌套与可空结构的 repetition/definition level。
4. **footer 统计**：文件末尾的 **footer** 保存 schema 以及每个 column chunk 的统计信息——min/max、null 数量、distinct 数量——使读取端能跳过无法满足谓词的整个 row group 或 page（**谓词下推，predicate pushdown**）。
5. **读取顺序**：由于 footer 在最后，读取端会先 seek 到文件末尾，再只读取所需的 column chunk。

**演进：**

1. **行式存储**：整行连续，列扫描需读全部列，无法跳过。
2. **列式 + 分块**：row group / column chunk / page 层级，支持列裁剪与分块压缩。
3. **footer 统计驱动跳过**：min/max/null 统计实现 row group 与 page 级谓词下推。

**面试追问：**

1. **跳过粒度**：footer 统计如何支持 row group 与 page 级跳过？
2. **低基数列**：字典编码为什么对低基数列特别有效？
3. **嵌套/可空**：definition/repetition level 如何编码 null 与嵌套而无需额外列？

**要点：**

1. **层级**：文件 → row group → column chunk → page（page 是编码/压缩单元）。
2. **编码**：字典编码 + RLE/bit-packing 压缩低基数与重复数据。
3. **level 编码**：definition/repetition level 编码 null 与嵌套，无需额外列。
4. **footer 跳过**：footer 统计信息（min/max/null 数量）驱动 row group 与 page 级跳过。

### 28. ORC vs Parquet

**频率：** 中

**题目：** ORC 与 Parquet 有何区别？何时应选择哪一个？

**方案：**

1. **共同点**：二者都是开放、列式、可切分（splittable）且支持谓词下推的格式，但来自不同生态且细节各异。
2. **ORC 特性**：**ORC**（Optimized Row Columnar）为 Hive 而生：它使用 **stripe**（相当于它的 row group，约 64–256 MB）并带有轻量级索引、内建 **bloom filter** 以及细粒度的行级统计，使得 Hive 中的谓词下推与 ACID 更新非常高效；它的压缩率通常也略好。
3. **Parquet 特性**：**Parquet** 源自 Impala/Dremel 一脉，是 Spark、Python（pandas/Arrow）以及大多数云引擎中事实上的标准，拥有最丰富的工具链与最广泛的互操作性。
4. **选 ORC**：当你的技术栈以 Hive/Hadoop 为中心、想要最好的 Hive ACID 与 bloom filter 跳过，或需要最大压缩率时，选 **ORC**。
5. **选 Parquet**：当你身处 Spark/Arrow/Python 或多引擎云端 lakehouse、互操作性最重要时，选 **Parquet**。实践中两者性能相当，通常由生态契合度来决定。

**演进：**

1. **Hive 栈**：选 ORC，受益于 stripe、bloom filter、Hive ACID 与更高压缩率。
2. **Spark/Arrow/云栈**：选 Parquet，受益于最广工具链与互操作性。
3. **性能相当**：实践中两者性能接近，由生态契合度决定选型。

**面试追问：**

1. **bloom filter**：ORC 的内建 bloom filter 在何种查询下收益最大？
2. **ACID 更新**：为什么 ORC 在 Hive ACID 场景更有优势？
3. **互操作性**：为什么 Parquet 成为跨引擎事实标准？

**要点：**

1. **同思路异血统**：思路相同（列式、可切分、下推），血统不同：ORC = Hive，Parquet = Spark/Arrow。
2. **ORC 优势**：stripe、内建 bloom filter、强 Hive ACID，压缩率通常略优。
3. **Parquet 优势**：工具链/互操作性最广，是 Spark/Python/云端的标准。
4. **决策依据**：决策通常取决于生态契合度，而非纯粹性能。

### 29. Avro 与 schema 演进

**频率：** 中

**题目：** 什么是 Avro？schema registry 与 schema 演进在 Avro 中如何工作？

**方案：**

1. **Avro 定位**：**Avro** 是一种紧凑的、面向行的二进制序列化格式，适合写密集、按整条记录访问的场景，如 Kafka 消息和原始摄入——与列式 Parquet 恰好相反的用例。
2. **schema 同行**：它的关键特性是数据与其 **schema**（的引用）一同写入，因此读取端总能解释字节。
3. **schema registry**：在流式系统中，**schema registry** 集中存储 schema，并给生产者/消费者一个较小的 **schema ID** 嵌入到每条消息中，而非完整 schema，从而节省字节并强制规则。
4. **schema 演进**：Avro 通过将写入端 schema 与读取端 schema 进行解析来支持 **schema 演进**：你可以新增字段（给它们默认值以便旧读取端兼容）、删除带默认值的字段，或通过 alias 重命名。
5. **兼容模式**：registry 会强制一种 **兼容模式**——backward（新 schema 读旧数据）、forward（旧 schema 读新数据）或 full——以防止生产者发布破坏性变更。这实现了生产者与消费者部署的解耦。

**演进：**

1. **裸序列化**：无 schema 元信息，读取端难以安全解释字节演进。
2. **Avro + schema 同行**：数据携带 schema 引用，读取端总能解析。
3. **registry + 兼容模式**：集中管理 schema、嵌入小 ID，用兼容模式拦截破坏性变更。

**面试追问：**

1. **行式 vs 列式**：为什么 Avro 适合 Kafka/摄入而不适合分析扫描？
2. **兼容模式选择**：backward/forward/full 分别适用于什么升级顺序？
3. **schema ID**：为什么嵌入 schema ID 而非完整 schema？

**要点：**

1. **格式定位**：Avro = 紧凑的行式二进制格式；适合 Kafka/摄入，不适合分析扫描。
2. **schema 管理**：schema 随数据同行；registry 集中管理 schema，并在每条消息中嵌入较小的 ID。
3. **演进手段**：带默认值地新增/删除字段、通过 alias 重命名；解析写入/读取端 schema。
4. **兼容模式**：兼容模式（backward/forward/full）拦截破坏性变更并解耦部署。

### 30. 小文件问题

**频率：** 高

**题目：** 大数据系统中的小文件问题是什么？如何解决？

**方案：**

1. **问题定义**：**小文件问题** 指数据集被存成海量的微小文件而非较少的大文件。
2. **HDFS 元数据压力**：在 **HDFS** 上，每个文件/block 都消耗 NameNode 内存，因此数百万个小文件会耗尽元数据容量。
3. **读取性能**：在任何引擎上，微小文件都会拖垮读取性能：每个文件都意味着单独的 open/seek/读 footer 开销、糟糕的压缩、微小且不可切分的任务，以及过多的调度与 listing 压力（在 S3 等对象存储上尤其严重，因为 LIST/GET 延迟占主导）。常见成因是流式微批、过度分区以及每个 task 写一个文件。
4. **compaction**：**compaction/bin-packing** 作业，把许多小文件重写为接近 block 大小的文件（如 128 MB–1 GB）。
5. **调优写入端**：Spark 中的 `coalesce`/`repartition`、更少的输出分区、流式中更大的 flush 间隔。
6. **表格式自动 compaction**：表格式的自动 compaction（Iceberg/Delta/Hudi 的 `OPTIMIZE`/compaction），同时也重写元数据。避免过多的分区列。目标是文件足够大以摊薄开销并保持可切分。

**演进：**

1. **原始小文件**：流式微批/过度分区/每 task 一文件，产生海量微小文件。
2. **批处理 compaction**：定期 bin-packing 到约 128 MB–1 GB 并调优写入并行度。
3. **表格式托管**：Iceberg/Delta/Hudi 的 OPTIMIZE/自动 compaction，顺带重写元数据。

**面试追问：**

1. **NameNode 瓶颈**：为什么小文件在 HDFS 上会耗尽 NameNode 内存？
2. **对象存储**：为什么小文件在 S3 上尤其痛苦？（LIST/GET 延迟）。
3. **成因治理**：如何从写入侧（分区/flush 间隔）根治而非事后 compaction？

**要点：**

1. **双重代价**：大量微小文件 → NameNode 内存压力（HDFS）以及处处的单文件 I/O/调度开销。
2. **对象存储痛点**：在对象存储（S3 LIST/GET 延迟）以及压缩/可切分性方面尤其痛苦。
3. **解决手段**：通过 compaction/bin-packing 到约 128 MB–1 GB，并调优写入并行度来解决。
4. **现代托管**：现代表格式提供 OPTIMIZE/自动 compaction；避免过度分区。

### 31. 开放表格式：Iceberg vs Delta vs Hudi

**频率：** 高

**题目：** 请对比 Apache Iceberg、Delta Lake 与 Apache Hudi。开放表格式解决了什么问题？

**方案：**

1. **元数据层**：开放表格式在数据湖的 Parquet/ORC 文件之上增加了一层 **元数据层**，以提供类数据库的保证：**ACID 事务**、**时间旅行（time travel）**（查询过去的快照）、安全的并发写入、schema 演进以及高效的 **upsert/delete**。它们通过 manifest/log 来追踪哪些文件属于某个表版本，而非信任目录 listing。
2. **Iceberg**：使用快照 + manifest 树，且与引擎无关；其标志性特性是 **隐藏分区（hidden partitioning）**——表存储分区变换，用户按原始列查询而无需了解物理布局，且分区可以演进。
3. **Delta Lake**：使用 JSON/Parquet 的 **事务日志**（`_delta_log`）；与 Spark/Databricks 紧密集成，`MERGE`、`OPTIMIZE` 与 Z-ordering 都很强。
4. **Hudi**：围绕 **upsert 与增量拉取** 构建，提供 Copy-on-Write 与 Merge-on-Read 两种表以权衡读写代价——非常适合 CDC 与可变数据。
5. **按工作负载选择**：引擎无关的 lakehouse 选 Iceberg，Spark/Databricks 选 Delta，重流式 upsert/CDC 选 Hudi。

**演进：**

1. **目录 listing → 元数据层**：早期数据湖信任目录 listing 来判断表内容，既不原子也不可靠；开放表格式用 manifest/log 显式追踪文件版本，从而获得 ACID 与时间旅行。
2. **静态分区 → 隐藏/可演进分区**：Iceberg 把分区变换下沉到表元数据，用户无需了解物理布局即可查询，分区方案还能随业务演进。
3. **全表覆盖 → 高效 upsert**：Hudi 的 Copy-on-Write/Merge-on-Read 把重写代价从整表降到受影响文件，使 CDC 与可变数据成为湖上的一等公民。

**面试追问：**

1. **时间旅行如何实现**：靠快照/事务日志记录每个版本引用的文件集，查询历史版本即读取对应快照的 manifest/log。
2. **隐藏分区的价值**：用户按原始列过滤即可自动裁剪，避免写错分区列导致全表扫描，且分区可演进而不重写历史。
3. **Copy-on-Write vs Merge-on-Read**：前者写时合并、读快写慢；后者写增量日志、写快但读时需合并，按读写比例权衡。

**要点：**

1. **共同能力**：三者都通过元数据在湖文件之上增加 ACID、时间旅行、schema 演进与 upsert/delete。
2. **Iceberg**：引擎无关的快照 + 隐藏/可演进分区。
3. **Delta**：事务日志、深度 Spark/Databricks 集成、MERGE/OPTIMIZE/Z-order。
4. **Hudi**：upsert 优先、Copy-on-Write vs Merge-on-Read，擅长 CDC/增量。

### 32. Hive 分区 vs 分桶

**频率：** 中

**题目：** Hive 中分区（partitioning）与分桶（bucketing）有何区别？动态分区有哪些坑？

**方案：**

1. **分区**：按列值把表拆成目录（如 `/date=2026-08-12/`），因此按该列过滤的查询能裁剪整个目录、读取远少的数据。它只适用于 **低基数** 列；对高基数列（如用户 ID）分区会造成目录爆炸和小文件问题。
2. **分桶**：则是在每个分区内把某列哈希到固定数量的文件（桶）中。由于相同 key 的行总是落入同一个桶，分桶能实现高效的 **bucket map join**（当两侧以相同方式分桶时无需 shuffle）以及更好的采样——正好适合高基数的 join key。
3. **动态分区坑**：经典的 **动态分区** 坑在于插入数据时分区值来自数据本身：可能一次性创建出无上限数量的分区，每个分区又让每个 task 写一个小文件，导致文件数和内存爆炸。
4. **防护手段**：包括限制分区数量、写入前按分区列进行 cluster/sort，以及选择合理的分区粒度。

**演进：**

1. **全表扫描 → 分区裁剪**：引入分区目录后，按分区列过滤可跳过无关目录，大幅降低 I/O。
2. **高基数困境 → 分桶**：分区对高基数列失效，分桶用固定哈希桶既控制文件数，又支持免 shuffle join 与采样。
3. **静态分区 → 动态分区及其治理**：动态分区便利但易爆炸，演进出限额、写前排序、合理粒度等治理手段。

**面试追问：**

1. **为何分区不适合高基数列**：每个值一个目录会产生海量目录和小文件，元数据与调度开销激增。
2. **bucket map join 的前提**：两表按相同列、相同桶数分桶，才能保证相同 key 落同一桶从而免 shuffle。
3. **如何缓解动态分区小文件**：限制分区数、写前按分区列 cluster/sort、合并小文件、选粗粒度分区。

**要点：**

1. **分区**：每个值一个目录 → 裁剪 I/O；仅适用于低基数列。
2. **分桶**：固定哈希桶 → 对高基数 key 实现免 shuffle join 与采样。
3. **可组合**：按日期分区，在每个分区内按用户 ID 分桶。
4. **动态分区风险**：可能产生过多分区/小文件；限制数量并在写入前排序。

### 33. Z-ordering 与数据跳过

**频率：** 中

**题目：** 什么是 Z-ordering（数据聚簇）？它如何改善文件/数据跳过？

**方案：**

1. **数据跳过原理**：数据跳过依赖每个文件的 min/max 统计：引擎只在文件统计与查询谓词有重叠时才读取该文件。只有当数据在物理上 **聚簇（clustered）** 使每个文件持有较窄的值范围时，跳过才有效。
2. **单列排序的局限**：按单列排序能完美聚簇该列，却让其他列散乱分布，因此按次要列过滤将无法跳过任何文件。
3. **Z-ordering**：是一种多维聚簇技术，它交错多列的比特（一条空间填充的 Z 曲线），使多维空间中相近的值被存储在相邻位置。结果是文件在 **所有** 被 Z-order 的列上同时拥有紧凑的 min/max 范围，因此按其中任一列过滤的查询都能跳过许多文件。
4. **代价与操作**：它是一次重写/compaction 操作（如 Delta 的 `OPTIMIZE ... ZORDER BY`），以写入代价换取显著更快的选择性读取。
5. **适用场景**：它在表被多个不同高基数列查询时表现最佳；若只有单一主导过滤条件，普通排序或分区更简单。

**演进：**

1. **目录分区 → 文件级跳过**：分区只能按分区列裁剪，文件级 min/max 统计把跳过粒度细化到单文件。
2. **单列排序 → 多维聚簇**：单列排序只优化一列，Z-order 交错比特让多列同时拥有紧凑范围。
3. **读代价 → 写时一次性重写换读**：Z-order 是 OPTIMIZE 时的一次性重写，用写入代价换长期的选择性读取加速。

**面试追问：**

1. **Z-order 与分区的取舍**：分区适合低基数主过滤列，Z-order 适合多个高基数维度；二者可配合使用。
2. **何时不值得 Z-order**：只有单一主导过滤条件时，普通排序或分区更简单、代价更低。
3. **min/max 统计失效的情形**：数据未聚簇时每个文件范围都很宽、互相重叠，统计无法排除任何文件。

**要点：**

1. **跳过依赖统计**：文件跳过使用 min/max 统计——只有数据聚簇成较窄的单文件范围时才有效。
2. **多维聚簇**：单列排序只帮一列；Z-order 交错比特以同时聚簇多列。
3. **效果**：使按多个高基数维度中任一列过滤时都能跳过文件。
4. **代价权衡**：这是代价较高的重写（OPTIMIZE/ZORDER）；多列选择性查询值得，单一过滤则过度。

### 34. 大数据压缩编码器

**频率：** 中

**题目：** 请对比 snappy、zstd、gzip 与 lz4 用于大数据存储，以及为什么可切分性（splittability）很重要？

**方案：**

1. **核心权衡**：核心权衡是 **压缩率 vs CPU 速度**，再加上 **可切分性**——即一个压缩文件能否被拆成可独立读取的块，使多个 task 并行处理同一个文件。一个不可切分的压缩文件（如原始 gzip 压缩的 CSV/JSON）会迫使单个 task 读取整份文件，扼杀并行度。
2. **Snappy**：快、压缩率中等；长期以来是 Parquet/ORC 的默认，因为格式本身已提供块级可切分性。
3. **Zstd**：压缩率接近 gzip，速度接近 snappy，且级别可调；越来越成为兼顾存储大小与速度的首选默认。
4. **Gzip**：压缩率高但慢，且自身不可切分——放在列式格式内部尚可，用于大型原始文本文件则很差。
5. **Lz4**：最快、压缩率最低；适合热/临时数据以及 CPU 最重要的 shuffle 场景。
6. **列式格式的可切分性**：注意，列式格式按 page/block 压缩，因此即便是"不可切分"的编码器在 row group 级别仍是可切分的；可切分性主要是原始文本文件才需担心的问题。

**演进：**

1. **高压缩率优先 → 速度优先**：gzip 时代重压缩率，大数据并行化后 snappy/lz4 以速度与可切分性取胜。
2. **单一默认 → 可调折中**：zstd 提供可调级别，让压缩率与速度在同一编码器内灵活折中，逐渐成为新默认。
3. **文本格式 → 列式格式**：列式格式按块压缩天然可切分，把编码器选择从"可切分性"问题简化为"大小/CPU"问题。

**面试追问：**

1. **为什么不可切分会扼杀并行度**：单文件只能由一个 task 读取，无法横向拆分，大输入时并行度崩塌。
2. **shuffle 场景选什么**：选 lz4/snappy 等最快编码器，因为 shuffle 对 CPU 敏感、数据临时。
3. **列式内部还需关心可切分性吗**：基本不需要，row group/block 级别已可切分，编码器主要影响大小与 CPU。

**要点：**

1. **权衡维度**：压缩率 vs CPU 速度，再加上并行读取所需的可切分性。
2. **各编码器定位**：Snappy = 快速默认；zstd = 综合最佳（压缩率与速度俱佳、可调）；gzip = 高压缩率但慢/不可切分；lz4 = 最快、压缩率低。
3. **原始文本风险**：原始 gzip/文本不可切分 → 每文件一个 task；大输入应避免。
4. **列式格式**：按块压缩，因此编码器选择主要影响大小/CPU，而非可切分性。

### 35. Kafka 消费者组再平衡与分区分配策略

**频率：** 高

**题目：** Kafka 中消费者组的再平衡（rebalance）是如何工作的？range、round-robin、sticky 和 cooperative 这几种分配器有何区别？

**方案：**

1. **再平衡触发**：一个消费者组会把某个 topic 的分区分摊给各个成员，使每个分区恰好由一个消费者拥有。当成员关系发生变化时——有消费者加入、离开，或被判定为已失效（错过 `session.timeout.ms` 内的心跳，或超过 `max.poll.interval.ms`）——组协调器（coordinator）会触发一次**再平衡**来重新分配分区。分配逻辑通过可插拔的 `partition.assignment.strategy` 在客户端运行。
2. **Range**：按每个 topic 分配连续的分区区间；实现简单，但当分区数不能整除成员数时负载会倾斜。
3. **RoundRobin**：把所有分区均匀地打散到各成员，均衡性更好，但每次再平衡都会重新洗牌所有权。
4. **Sticky**：在保持均衡的同时尽量保留原有分配，从而把变动降到最低。
5. **Cooperative**（增量式）：是关键演进：不同于旧的"停止一切（stop-the-world）"急切协议中所有人先放弃全部分区，它只放弃必须迁移的分区，因此不受影响的消费者可以继续处理。
6. **核心权衡**：其权衡在于扩缩容时的稳定性与可用性，与分配逻辑的简单性之间。

**演进：**

1. **Range → RoundRobin**：从按 topic 连续分配（易倾斜）演进到全局打散，换取更好的负载均衡。
2. **急切式 → Sticky**：Sticky 在均衡基础上尽量保留原分配，减少不必要的分区迁移。
3. **停止一切 → Cooperative 增量**：Cooperative 只放弃需迁移的分区，避免全局暂停，保障扩缩容时的可用性。

**面试追问：**

1. **如何减少无谓再平衡**：调好 `session.timeout.ms`、心跳间隔与 `max.poll.interval.ms`，避免处理慢被误判失效。
2. **急切与增量的区别**：急切式所有成员先放弃全部分区再重分，增量式只迁移必要分区、其余继续处理。
3. **分配在哪里计算**：在客户端由 leader 消费者按 `partition.assignment.strategy` 计算，协调器负责协调。

**要点：**

1. **再平衡机制**：成员变化时协调器重新分配分区；分配在客户端计算。
2. **急切 vs 最小迁移**：Range/round-robin 是急切式（停止一切）；sticky/cooperative 把迁移量降到最低。
3. **Cooperative 优势**：增量再平衡避免全局暂停——只放弃需要迁移的分区。
4. **参数调优**：调好 `session.timeout.ms`、心跳与 `max.poll.interval.ms` 以避免无谓的再平衡。

### 36. Kafka 持久性：acks、ISR 与 min.insync.replicas

**频率：** 高

**题目：** acks、ISR 与 min.insync.replicas 是如何共同控制 Kafka 的持久性/吞吐量权衡的？

**方案：**

1. **ISR 基础**：Kafka 会把每个分区复制到一个 leader 加若干 follower 上；那些跟上进度的 follower 组成**同步副本集（ISR，in-sync replica set）**。生产者的 `acks` 设置决定何时确认一次写入。
2. **acks=0**：发完即忘——吞吐量最高，但没有持久性保证（若 leader 在落盘前故障则数据丢失）。
3. **acks=1**：仅 leader 确认——很快，但若 leader 在复制前崩溃会丢掉最近的写入。
4. **acks=all**：leader 等待每一个 ISR 成员都完成复制——持久性最强。
5. **min.insync.replicas**：单靠 `acks=all` 还不够：如果 ISR 已缩减到只剩 leader，一次确认仍然只意味着一份副本。**min.insync.replicas** 设定了底线——当 `min.insync.replicas=2` 且 `acks=all` 时，除非至少两个副本处于同步状态，否则写入会失败（NotEnoughReplicas），从而保证存在一份可幸存的副本。
6. **代价权衡**：其权衡在于：更高的持久性会增加复制延迟并降低可用性（副本落后时写入被拒），因此你要按 topic 根据能容忍多少数据丢失来调优。

**演进：**

1. **acks=0/1 → acks=all**：从只求吞吐、容忍丢失，演进到等待整个 ISR 确认以获得最强持久性。
2. **acks=all → 配合 min.insync.replicas**：发现 ISR 塌缩到只剩 leader 时 acks=all 失去意义，于是引入下限保证可幸存副本数。
3. **持久性 ↔ 可用性折中**：提高持久性会增加延迟、副本落后时拒写，需按 topic 容忍度逐一调优。

**面试追问：**

1. **典型生产配置**：RF=3、`min.insync.replicas=2`、`acks=all`，可容忍一个副本故障仍不丢数据。
2. **谁能当选 leader**：在禁用非干净选举（unclean leader election）的前提下，只有 ISR 成员能成为 leader。
3. **ISR 塌缩的后果**：若同步副本不足 min.insync.replicas，写入直接失败（NotEnoughReplicas）而非静默降级。

**要点：**

1. **ISR 定义**：完全跟上 leader 的副本；只有 ISR 成员能成为 leader（在禁用非干净选举的前提下）。
2. **acks 层级**：acks=0/1/all 用吞吐量换持久性；acks=all 等待整个 ISR。
3. **min.insync.replicas**：防止 ISR 塌缩——要与 acks=all 配合（如 RF=3、min.insync=2）。
4. **没有免费午餐**：持久性以延迟和可用性为代价。

### 37. Kafka 日志压缩与保留策略

**频率：** 中

**题目：** 什么是日志压缩（log compaction）？它与按时间/大小保留有何不同？何时应使用压缩 topic？

**方案：**

1. **按时间/大小保留**：Kafka 默认的清理策略是**按时间或大小保留**（`retention.ms`/`retention.bytes`）：超过时限或体积上限的整个日志段会被删除，与内容无关。
2. **日志压缩**：（`cleanup.policy=compact`）则根本不同——它会*为每个 key 至少无限期保留最新的值*，只对被覆盖的旧记录做垃圾回收。后台的清理器会重写日志段，为每个 key 保留最新的一条记录。
3. **墓碑（tombstone）**：一条值为 null 的记录是**墓碑（tombstone）**，用于删除该 key（会保留 `delete.retention.ms` 一段时间，好让消费者能观察到这次删除）。
4. **可重放变更日志**：这就把一个 topic 变成了持久且可重放的变更日志（changelog）：新消费者可以从头读取来重建完整的当前状态。
5. **使用场景**：当你关心的是最新快照而非历史时，就用压缩来保存带 key 的状态——Kafka Streams 状态存储的 changelog、`__consumer_offsets`、CDC/物化缓存，以及配置/查找表。对于每条事件都重要的事件流（日志、指标、点击流），用按时间保留。你也可以两者结合（`compact,delete`）。

**演进：**

1. **按时间/大小删除 → 按 key 保留最新**：保留策略不看内容整段删除，压缩转为按 key 语义保留最新值。
2. **删除表达 → 墓碑机制**：压缩下用 null 值墓碑表达删除，并以 `delete.retention.ms` 保证消费者能观察到。
3. **二选一 → compact,delete 组合**：可同时压缩并设置上限，兼顾状态快照与存储边界。

**面试追问：**

1. **为什么需要墓碑**：压缩只保留最新值，删除必须用显式 null 记录表达，否则 key 永远不被清除。
2. **消费者如何重建状态**：从头重放压缩 topic，每个 key 的最新值即可还原完整当前状态。
3. **压缩 vs 保留如何选**：带 key 的状态快照用压缩，每条事件都重要的事件历史用按时间/大小保留。

**要点：**

1. **两种策略**：保留按时限/大小删除；压缩为每个 key 永久保留最新值。
2. **墓碑**：（null 值）删除某个 key；通过 delete.retention.ms 短暂保留。
3. **用途**：压缩 topic 充当可重放的变更日志，用于状态重建。
4. **选型**：带 key 的快照（Streams 存储、offsets、CDC）用压缩；事件历史用保留。

### 38. Kafka Connect 与基于 Debezium 的 CDC

**频率：** 中

**题目：** Kafka Connect 解决了什么问题？Debezium 又是如何实现变更数据捕获（CDC）的？

**方案：**

1. **Kafka Connect**：是一个在 Kafka 与外部系统之间流式传输数据的框架，无需编写定制的生产者/消费者代码。**Source** 连接器把数据拉入，**sink** 连接器把数据推出；连接器把工作拆分为分布在分布式 worker 集群上的**任务（task）**，Connect 负责 offset 跟踪、重启、扩缩容以及 schema 转换（常借助 Schema Registry）。
2. **Debezium**：是一套用于**变更数据捕获（Change Data Capture）**的 source 连接器——捕获数据库中每一次行级的插入/更新/删除，并把它作为事件流发出。
3. **读事务日志**：关键在于，它读取数据库的**事务日志**（MySQL binlog、Postgres WAL 逻辑复制、Mongo oplog），而不是轮询表，因此能以低开销、按提交顺序捕获变更，且不会漏掉删除。
4. **快照 + 流式**：它会先对现有数据做一次初始**快照（snapshot）**，随后流式输出增量变更；每个事件都携带变更前/后的镜像以及元数据。
5. **下游应用**：由于输出进入 Kafka（通常是压缩的）topic，CDC 便成为复制、缓存失效、搜索索引以及用于可靠事件驱动集成的 outbox 模式的骨干。

**演进：**

1. **定制生产消费 → Connect 框架**：从手写集成代码演进到可复用框架，内建任务、offset、重启与扩缩容。
2. **轮询表 → 读事务日志**：Debezium 从轮询式 CDC 演进到基于日志（binlog/WAL/oplog），低开销、保序、不漏删除。
3. **全量快照 → 快照 + 增量流**：先快照建立基线，再持续流式增量，支撑复制、缓存失效、搜索索引等。

**面试追问：**

1. **为什么读日志优于轮询**：日志保留提交顺序、开销低、能捕获删除，轮询则漏删除且压力大。
2. **CDC 事件结构**：每个事件含变更前/后镜像与元数据，支持下游还原与审计。
3. **与压缩 topic/outbox 的配合**：输出写入压缩 topic 可作 changelog，outbox 模式借 CDC 实现可靠事件发布。

**要点：**

1. **Connect 定位**：可复用的 source/sink 框架，内建任务、offset 管理与扩缩容。
2. **CDC 与 Debezium**：CDC 捕获行级数据库变更；Debezium 读取事务日志（binlog/WAL），而非轮询。
3. **基于日志的优势**：保留提交顺序、开销低，并能捕获删除。
4. **工作流**：先快照再流式；天然与压缩 topic 及 outbox 模式配合。

### 39. 流处理中的背压

**频率：** 中

**题目：** 什么是流式系统中的背压（backpressure）？各框架是如何处理它的？

**方案：**

1. **背压定义**：当下游算子无法以上游阶段产出的速度处理记录时，就出现了背压。若没有让 source 减速的机制，缓冲区会无界地增长，作业要么内存耗尽，要么丢数据。健康的应对方式是把这种减速一路向上游传播，直达 source，使摄入被节流到真正可持续的速率。
2. **Flink**：通过有界的网络缓冲区和基于信用（credit）的流控天然地做到这一点：慢速消费者停止授予缓冲信用，从而阻塞生产者的写入，压力级联式地回传到 source 连接器（如 Kafka），后者只是减少轮询频率——offset 仍然正确地推进。
3. **Spark Structured Streaming**：则使用反应式限速（`maxOffsetsPerTrigger` / 自适应背压）来限制每个微批的摄入量。
4. **朴素推送系统对比**：关键对比在于一个没有任何流控的朴素推送系统——它只能缓冲、溢写或丢弃。
5. **观测与兜底**：观察背压指标是定位瓶颈算子的标准手段。在无法让 source 减速的场景下，负载丢弃（load shedding）是兜底方案。

**演进：**

1. **无界缓冲 → 向上游传播**：朴素系统靠缓冲/溢写/丢弃应对，演进到把减速传播到 source 的流控模型。
2. **Flink 的信用流控**：有界缓冲区 + 基于信用的流控天然节流 Kafka source，offset 仍正确推进。
3. **Spark 的微批限速**：用 `maxOffsetsPerTrigger`/自适应背压从每个微批层面限制摄入量。

**面试追问：**

1. **背压为何必须传到 source**：否则缓冲无界增长，最终 OOM 或丢数据，只有节流摄入才可持续。
2. **Flink 与 Spark 的处理差异**：Flink 靠连续的信用流控阻塞上游，Spark 在微批边界限制摄入条数。
3. **无法让 source 减速怎么办**：采用负载丢弃（load shedding）作为最后手段，主动丢弃部分负载保作业存活。

**要点：**

1. **定义**：背压 = 下游比上游慢；必须传播到 source，而不能无限缓冲。
2. **Flink**：用有界缓冲区 + 基于信用的流控，天然地节流 Kafka source。
3. **Spark**：按微批限制摄入量（maxOffsetsPerTrigger / 自适应背压）。
4. **观测与兜底**：背压指标可精确定位瓶颈；负载丢弃是最后手段。

### 40. 事件时间处理中的 watermark 与允许延迟

**频率：** 高

**题目：** watermark、允许延迟（allowed lateness）与侧输出（side output）是如何协同处理乱序及迟到的事件时间数据的？

**方案：**

1. **事件时间与乱序**：在事件时间处理中，每条记录都携带自己的时间戳，但记录会乱序到达，因此引擎需要一个"我们在事件时间上推进到哪了"的概念。
2. **Watermark**：就是这个信号：一个时间为 T 的 watermark 断言（大概率）不会再有时间戳 ≤ T 的事件到达，这让引擎能够触发事件时间窗口和定时器。Watermark 生成时带有一个有界乱序（bounded-out-of-orderness）延迟——延迟越大越能容忍乱序，但也提高了延迟，因此这是核心的延迟/完整性权衡。当 watermark 越过某个窗口的结束时间时，该窗口触发。
3. **允许延迟**：会在窗口触发后额外保留一段宽限期的窗口状态：在此期间迟到但仍在期限内的事件会再次触发并更新（已发出的）结果。
4. **侧输出**：晚于 watermark + 允许延迟的事件才是真正迟到的；它们不会被悄悄丢弃，而可以被路由到**侧输出**（一条单独的流），用于记录、对账或走慢速路径进行修正。
5. **可调谱系**：这就提供了一条从低延迟到完全完整、可显式调节的谱系。

**演进：**

1. **处理时间 → 事件时间 + watermark**：从以处理时间近似，演进到按记录自带时间戳 + watermark 推进事件时间。
2. **一次触发 → 允许延迟重触发**：窗口不止触发一次，宽限期内迟到事件可再次触发并更新结果。
3. **静默丢弃 → 侧输出**：超期事件不再被悄悄丢弃，而路由到侧输出供记录、对账或慢路径修正。

**面试追问：**

1. **延迟与完整性如何权衡**：有界乱序延迟越大越能容忍乱序、结果越完整，但端到端延迟越高。
2. **允许延迟与 watermark 的关系**：窗口在 watermark 越过结束时间时触发，允许延迟额外保留状态以处理期限内迟到。
3. **真正迟到的事件去哪**：晚于 watermark + 允许延迟者进入侧输出，可做日志、对账或修正，而非丢弃。

**要点：**

1. **Watermark**：表示"事件时间已推进到 T"；即便乱序到达也能驱动窗口/定时器触发。
2. **有界乱序延迟**：在延迟与对乱序的容忍度之间做权衡。
3. **允许延迟**：在窗口触发后于宽限期内为迟到事件重新触发窗口。
4. **侧输出**：超过 watermark + 允许延迟的数据进入侧输出，而不是被悄悄丢弃。

### 41. Flink 中的状态后端与 RocksDB

**频率：** 中

**题目：** Flink 有哪些状态后端（state backend）？为什么大规模 keyed state 与增量检查点会用 RocksDB？

**方案：**

1. **keyed state**：Flink 算子会保存必须在故障后存活的 **keyed state**（按 key 分区：value/list/map 状态、聚合、窗口内容）。**状态后端**决定工作状态存放在何处以及检查点如何存储。
2. **HashMapStateBackend**：把状态以 Java 对象形式放在 JVM 堆上——访问最快，但受堆大小限制且易受 GC 压力影响，因此适合小规模状态。
3. **EmbeddedRocksDBStateBackend**：把状态存放在每个 task manager 上一个内嵌的 RocksDB 实例（磁盘上的 LSM 树）中，因此状态可以远超内存并溢写到本地磁盘；访问需付出序列化加磁盘的代价，但能扩展到 TB 级。
4. **增量检查点（incremental checkpoints）**：它的决定性优势——因为 RocksDB 是由不可变 SST 文件构成的 LSM 树，一次检查点只上传自上次以来发生变化的 SST 文件，而非整份状态，对于大规模、缓慢变化的状态可大幅缩小检查点体积与耗时。
5. **权衡**：每次访问的序列化开销与调优（block cache、write buffer、compaction），对比在堆上状态的原始速度。

**演进：**

1. **小状态起步**：状态规模小时用 HashMapStateBackend，堆上对象访问最快。
2. **扩展到 TB 级**：状态超过内存时迁移到 EmbeddedRocksDBStateBackend，溢写本地磁盘。
3. **优化检查点**：大规模、缓慢变化的状态启用增量检查点，只上传变化的 SST 文件。

**面试追问：**

1. **增量检查点原理**：为什么 LSM 树的不可变 SST 文件能支撑只上传变化部分？
2. **调优项**：RocksDB 后端如何调 block cache、write buffer 与 compaction？
3. **选型判断**：什么规模下应从 HashMapStateBackend 切换到 RocksDB？

**要点：**

1. **Keyed state**：按 key 分区；状态后端决定它存放在哪以及如何做快照。
2. **HashMapStateBackend**：堆上对象，最快但受堆限制（小状态）。
3. **RocksDB 后端**：磁盘上的 LSM，状态可超过内存，但要付序列化代价。
4. **增量检查点**：只上传变化的 SST 文件——这是大状态选择 RocksDB 的关键原因。

### 42. Flink 中的检查点与保存点

**频率：** 中

**题目：** Flink 中检查点（checkpoint）与保存点（savepoint）有何区别？保存点又如何支撑升级与重新伸缩？

**方案：**

1. **共同点**：两者都是作业分布式状态的一致性快照，但用途不同。
2. **检查点**：Flink 为容错而自动、周期性拍下的快照：故障时作业从最新的检查点重启并以 exactly-once 恢复。它们被优化得廉价且频繁（配合 RocksDB 常为增量式），由系统所有，且通常在作业终止时被丢弃——它们并非为长期可移植而设计。
3. **保存点**：手动触发、自包含的快照，采用稳定、规范的格式，意在持久且可移植。由于保存点使用格式稳定、带算子 ID 的布局，你可以停止一个作业、部署新代码，再从保存点重启——从而实现零数据丢失的**应用升级**、Flink 版本迁移以及 A/B 变更。
4. **重新伸缩（rescaling，改变并行度）**：保存点还携带**最大并行度 / key group** 元数据，因此状态可以在不同数量的子任务间重新分布。
5. **经验法则**：检查点让运行中的作业存活，保存点让你有意地演进它。为算子显式指定 UID 至关重要，这样代码变更后状态才能正确映射。

**演进：**

1. **容错先行**：先用检查点保证运行中作业能从故障以 exactly-once 恢复。
2. **有计划运维**：需要升级代码/迁移版本时，手动触发保存点并从中重启。
3. **弹性伸缩**：借助 key group 元数据，从保存点在不同并行度间重新分布状态。

**面试追问：**

1. **UID 的作用**：为什么不指定算子 UID 会导致升级后状态丢失？
2. **格式差异**：保存点的规范格式与检查点格式有何不同，为何更可移植？
3. **增量与可移植**：增量检查点能否当作保存点用于跨版本迁移？

**要点：**

1. **检查点**：自动、频繁、系统所有，用于恢复；关停时常被丢弃。
2. **保存点**：手动、可移植、格式稳定，用于有计划的运维操作。
3. **支撑能力**：保存点通过 key group 重新分布支撑代码升级、Flink 版本迁移与重新伸缩。
4. **UID**：为算子指定稳定的 UID，使状态在变更后能正确恢复。

### 43. 缓慢变化维（SCD 各类型）

**频率：** 高

**题目：** 什么是缓慢变化维？如何实现 SCD 的 1、2、3、6 型？

**方案：**

1. **概念**：SCD 描述维度表如何处理属性随时间的变化（例如客户搬到别的城市）。选择哪种类型决定了历史是否被保留。
2. **Type 1**：就地覆盖旧值——不保留历史，最简单，适用于变化只是纠错、过去的值无关紧要时。
3. **Type 2**：每次变化新增一行并保留旧行，用**代理键（surrogate key）**外加 `effective_date`、`end_date` 和 `is_current` 标志来追踪。它是保留完整历史的主力方案，但会让表膨胀，且事实表必须关联到事件发生时刻有效的那个代理键。
4. **Type 3**：增加一列（如 `previous_city`）只保留上一个值——历史有限，只能回退一步。
5. **Type 6**（「1+2+3」）：把三者结合：既有保留历史的 Type 2 行，又有一列在所有行上都更新的「当前」属性（Type 1 行为），这样你既能按事件当时的值报表，也能按今天的值报表。
6. **实现方式**：用 MERGE/upsert：让当前行过期，再插入一个新版本。

**演进：**

1. **只需当前值**：用 Type 1 直接覆盖，最简单无历史。
2. **需要完整历史**：升级到 Type 2，用代理键和 effective/end 日期版本化。
3. **兼顾历史与当前**：用 Type 6 把 Type 2 行与一列维护的「当前」属性结合。

**面试追问：**

1. **代理键必要性**：为什么 Type 2 必须用代理键而非业务主键？
2. **事实表关联**：事实表如何关联到事件发生时刻有效的那个版本？
3. **表膨胀治理**：Type 2 导致表膨胀时有哪些缓解手段？

**要点：**

1. **Type 1/Type 2**：Type 1 = 覆盖、无历史；Type 2 = 新增带 effective/end 日期 + 当前标志的版本化行。
2. **Type 3/Type 6**：Type 3 = 用额外一列保留一个旧值；Type 6 = Type 2 行加一列维护的「当前」列。
3. **代理键**：Type 2 需要代理键，让事实表指向事件当时有效的版本。
4. **实现**：用 MERGE 实现：关闭旧行、插入新行；注意表膨胀。

### 44. 事实表类型

**频率：** 高

**题目：** 事务型、周期快照、累积快照事实表分别是什么？各在什么时候用？

**方案：**

1. **总览**：三种事实表粒度建模不同的度量模式。
2. **事务型事实表**：在事件发生的那一刻每个原子事件记录一行（一笔销售、一次点击）。它粒度最细、最灵活，在大多数维度上可加，但可能变得极其庞大，且难以回答「某个时间点的状态」。
3. **周期快照事实表**：按固定间隔采集度量——每个实体每天/每周/每月一行（如每日账户余额、在库库存）。它能廉价地回答趋势问题、大小可预测，但度量常常是**半可加的**（余额不能跨时间求和，只能取平均或期末值）。
4. **累积快照事实表**：建模一个有明确生命周期和多个里程碑的流程——每个实例一行（如一个订单），随其流经各阶段而**就地更新**，包含多个日期列和它们之间的时延度量。它非常适合流程/时延分析，但需要更新，不像事务粒度那样只追加。

**演进：**

1. **捕获原子事件**：先用事务型事实表记录最细粒度的每个事件。
2. **回答趋势问题**：再加周期快照事实表按固定间隔采集度量。
3. **分析流程时延**：对有生命周期的流程用累积快照事实表，就地更新里程碑日期。

**面试追问：**

1. **半可加度量**：为什么余额这类度量不能跨时间求和，如何正确聚合？
2. **粒度选择**：如何让事实表粒度匹配要回答的业务问题？
3. **更新 vs 追加**：累积快照需要更新会带来哪些工程代价？

**要点：**

1. **事务型**：每个事件一行，粒度最细、可加、量巨大、无时点状态。
2. **周期快照**：每个实体每周期一行；擅长趋势；度量常为半可加。
3. **累积快照**：每个流程实例一行可更新，含里程碑日期与时延。
4. **原则**：让粒度匹配问题；累积快照是更新的，不是只追加的。

### 45. ETL vs ELT

**频率：** 高

**题目：** ETL 与 ELT 有何区别？为什么 ELT 随云数仓兴起？

**方案：**

1. **ETL**（Extract, Transform, Load）：在把数据加载进数仓*之前*，先在一个独立的处理层里做转换，因此只有清洗、建模后的数据落地。
2. **ELT**（Extract, Load, Transform）：先把原始数据加载进数仓，然后利用数仓自身的 SQL 引擎*就地*转换。
3. **ELT 兴起原因**：云数仓（Snowflake、BigQuery、Redshift）提供廉价、弹性、存算分离的存储和可大规模扩展的算力，因此把转换下推到数据已经所在的位置（push-down）非常高效。
4. **ELT 好处**：原始数据被保留，需求变化时可以重新转换而无需重新抽取；转换变成版本化的 SQL（如 dbt），分析师可以自己负责，提升敏捷性和可测试性；加载与转换在托管算力上独立扩展。
5. **ETL 仍更优的场景**：当你必须在数据落地*之前*就清洗/脱敏（合规、PII）、数据源需要大量非 SQL 处理、或存储原始数据代价高昂或被禁止时。

**演进：**

1. **传统处理层**：早期用 ETL 在独立处理层转换后再落地干净数据。
2. **云数仓下推**：云存算分离后转向 ELT，把转换下推到数仓内用 SQL 执行。
3. **版本化 SQL**：进一步用 dbt 把转换变成版本化、可测试、分析师可自助的 SQL。

**面试追问：**

1. **下推效率**：为什么存算分离让下推转换（push-down）更高效？
2. **合规约束**：PII/合规要求如何迫使你保留 ETL 的落地前清洗？
3. **原始数据价值**：保留原始数据对需求变更带来哪些具体好处？

**要点：**

1. **顺序差异**：ETL 先转换后加载（落地即干净数据）；ELT 先加载原始数据，再在数仓内用 SQL 转换。
2. **兴起动因**：ELT 随廉价弹性的云存储/算力和下推转换而兴起。
3. **ELT 优势**：保留原始数据、支持版本化 SQL（dbt），并让加载/转换独立扩展。
4. **ETL 适用**：当必须落地前脱敏/清洗或需要非 SQL 处理时优先选 ETL。

### 46. MPP 与交互式查询引擎

**频率：** 中

**题目：** Presto/Trino、Impala、Hive-on-Tez 在架构上有何不同？各在什么时候用？

**方案：**

1. **总览**：三者都在数据湖存储上跑 SQL，但执行模型不同。
2. **Presto/Trino**：分布式 MPP 引擎，由一个协调器加多个 worker 组成，采用**全内存、流水线化**的执行模型——对交互式/即席查询非常快，且擅长跨多种数据源的**联邦查询**（Hive、MySQL、Kafka、S3）。因为它偏好内存，超大批量 join 若不精心调优可能失败。
3. **Impala**：也是 MPP、面向内存，用与数据节点同机部署的常驻 C++ 守护进程，为 Hadoop/HDFS 栈提供低延迟 BI；它与该生态紧耦合。
4. **Hive-on-Tez**：把 SQL 编译成运行在 YARN 上的任务 DAG——它会溢写到磁盘，专为**大规模、容错的批量 ETL** 而生，这类场景下海量数据上的吞吐和可靠性比亚秒级延迟更重要。
5. **选型速查**：交互式/即席 + 联邦 → Trino；Hadoop 上的低延迟 BI → Impala；重型、有韧性的批量 ETL → Hive-on-Tez。

**演进：**

1. **批量 ETL 起步**：重型、容错批处理用 Hive-on-Tez，溢写磁盘保吞吐与可靠。
2. **低延迟 BI**：在 Hadoop/HDFS 栈上用 Impala 提供亚秒级 BI。
3. **交互式联邦**：需要即席查询和跨源联邦时引入 Trino/Presto 的内存流水线 MPP。

**面试追问：**

1. **内存失败**：Trino 超大批量 join 为什么可能失败，如何调优规避？
2. **紧耦合代价**：Impala 与 Hadoop/HDFS 紧耦合带来哪些限制？
3. **延迟 vs 韧性**：如何在延迟和批处理韧性之间权衡选引擎？

**要点：**

1. **Trino/Presto**：内存流水线 MPP，擅长交互式查询和跨源联邦。
2. **Impala**：数据节点上的 MPP C++ 守护进程，低延迟 BI，与 Hadoop/HDFS 紧耦合。
3. **Hive-on-Tez**：YARN 上的 DAG，溢写磁盘，为大规模容错批量 ETL 而生。
4. **选择依据**：按延迟 vs 批处理韧性、以及是否需要联邦来选择。

### 47. 用 Airflow 做工作流编排

**频率：** 高

**题目：** Airflow 如何编排数据管道？是什么让任务能安全地调度和回填？

**方案：**

1. **DAG**：Airflow 把管道定义为 **DAG**——带依赖的有向无环任务图，用 Python 编写，由调度器通过 operator/executor 运行。
2. **逻辑/执行日期（logical/execution date）**：每次 DAG 运行都以一个逻辑/执行日期为键，代表所处理的数据区间，这是正确性的基础。
3. **幂等任务**：在重跑时产生相同结果（如写入确定性分区、覆盖而非追加、使用 MERGE），这样重试和重跑不会重复数据。
4. **回填（Backfill）**：通过为过去的日期运行 DAG 来重放历史区间；只有当任务幂等、且以执行日期而非 `now()` 参数化时才能干净地工作。
5. **常见陷阱**：混淆执行日期与挂钟时间——「某天」的运行是在那天结束时触发的；非幂等的追加在重试时重复计数；任务间存在隐藏依赖/共享状态，而非通过 XCom 或存储传递数据；过多的 catchup/并发导致运行重叠和资源争抢。

**演进：**

1. **定义任务图**：先用 Python 把管道建成带依赖的 DAG。
2. **保证幂等**：把任务改造为确定性分区、覆盖/MERGE，让重试安全。
3. **启用回填**：以执行日期（而非 now()）参数化，使历史区间可干净重放。

**面试追问：**

1. **执行日期语义**：为什么「某天」的运行在那天结束时才触发？
2. **幂等实现**：确定性分区、覆盖、MERGE 分别如何保证幂等？
3. **XCom vs 共享状态**：任务间传数据为何优先用 XCom 而非隐藏共享状态？

**要点：**

1. **DAG**：Python 定义的任务图；运行以逻辑/执行日期（数据区间）为键。
2. **幂等任务**：确定性分区、覆盖/MERGE 让重试和重跑安全。
3. **回填**：重放过去区间——只有任务以执行日期（而非 now()）为键时才正确。
4. **陷阱**：执行 vs 挂钟时间混淆、非幂等追加、隐藏状态、catchup 争抢。

### 48. 数据质量、血缘与治理

**频率：** 中

**题目：** 数据质量校验、血缘与数据目录如何在数据治理中协同工作？

**方案：**

1. **背景**：随着管道增多，信任成为瓶颈，三项能力来应对它。
2. **数据质量**：强制执行校验规则——非空、唯一性、取值范围、参照完整性、新鲜度、行数异常——用 Great Expectations 或 dbt tests 等工具，最好作为闸门在坏数据扩散前让管道失败。
3. **血缘（Lineage）**：追踪数据在表与作业之间的列到列流动，让你能做**影响分析**（改这一列会破坏什么）和**根因分析**（哪个上游源污染了某个指标）。
4. **数据目录**：可搜索的数据集清单，含 schema、负责人、描述、分类（如 PII）和热度，让人们无需靠口口相传就能发现和理解数据。
5. **三者协同**：共同构成治理：目录回答*有什么、谁负责*，血缘回答*来自哪里、什么依赖它*，质量回答*能否信任它*——再辅以访问、保留和分类策略。

**演进：**

1. **先建校验闸门**：用数据质量规则在坏数据扩散前让管道失败。
2. **再追血缘**：补上列级血缘以支撑影响分析和根因排查。
3. **最后建目录与策略**：加上可搜索目录及访问/保留/分类策略，形成完整治理。

**面试追问：**

1. **闸门时机**：数据质量校验为何应作为管道闸门而非事后检查？
2. **列级血缘价值**：列到列血缘对根因分析具体如何帮助？
3. **目录分类**：目录如何标注 PII 等分类并与治理策略联动？

**要点：**

1. **数据质量**：自动化校验闸门（非空、唯一、范围、新鲜度），用 GE/dbt tests。
2. **血缘**：列级流动，支撑影响分析和根因排查。
3. **目录**：可搜索清单，含 schema、负责人、描述和分类。
4. **治理**：把三者加上访问/保留/分类策略结合起来，使数据可信。

### 49. 宽列存储：HBase 与 Cassandra

**频率：** 中

**题目：** HBase 和 Cassandra 的宽列数据模型是什么？什么时候用它而非数仓？

**方案：**

1. **数据模型**：宽列存储把数据组织为一个分布式、有序的映射：行以**行/分区键**为键，归入**列族（column family）**，每行可以持有不同的、稀疏的列。
2. **优化目标**：它们为**大规模写入吞吐和按键的低延迟查找**而生，而非即席分析。
3. **HBase**：偏 CP，构建在 HDFS 上，含一个 master 和多个 region server，提供强一致性并与 Hadoop 紧密集成。
4. **Cassandra**：偏 AP、无主——一个点对点的环，具备可调一致性且无单点故障，非常适合多区域、永远在线的写入。
5. **查询驱动建模**：因为没有灵活的 join 或任意过滤，你要围绕确切的访问模式来塑造表（和分区键）。用它们做运营型服务——时间序列、IoT、消息、用户画像、会话/特征存储。当你需要对历史数据做复杂即席 SQL、join 和聚合来做分析时，则改用**数仓**。
6. **选型速查**：HBase → 强一致性、Hadoop 生态；Cassandra → 高可用、多区域写入、可调一致性。

**演进：**

1. **确定访问模式**：先围绕确切的按键查询塑造表和分区键。
2. **按一致性需求选型**：强一致/Hadoop 生态选 HBase，高可用/多区域写入选 Cassandra。
3. **分析需求回数仓**：需要复杂即席 SQL、join、聚合时改用数仓。

**面试追问：**

1. **CP vs AP**：HBase 与 Cassandra 在 CAP 取舍上的根本差异是什么？
2. **分区键设计**：分区键选得不好会导致什么问题（如热点）？
3. **为何不能即席分析**：无 join/任意过滤对分析型查询意味着什么？

**要点：**

1. **数据模型**：分区键 + 列族，每行稀疏、宽列；一个分布式有序映射。
2. **优化目标**：为高写入吞吐和低延迟按键查找优化，而非即席分析。
3. **HBase/Cassandra**：HBase = HDFS 上的 CP/强一致；Cassandra = 无主 AP，一致性可调。
4. **建模原则**：围绕查询建表（无 join）；复杂分析型 SQL 用数仓。

### 50. 在数据湖中处理 PII 与 GDPR

**频率：** 中

**题目：** 如何在数据湖中处理 PII 与 GDPR 要求？

**方案：**

1. **设计原则**：数据湖会长期保留原始数据，因此对个人数据的保护必须在设计之初就纳入，而非事后附加。分层部署多重控制。
2. **加密**：静态加密（如 KMS 管理的 S3/HDFS 加密）和传输中加密，让原始存储永远不是明文。
3. **脱敏/令牌化/假名化**：让大多数使用者只看到哈希或令牌化的标识符，重识别仅限授权角色；列级访问控制和动态脱敏落实最小权限。
4. **被遗忘权（擦除）**：对象存储中不可变的列式文件无法更新单行，因此要用支持行级 DELETE/MERGE 的湖仓表格式（Delta/Iceberg/Hudi），或用**加密粉碎（crypto-shredding）**——用每个主体独立的密钥加密其数据，删除密钥即让数据不可恢复。
5. **按租户/区域分区**：让某租户或某区域的数据物理隔离，从而简化删除、满足**数据驻留（data-residency）**规则并限制影响范围。
6. **治理包裹**：再用一个能**分类** PII 的目录、追踪个人数据扩散的血缘、保留策略以及访问审计日志把这些包裹起来——治理才是让合规可被证明的关键。

**演进：**

1. **加密打底**：先对静态和传输中的数据加密，确保原始存储不是明文。
2. **脱敏限权**：再对使用者脱敏/令牌化，用列级访问控制落实最小权限。
3. **可删除与可证明**：引入行级 DELETE/MERGE 或加密粉碎支撑被遗忘权，并加分类/血缘/审计让合规可证明。

**面试追问：**

1. **crypto-shredding**：为什么删除每主体密钥能替代单行删除实现擦除？
2. **不可变文件删除**：列式不可变文件为何需要 Delta/Iceberg/Hudi 才能行级删除？
3. **数据驻留**：按区域分区如何同时满足数据驻留与限制影响范围？

**要点：**

1. **加密与脱敏**：静态和传输中都加密；脱敏/令牌化让大多数使用者永不接触原始 PII。
2. **被遗忘权**：湖仓行级 DELETE/MERGE 或加密粉碎（删除每主体密钥）。
3. **分区隔离**：按租户/区域分区以实现隔离、数据驻留和更易删除。
4. **治理证明**：加上分类、血缘、保留和审计日志，让合规可被证明。

### 51. Spark SQL 执行：RDD vs DataFrame vs Dataset

**频率：** 高

**题目：** Spark SQL 如何执行一条查询？RDD、DataFrame、Dataset 三套 API 之间有哪些取舍？

**方案：**

1. **执行流水线**：一条 Spark SQL 查询（SQL 字符串或 DataFrame 调用）先被解析为**未解析的逻辑计划**，对着 catalog 解析后，由 **Catalyst** 优化器改写（谓词/投影下推、常量折叠、连接重排）成优化后的逻辑计划，最后下沉为多个**物理计划**并按代价选一个。

2. **代码生成**：随后 **Tungsten** 生成整段（whole-stage）字节码，直接在堆外二进制行上运算。你用哪套 API 决定了能吃到多少这套优化。

3. **RDD**：任意 JVM 对象和 lambda；控制力最强，但对 Catalyst *不透明*，因此没有下推、没有列式/堆外编码，序列化开销全额承担。

4. **DataFrame**：带 schema 的 `Dataset[Row]`；被 Catalyst/Tungsten 充分优化，做关系型工作最快，但无类型（错误在运行时才暴露）。

5. **Dataset[T]**：带 encoder 的强类型、编译期安全的 JVM 对象；比 DataFrame 更安全，但带类型的 lambda 会变成黑盒，阻断部分优化并增加(反)序列化开销。

6. **选型原则**：优先用 DataFrame/Dataset；只有在关系模型表达不了、需要底层控制时才降到 RDD。

**演进：**

1. **RDD 时代**：最初只有 RDD，提供最大控制力，但对优化器完全不透明，序列化和缺乏下推成为瓶颈。

2. **DataFrame 引入**：加上 schema 后被 Catalyst/Tungsten 充分优化，关系型工作最快，但失去编译期类型安全。

3. **Dataset 融合**：带 encoder 的强类型 API 兼顾安全与优化，但带类型的 lambda 仍会退化为黑盒。

**面试追问：**

1. **为什么 RDD 吃不到下推**：因为 Catalyst 看不透任意 JVM lambda，无法分析其语义，所以无下推、无列式编码。

2. **DataFrame 的代价**：无类型，错误在运行时才暴露；Dataset 的带类型 lambda 会变黑盒阻断优化。

3. **何时降到 RDD**：仅当关系模型表达不了、需要对象级底层控制时。

**要点：**

1. **流程**：解析 → 解析引用 → Catalyst 逻辑优化 → 基于代价选物理计划 → Tungsten 代码生成。

2. **RDD 不透明**：RDD 对 Catalyst 不透明——无下推、无列式编码、序列化开销高。

3. **类型与优化权衡**：DataFrame = 已优化但无类型；Dataset = 有类型但带类型的 lambda 会阻断优化。

4. **默认选型**：默认用 DataFrame/Dataset；只在真正需要对象级控制时才用 RDD。

### 52. Bucketing 与免 shuffle 的分桶连接

**频率：** 中

**题目：** Spark 中的 bucketing 是什么？它如何实现一个不需要 shuffle 的连接？

**方案：**

1. **定义**：Bucketing 按 `hash(bucketColumn) % numBuckets` 把表预先分成**固定数量的桶**，每个桶持久化为一组文件，布局记录在 metastore 中。

2. **免 shuffle 连接**：因为相同 key 的行总落在同一个桶里，两张**在同一列上、分成相同桶数**的表可以桶对桶地在本地完成连接——sort-merge join 通常需要的 exchange（shuffle）被消除了，这在两表都大到无法广播时正是意义所在。

3. **与 partitioning 区别**：partitioning 按低基数列建目录做粗粒度的*裁剪*，而 bucketing 按高基数的连接/聚合 key 控制*文件分布*。

4. **注意事项**：桶数必须匹配（或一方是另一方的倍数，配合 Spark 的 bucket-coalescing），需启用 spark.sql.sources.bucketing，且桶数的选择是一种承诺——桶太少任务过大，桶太多会造成小文件问题，重新分桶则需要重写数据。

**演进：**

1. **普通 sort-merge join**：两表都需 shuffle exchange 把相同 key 对齐到同一分区，大表代价高。

2. **预先 bucketing**：把哈希布局固化到文件并记录于 metastore，相同列同桶数即可桶对桶本地连接，消除 exchange。

3. **bucket-coalescing**：允许一方桶数是另一方的倍数时仍免 shuffle，放宽了桶数必须严格相等的限制。

**面试追问：**

1. **bucketing 和 partitioning 能否共用**：能，partitioning 做目录裁剪，bucketing 在分区内控制文件分布。

2. **桶数选多少**：是一种固定承诺，太少任务过大，太多造成小文件，改动需重写数据。

3. **桶数不匹配会怎样**：无法免 shuffle，退回普通连接，除非满足倍数关系并启用 coalescing。

**要点：**

1. **桶定义**：桶 = 确定性的 `hash(key) % N` 文件布局，记录在 metastore 中。

2. **免 shuffle 条件**：同一列 + 相同桶数 → sort-merge join 无需 shuffle exchange。

3. **与分区对比**：Partitioning 按低基数目录裁剪；bucketing 按高基数 key 分布数据。

4. **主要坑点**：桶数是固定承诺；不匹配、小文件、重写是主要坑点。

### 53. 用于分析的窗口函数

**频率：** 高

**题目：** SQL/Spark 的窗口函数如何工作？PARTITION BY、ORDER BY 和 frame 子句各自控制什么？

**方案：**

1. **核心语义**：窗口函数在**与当前行相关的一组行上计算值，但不折叠这些行**——与 GROUP BY 不同，每一行输入都被保留并得到自己的结果。

2. **PARTITION BY**：把行拆成互相独立的分组（类似 GROUP BY，但不聚合）。

3. **ORDER BY**：在每个分区内排序，排名和偏移函数必需，并定义「之前/之后」。

4. **frame**：（`ROWS`/`RANGE BETWEEN … AND …`）界定哪些有序行参与聚合，用于累计和或移动平均。

5. **函数分类**：函数分为排名类（`ROW_NUMBER`、`RANK`、`DENSE_RANK`、`NTILE`）、偏移类（`LAG`、`LEAD`）和窗口聚合类（`SUM`、`AVG`）。

6. **默认 frame 细节**：有 ORDER BY 但没有显式 frame 时，SQL 默认 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`，而 `RANGE` 会把并列（peer）行绑在一起（相同值 = 相同累计和），`ROWS` 则按物理行数计。

7. **Spark 性能**：在 Spark 中每个不同的窗口规格都会按分区 key 触发一次 shuffle 和排序，因此倾斜或高基数的分区是性能风险。

**演进：**

1. **GROUP BY 聚合**：折叠行只得每组一行结果，无法在保留明细的同时算组内统计。

2. **窗口函数**：在相关行上算出逐行结果而不折叠，支持排名、偏移、累计/移动聚合。

3. **frame 精细化**：从默认 `RANGE UNBOUNDED PRECEDING → CURRENT ROW` 到显式 `ROWS`/`RANGE` 控制并列行与物理行的处理。

**面试追问：**

1. **ROWS 与 RANGE 区别**：ROWS 按物理行数计；RANGE 把相同值的并列行绑在一起得相同累计和。

2. **窗口函数为何慢**：每个窗口规格在 Spark 中强制一次 shuffle+排序，倾斜/高基数分区伤性能。

3. **排名三兄弟区别**：`ROW_NUMBER`、`RANK`、`DENSE_RANK` 在并列时编号策略不同。

**要点：**

1. **逐行不折叠**：窗口在相关行上算出逐行结果而不折叠行（与 GROUP BY 不同）。

2. **三子句职责**：PARTITION BY = 分组；ORDER BY = 排名/偏移所需的排序；frame = 哪些行参与聚合。

3. **默认 frame**：有 ORDER BY 时默认 frame 是 `RANGE UNBOUNDED PRECEDING → CURRENT ROW`；ROWS 与 RANGE 在并列上不同。

4. **性能代价**：每个窗口规格在 Spark 中都强制一次 shuffle+排序；倾斜的分区 key 伤性能。

### 54. 基于代价的优化与表统计信息

**频率：** 中

**题目：** 基于代价的优化如何使用表统计信息？为什么 ANALYZE 和直方图很重要？

**方案：**

1. **CBO 定义**：基于规则的优化套用固定改写，而**基于代价的优化（CBO）**通过估算备选计划的代价来比较它们，而这些估算的好坏完全取决于引擎手里的**统计信息**。

2. **ANALYZE 收集内容**：`ANALYZE TABLE … COMPUTE STATISTICS` 收集表级统计（行数、总大小）和列级统计（distinct 数/NDV、min/max、null 数、平均长度），并可选地收集描述列内取值分布的**直方图**。

3. **估算驱动决策**：CBO 用这些来估算每个算子的**选择率（selectivity）**和输出基数，从而驱动关键决策：**连接重排**（先连接最有选择性/最小的中间结果，缩小下游数据量）、**连接策略选择**（按估算大小在 broadcast、shuffle、sort-merge 之间取舍）以及 build 端的选择。

4. **直方图作用**：直方图之所以重要，是因为均匀分布假设会严重误估倾斜列——等高（equi-height）直方图能刻画少数取值占主导，从而修正范围和等值过滤的选择率。

5. **统计新鲜度与 AQE**：过时的统计信息是灾难性执行计划的经典成因，因此统计必须随数据变化刷新；Spark 还有运行时 AQE，用实际 shuffle 大小来纠正估算。

**演进：**

1. **基于规则优化（RBO）**：套用固定改写，不看数据分布，对倾斜或大小差异无感知。

2. **基于代价优化（CBO）**：靠收集的统计估算代价来比较计划，驱动连接重排与策略选择。

3. **运行时 AQE**：当静态统计过时或缺失时，用实际 shuffle 大小在运行时纠正估算。

**面试追问：**

1. **统计过时会怎样**：产生灾难性执行计划，必须随数据变化刷新。

2. **直方图解决什么**：修正均匀分布假设对倾斜列的误估，用等高直方图刻画主导取值。

3. **CBO 做哪些关键决策**：连接重排、连接策略选择（broadcast/shuffle/sort-merge）、build 端选择。

**要点：**

1. **CBO 依赖统计**：CBO 按估算代价选计划；估算完全依赖已收集的统计信息。

2. **ANALYZE 内容**：ANALYZE 收集表级（行数/大小）和列级（NDV、min/max、null）统计，外加可选直方图。

3. **统计用途**：统计驱动连接重排、连接策略选择以及基数/选择率估算。

4. **直方图与刷新**：直方图修正倾斜列的误估；过时统计导致坏计划——AQE 在运行时纠正。

### 55. 用 salting 与 skew hint 处理倾斜连接

**频率：** 高

**题目：** 当连接被少数热点 key 搞倾斜时，salting 和 skew hint 如何解决？

**方案：**

1. **倾斜成因**：在 shuffle 连接中，某个 key 的所有行都发往一个 task；如果少数 key 占了不成比例的行数，这些 task 就会比其余的跑得久得多——作业的尾部被少数拖后腿的分区主导，而其他核在空转。

2. **Salting（加盐）**：把热点 key 打散：给倾斜一侧的 key 追加一个 `0…N-1` 的随机后缀，让一个热点 key 变成分布到 N 个 task 的 N 个子 key，并把另一侧**膨胀（explode）**——将每条匹配行与全部 N 个盐值做交叉连接，使两半仍能相遇。这是用小表侧的额外数据复制换取均衡的并行度。

3. **AQE 倾斜连接处理**：现代 Spark 用 **AQE 倾斜连接处理**（`spark.sql.adaptive.skewJoin.enabled`）自动化了常见情形：它在运行时检测大于「中位数阈值」的分区并自动把它们**切分**成更小的子分区。

4. **skew hint**：（支持的引擎中的 `/*+ SKEW */`）告诉优化器哪个 key/列倾斜，以便主动切分。

5. **优先级**：优先用 AQE/hint；只有自动化搞不定时才手动加盐。

**演进：**

1. **朴素 shuffle 连接**：相同 key 全发往一个 task，热点 key 导致拖后腿分区主导作业时长。

2. **手动 salting**：给热点 key 加随机后缀打散，另一侧膨胀复制，换取均衡并行度。

3. **AQE 自动切分 / skew hint**：运行时自动检测并切分超大分区，或用 hint 主动告知，免去手动改代码。

**面试追问：**

1. **salting 的代价**：用小表侧的额外数据复制（膨胀）换取均衡并行度。

2. **AQE 如何判定倾斜**：运行时检测大于「中位数阈值」的分区并自动切分成更小子分区。

3. **三种手段怎么选**：优先 AQE/hint 自动化，手动加盐作兜底。

**要点：**

1. **倾斜本质**：倾斜 key 造成拖后腿的 task——最慢的分区决定作业运行时间。

2. **Salting 机制**：Salting = 把热点 key 随机化成 N 个子 key，并复制另一侧的匹配行。

3. **AQE 自动化**：AQE 倾斜连接在运行时自动切分超大分区（无需改代码）。

4. **hint 与优先级**：skew hint 告诉优化器哪个 key 是热点；优先自动化，手动加盐作兜底。

### 56. 物化视图与查询结果缓存

**频率：** 中

**题目：** 物化视图和查询结果缓存如何加速分析引擎？各有什么取舍？

**方案：**

1. **共同本质**：两者都是用存储和新鲜度换速度，但粒度不同。

2. **物化视图（MV）**：把一条查询的*结果*（常是连接+聚合的汇总）持久化为一张物理表；收益是**自动查询改写**——优化器透明地把匹配的查询（或子表达式）重定向到更小的 MV，于是许多不同的查询无需按名引用就能受益。

3. **MV 维护代价**：MV 随底表变化而变陈旧，必须刷新，要么**全量**（重算）要么**增量**（只应用增量），且引擎必须知道 MV 足够新才能用。

4. **查询结果缓存**：把某条具体查询的确切输出按查询文本/计划（通常还有底层数据版本）作 key 记忆下来，完全相同的重跑瞬间返回，但输入一变即失效——对重复的仪表盘很好，对参数变化的查询无用。

5. **取舍对比**：MV 覆盖面广、可复用，但需要刷新策略；结果缓存廉价且自动，但对任何改动和查询文本变化都很脆弱。

**演进：**

1. **每次重算**：无缓存，每条查询都从底表重新计算，重复分析代价高。

2. **结果缓存**：按查询文本/计划作 key 记忆确切输出，相同重跑瞬间返回，但输入一变即失效。

3. **物化视图**：持久化结果为表并自动改写匹配查询，覆盖面广、可复用，代价是刷新与陈旧跟踪。

**面试追问：**

1. **MV 如何被用上**：优化器透明改写，把匹配查询（或子表达式）重定向到更小的 MV，无需按名引用。

2. **全量 vs 增量刷新**：全量重算整表；增量只应用底表的增量，代价更低但实现更复杂。

3. **结果缓存为何脆弱**：按查询文本/数据版本作 key，输入或文本一变即失效。

**要点：**

1. **MV 与自动改写**：MV 把查询结果持久化为表；优化器自动把匹配查询改写到它。

2. **MV 维护**：全量 vs 增量刷新，外加陈旧/新鲜度跟踪。

3. **结果缓存机制**：结果缓存记忆确切的查询输出；相同重跑瞬间返回，输入一变即失效。

4. **取舍总结**：MV = 广泛/可复用但需刷新；结果缓存 = 廉价/自动但对变化脆弱。

### 57. 近似查询算法：HyperLogLog 与 t-digest

**频率：** 中

**题目：** HyperLogLog 和 t-digest 这类算法如何给出快速的近似答案？何时该用它们？

**方案：**

1. **精确方案的痛点**：精确的 count-distinct 和精确分位数需要保存或排序全部不同值，在大规模下内存代价过高且不易廉价并行。

2. **HyperLogLog（HLL）**：用固定的极小内存（数十亿不同项只需几 KB）估算基数：对每个值哈希，并按桶跟踪见到的最大前导零个数——直觉是前导零的连串越长意味着不同值越多——得到一个低且有界的相对误差（约 1–2%）。

3. **HLL 可合并性**：关键在于 HLL 的 **sketch 可合并**：你可以对来自不同分区/日期的 sketch 求并集，这正是它适合分布式引擎（`approx_count_distinct`）和预聚合的原因。

4. **t-digest**：（以及 GK）通过维护一组紧凑的加权 centroid 来近似**分位数/百分位**，在分布尾部保留更多精度，因此 p50/p99 保持准确而内存很小；它同样可合并。

5. **使用场景**：当答案在几个百分点内即可，且你需要速度、可合并性或有界内存时就用它们——仪表盘、监控、独立访客数、延迟 SLO——而非要求精确的计费或对账。

**演进：**

1. **精确计算**：保存/排序全部不同值，内存随基数线性增长，不易并行。

2. **HLL/t-digest sketch**：固定小内存给出有界误差的基数和分位数估计，且 sketch 可合并。

3. **分布式/增量复用**：可合并性让 sketch 跨分区/时间求并，支撑 `approx_count_distinct` 和预聚合。

**面试追问：**

1. **HLL 为什么能几 KB 估数十亿**：靠哈希后桶内最大前导零个数反推基数，误差约 1–2%。

2. **可合并性为何关键**：sketch 能跨分区/时间求并，适合分布式与增量使用。

3. **何时不能用近似**：精确计费/对账等要求精确的场景绝不能用。

**要点：**

1. **HLL 特性**：HLL 用几 KB 内存靠前导零个数估算 count-distinct；误差约 1–2%，sketch 可合并。

2. **t-digest 特性**：t-digest 用加权 centroid 近似分位数/百分位，尾部分辨率高，可合并。

3. **可合并性**：可合并性是关键：sketch 能跨分区/时间求并，适合分布式与增量使用。

4. **适用边界**：在可接受小误差时为速度/内存而用；绝不用于精确计费/对账。

### 58. 大数据中的 Bloom filter

**频率：** 中

**题目：** 大数据中如何用 Bloom filter 做连接裁剪和存储层跳过？

**方案：**

1. **定义与单侧保证**：Bloom filter 是一个紧凑的位数组加 k 个哈希函数，回答集合成员判断时**没有假阴性、但可能有假阳性**——「一定不在」是确定的，「可能在」不确定。这种单侧保证使它成为廉价的预过滤器。

2. **运行时连接裁剪**：在**运行时连接裁剪**（Spark 的 runtime filter / 动态过滤）中，引擎用较小连接侧的 key 构建一个 Bloom filter 并把它下推到较大侧的扫描，于是不可能匹配的行在 shuffle 之前就被丢弃——削减 I/O 和 shuffle 量，思路类似半连接（semi-join）。

3. **存储层跳过**：在**存储层**，ORC、Parquet 等格式可为每个列块 / row group 存 Bloom filter，让读取端**跳过**整个「过滤器说所查值不存在」的块——对 min/max zone map 无能为力的高基数等值谓词（如随机 ID）尤其有力。

4. **取舍**：假阳性率由每元素位数和哈希个数调节，过滤器耗费空间和构建时间，且只对等值/成员判断有用，对范围谓词无效。

**演进：**

1. **全量扫描**：读取端对大表全扫，无法在读取/shuffle 前裁掉不可能匹配的行。

2. **运行时连接过滤**：用小侧 key 建 Bloom filter 下推到大侧扫描，shuffle 前裁剪（半连接效果）。

3. **存储层 Bloom filter**：ORC/Parquet 为 row group 存过滤器，让高基数等值查找跳过整块。

**面试追问：**

1. **为什么没有假阴性**：位数组只置位不清位，命中的元素一定被标记，所以「一定不在」可靠。

2. **和 min/max zone map 的互补**：zone map 对范围谓词有效但对高基数随机等值无力，Bloom filter 正好补上。

3. **假阳性率怎么调**：由每元素位数和哈希函数个数权衡，换取空间与构建时间。

**要点：**

1. **单侧保证**：Bloom filter：无假阴性、可能假阳性——「可能在 / 一定不在」。

2. **连接裁剪**：运行时/动态连接过滤在 shuffle 前裁剪大表侧，削减 I/O（半连接效果）。

3. **存储跳过**：存储层 Bloom filter（ORC/Parquet）为高基数等值查找跳过 row group。

4. **适用与取舍**：只对等值/成员有用，对范围无效；假阳性率与空间相互权衡。

### 59. UDF vs 内置函数

**频率：** 高

**题目：** 为什么内置函数通常比 UDF 快？UDF 施加了哪些优化限制？

**方案：**

1. **内置函数优势**：内置（原生）函数是 **Catalyst 已知的**：它们直接在 Tungsten 的堆外二进制行上运算，参与整段代码生成，可被优化器下推和重排。

2. **UDF 是黑盒**：而 **UDF 是黑盒**——Catalyst 看不透它，因此会禁止*穿过* UDF 的谓词下推、阻断相关优化和 codegen 融合，并把它当作不透明的 map。

3. **JVM UDF 序列化开销**：更糟的是序列化开销：Scala/Java UDF 仍跑在 JVM 上，但会强制把内部二进制格式转换成 JVM 对象再转回来。

4. **Python UDF 代价**：**Python UDF** 代价高得多，因为每一行（或每批）都必须序列化、通过管道送到独立的 Python worker 进程再送回。

5. **向量化 UDF 缓解**：**Pandas/向量化 UDF**（基于 Arrow）通过用近乎零拷贝的 Arrow 传输列式批次来缓解这一点，摊薄开销并支持向量化执行——远快于逐行的 Python UDF，但对下推仍是不透明的。

6. **经验法则**：能用内置就用内置；若非写 UDF 不可，优先原生/SQL 表达式，其次向量化 Pandas UDF，并把过滤器推到 UDF *之前*。

**演进：**

1. **内置/原生表达式**：Catalyst 透明，享受 Tungsten 二进制行、codegen、下推、重排。

2. **JVM/Python UDF**：黑盒阻断优化并增加(反)序列化开销；Python UDF 还要跨进程逐行/逐批传输。

3. **Pandas/Arrow 向量化 UDF**：用近零拷贝 Arrow 列式批次摊薄开销并支持向量化，但对下推仍不透明。

**面试追问：**

1. **为什么 UDF 阻断下推**：Catalyst 看不透其语义，无法把谓词推过它，只能当不透明 map。

2. **Python UDF 为何最贵**：每行/每批跨越 JVM↔Python 进程边界序列化传输。

3. **写 UDF 的降级顺序**：优先原生/SQL 表达式，其次向量化 Pandas UDF，并把过滤器推到 UDF 之前。

**要点：**

1. **内置透明**：内置函数对 Catalyst 透明：Tungsten 二进制行、codegen、下推、重排。

2. **UDF 黑盒**：UDF 是黑盒——阻断下推/codegen 并增加(反)序列化开销。

3. **Python UDF 最贵**：Python UDF 每行/每批跨越 JVM↔Python 进程边界；最昂贵的选项。

4. **向量化缓解**：Pandas/Arrow 向量化 UDF 摊薄开销；仍要把过滤器推到任何 UDF 之前。

### 60. 静态分区裁剪 vs 动态分区裁剪

**频率：** 高

**题目：** 静态分区裁剪和动态分区裁剪有何区别？为什么 DPP 对星型模式连接很重要？

**方案：**

1. **分区裁剪目的**：分区裁剪跳过读取不可能满足查询的分区，大幅削减分区表上的 I/O。

2. **静态分区裁剪**：发生在**编译期**：当过滤是分区列上的字面量（`WHERE dt = '2026-08-12'`）时，优化器对着分区元数据求解谓词，规划只扫描那些目录——无需任何运行时信息。

3. **星型模式的难题**：但在**星型模式连接**中，过滤常在*维度*表上（`WHERE dim.country = 'US'`），而巨大的分区*事实*表按连接 key 分区；裁剪用的值不是字面量，在维度侧求值之前无从得知，因此静态裁剪帮不上忙，引擎会扫描整张事实表。

4. **动态分区裁剪（DPP）**：解决这点：运行时 Spark 先对过滤后的维度侧求值，抽取存活的连接 key 值（常作为 broadcast/Bloom filter），并把它们下推到事实表扫描，于是只读取匹配的分区。

5. **收益**：这把全表扫描变成一个小子集——在大事实表上常带来数量级的收益。

**演进：**

1. **无裁剪**：扫描整张分区表，分区表上 I/O 代价巨大。

2. **静态裁剪**：编译期对字面量分区过滤求解元数据，只扫目标目录，但对非字面量（维度过滤）无能为力。

3. **动态裁剪（DPP）**：运行时对维度侧求值并把存活 key 下推到事实表扫描，裁掉绝大多数分区。

**面试追问：**

1. **为什么星型模式静态裁剪失效**：过滤在维度表上，事实表的分区值不是编译期字面量。

2. **DPP 用什么下推 key**：常用 broadcast/Bloom filter 把存活的连接 key 下推到事实表扫描。

3. **DPP 的前提**：需要 broadcast/AQE 支持，且事实表按连接 key 分区。

**要点：**

1. **静态裁剪**：静态裁剪在编译期用元数据求解分区列上的字面量过滤。

2. **星型难题**：星型模式的过滤在维度表上，事实表分区值不是编译期字面量。

3. **DPP 机制**：DPP 在运行时对维度求值，把存活的 key 下推到事实表扫描。

4. **DPP 收益**：DPP 动态裁剪事实表分区——I/O 大幅节省；需要 broadcast/AQE 支持。

### 61. 批量摄取模式：全量与增量抽取

**频率：** 高

**题目：** 如何把数据从业务数据库摄取到数据湖或数仓？如何在全量与增量抽取之间做选择？

**方案：**

1. **批量摄取模式**：批量摄取（即 Sqoop/JDBC 连接器模式）按调度周期，对源库并行执行按范围分区的查询，并把分区文件写入数据湖。核心决策是**全量 vs 增量**抽取。
2. **全量抽取**：每次都重读整张表——简单、可自我纠正，但代价高，超过几百万行就不现实。
3. **增量抽取**：只读自上次水位线以来发生变化的行，依据单调递增的主键或 `updated_at` 时间戳（Sqoop 的 `--incremental append`/`lastmodified`），并在两次运行之间持久化高水位标记。
4. **保护源库**：为避免冲击生产库，应在只读副本上抽取、限制并行度（切分列、mapper 数量），并落到**贴源/bronze** 层供后续转换。
5. **注意坑**：增量抽取会漏掉硬删除，以及未触及水位列却被更新的行，时钟偏差或不唯一的时间戳还可能丢掉边界行——这正是高保真采集常常更青睐 CDC 的原因。

**演进：**

1. **全量起步**：从简单、可自愈但成本为 O(表大小) 的全量抽取起步，小表够用。
2. **转向增量**：数据量增长到百万行以上后，切换到基于水位线、便宜但脆弱的增量抽取。
3. **升级 CDC**：当增量抽取漏删除、漏更新的缺陷无法容忍时，升级到高保真的 CDC 采集。

**面试追问：**

1. **删除如何捕获**：增量抽取基于水位列，硬删除不会更新任何列，因此会被漏掉——需要软删除标记或 CDC。
2. **水位列陷阱**：时钟偏差或不唯一时间戳会丢边界行；可用单调递增 id 或重叠窗口兜底。
3. **源端保护**：为何在只读副本上抽取并限制 mapper/切分列，以保护生产 OLTP 系统。

**要点：**

1. **成本权衡**：全量 = 简单、可自愈，但成本为 O(表大小)；增量 = 基于水位线、便宜，但脆弱。
2. **水位标记**：使用单调递增 id 或 `updated_at` 高水位标记，并跨运行持久化。
3. **保护源端**：对副本做分区/并行读取，保护源端 OLTP 系统。
4. **落 bronze**：增量抽取会漏掉删除和不触及水位列的更新；原始数据先落到 bronze/staging。

### 62. 流式摄取：微批与连续处理

**频率：** 高

**题目：** 微批摄取与连续流处理有何区别？如何把流可靠地送入数据湖？

**方案：**

1. **流式摄取概念**：流式摄取持续把事件（例如来自 Kafka）搬入数据湖，而引擎模型决定了延迟/吞吐的权衡。
2. **微批**：（Spark Structured Streaming 的默认模式）把事件按触发间隔缓冲成小批，每批作为一个微型作业处理——延迟较高（秒级），但吞吐极佳，通过偏移量检查点实现简单的 exactly-once，并可复用批处理运行时。
3. **连续/逐条**：（Flink，或 Spark 的 continuous 模式）在事件到达时逐条处理——延迟亚秒/毫秒级，代价是更细粒度检查点带来的复杂度。
4. **可靠送入数据湖**：写入端要**把源端偏移量与已提交文件一起做检查点**，这样重启后能精确地从中断处恢复。
5. **小文件问题**：必须应对**小文件问题**，即批量写入并做合并（compaction）。
6. **事务型表格式**：落入事务型表格式（Delta/Iceberg/Hudi）可获得原子提交，读者永远不会看到写了一半的数据，同时支持下游增量消费。

**演进：**

1. **先微批**：以微批起步，复用批处理运行时、延迟较高但吞吐极佳且 exactly-once 实现简单。
2. **再连续**：对亚秒/毫秒级延迟有需求时，切到连续/逐条处理，接受更复杂的检查点。
3. **加事务表**：为获得原子提交与下游增量消费，演进到 Delta/Iceberg/Hudi 表格式。

**面试追问：**

1. **exactly-once 如何保证**：靠偏移量检查点——把源端偏移量与已提交文件一起检查点，重启后从中断处恢复。
2. **小文件从何而来**：高频批量写入产生大量小文件，需批量写入 + compaction 治理。
3. **延迟 vs 吞吐**：微批换吞吐与简单性，连续换低延迟但复杂度高，如何据业务选型。

**要点：**

1. **微批特征**：微批 = 缓冲式微型作业，延迟较高、吞吐极佳，基于偏移量检查点实现简单 exactly-once。
2. **连续特征**：连续 = 逐条处理，毫秒级延迟，检查点更复杂。
3. **原子提交**：把源端偏移量与输出文件原子提交，确保重启后能正确恢复。
4. **表格式**：写入 Delta/Iceberg/Hudi 获得原子提交；批量写入/合并以避免小文件。

### 63. 幂等与 exactly-once 的下游 sink

**频率：** 高

**题目：** 既然重试与故障不可避免，如何在管道的 sink 端实现 exactly-once（或 effectively-once）投递？

**方案：**

1. **问题本质**：由于处理可能崩溃并重放，任何 at-least-once 的源都会重复投递记录，因此 sink 必须让重复变得无害——实际目标是 **effectively-once**。
2. **幂等写入**：按确定性的业务/自然键做 upsert（MERGE/UPSERT），这样重放同一条记录是覆盖而非重复。
3. **去重**：为记录携带唯一事件 id，借助状态存储或去重表（通常在某个时间/水位窗口内）丢弃已见过的 id。
4. **事务型/两阶段提交 sink**：在一个原子事务中同时写输出并提交源端偏移量（Kafka 事务、Flink 的 `TwoPhaseCommitSinkFunction`、Delta/Iceberg 原子提交），使得半成品写入永不可见。
5. **反模式**：用自动生成 id 盲目 append，每次重试都会重复计数。选择满足需求的最廉价保证：带键数据用幂等 upsert，需要多记录原子可见时用事务提交。
6. **确定性**：非确定性转换（如 `now()`、随机 id）即便配幂等 sink 也会破坏重放安全。

**演进：**

1. **先幂等 upsert**：带自然键的数据，优先用最廉价的幂等 upsert 实现 effectively-once。
2. **再去重**：无稳定业务键时，引入唯一事件 id + 窗口内状态/去重表。
3. **最后事务提交**：需要多记录原子可见时，升级到事务型/2PC sink 同时提交数据与偏移量。

**面试追问：**

1. **为何 exactly-once 常是伪命题**：端到端严格一次难达，effectively-once 才是工程现实，重点让重复无害。
2. **去重表如何不无限膨胀**：用时间/水位窗口限定去重范围，过期清理。
3. **非确定性为何致命**：`now()`/随机 id 使重放产生不同结果，即便 sink 幂等也无法对齐。

**要点：**

1. **默认 at-least-once**：重试使 at-least-once 成为默认；设计 sink 使重复不会污染结果。
2. **幂等 upsert**：按自然键做幂等 upsert 是最简单的 effectively-once 机制。
3. **去重**：在窗口内用唯一事件 id 通过状态/去重表去重。
4. **事务 + 确定性**：事务型/2PC sink 原子提交数据 + 偏移量；保持转换确定性。

### 64. 数据契约与基于 schema registry 的治理

**频率：** 中

**题目：** 什么是数据契约？schema registry 如何在生产者与消费者之间强制兼容性？

**方案：**

1. **数据契约（data contract）**：是关于生产者所发出数据的形态与语义的一份显式、带版本的约定——字段名/类型、可空性、单位、语义含义、SLA（新鲜度、数据量）以及归属。它把责任左移：生产者不能再悄无声息地破坏下游作业。
2. **schema registry**：（如 Confluent Schema Registry 搭配 Avro/Protobuf/JSON Schema）把结构部分工程化：每个 topic/subject 有注册的 schema 版本，生产者/消费者在序列化时对其校验。
3. **兼容模式**：registry 强制**兼容模式**——*backward*（新 schema 能读旧数据：可安全删字段/加可选字段）、*forward*（旧读者能处理新数据）、*full*（双向）——在发布时而非凌晨三点的生产环境里拒绝不兼容变更。
4. **CI 拦截**：配合 CI 检查，数据契约能在 pull request 阶段拦住破坏性变更。
5. **语义超越结构**：除结构外，契约还编码了 registry 单独无法覆盖的语义与质量预期，因此团队会把 registry 与数据质量测试、清晰的版本/弃用策略配合使用。

**演进：**

1. **先上 registry**：从 schema registry 开始，把结构兼容性工程化并在序列化时校验。
2. **加兼容模式**：配置 backward/forward/full 策略，在发布时拒绝破坏性变更。
3. **补语义契约**：再叠加数据契约与质量测试，覆盖 registry 无法捕捉的语义与 SLA。

**面试追问：**

1. **backward 与 forward 区别**：backward 让新 schema 读旧数据，forward 让旧读者处理新数据，full 双向兼容。
2. **registry 不够在哪**：只管结构，不管单位、语义含义、SLA、归属——需契约补齐。
3. **如何落地左移**：在 CI/PR 阶段跑兼容性 + 质量检查，把破坏拦在上线前。

**要点：**

1. **契约定义**：数据契约 = 带版本的生产者承诺：schema、语义、SLA、归属。
2. **registry 职责**：schema registry 存储带版本的 schema，并在（反）序列化时校验。
3. **兼容模式**：兼容模式（backward/forward/full）在上线前拒绝破坏性变更。
4. **CI 强制**：在 CI 中强制执行；配合质量测试覆盖 registry 无法捕捉的语义。

### 65. 回填与重处理且不重复计数

**频率：** 高

**题目：** 如何安全地回填（backfill）或重处理历史数据，而不产生重复或重复计数的指标？

**方案：**

1. **回填的危险**：回填是对过去时间区间重跑管道——用于修 bug、加列或初始化新表——其危险在于朴素的重跑会在既有输出之上 append，导致一切被重复计数。
2. **幂等基础**：基础在于**幂等、按分区限定的写入**：每次运行都应是其输入分区的纯函数（以执行/逻辑日期为键，而非 `now()`），并且必须**原子地覆盖该分区**（`INSERT OVERWRITE`/动态分区覆盖，或在事务表中先删后插），而不是 append。
3. **分区替换**：重算一段日期范围，并原子地替换每个分区。
4. **隔离的回填目标**：写入影子表/分支，校验后再提升（promote）。
5. **有界、并行的窗口**：按日期分块回填，以控制负载与成本。
6. **编排与状态**：当任务以逻辑日期参数化并支持 catchup 时，编排器有帮助，但只有幂等性才能让重放安全。此外要冻结迟到数据的假设、保持转换确定性，并重置任何已存的水位线/偏移量，以免流式状态跳过被重处理的区间。

**演进：**

1. **从 append 到覆盖**：先认识到朴素 append 会重复计数，改为按分区原子覆盖。
2. **加隔离目标**：对高风险回填写入影子表/分支，校验通过再提升。
3. **分块并行**：数据量大时按日期有界分块并行回填，控制负载与成本。

**面试追问：**

1. **为何以逻辑日期为键**：用执行/逻辑日期而非 `now()`，保证每次运行是输入分区的纯函数。
2. **流式状态怎么办**：必须重置水位线/偏移量，否则流式状态会跳过被重处理的区间。
3. **确定性为何必须**：非确定性转换会使回填输出与原输出不一致，破坏重放安全。

**要点：**

1. **避免重复计数**：重跑时朴素 append 会重复计数；写入要幂等且按分区限定。
2. **原子覆盖**：以逻辑/执行日期为键，并原子覆盖目标分区。
3. **三种策略**：用分区替换、影子表或有界窗口；提升前先校验。
4. **重置状态**：重置水位线/偏移量并保持转换确定性，以保证重放安全。

### 66. 用 MERGE INTO / CDC upsert 做增量处理

**频率：** 高

**题目：** `MERGE INTO` 如何支撑增量 upsert？如何把一条 CDC 变更流合并进 lakehouse 表？

**方案：**

1. **MERGE INTO 语义**：`MERGE INTO` 是一条原子语句，用变更源来协调目标表：`WHEN MATCHED THEN UPDATE/DELETE ... WHEN NOT MATCHED THEN INSERT`。它是 lakehouse 表（Delta/Iceberg/Hudi）上增量处理的主力，把不可变的列式存储变成可事务性 upsert 的对象。
2. **CDC 场景**：对于 **CDC**，源是一条按主键标识的增删改流（来自 Debezium/Kafka Connect）；你把每个微批 merge 进去，使目标镜像 OLTP 源的当前状态。
3. **批内去重**：**先按键对批次去重**——一个键在一个批次里可能变多次，按 CDC 序列号/LSN 而非到达顺序保留最新的一条。
4. **处理删除**：用 `WHEN MATCHED ... THEN DELETE` 处理删除。
5. **排序/序列列**：使用**排序/序列列**，让乱序的旧变更不会覆盖较新的值。
6. **性能注意**：MERGE 会重写被触及的文件，因此要按 merge 键分区并做 Z-order/聚簇，并定期 compaction 以压低写放大。

**演进：**

1. **从全量到 merge**：由全表重算演进到用 `MERGE INTO` 做原子增量 upsert。
2. **接入 CDC 流**：从 Debezium/Kafka Connect 取增删改流，逐微批 merge 以镜像源状态。
3. **治理写放大**：随数据增长，按 merge 键分区/聚簇并定期 compaction 控制写放大。

**面试追问：**

1. **乱序如何处理**：用排序/序列列（LSN），让旧变更不覆盖新值；批内按 LSN 保留最新。
2. **删除为何易漏**：需显式 `WHEN MATCHED ... THEN DELETE`，否则源端删除不会反映到目标。
3. **MERGE 为何慢**：会重写触及的文件，分区/聚簇/compaction 是降低写放大的关键。

**要点：**

1. **MERGE INTO**：`MERGE INTO` = 原子的 matched-更新/删除 + not-matched-插入；支撑 lakehouse upsert。
2. **CDC merge**：以主键为键，应用增/改/删以镜像源状态。
3. **去重与排序**：merge 前按 CDC 序列号/LSN 对每个键去重；用排序列避免旧值覆盖新值。
4. **写放大治理**：MERGE 会重写文件——按 merge 键分区/聚簇并 compaction 以限制写放大。

### 67. 超越 Airflow 的编排：基于资产的调度

**频率：** 中

**题目：** Dagster 和 Prefect 与 Airflow 有何不同？什么是数据感知（基于资产）的调度？

**方案：**

1. **Airflow**：把管道建模为**任务 DAG**——你编排的是*操作*及其先后顺序，但框架本身并不知道每个任务产出什么数据。
2. **Dagster**：引入**软件定义资产（software-defined assets）**：你声明*数据对象*（表、文件、ML 模型）及其依赖，Dagster 据此推导执行图，并可基于**数据感知**调度——当上游变化或变陈旧时重新物化某资产，而不仅靠 cron。
3. **Dagster 的一等公民**：这使血缘、新鲜度策略、分区和数据质量检查成为一等公民，并改善本地可测性与带类型的 IO。
4. **Prefect**：走更轻量、更 Pythonic 的动态路线：flow 和 task 就是带重试、缓存的普通函数，支持运行时动态生成 DAG（无需僵硬的预声明图），适合命令式、参数繁多的工作流。
5. **选型经验法则**：成熟的、以任务为中心的批处理调度选 Airflow；想要以资产/血缘为中心、数据感知强的平台选 Dagster；重视动态、代码优先、少仪式感的 flow 选 Prefect。

**演进：**

1. **任务编排起步**：从 Airflow 的任务 DAG 起步，编排操作顺序。
2. **转向资产中心**：需要血缘、新鲜度、数据感知调度时，转向 Dagster 的软件定义资产。
3. **动态 flow 分支**：重视动态、代码优先、少仪式感时，选 Prefect 的 Pythonic flow。

**面试追问：**

1. **什么是数据感知调度**：上游数据变化或变陈旧时重新物化资产，而非仅按 cron 定时触发。
2. **资产 vs 任务区别**：资产声明的是数据对象及依赖，任务声明的是操作及顺序。
3. **何时不必换 Airflow**：成熟、以任务为中心的批处理场景，Airflow 仍是稳妥选择。

**要点：**

1. **Airflow**：Airflow = 任务 DAG 编排；引擎不感知所产出的数据。
2. **Dagster**：Dagster = 软件定义资产；基于数据新鲜度/陈旧度调度，内建血缘。
3. **Prefect**：Prefect = 动态、Pythonic 的 flow，带重试/缓存与运行时生成的 DAG。
4. **资产调度价值**：基于资产的调度在上游数据变化时重新物化输出，而不仅按 cron。

### 68. 管道测试与数据质量框架

**频率：** 中

**题目：** 如何测试数据管道？Great Expectations、dbt tests 这类框架各扮演什么角色？

**方案：**

1. **两种失败方式**：数据管道有两种失败方式——**代码**错了，或**数据**错了——因此测试要覆盖两者。
2. **测代码**：用小规模夹具单元测试转换逻辑，并在 CI 上用样本数据集跑集成测试。
3. **dbt tests**：在 YAML 中声明式覆盖常见场景——`not_null`、`unique`、`accepted_values`、`relationships`（引用完整性）——外加自定义 SQL/singular 测试，作为构建的一部分运行，测试失败可中止管道。
4. **Great Expectations**：提供更丰富、可复用的「expectation」套件（分布、范围、行数增量、正则、新鲜度）、验证 *checkpoint*、用于自动建议 expectation 的 profiling，以及人类可读的 **Data Docs**。
5. **最佳实践**：把这些检查作为层边界（bronze→silver→gold）上的**关卡**，让坏数据尽早失败而非扩散，区分硬失败（阻断）与软告警（提醒），并监控趋势做异常检测，而不只用通过/失败阈值。

**演进：**

1. **先测代码**：从夹具单元测试与 CI 集成测试起步，保证转换逻辑正确。
2. **加数据断言**：引入 dbt tests 声明式覆盖 not_null/unique 等常见场景。
3. **升级质量框架**：需要分布/新鲜度/profiling/Data Docs 时，叠加 Great Expectations 与关卡。

**面试追问：**

1. **代码 bug 与数据 bug 如何分测**：代码用夹具单元/集成测试，数据用运行时行断言。
2. **硬失败 vs 软告警**：阻断性失败停管道，软告警只提醒，避免误阻正常波动。
3. **为何要监控趋势**：行数/分布异常用趋势检测更灵敏，优于固定通过/失败阈值。

**要点：**

1. **双重测试**：既测代码（在夹具上做单元/集成测试），也测数据（对行做运行时断言）。
2. **dbt tests**：dbt tests = 声明式 not_null/unique/accepted_values/relationships 加自定义 SQL 测试。
3. **Great Expectations**：Great Expectations = 丰富可复用的 expectation 套件、checkpoint、profiling、Data Docs。
4. **关卡策略**：把检查作为层间关卡；区分阻断性失败与告警；追踪趋势。

### 69. dbt 与 ELT 转换建模

**频率：** 高

**题目：** dbt 如何组织 ELT 转换？model、ref 与增量物化各带来什么？

**方案：**

1. **ELT 中的 T**：dbt 是 **ELT 中的 T**：先把原始数据加载进数仓，再在库内用 SQL 转换。
2. **model**：一个 **model** 就是 `.sql` 文件里的一条 `SELECT`，dbt 会把它变成表或视图；你从不手写 DDL。
3. **`ref()`**：model 之间用 **`ref()`** 相互引用，dbt 据此构建依赖 DAG、解析环境正确的表名并确定运行顺序——这正是血缘与增量构建能自动化的原因。
4. **物化方式（materialization）**：控制 model 如何持久化：*view*（便宜、始终最新）、*table*（每次运行重算）、*ephemeral*（内联为 CTE），以及 **incremental**（只处理新增/变更的行，通过 `is_incremental()` 过滤，按唯一键 append 或 merge，避免每次都重建大表）。
5. **其他能力**：dbt 还提供 Jinja 宏以复用、`sources` 及新鲜度检查、测试与文档，以及用于 SCD Type 2 的 snapshot。
6. **最终形态**：最终形成受版本控制、可测试、模块化的分析工程，采用分层 model（staging → intermediate → marts）。

**演进：**

1. **view 起步**：小 model 用 view，便宜且始终最新。
2. **转 table**：重算成本可接受但查询频繁时，物化为 table。
3. **升 incremental**：大表重建昂贵时，用 incremental + `is_incremental()` + 唯一键 merge 只处理变更行。

**面试追问：**

1. **ref() 带来什么**：自动构建依赖 DAG、解析环境表名、确定运行顺序并贯通血缘。
2. **何时用 incremental**：大表全量重建太贵、且有稳定唯一键与变更标识时。
3. **snapshot 作用**：实现 SCD Type 2，记录维度属性的历史变更版本。

**要点：**

1. **dbt 定位**：dbt = ELT 的转换层：SQL `SELECT` model 编译为表/视图，无需手写 DDL。
2. **`ref()`**：`ref()` 构建 DAG、处理运行顺序，并贯通 staging→marts 的血缘。
3. **物化方式**：物化：view、table、ephemeral 与 incremental（`is_incremental()` + 唯一键 merge）。
4. **配套能力**：增加宏、sources/新鲜度、测试、文档以及 SCD2 snapshot，形成可测试的分析工程。

### 70. 迟到维度与批处理中的乱序处理

**频率：** 中

**题目：** 在批处理管道中如何处理迟到维度（late-arriving dimension）与乱序事件？

**方案：**

1. **迟到维度问题**：在维度管道里，事实常常先于其维度行到达——即**迟到维度**（或称「早到事实」）。若丢弃它或用内连接，你会悄无声息地丢失事实。
2. **推断/占位维度成员（inferred/placeholder member）**：标准解法是按自然键插入一条带代理键、属性未知的桩维度行，立刻把事实连接到它，然后**在真实维度到达时就地更新该桩行**，使代理键（以及所有指向它的事实）保持有效。
3. **SCD Type 2 的迟到变更**：迟到的*变更*更棘手：一条带较早生效日期的变更必须插入到正确的历史时段里，拆分/调整相邻版本的有效期窗口，并重述（restate）本应指向修正后版本的事实。
4. **按事件时间分区**：批处理中的乱序处理依赖**按事件时间（而非处理时间）分区**。
5. **回看窗口（lookback）**：以回看窗口重处理近期窗口使迟到数据落入其真实分区。
6. **幂等覆盖**：用幂等覆盖使重跑这些分区不会重复计数。

**演进：**

1. **占位先行**：事实先到时插入推断/占位维度成员，避免用内连接丢失事实。
2. **回填属性**：真实维度到达后就地更新桩行，保持代理键稳定。
3. **SCD2 重述**：迟到变更需插入正确历史窗口、调整有效期并重述受影响事实。

**面试追问：**

1. **为何代理键要稳定**：桩行更新属性但保留代理键，既有事实无需重连即仍有效。
2. **事件时间 vs 处理时间**：按事件时间分区 + 回看窗口，才能让迟到数据落入真实分区。
3. **SCD2 为何最棘手**：须插入正确历史时段、拆分相邻版本有效期并重述指向修正版本的事实。

**要点：**

1. **占位成员**：迟到维度：插入推断/占位成员以免丢失事实，随后回填属性。
2. **代理键稳定**：真实维度到达时保持代理键稳定，使既有事实仍然有效。
3. **SCD2 迟到变更**：SCD2 迟到变更必须插入正确历史窗口并重述受影响的事实。
4. **乱序处理**：按事件时间分区、重处理回看窗口，并对乱序数据用幂等覆盖。

### 71. Spark 内存管理

**频率：** 高

**题目：** Spark 如何管理 executor 和 driver 内存？如何诊断和预防 OutOfMemory 错误？

**方案：**

1. **统一内存管理器**：每个 executor 的 JVM 堆（`spark.executor.memory`）由**统一内存管理器**划分：一块共享区域（`spark.memory.fraction`，默认 0.6）在 **execution** 内存（shuffle、join、排序、聚合）与 **storage** 内存（缓存块）之间动态平衡，另加一小块给你自己对象用的 **user** 区域。
2. **动态平衡与驱逐**：压力之下 execution 可以驱逐已缓存的 storage，反之则不行。
3. **堆外 overhead**：堆之外，`spark.executor.memoryOverhead` 覆盖堆外/原生需求（Netty 缓冲、Python worker），还可通过 `spark.memory.offHeap` 启用堆外 execution。
4. **溢写到磁盘**：当 execution 内存耗尽时，Spark 会**溢写到磁盘**而不是失败，但大量溢写会摧毁性能。
5. **OOM 来源**：OOM 通常来自 **driver**（大的 `collect()` 或广播）或 executor（超大/倾斜分区、宽聚合、单 executor 核数过多）。
6. **解法**：提高分区数以缩小每个 task 的数据量、加大 overhead、避免 `collect`、限制广播大小，以及减少 executor 核数让并发 task 更好地共享内存。

**演进：**

1. **统一管理器**：把堆划分为共享的 execution+storage 区域（0.6）加一块 user 区域；overhead 是独立的堆外内存。
2. **驱逐与溢写**：压力下 execution 驱逐 storage；溢写到磁盘避免失败但很慢。
3. **诊断与修复**：Driver OOM 源自 collect/广播，executor OOM 源自超大/倾斜分区；通过更多分区、更高 overhead、更少单 executor 核数、避免 collect 来修复。

**面试追问：**

1. **为何 execution 能驱逐 storage 而反之不行**：execution 内存是任务正确性所必需的（溢写代价高但不可省），缓存块可以重算，因此设计上让 execution 优先抢占。
2. **collect 为何危险**：`collect()` 把所有分区数据拉回 driver 单点，极易击穿 driver 堆；应改用聚合、`take` 或写文件。
3. **调 overhead 还是堆**：堆外/原生需求（Netty、Python worker）溢出时调 `spark.executor.memoryOverhead`，堆内对象/缓存压力才调 `spark.executor.memory`。

**要点：**

1. **统一管理器**：把堆划分为共享的 execution+storage 区域（0.6）加一块 user 区域；overhead 是独立的堆外内存。
2. **驱逐与溢写**：压力下 execution 驱逐 storage；溢写到磁盘避免失败但很慢。
3. **OOM 来源**：Driver OOM 源自 collect/广播；executor OOM 源自超大/倾斜分区。
4. **修复手段**：通过更多分区、更高 overhead、更少单 executor 核数、避免 collect 来修复。

### 72. Shuffle 内部机制与调优

**频率：** 高

**题目：** Spark shuffle 过程中发生了什么？如何调优？

**方案：**

1. **map 端写出**：宽转换会把每个 map task 的输出写入按目标 reducer 分区的桶中，排序并溢写到本地磁盘成为 **shuffle 文件**。
2. **reduce 端拉取**：随后 reduce task 通过网络从每个 mapper 拉取属于自己的那一份——这是一次全对全传输，也是 Spark 最昂贵的操作。
3. **分区数权衡**：reduce 分区数由 `spark.sql.shuffle.partitions`（默认 200）决定；太少会使分区过大、溢写严重，太多则产生大量小 task 和调度开销——AQE 的 coalesce 通过在运行时合并 shuffle 后的小分区来缓解。
4. **external shuffle service**：由一个常驻守护进程（在 NodeManager 上）提供 shuffle 文件，因此 executor 被移除时不会丢失其 shuffle 输出——这对动态分配至关重要。
5. **调优手段**：把分区大小调到合适（每个约 100–200 MB）、启用 AQE、为大 shuffle 提高 `spark.reducer.maxSizeInFlight` 和 shuffle 缓冲、优先用 `reduceByKey`/广播 join 以减少 shuffle 数据量，并在 UI 中关注溢写指标。

**演进：**

1. **shuffle 全流程**：map 端分区+排序+溢写到本地文件，再由 reducer 做全对全网络拉取。
2. **分区数与 AQE**：`spark.sql.shuffle.partitions`（默认 200）太少 → 溢写，太多 → 开销；AQE 会合并。
3. **解耦生命周期**：external shuffle service 把 shuffle 文件与 executor 生命周期解耦 → 支撑动态分配。

**面试追问：**

1. **为什么 shuffle 这么贵**：它触发磁盘溢写、序列化和全对全网络传输，无法像窄转换那样流水线化。
2. **AQE 如何缓解分区数难题**：运行时根据实际统计合并过小的 shuffle 分区、动态切换 join 策略、处理倾斜，避免静态配死 200。
3. **reduceByKey 为何优于 groupByKey**：`reduceByKey` 在 map 端先做局部聚合（combine），显著减少 shuffle 传输的数据量。

**要点：**

1. **机制**：Shuffle = map 端分区+排序+溢写到本地文件，再由 reducer 做全对全网络拉取。
2. **分区数**：`spark.sql.shuffle.partitions`（默认 200）：太少 → 溢写，太多 → 开销；AQE 会合并。
3. **shuffle service**：external shuffle service 把 shuffle 文件与 executor 生命周期解耦 → 支撑动态分配。
4. **减量**：用 reduceByKey/广播 join 减少 shuffle；监控溢写与拉取指标。

### 73. 推测执行与拖后腿任务的缓解

**频率：** 中

**题目：** Spark 中的推测执行（speculative execution）是什么？何时有用、何时有害？

**方案：**

1. **拖后腿任务定义**：**拖后腿任务（straggler）**是运行远慢于同侪的 task——可能源自慢/将坏的磁盘、吵闹邻居、超载节点或数据不均。
2. **stage 木桶效应**：由于一个 stage 只有等最慢的 task 完成才结束，一个 straggler 就会拉长整体墙钟时间。
3. **推测执行机制**：**推测执行**（`spark.speculation`）让 driver 监视 task 时长，当某个 task 运行时间远超本 stage 已完成 task 的中位数（`spark.speculation.multiplier`，在 `spark.speculation.quantile` 比例的 task 完成之后）时，在另一节点启动一个**副本**；谁先完成谁胜出，另一个被杀掉。这以额外资源为代价掩盖了*硬件/环境*层面的慢。
4. **对数据倾斜无效**：关键在于，推测执行**并不能**解决**数据倾斜**——处理超大分区的 task 的副本同样慢，所以倾斜要用加盐/AQE 来处理。
5. **非幂等风险**：对非幂等的 task（如向外部系统写入且无原子提交）应避免推测执行，否则副本可能造成重复写入。

**演进：**

1. **问题根源**：Straggler = 异常慢的 task；stage 要等它最慢的 task。
2. **缓解机制**：推测执行为慢 task 启动副本；先完成者胜出，另一个被杀掉；适合硬件/环境层面的慢。
3. **边界与风险**：对数据倾斜无用（用加盐/AQE 解决），且当心非幂等副作用与额外资源消耗。

**面试追问：**

1. **推测执行为何对倾斜无用**：倾斜 task 慢是因为数据量本身大，副本处理同样的大分区依然慢，解决不了根因。
2. **如何避免副本重复写**：使用原子/幂等提交协议（如 FileOutputCommitter v2、事务性 sink），或对有副作用的 task 关闭推测执行。
3. **multiplier 与 quantile 怎么调**：集群波动大时放宽 multiplier 避免误触发，追求低延迟时收紧 quantile 让推测更早启动。

**要点：**

1. **Straggler**：异常慢的 task；stage 要等它最慢的 task。
2. **机制**：推测执行为慢 task 启动副本；先完成者胜出，另一个被杀掉。
3. **适用场景**：适合硬件/环境层面的慢；对数据倾斜无用（用加盐/AQE 解决）。
4. **代价**：当心非幂等副作用；它还会消耗额外集群资源。

### 74. Spark 的动态资源分配

**频率：** 中

**题目：** Spark 的动态资源分配如何工作？它有什么前提要求？

**方案：**

1. **按负载伸缩**：启用**动态分配**（`spark.dynamicAllocation.enabled`）后，Spark 会根据负载调整 executor 数量，而不是在应用整个生命周期内固定持有一批。
2. **扩容逻辑**：当 task 排队超过 backlog 超时时，它会**申请更多 executor**（指数增长），直到 `maxExecutors`。
3. **缩容逻辑**：当 executor 空闲超过 `executorIdleTimeout` 时，它会把它们**释放**回集群管理器（YARN/K8s），直到 `minExecutors`。
4. **收益**：这提升了多租户集群的利用率，并为突发型或大量空闲的作业（如长时间的 notebook 会话）降低成本。
5. **shuffle 难点**：executor 持有后续 stage 需要的 shuffle 文件，移除它会迫使重算——因此动态分配传统上需要 **external shuffle service**（或在 Kubernetes 上通过 shuffle tracking / 持久卷 / 优雅下线来保留或迁移 shuffle 块）。
6. **缓存丢失**：被移除 executor 上的缓存数据同样会丢失，所以要调 `cachedExecutorIdleTimeout` 来保护持有缓存的 executor。

**演进：**

1. **伸缩规则**：在 task 积压时扩容 executor、在空闲时缩容，介于 min 与 max 之间。
2. **价值**：为突发/交互式负载提升集群利用率并降低成本。
3. **前提条件**：需要 external shuffle service（或 K8s shuffle tracking）保 shuffle 文件，并用 cachedExecutorIdleTimeout 保护缓存块。

**面试追问：**

1. **没有 external shuffle service 会怎样**：移除持有 shuffle 文件的 executor 会触发后续 stage 重算，抵消动态分配的收益甚至更慢。
2. **K8s 上如何替代 shuffle service**：通过 shuffle tracking、持久卷或优雅下线（graceful decommission）在缩容前保留或迁移 shuffle/缓存块。
3. **min/max 如何设**：min 保证基础并行度与交互响应，max 防止单作业抢占多租户集群；指数增长平衡响应速度与抖动。

**要点：**

1. **伸缩**：在 task 积压时扩容 executor、在空闲时缩容，介于 min 与 max 之间。
2. **价值**：为突发/交互式负载提升集群利用率并降低成本。
3. **shuffle 前提**：需要 external shuffle service（或 K8s shuffle tracking），使移除 executor 不丢失 shuffle 文件。
4. **缓存保护**：被移除 executor 会丢失缓存块；用 cachedExecutorIdleTimeout 保护。

### 75. 小文件合并作业与最优文件大小

**频率：** 高

**题目：** 如何设计一个针对小文件的合并（compaction）作业？目标文件大小应设为多少？

**方案：**

1. **小文件之害**：流式摄取和高度分区的写入会产生大量小文件，它们膨胀元数据、拖慢列举、并为每个文件生成一个小 task——摧毁扫描吞吐。
2. **合并作业机制**：**合并（bin-packing）作业**周期性地把每个分区里的众多小文件重写为更少的大文件：读取该分区、`repartition`/`coalesce` 到期望的文件数、再重写。
3. **目标文件大小**：目标文件大小大致在 **128 MB–1 GB**——常见为约 128–256 MB，以匹配 HDFS 块大小和 Parquet 行组行为并保持 task 大小合适，纯扫描型负载可更大（512 MB–1 GB）。
4. **文件数计算**：目标文件数按 `分区总字节 / 目标大小` 计算。
5. **湖仓自动化**：湖仓格式将其自动化：Delta 的 `OPTIMIZE`（配合 `ZORDER`）和自动合并、Iceberg 的 `rewrite_data_files`、Hudi 的 clustering/compaction——都执行原子的、快照隔离的重写，使读者不受干扰。
6. **频率权衡**：在频率与成本间权衡：合并太频繁浪费 I/O，太少则小文件惩罚依旧存在。

**演进：**

1. **问题**：小文件 → 元数据膨胀、列举变慢、每个文件一个小 task。
2. **合并方案**：合并作业通过重写把每分区众多小文件打包成更少的大文件；目标约 128 MB–1 GB（常为 128–256 MB），文件数 = 总字节 / 目标大小。
3. **原生能力**：Delta OPTIMIZE/ZORDER、Iceberg rewrite_data_files、Hudi clustering 做原子合并。

**面试追问：**

1. **为何目标对准 128–256 MB**：匹配 HDFS 块大小与 Parquet 行组，使 task 粒度合适、既不碎也不过大。
2. **合并时如何不影响读者**：湖仓格式用快照隔离/原子提交重写，读者继续读旧快照，提交后无缝切换。
3. **repartition 还是 coalesce**：需要跨分区均匀重分布用 `repartition`（含 shuffle），仅减少文件数且避免 shuffle 用 `coalesce`。

**要点：**

1. **危害**：小文件 → 元数据膨胀、列举变慢、每个文件一个小 task。
2. **机制**：合并作业通过重写把每分区众多小文件打包成更少的大文件。
3. **大小与数量**：目标约 128 MB–1 GB（常为 128–256 MB）；文件数 = 总字节 / 目标大小。
4. **原生工具**：Delta OPTIMIZE/ZORDER、Iceberg rewrite_data_files、Hudi clustering 做原子合并。

### 76. 外部缓存与加速层

**频率：** 中

**题目：** 像 Alluxio 这样的层解决什么问题？何时该在大数据栈中加入它？

**方案：**

1. **存算分离的代价**：计算与存储分离（Spark/Presto 跑在 S3/HDFS 之上）意味着每次查询都要付远程读延迟，而在云对象存储上还有按请求计费和出口流量费，外加热点前缀上的限流。
2. **分布式缓存层**：**Alluxio**（及类似的存储缓存）在计算与底层存储之间插入一层**分布式缓存**：热数据被缓存在计算节点的内存/SSD 中，以接近本地的延迟提供服务，同时 Alluxio 在异构后端（S3、HDFS、GCS）之上呈现一个**统一命名空间**。
3. **最佳场景**：它在对同一数据集的**重复读取**上表现出色——交互式 BI、迭代式 ML、多个作业共享表——以及在计算与存储解耦时恢复**数据本地性**。
4. **与 persist 的区别**：注意它跨集群缓存数据，不同于 Spark 进程内的 `persist()`（后者只存在于单个应用的 executor 内）；Alluxio 是跨应用的，并能在作业重启后存活。
5. **取舍**：增加基础设施、内存/SSD 成本，以及缓存一致性/淘汰管理，所以只有在读放大很高时它才物有所值。

**演进：**

1. **定位**：在计算与对象/远程存储之间加一层分布式缓存，实现接近本地的读取。
2. **收益**：降低远程读延迟、请求/出口成本、热点前缀限流；统一命名空间；最适合重复/交互/迭代读取及计算存储解耦。
3. **特性与代价**：跨应用且持久，不同于单应用的 persist()；代价是基础设施加一致性管理。

**面试追问：**

1. **何时不值得加 Alluxio**：读放大低、数据一次性读、或已有本地存储时，额外的内存/SSD 与运维成本无法回本。
2. **缓存一致性如何保证**：当底层存储被外部写入更新时需要失效/刷新策略，否则可能读到陈旧缓存。
3. **和 persist 的根本差异**：`persist()` 作用域是单应用 executor，随应用结束而丢失；Alluxio 跨应用共享并持久存活。

**要点：**

1. **定位**：在计算与对象/远程存储之间加一层分布式缓存，实现接近本地的读取。
2. **收益**：降低远程读延迟、请求/出口成本、热点前缀限流；统一命名空间。
3. **场景**：最适合重复/交互/迭代读取以及计算存储解耦（本地性）。
4. **区别与代价**：跨应用且持久，不同于单应用的 persist()；代价是基础设施加一致性管理。

### 77. 云成本优化

**频率：** 高

**题目：** 如何优化云上大数据负载的成本？

**方案：**

1. **spot/preemptible 实例**：把可中断的工作跑在 **spot/preemptible 实例**上（最多便宜约 70–90%）——对 **executor/worker 节点**是安全的，因为 Spark 会重算丢失的 task，但要把 **driver/master 和 shuffle service 放在按需实例上**以避免整个作业失败；混用实例类型并配置回退到按需。
2. **自动扩缩**：给集群做**自动扩缩**（动态分配、托管自动扩缩），只为在用容量付费，并关停空闲集群。
3. **存储分层**：存储方面，用**分层/生命周期策略**（S3 Standard → Infrequent Access → Glacier）自动把冷数据下沉。
4. **减少请求数**：合并小文件以减少请求数。
5. **减少扫描字节**：用**列式格式 + 压缩 + 分区裁剪**让查询扫描更少数据——在 BigQuery/Athena 这类按扫描计费的引擎里，扫描字节数*就是*账单。
6. **选型与监控**：此外要合理选型实例、优先用临时作业集群而非常驻集群，并用成本标签和预算做监控以归因支出。

**演进：**

1. **计算定价**：worker 用 spot/preemptible（Spark 重跑 task）；driver/master + shuffle 留在按需实例。
2. **弹性**：自动扩缩并自动关停空闲集群；合理选型并使用临时作业集群。
3. **存储与扫描**：存储生命周期分层（Standard → IA → Glacier）、合并小文件减少请求数；列式 + 压缩 + 分区裁剪减少扫描字节 = 在 Athena/BigQuery 上直接省钱。

**面试追问：**

1. **为何 driver 不能用 spot**：driver/master 丢失会导致整个作业失败且无法重算，必须放按需实例保证稳定。
2. **按扫描计费如何省钱**：列式格式 + 压缩 + 分区裁剪让引擎只读必要字节，因为扫描字节数直接等于账单。
3. **常驻集群 vs 临时集群**：临时作业集群跑完即释放，避免空闲计费，适合批作业；常驻集群仅在高频交互下才划算。

**要点：**

1. **计算**：worker 用 spot/preemptible（Spark 重跑 task）；driver/master + shuffle 留在按需实例。
2. **弹性**：自动扩缩并自动关停空闲集群；合理选型并使用临时作业集群。
3. **存储**：存储生命周期分层（Standard → IA → Glacier）；合并小文件以减少请求数。
4. **扫描**：列式 + 压缩 + 分区裁剪减少扫描字节 = 在 Athena/BigQuery 上直接省钱。

### 78. Serverless 大数据

**频率：** 中

**题目：** 像 EMR Serverless、Databricks、BigQuery 这类 serverless 大数据平台的弹性取舍是什么？

**方案：**

1. **无需预配**：Serverless 平台省去了集群预配：你提交一个作业或查询，平台按需分配容量、自动扩缩，并按**消耗的资源秒数或字节/slot 数**计费，而不是为空闲集群时间付费。
2. **各平台形态**：**EMR Serverless** 和 **Databricks serverless（SQL/作业）**按作业上下伸缩 executor；**BigQuery** 全托管运行，采用按需（按扫描字节）定价或预留 **slot**（容量单位）以获得可预测成本。
3. **好处**：零空闲成本、启动快、无需集群运维——非常适合突发、不可预测或间歇性的负载。
4. **取舍**：对实例类型/调优的控制更少、可能有**冷启动**延迟、对重度稳定负载的成本更难预测（此时预留/承诺型集群或 slot 预留更便宜）、共享池上的吵闹邻居波动，以及可能的功能/库限制。
5. **经验法则**：突发和开发/临时性工作用 serverless；大型、连续、可预测的流水线用预配/预留。

**演进：**

1. **计费模型**：无需预配；自动扩缩并按资源秒 / 字节 / slot 计费，而非空闲时间。
2. **优势**：零空闲成本、启动快、无运维——适合突发、间歇、临时性工作。
3. **边界**：取舍是调优控制更少、冷启动、稳定高负载下成本可预测性更弱；稳定重度流水线通常在预留容量/slot 或预配集群上更便宜。

**面试追问：**

1. **为何稳定负载用 serverless 反而贵**：持续高利用率下按用量计费缺少规模折扣，预留 slot/承诺型集群的单价更低。
2. **冷启动影响什么场景**：对延迟敏感的交互查询或短作业，首调度的容量分配延迟占比高。
3. **BigQuery 按需 vs slot 预留**：零散/不可预测查询用按扫描字节的按需定价，稳定大量查询用 slot 预留锁定成本。

**要点：**

1. **计费**：无需预配；自动扩缩并按资源秒 / 字节 / slot 计费，而非空闲时间。
2. **优势**：零空闲成本、启动快、无运维——适合突发、间歇、临时性工作。
3. **取舍**：调优控制更少、冷启动、稳定高负载下成本可预测性更弱。
4. **选型**：稳定重度流水线通常在预留容量/slot 或预配集群上更便宜。

### 79. 大数据作业的基准测试与性能剖析

**频率：** 中

**题目：** 如何找出一个慢 Spark 作业的瓶颈？

**方案：**

1. **从 Spark UI 入手**：先看 **Spark UI**。**stages/时间线**视图能显示哪个 stage 占主导、task 是否均衡。
2. **判别倾斜还是并行度不足**：若某个 stage 里一个 task 的时长和 input/shuffle-read 远超中位数，说明是**倾斜**，而所有 task 都均匀地慢则指向并行度不足或资源受限。
3. **关键指标**：检查 **shuffle read/write 和溢写**指标（内存和磁盘溢写 = 压力——加分区/内存）、**GC 时间**（高 = 内存压力或堆太小），以及**事件时间线**看时间花在计算、调度延迟还是 task 反序列化上。
4. **SQL 标签页**：**SQL 标签页**展示物理计划、每算子行数，以及扫描读太多（缺少裁剪）或 join 未做广播的地方。
5. **归类对症**：把瓶颈归类为 I/O、shuffle、CPU/序列化、GC/内存或调度，再对症处理。
6. **可复现基准**：为了可复现的基准，固定数据和配置、一致地预热缓存、多次试验、每次只改一个变量。

**演进：**

1. **先看 UI**：先看 Spark UI：stage 时间线揭示主导 stage 和倾斜（某个超大 task）。
2. **看指标定类别**：关注 shuffle read/write、溢写、GC 时间、调度延迟以定位瓶颈类别；SQL 标签页展示物理计划、每算子行数、缺失的裁剪或未广播的 join。
3. **严谨基准**：固定输入/配置、多次试验、每次只改一个变量。

**面试追问：**

1. **如何从 UI 区分倾斜与并行度不足**：单个 task 显著超过中位数是倾斜，全体 task 均匀地慢是并行度/资源不足。
2. **高 GC 时间说明什么**：内存压力或堆太小，考虑加内存、减每 executor 核数、减少缓存或优化数据结构。
3. **为何基准要每次只改一个变量**：隔离变量才能把性能变化归因到具体改动，避免多因素混淆结论。

**要点：**

1. **入口**：先看 Spark UI：stage 时间线揭示主导 stage 和倾斜（某个超大 task）。
2. **指标**：关注 shuffle read/write、溢写、GC 时间、调度延迟以定位瓶颈类别。
3. **SQL 标签页**：展示物理计划、每算子行数、缺失的裁剪或未广播的 join。
4. **基准**：严谨基准：固定输入/配置、多次试验、每次只改一个变量。

### 80. 为对象存储选择分区策略

**频率：** 高

**题目：** 如何为对象存储上的数据集选择分区列？什么是过度分区？

**方案：**

1. **物理分区与裁剪**：物理分区把数据写成 `.../date=2026-08-12/region=us/` 这样的目录布局，使引擎能根据查询谓词**裁剪**整个分区而无需扫描。
2. **选列标准**：选择那些 (a) 频繁出现在查询**过滤条件**中、且 (b) **基数适中**的列。对时序数据，**日期/时间**是经典选择。
3. **过度分区陷阱**：陷阱在于**过度分区**：选一个高基数列（user_id、精确到秒的时间戳）或嵌套过多列，会让目录数量爆炸，每个目录只装几个小文件——重新引发小文件问题、膨胀元数据、拖慢列举/计划。
4. **分区不足**：分区不足则使分区过大、无法有效裁剪。
5. **目标尺度**：目标是让分区落在约几百 MB 到 GB 的范围、目录数量合理。
6. **高基数替代方案**：对高基数过滤，用**分桶（bucketing）**或湖仓的**数据跳过/Z-ordering/clustering**（Iceberg 隐藏分区、Delta Z-order）而非分区列。用真实查询模式来验证，并关注每分区文件数。

**演进：**

1. **选列**：按过滤中常见且基数适中的列分区；日期/时间是经典选择。
2. **收益**：分区支持分区裁剪 → 扫描更少数据。
3. **陷阱与替代**：过度分区（高基数/列过多）→ 小文件、元数据膨胀、计划变慢；对高基数过滤用分桶或 Z-order/数据跳过/隐藏分区。

**面试追问：**

1. **为什么高基数列不宜做分区列**：目录数量爆炸、每目录仅几个小文件，重演小文件与元数据膨胀，并拖慢列举与计划。
2. **分桶和分区的区别**：分区按值切目录支持裁剪，分桶按哈希固定桶数、适合高基数列的 join/聚合而不炸目录。
3. **如何验证分区策略**：用真实查询模式检验裁剪效果，并关注每分区文件数与分区大小是否落在合理区间。

**要点：**

1. **选列**：按过滤中常见且基数适中的列分区；日期/时间是经典选择。
2. **收益**：分区支持分区裁剪 → 扫描更少数据。
3. **过度分区**：过度分区（高基数/列过多）→ 小文件、元数据膨胀、计划变慢。
4. **替代方案**：对高基数过滤用分桶或 Z-order/数据跳过/隐藏分区。

### 81. LSM-tree 存储引擎

**频率：** 高

**题目：** LSM-tree 如何工作，为什么它是写密集型 NoSQL 引擎的首选存储模型？

**方案：**

1. **写路径顺序化**：**Log-Structured Merge-tree（日志结构合并树）**把随机写转化为顺序写。每次写入首先追加到 **预写日志（WAL）**（保证持久性），再更新内存中的有序结构 **memtable**。
2. **刷盘为不可变 SSTable**：当 memtable 写满时，它会被刷成一个不可变、有序的磁盘文件 **SSTable**；写入从不修改已有文件，因此保持快速且顺序化。
3. **compaction 合并**：随着时间推移会累积大量 SSTable，因此后台的 **compaction（合并）**进程会将它们合并，丢弃被覆盖的值和墓碑（tombstone）。
4. **读路径优化**：读取必须检查 memtable 加上可能的多个 SSTable，所以引擎会加入 **Bloom filter**（跳过不可能包含某 key 的 SSTable）和稀疏块索引。
5. **核心权衡**：**写放大 vs 读放大**：leveled compaction 提供更紧凑的读/空间上界但重写数据更多；size-tiered compaction 写入更便宜但会导致空间和读放大。
6. **典型落地**：这种写优化设计支撑了 Cassandra、HBase、RocksDB 和 LevelDB。

**演进：**

1. **随机写到顺序写**：从原始随机写磁盘，演进为 WAL + memtable 的顺序追加模型。
2. **单文件到多 SSTable**：内存写满刷成不可变 SSTable，累积后由 compaction 合并清理。
3. **compaction 策略分化**：从简单合并演进为 leveled（读/空间优化）与 size-tiered（写优化）两条路线。

**面试追问：**

1. **Bloom filter 作用**：为什么读取要靠 Bloom filter，它如何降低无谓的 SSTable 扫描？
2. **写放大来源**：leveled 与 size-tiered 的写放大/读放大差异从何而来，如何按负载取舍？
3. **崩溃恢复**：WAL 在宕机后如何重建 memtable，持久性是怎样保证的？

**要点：**

1. **写路径**：WAL + 内存 memtable → 刷成不可变有序 SSTable；写入是顺序追加。
2. **compaction**：compaction 合并 SSTable，丢弃被覆盖的值和 tombstone。
3. **读路径**：读取检查 memtable + SSTable；Bloom filter 与块索引降低读取代价。
4. **核心权衡**：leveled（读/空间优化）vs size-tiered（写优化）compaction。

### 82. HBase 内部机制：region、split 与 hotspotting

**频率：** 中

**题目：** HBase 如何在 region 间分布数据，row-key 设计与 compaction 又如何影响性能？

**方案：**

1. **表与 region 分区**：HBase 将一张表存储为一个有序映射，按 **region** 分区，每个 region 拥有一段连续的 **row-key 范围**。
2. **服务与元数据**：region 由 **RegionServer** 服务；**HMaster** 负责分配与负载均衡，元数据存放在 `hbase:meta` 表中（通过 ZooKeeper 定位）。
3. **hotspotting 问题**：由于行按 key 物理排序，单调递增的 key（时间戳、顺序 ID）会把所有写入都发送到 **某台服务器上的最后一个 region**——这就是经典的 **hotspotting（热点）**问题。
4. **缓解手段**：**salting**（前缀加哈希桶）、**key 哈希**或字段反转来分散写入。
5. **region split**：当某个 region 增长超过阈值时会发生 **region split**，分裂为两个子 region，随后可能在服务器间重新均衡。
6. **region 内 LSM 引擎**：每个 region 内部使用 LSM 引擎：写入命中 WAL 和 MemStore，刷成 **HFile**，**minor compaction** 合并小 HFile，而 **major compaction** 按列族重写所有文件，物理删除被删单元和过期版本。major compaction 的 I/O 开销很大，通常安排在低峰期。

**演进：**

1. **范围分区到自动 split**：从固定 region 范围演进为超阈值自动 split 并重新均衡。
2. **顺序 key 到打散 key**：为规避 hotspotting，row-key 设计从单调递增演进为 salting/哈希/反转。
3. **minor 到 major compaction**：从合并小 HFile 的 minor compaction 演进到按列族全量重写并清除删除的 major compaction。

**面试追问：**

1. **定位一行**：客户端如何通过 ZooKeeper 和 `hbase:meta` 定位某行所在的 RegionServer？
2. **salting 代价**：salting 解决写热点，但会给范围扫描带来什么代价？
3. **major compaction 调度**：为什么 major compaction 要排在低峰期，它对读延迟有何影响？

**要点：**

1. **分区与定位**：表 = 有序行，按范围切分为 region，由 RegionServer 服务；ZooKeeper + meta 定位。
2. **热点修复**：顺序 row-key 导致 hotspotting；用 salting、哈希或 key 反转修复。
3. **split**：region 变大时自动 split，然后在集群中重新均衡。
4. **compaction**：minor compaction 合并 HFile；major compaction 重写所有文件并清除删除/旧版本（I/O 重）。

### 83. Cassandra 数据建模

**频率：** 高

**题目：** 如何在 Cassandra 中建模数据，partition key 与 clustering key 有何区别？

**方案：**

1. **查询优先建模**：Cassandra 建模是 **查询优先（query-first）**的：先列举读查询，然后为每个查询设计一张表，使每次读取只命中单个分区——因为没有高效的 join 或任意过滤。
2. **主键两部分**：**主键（primary key）**由两部分组成。
3. **partition key**：（第一个组件，可为复合）被哈希以决定哪些节点拥有该行；共享同一 partition key 的所有行存放在一起，是分布和单分区读取的单位。
4. **clustering key**：（其余组件）定义 **分区内的排序顺序**，支持高效的范围扫描和 `ORDER BY`。
5. **反范式化**：这促成刻意的 **反范式化（denormalization）**：同一份数据被写入多张为不同查询而设计的表。
6. **partition key 设计**：好的 partition key 具备 **高基数和均匀分布**，同时保持分区大小有界——过粗的 key（如单一天）会造成无界的“热”分区，而过细的 key 又阻碍范围查询。
7. **避免反模式**：你要避免 `ALLOW FILTERING` 和跨分区扫描，接受写端的数据重复以换取可预测的低延迟读取。

**演进：**

1. **范式到反范式**：从关系型的范式化 join 演进为按查询反范式化、同一数据写多表。
2. **主键职责分离**：主键演进为 partition key（放置/分布）+ clustering key（分区内排序）两层职责。
3. **key 粒度调优**：partition key 从过粗（热分区）或过细（阻碍范围）演进到高基数、均匀且大小有界。

**面试追问：**

1. **复合 partition key**：何时需要复合 partition key，它如何改变数据放置与读取？
2. **ALLOW FILTERING 代价**：为什么要避免 `ALLOW FILTERING`，它在底层做了什么？
3. **热分区排查**：如何发现并修复无界的热分区（如按天分区）？

**要点：**

1. **建模方式**：按查询建模；一个查询 = 一张表 = 理想情况下读取一个分区（无 join）。
2. **主键职责**：partition key → 放置/分布；clustering key → 分区内排序与范围扫描。
3. **反范式化**：刻意反范式化：将数据在多张按查询设计的表中重复。
4. **key 设计**：partition key 要保证均匀分布和有界大小；避免 ALLOW FILTERING 和无界热分区。

### 84. 实时 OLAP 引擎内部机制

**频率：** 高

**题目：** Druid、Pinot、ClickHouse 这类实时 OLAP 引擎如何实现亚秒级分析查询？

**方案：**

1. **列式存储**：这些引擎都是 **列式（columnar）**的，将数据存储在不可变、自包含的 **segment**（Druid/Pinot）或 **part**（ClickHouse）中，按时间分区并大量建索引。
2. **按列压缩扫描**：因为每列单独存储并压缩（字典、行程编码 RLE、delta），查询只扫描它涉及的列。
3. **摄取时预聚合**：Druid 和 Pinot 支持 **摄取时预聚合（rollup）**，在定义的粒度上把原始事件折叠成聚合行，使许多看板读取预计算结果。
4. **索引与查询层**：它们还加入丰富的索引——维度上的 **bitmap/倒排索引**用于快速过滤，加上有序/范围索引——以及一个 scatter-gather 查询层，向 segment 服务器扇出并合并部分聚合。
5. **ClickHouse MergeTree**：ClickHouse 则依赖 **MergeTree** 家族：数据按 **主键/排序键**排序，配合稀疏索引和跳数索引（skipping index），后台 **merge** 合并 part（可选地通过 `AggregatingMergeTree` 聚合）。
6. **实时与历史分离**：三者都把 **实时摄取**（从内存/新鲜 segment 立即可查）与 **历史**优化存储分离，同时兼顾新鲜度与速度。

**演进：**

1. **行式到列式**：从行式 OLTP 存储演进为按列压缩、只扫描涉及列的列式存储。
2. **原始事件到 rollup**：从查询时聚合演进为摄取时 rollup 预聚合，降低看板读取成本。
3. **实时与历史分层**：从单一存储演进为实时（新鲜/内存）与历史（优化）两层并存。

**面试追问：**

1. **rollup 取舍**：摄取时 rollup 提升查询速度，但牺牲了什么（明细可查性）？
2. **bitmap vs 跳数索引**：Druid/Pinot 的 bitmap 索引与 ClickHouse 的跳数索引适用场景有何不同？
3. **scatter-gather 瓶颈**：scatter-gather 查询在 segment 数巨大时会遇到什么瓶颈？

**要点：**

1. **列式基础**：列式、压缩、不可变、按时间分区的 segment/part，逐列扫描。
2. **Druid/Pinot**：摄取时 rollup 预聚合 + bitmap/倒排索引；scatter-gather 查询。
3. **ClickHouse**：MergeTree 有序主键、稀疏 + 跳数索引、后台 merge。
4. **分层**：分离实时（新鲜、内存）与历史（优化）层，兼顾新鲜度与速度。

### 85. 大规模搜索与分析中的 Elasticsearch

**频率：** 高

**题目：** Elasticsearch 如何利用倒排索引和分片来支撑大规模的搜索与聚合？

**方案：**

1. **倒排索引**：Elasticsearch（基于 Lucene）将文档索引进 **倒排索引（inverted index）**：对每个分析后的词项（term），它存储一个包含该词项的文档倒排列表（posting list），使全文检索和布尔/短语查询很快。
2. **分片与副本**：一个索引被切分为 **主分片（primary shard）**（每个都是独立的 Lucene 索引）加上用于高可用和读吞吐的 **副本分片（replica shard）**；分片数量在创建时基本固定，因此容量规划很重要。
3. **写入与近实时**：写入先到主分片再复制；新文档落入内存缓冲，在 **refresh** 时刷成不可变的 **段（segment）**（近实时，约 1 秒），这也是 ES 并非立即一致的原因。段会周期性地被合并。
4. **scatter-gather 搜索**：搜索是 **scatter-gather**：协调节点查询每个分片并合并结果。
5. **聚合走 doc values**：对于 **分析**，聚合运行在 **doc values**（一种列式的磁盘结构）之上而非倒排索引，从而实现快速的 group-by、直方图和指标计算。
6. **扩展陷阱**：扩展陷阱包括 **深分页**（应使用 `search_after`）、过度分片，以及给堆内存造成压力的高基数聚合。

**演进：**

1. **检索到分析**：从倒排索引驱动的全文检索，演进到 doc values 驱动的聚合分析。
2. **单索引到分片+副本**：从单一 Lucene 索引演进为固定主分片 + 副本的分布式架构。
3. **深分页优化**：从 `from/size` 深分页演进到 `search_after` 以规避堆压力。

**面试追问：**

1. **为何不立即一致**：refresh 的约 1 秒延迟如何导致 ES 的近实时而非强一致？
2. **分片数固定**：既然分片数创建时基本固定，容量规划要考虑哪些因素？
3. **高基数聚合**：高基数聚合为什么给堆内存造成压力，如何缓解？

**要点：**

1. **两类结构**：倒排索引（term → posting list）驱动全文检索；doc values（列式）驱动聚合。
2. **分片模型**：索引 = 主分片（数量固定）+ 副本；写入复制，读取跨分片 scatter-gather。
3. **近实时**：文档在 refresh（约 1 秒）后作为不可变、稍后合并的段可见。
4. **陷阱**：警惕过度分片、深分页（用 search_after）和高基数聚合。

### 86. 大规模图处理

**频率：** 中

**题目：** Pregel/GraphX 的以顶点为中心模型如何处理海量图，它与图数据库有何不同？

**方案：**

1. **MapReduce 的不适配**：大规模图算法（PageRank、最短路径、连通分量）在 MapReduce 上表现不佳，因为它们要反复迭代整张图。
2. **Pregel 以顶点为中心**：**Pregel** 引入了建立在 **BSP（Bulk Synchronous Parallel，整体同步并行）**超步（superstep）之上的 **以顶点为中心、“像顶点一样思考”**的模型。
3. **超步机制**：在每个超步中，每个活跃顶点接收上一步的消息、更新自身状态，并沿着边发送消息；一个全局屏障（barrier）同步各超步，当所有顶点都 **投票停止（vote to halt）**时任务结束。
4. **分布式执行**：这天然映射到分布式执行——顶点被分区到各 worker 上，只有消息跨网络传输。
5. **GraphX 实现**：**GraphX**（Spark）通过其 RDD 上的 `Pregel` API 和 `aggregateMessages` 表达同样的思想，统一了图处理与数据并行处理。
6. **与图数据库的区别**：这与 **图数据库**（如 Neo4j）不同：数据库针对存储、已建索引的关系优化 **低延迟遍历和事务型 OLTP 查询**，而 Pregel/GraphX 是用于整图迭代计算的 **批量分析**引擎。

**演进：**

1. **MapReduce 到 Pregel**：从在 MapReduce 上别扭地迭代整图，演进为以顶点为中心的 BSP 模型。
2. **Pregel 到 GraphX**：从独立 Pregel 系统演进为 Spark 上的 GraphX，统一图与数据并行处理。
3. **批量分析 vs 事务遍历**：图计算分化为批量整图分析与图数据库的低延迟事务遍历两条路线。

**面试追问：**

1. **vote to halt**：投票停止机制如何决定整个任务何时终止？
2. **消息量爆炸**：某些图算法下跨网络消息量会激增，如何通过 combiner/aggregateMessages 缓解？
3. **选型边界**：什么样的问题该用 Pregel/GraphX，什么样的该用 Neo4j？

**要点：**

1. **迭代难题**：迭代图算法需要反复的全图遍历——在 MapReduce 上很别扭。
2. **Pregel 模型**：Pregel = 以顶点为中心的 BSP：接收 → 计算 → 发送的超步，屏障同步，所有顶点投票停止时结束。
3. **分布式执行**：顶点分区到各 worker，只有消息跨网络传输。GraphX 将其带入 Spark。
4. **定位区别**：Pregel/GraphX = 批量整图分析；图数据库 = 低延迟事务型遍历。

### 87. 向量数据库与 ANN 检索

**频率：** 高

**题目：** 向量数据库如何在大规模下进行嵌入相似度检索，HNSW 和 IVF 索引如何工作？

**方案：**

1. **嵌入与最近邻**：向量数据库存储高维 **嵌入（embedding）**，并按相似度（cosine/点积/L2）回答 **最近邻**查询。
2. **ANN 换加速**：精确检索每次查询为 O(N)，在数十亿向量规模下不可行，因此它们使用 **近似最近邻（ANN，Approximate Nearest Neighbor）**索引，用少量召回率换取巨大的加速。
3. **HNSW**：**HNSW**（Hierarchical Navigable Small World）构建一个多层邻近图：检索从稀疏的顶层开始并贪婪地向下下降，提供近似对数的查询时间和高召回率，代价是高内存和构建时间（通过 `M` 和 `efConstruction/efSearch` 调优）。
4. **IVF**：**IVF**（Inverted File，倒排文件）则将向量 **聚类**（k-means）进若干 cell，查询时只探测 `nprobe` 个最近的 cell——内存更省、召回/速度可调——并通常与 **PQ（Product Quantization，乘积量化）**结合以压缩向量，用于内存受限的十亿级数据集。
5. **生产增强**：生产系统还会加入 **元数据过滤**（混合查询）、分片，并经常将稠密向量得分与关键词/BM25 得分结合以实现混合检索。

**演进：**

1. **精确到近似**：从 O(N) 的精确最近邻演进为以召回率换速度的 ANN 索引。
2. **HNSW 与 IVF 分化**：ANN 分化为高召回高内存的 HNSW 图与可调省内存的 IVF 聚类两条路线。
3. **纯向量到混合检索**：从单纯向量得分演进为叠加元数据过滤与关键词/BM25 的混合检索。

**面试追问：**

1. **ef 调参**：`efConstruction/efSearch` 与 `M` 如何在召回、速度、内存间折中？
2. **nprobe 取舍**：IVF 的 `nprobe` 增大如何影响召回与延迟？
3. **PQ 精度损失**：PQ 压缩为什么会牺牲精度，何时值得用在十亿级数据集？

**要点：**

1. **换取规模**：精确最近邻是 O(N)；ANN 索引以召回率换速度实现规模化。
2. **HNSW**：分层可导航图，高召回高速度、高内存；调 M/ef。
3. **IVF**：聚类成 cell，探测 nprobe 个最近的；配合 PQ 压缩用于十亿级。
4. **生产增强**：生产系统加入元数据过滤、分片和混合（向量 + 关键词/BM25）检索。

### 88. 选择 NoSQL 数据模型

**频率：** 高

**题目：** 如何在 key-value、wide-column 和 document 数据库之间选择，各有什么权衡？

**方案：**

1. **匹配访问模式**：让 **数据模型匹配访问模式**。
2. **key-value**：**key-value** 存储（Redis、最简形式的 DynamoDB）把一个不透明的 key 映射到一个 blob——最快最简单，适合缓存、会话和按已知 key 查找，但无法按值查询。
3. **wide-column**：**wide-column** 存储（Cassandra、HBase）使用 partition key 加稀疏、有序的列；它们擅长 **海量写吞吐和分区内范围扫描**（时序、事件日志、feed），但要求严格的查询优先建模且无 join。
4. **document**：**document** 存储（MongoDB）保存自描述的 JSON/BSON，具备 **二级索引和对任意字段的丰富查询**，适合演进式 schema 和面向聚合的实体（商品目录、用户画像），但在写吞吐和跨文档一致性上有一定代价。
5. **横切因素**：**一致性模型**（CP vs AP、可调仲裁）、**查询灵活性** vs 原始性能，以及关系是否更适合用 **图**数据库。
6. **诚实默认**：诚实的默认做法通常是：只有当关系型数据库的规模或灵活性瓶颈真正显现时，才去动用这些 NoSQL。

**演进：**

1. **关系型到 NoSQL**：从默认关系型，演进到规模/灵活性瓶颈显现时才引入 NoSQL。
2. **按访问模式分化**：NoSQL 按访问模式分化为 key-value、wide-column、document 三类。
3. **加入横切维度**：选型从单看性能演进到综合一致性（CP/AP）与查询灵活性。

**面试追问：**

1. **CP vs AP**：可调仲裁如何让同一系统在 CP 与 AP 间切换？
2. **何时上图数据库**：关系复杂到什么程度就应该用图数据库而非 document？
3. **迁移时机**：如何判断关系型真正触到规模/灵活性瓶颈？

**要点：**

1. **key-value**：最快，仅按 key 查找——缓存、会话。
2. **wide-column**：partition + 有序列，巨大的写吞吐和分区内范围；严格的查询优先建模。
3. **document**：丰富的按字段查询和灵活 schema；跨文档一致性/吞吐较弱。
4. **选型原则**：依据访问模式、一致性（CP/AP）和查询灵活性选择；没有真正理由不要放弃关系型。

### 89. 分布式存储中的二级索引

**频率：** 中

**题目：** 分布式数据存储中的本地二级索引与全局二级索引有何区别，各有什么一致性和性能代价？

**方案：**

1. **二级索引的必要**：**二级索引（secondary index）**让你能按非主键属性查询，但在分区存储中，索引本身也必须分布式，存在两种策略。
2. **本地索引**：**本地（分区）索引**将索引项与数据存放在 **同一节点/分区**上（如 Cassandra 二级索引、DynamoDB LSI）。
3. **本地索引代价**：写入保持便宜且本地化，但对索引字段的查询通常没有 partition key，因此必须 **在所有分区上 scatter-gather**——节点少时尚可，规模大时代价高。
4. **全局索引**：**全局索引**是一个按 **被索引的值**为 key 的、单独分区的结构（如 DynamoDB GSI、Cassandra 的 SASI/物化视图模式）：查找直接命中持有匹配项的那个分区，所以 **读取高效**。
5. **全局索引代价**：但每次写入都必须 **更新一个远程索引分区**，带来写放大、跨分区协调，以及基表与索引之间通常为 **最终（异步）一致性**。
6. **一般规律**：本地 = 写便宜/读昂贵；全局 = 读高效/写代价高且往往最终一致。

**演进：**

1. **主键到非主键查询**：从只能按主键查询，演进到用二级索引支持非主键属性查询。
2. **本地到全局**：从同置的本地索引（读需 scatter-gather）演进到按值分区的全局索引（读定向）。
3. **强一致到最终一致**：全局索引为换取读效率，基表与索引间通常退化为最终一致。

**面试追问：**

1. **scatter-gather 成本**：本地索引的 scatter-gather 为什么随节点数增长而恶化？
2. **写放大来源**：全局索引的写放大与跨分区协调具体发生在哪一步？
3. **一致性影响**：基表与全局索引的最终一致会给读取带来哪些异常？

**要点：**

1. **定义**：二级索引 = 按非主键属性查询；在分区存储中必须分布式。
2. **本地索引**：与数据同置，写便宜，但读取需 scatter-gather 所有分区。
3. **全局索引**：按被索引值分区，读取高效定向，但写入命中远程分区。
4. **全局代价**：全局索引带来写放大，且通常与基表最终一致。

### 90. 读/写路径、tombstone 与 compaction 陷阱

**频率：** 中

**题目：** 在基于 LSM 的存储中，删除如何通过 tombstone 工作，它们又会导致哪些 compaction 陷阱？

**方案：**

1. **删除写 tombstone**：在 LSM 存储中，数据是不可变的，因此 **删除不能原地移除任何东西**——它写入一个 **tombstone（墓碑）**，一个记录某 key（或范围）已被删除的标记，用来遮蔽所有更旧的值。
2. **清除时机**：tombstone 只在 **compaction** 期间被物理清除，而且不是立即清除：它们必须至少存活 `gc_grace_seconds`，以便删除能传播到每个副本（否则某个陈旧副本可能让数据复活——**僵尸行 zombie rows**）。
3. **读路径受累**：读路径必须合并 memtable 和所有相关 SSTable 并遵守 tombstone，因此累积的 tombstone 会 **急剧拖慢读取**：一个扫描充满 tombstone 的分区的查询（如“插入后删除”的队列式负载）会读取并丢弃大量数据，甚至可能超时。
4. **其他陷阱**：**范围 tombstone** 和 TTL 过期会使 SSTable 膨胀；**大分区**放大 compaction I/O；不均衡的 size-tiered compaction 造成 **空间放大**。
5. **缓解手段**：包括避免删除密集/队列式模式、审慎使用 TTL、调优 compaction 策略，以及监控每次读取的 tombstone 数。

**演进：**

1. **原地删除到 tombstone**：因数据不可变，删除从原地移除演进为写 tombstone 标记。
2. **即时清除到延迟清除**：tombstone 清除从即时演进为必须存活 `gc_grace_seconds` 以避免僵尸行。
3. **发现到治理**：从被动遭遇读变慢，演进到主动避免删除密集模式、调优 compaction 并监控 tombstone 数。

**面试追问：**

1. **gc_grace 取舍**：`gc_grace_seconds` 调大或调小分别有什么风险？
2. **队列式反模式**：为什么“插入后删除”的队列式负载在 LSM 上是反模式？
3. **空间放大**：size-tiered compaction 不均衡时空间放大是如何产生的？

**要点：**

1. **tombstone 机制**：删除写入 tombstone（标记），而非原地移除；更旧的值被遮蔽。
2. **清除条件**：tombstone 仅在 gc_grace 之后由 compaction 清除，以避免僵尸/复活的行。
3. **读性能**：tombstone 堆积（队列式插入/删除模式）严重拖慢读取并可能超时。
4. **其他陷阱**：警惕大分区、范围/TTL tombstone 和空间放大；调优 compaction 并避免删除密集设计。

### 91. Feature store 与离线/在线一致性

**频率：** 高

**题目：** feature store 解决什么问题？如何保证离线/在线一致性（offline/online parity）与时点正确性（point-in-time correctness）？

**方案：**

1. **集中管理**：feature store 集中管理特征的计算、存储与服务，让训练与推理共用一份定义。
2. **避免训练/服务偏差**：从而避免一个经典 bug——某特征在批处理训练作业里以一种方式计算、在在线请求路径里又以略有差异的方式计算（训练/服务偏差，training/serving skew）。
3. **两层存储**：它有两层：**离线存储**（列式数仓/数据湖）保存完整历史用于训练，低延迟的**在线存储**（Redis、DynamoDB、Cassandra）按实体保存最新值用于服务。
4. **一致性来源**：一致性来自把转换只定义一次并物化到两侧，或复用同一份代码。
5. **时点正确性**：这是微妙之处——构建训练集时，你必须把每个标签按事件时间戳 *as of* 关联到当时的特征值，绝不能泄露未来数据，即基于事件时间的 as-of/point-in-time join。
6. **运维职责**：feature store 还负责管理新鲜度、回填（backfill）、版本管理以及跨团队复用。

**演进：**

1. **共用定义**：先用一份特征定义物化到离线/在线两侧，解决训练/服务偏差。
2. **时点正确**：再引入 point-in-time（as-of）join 防止未来特征值造成的标签泄露。
3. **规模化治理**：最终叠加新鲜度 SLA、回填、版本管理与跨团队复用。

**面试追问：**

1. **skew 来源**：训练/服务偏差具体从哪些环节产生，如何检测？
2. **as-of join**：point-in-time join 的实现成本与数据量关系如何？
3. **在线存储选型**：Redis、DynamoDB、Cassandra 在延迟与一致性上如何取舍？

**要点：**

1. **共用定义**：通过在离线与在线存储间共用一份特征定义，解决训练/服务偏差。
2. **两层存储**：离线存储 = 用于训练的历史；在线存储 = 用于推理的低延迟最新值。
3. **防泄露**：point-in-time（as-of）join 防止未来特征值造成的标签泄露。
4. **附加能力**：附带新鲜度 SLA、回填、版本管理与跨团队复用。

### 92. 数据版本管理与可复现性

**频率：** 中

**题目：** 如何对数据集做版本管理以让实验和流水线可复现？Delta/Iceberg time travel、lakeFS、DVC 各自解决什么问题？

**方案：**

1. **可复现定义**：可复现意味着你能针对某次运行最初看到的完全相同的数据，重新跑一遍流水线或重新训练模型；三种方案作用于不同层次。
2. **表格式 time travel**：（Delta、Iceberg、Hudi）每次提交产生一个不可变快照，因此你可以按版本或时间戳 `AS OF` 查询，并把训练固定到某个 snapshot ID。这是表级别的、湖仓原生的能力。
3. **lakeFS**：对*整个*对象存储提供类 git 的分支、提交与合并，带来原子的多表版本管理，以及用于实验或在真实数据上跑 CI 的隔离分支。
4. **DVC**：与 git 配套、面向文件/工件（数据集、模型）的版本管理，把大 blob 存到远端存储，git 只跟踪轻量指针——适合 ML 仓库。
5. **三要素固定**：把数据版本与代码（git SHA）、环境（容器/锁文件）版本结合起来；只有三者都固定，一次运行才算真正可复现。

**演进：**

1. **表级**：先用 Delta/Iceberg time travel 在表级别固定快照。
2. **对象存储级**：再用 lakeFS 对整个对象存储做类 git 的原子多表版本管理。
3. **工件级**：对大数据/模型工件用 DVC 的指针加远端存储；最终三要素（数据+代码+环境）一并固定。

**面试追问：**

1. **time travel 成本**：不可变快照的保留策略与存储成本如何权衡？
2. **lakeFS vs DVC**：两者在多表原子性与工件管理上如何选择？
3. **环境固定**：容器/锁文件如何纳入可复现体系？

**要点：**

1. **表级快照**：Delta/Iceberg time travel = 不可变快照，按版本/时间戳 AS OF 查询，表级别。
2. **对象存储**：lakeFS = 对整个对象存储做类 git 的分支/提交/合并，原子的多表操作。
3. **工件版本**：DVC = 用 git 跟踪的指针加远端存储，为大数据/模型工件做版本管理。
4. **三要素**：真正的可复现需要同时固定 数据 + 代码 SHA + 环境。

### 93. Data mesh 与面向领域的数据所有权

**频率：** 中

**题目：** 什么是 data mesh？与集中式数据平台相比，它的核心原则有哪些？

**方案：**

1. **背景**：data mesh 是对「单一中央数据团队拥有所有流水线却不懂任何业务领域」这一瓶颈的社会技术回应，围绕四条原则去中心化所有权。
2. **面向领域的所有权**：生产数据的团队（订单、支付）端到端拥有自己的分析数据。
3. **数据即产品**：每份数据集有负责人、SLA、文档、可发现性和质量保证，像给消费者提供的 API 一样对待。
4. **自助式数据平台**：中央平台团队提供铺好路的基础设施（存储、流水线、catalog、治理工具），让各领域无需重造轮子即可交付。
5. **联邦式计算化治理**：互操作性、安全、PII 等全局标准由中央定义，但以自动化/代码化方式在各领域强制执行。
6. **权衡**：它提升了可扩展性和领域契合度，但要求组织成熟度，做得不好就退化成重复劳动、彼此不一致的数据孤岛。

**演进：**

1. **从集中到去中心**：先把流水线所有权从中央团队转移到懂数据的各领域。
2. **产品化**：再把数据集当作有 SLA、文档的产品对外提供。
3. **平台+治理**：最终用自助平台降低重造成本，用联邦治理保证全局一致。

**面试追问：**

1. **成熟度门槛**：组织需要具备什么能力才适合落地 data mesh？
2. **治理冲突**：联邦式治理如何平衡全局标准与领域自治？
3. **失败模式**：做得差为何会退化成不一致的数据孤岛？

**要点：**

1. **四原则**：领域所有权、数据即产品、自助式平台、联邦式治理。
2. **所有权转移**：把流水线所有权从中央团队转移到懂数据的各领域。
3. **产品化**：数据产品有负责人、SLA、文档与质量——像 API 一样被消费。
4. **权衡**：对规模化很有力，但需要组织成熟度；做得差会变成彼此不一致的孤岛。

### 94. Data catalog、发现与元数据管理

**频率：** 中

**题目：** 除了可搜索的表清单，现代 data catalog 的有效性还在于什么？元数据如何采集并保持最新？

**方案：**

1. **有效性前提**：catalog 只有在元数据可信且能自动保持新鲜时才有用，因此其有效性取决于如何摄取和关联元数据，而非搜索框本身。
2. **三类元数据**：现代 catalog（DataHub、Amundsen、OpenMetadata、Unity Catalog）采集三类元数据——**技术元数据**（schema、分区、格式）、**运营元数据**（新鲜度、行数、上次运行、热度/查询日志）、**业务元数据**（负责人、描述、术语表、PII/分类标签）。
3. **自动采集**：元数据通过接入摄取、编排与查询引擎的**爬虫与推送式发射器**采集，因此随流水线运行而更新，而非靠会腐坏的人工录入。
4. **关键能力**：用于影响/根因分析的**列级血缘**、**自动 PII 分类**与打标、按热度和认证状态对发现结果排序，以及通过 **API** 暴露一切以便治理和访问策略消费。
5. **成败关键**：当 catalog 沦为人工的副业项目时采用就会失败；当元数据生成嵌入平台时才会成功。

**演进：**

1. **从表清单起步**：先有可搜索的表名，再补齐技术/运营/业务三类元数据。
2. **自动化采集**：从人工录入转向爬虫/推送式发射器随流水线更新。
3. **能力增强**：最终叠加列级血缘、自动 PII 分类与 API 优先的策略消费。

**面试追问：**

1. **血缘粒度**：列级血缘相比表级血缘在实现上有何额外代价？
2. **元数据新鲜度**：如何保证推送式发射器不漏数据、不陈旧？
3. **采用失败**：为什么纯人工维护的 catalog 会腐坏？

**要点：**

1. **三类元数据**：采集技术 + 运营 + 业务元数据，而不仅是表名。
2. **自动采集**：通过流水线中的爬虫/推送式发射器自动采集——保持新鲜，而非人工维护。
3. **关键能力**：列级血缘、自动 PII 分类、按热度/认证排序。
4. **API 优先**：让策略和工具消费元数据；纯人工的 catalog 会腐坏、采用失败。

### 95. 加密、列掩码与 tokenization

**频率：** 中

**题目：** 静态/传输加密、列级掩码（column masking）和 tokenization 有何区别？分别在什么场景使用？

**方案：**

1. **分层控制**：它们是分层的控制手段，而非彼此替代。
2. **传输加密**：（客户端、broker、存储之间的 TLS）保护在途数据。
3. **静态加密**：（KMS 托管密钥，最好用信封加密配以每数据集的数据密钥）保护落盘字节，并支持 **crypto-shredding**——删除密钥使数据不可恢复以满足擦除请求。二者都很粗粒度：任何有查询权限的人仍能看到明文值，所以要叠加更细的控制。
4. **列级/动态掩码**：在查询时按调用者角色生效——分析师看到 `****1234` 而反欺诈团队看到完整号码——存储数据保持不变，由策略驱动。
5. **tokenization**：用替身 token 替换敏感值，真实值保存在单独受保护的保险库（vault）中；与加密不同，它通常在没有 vault 查询时不可逆，且可保持格式，因此下游连接和分析可在 token 上进行而不暴露 PII。
6. **选型**：加密作为基线随处使用，掩码用于基于角色的读取控制，tokenization 用于原始值绝不能进入分析域的场景。

**演进：**

1. **基线加密**：先用传输（TLS）+ 静态（KMS/信封）加密作为粗粒度基线。
2. **角色脱敏**：再叠加列级/动态掩码做基于角色的读取控制。
3. **彻底隔离**：对原始值绝不能进入分析域的场景用 tokenization 加 vault。

**面试追问：**

1. **crypto-shredding**：信封加密如何支撑按数据集的密钥删除与擦除？
2. **掩码 vs tokenization**：二者在可逆性与格式保持上有何根本差异？
3. **性能影响**：查询时动态掩码对延迟有何开销？

**要点：**

1. **加密基线**：传输（TLS）+ 静态（KMS/信封）加密是粗粒度基线；支持 crypto-shredding。
2. **需叠加**：仅有加密时任何有查询权限者仍见明文——需叠加更细控制。
3. **动态掩码**：列级/动态掩码 = 查询时、基于角色的脱敏；存储数据不变。
4. **tokenization**：替身 token 加单独 vault 中的真实值；保持格式、可连接而不暴露 PII。

### 96. 多租户与数据隔离

**频率：** 中

**题目：** 在共享的大数据平台上，如何在存储、计算和访问层面为租户提供隔离？

**方案：**

1. **权衡本质**：多租户是在成本效率与故障爆炸半径之间做权衡，因此要在三个维度上隔离。
2. **存储隔离**：每租户单独的 bucket/数据库/schema（至少按租户分区/前缀），配以作用域收紧的 bucket 策略和表 ACL，使一个租户永远读不到另一个租户的路径；强隔离需求可能要求单独的账户/密钥。
3. **计算隔离**：通过资源队列（YARN/Kubernetes 命名空间、每租户数仓或独立 Spark 池）、配额和限流，防止一个租户的重作业饿死其他租户——即「吵闹邻居」问题。
4. **访问隔离**：一个集中式授权层（Ranger、Lake Formation、Unity Catalog）按租户身份强制行/列级策略，加上每租户加密密钥，使即便平台运维也无法跨越边界。
5. **隔离谱系**：从完全共享（最便宜、隔离最弱）到每租户完全独立基础设施（最强、最贵）；受监管的租户往往有理由选择独立那一端。
6. **审计**：每租户的审计日志用于证明隔离确实生效。

**演进：**

1. **共享起步**：先以完全共享降低成本，用分区/前缀做软隔离。
2. **三维强化**：再在存储、计算、访问三维度逐步收紧。
3. **独立到底**：对受监管租户走向每租户独立账户/密钥/基础设施。

**面试追问：**

1. **吵闹邻居**：计算配额与限流如何防止一个租户饿死其他租户？
2. **策略引擎**：Ranger/Lake Formation/Unity 如何强制行/列级策略？
3. **隔离证明**：如何用审计日志向合规方证明隔离生效？

**要点：**

1. **三维隔离**：在三个维度隔离：存储（bucket/schema/ACL）、计算（队列/配额）、访问（策略引擎）。
2. **防吵闹邻居**：计算配额防止「吵闹邻居」——一个租户饿死其他租户。
3. **集中授权**：集中式授权（Ranger/Lake Formation/Unity）配每租户密钥和行/列策略。
4. **谱系选择**：共享（便宜、弱）到每租户独立基础设施（强、贵）；按合规需求选择。

### 97. 数据湖/数仓的灾备与备份

**频率：** 中

**题目：** 如何为数据湖或数仓设计灾难恢复与备份？RPO 和 RTO 决定了什么？

**方案：**

1. **RPO/RTO**：**RPO**（恢复点目标）是你能容忍多少数据丢失；**RTO**（恢复时间目标）是恢复允许花多长时间——二者共同决定成本与架构。
2. **对象存储数据湖**：持久性很高，但你仍需用**跨区域复制**、**版本管理**和不可变/对象锁（WORM）来防范损坏和误删/恶意删除，使一个坏作业或勒索软件无法抹掉历史。
3. **湖仓表格式**：通过快照 **time travel** 和保留策略增加安全性，让你把表回滚到某个良好版本。
4. **数仓**：使用快照、时点恢复和跨区域副本。
5. **分级匹配**：按重要性匹配等级——第二区域的热备提供低 RTO 但成本高；周期性快照到更廉价存储则 RTO 较高但成本低。
6. **演练与隔离**：关键是要**定期演练恢复**——未经测试的备份不算备份——并把灾备凭证/账户分离，使同一次入侵无法同时摧毁主用和备份。

**演进：**

1. **定目标**：先用 RPO/RTO 确定可容忍的丢失与停机，进而定成本与架构。
2. **防删防损**：再用跨区域复制 + 版本管理 + 对象锁/WORM 防范损坏与删除。
3. **可回滚+演练**：最终用 time travel/时点恢复支持回滚，并定期演练、隔离凭证。

**面试追问：**

1. **RPO/RTO 取舍**：热备与周期快照如何在 RTO 与成本间权衡？
2. **防勒索**：对象锁/WORM 如何防范勒索软件抹除历史？
3. **演练验证**：为什么说未经测试的备份不算备份？

**要点：**

1. **目标定义**：RPO = 可容忍的数据丢失；RTO = 可容忍的停机时间——二者决定成本与设计。
2. **数据湖防护**：跨区域复制 + 版本管理 + 对象锁/WORM，防范损坏与删除。
3. **可回滚**：表格式 time travel 与数仓时点恢复支持回滚到良好状态。
4. **演练隔离**：定期演练恢复；隔离灾备凭证，使一次入侵无法同时抹掉主用与备份。

### 98. 数据可观测性与 SLA

**频率：** 中

**题目：** 除了流水线作业状态，数据可观测性还监控什么？新鲜度、体量、schema、分布检查如何构成数据 SLA？

**方案：**

1. **绿灯不等于正确**：流水线「绿灯」（作业跑了）不代表数据正确，因此数据可观测性沿多个支柱监控数据本身。
2. **新鲜度**：表是否在预期窗口内更新——最常见的失败。
3. **体量**：行数是否在正常范围内——骤降/骤增预示上游损坏或重复。
4. **schema**：意外的列增删/类型变更会悄悄破坏消费者。
5. **分布**：空值率、取值范围、基数和取值漂移，预示质量退化或影响模型的数据漂移。
6. **工具与告警**：Monte Carlo、Great Expectations、Soda 等工具计算这些指标，并且关键在于**对异常告警**——往往基于 ML 学习出的基线而非仅靠手工设定的阈值——并把故障关联到血缘以快速根因定位。
7. **数据 SLA**：把预期的新鲜度/体量/质量固化为**数据 SLA**（带负责人和错误预算，如同数据版的 SRE），能把「有人发现看板出错了」转变为在消费者受影响之前的主动、基于契约的检测。

**演进：**

1. **超越作业状态**：先从只看作业成功，转向监控新鲜度/体量/schema/分布四支柱。
2. **学习基线**：再用 ML 学习出的基线做异常检测、与血缘打通根因。
3. **契约化**：最终固化为带负责人和错误预算的数据 SLA，使检测主动化。

**面试追问：**

1. **基线 vs 阈值**：学习出的基线相比静态阈值的优势与风险是什么？
2. **分布漂移**：如何区分正常波动与会拖垮模型的数据漂移？
3. **错误预算**：数据 SLA 的错误预算如何定义与运营？

**要点：**

1. **四大支柱**：新鲜度、体量、schema、分布——仅看作业成功会掩盖坏数据。
2. **异常检测**：用学习出的基线做异常检测，而非仅静态阈值；告警与血缘打通。
3. **分布监控**：捕获会拖垮模型和指标的数据/质量漂移。
4. **数据 SLA**：带负责人和错误预算的数据 SLA 让检测变得主动且契约化。

### 99. 流式 join 及其挑战

**频率：** 中

**题目：** stream-stream 与 stream-table join 如何工作？难点何在？

**方案：**

1. **根本难点**：join 无界流很难，因为你无法等到「全部」数据到齐。
2. **stream-stream join**：匹配来自两条流的事件——例如广告曝光与点击——但匹配可能相隔数秒甚至数分钟，因此引擎要求**窗口化 join**（在一个时间界限内 join）并必须为该窗口**缓冲状态**；没有界限，状态会无限增长。
3. **乱序与水位线**：乱序和迟到事件意味着你要依赖**事件时间和水位线（watermark）**来决定何时关闭窗口、发出未匹配事件（或丢弃）。
4. **stream-table join**：用参考/维度数据（如用户画像）为每个事件做增强。
5. **时态正确性**：微妙之处在于时间正确性——表本身也在变化，因此你需要一个**时态/版本化 join**，按事件时间 *as of* 去查维度值，而非当前值，并且必须让该查询状态保持新鲜和一致。
6. **运维挑战**：二者的主要运维挑战都是状态大小、故障下的 exactly-once 语义以及数据倾斜。

**演进：**

1. **窗口化**：先用窗口化 join 限定 stream-stream 的匹配界限、控制缓冲状态。
2. **水位线**：再用事件时间/水位线处理迟到/乱序事件与窗口关闭。
3. **时态 join**：对 stream-table 用时态（as-of）join 匹配正确维度版本。

**面试追问：**

1. **状态膨胀**：无界状态如何监控与限制，窗口大小如何选？
2. **水位线策略**：迟到事件是发出还是丢弃，如何权衡正确性与延迟？
3. **exactly-once**：故障恢复下如何保证 join 结果不重不漏？

**要点：**

1. **窗口化状态**：stream-stream 需要带缓冲状态的窗口化 join；无界状态是核心风险。
2. **水位线**：水位线/事件时间决定窗口何时关闭、如何处理迟到/乱序事件。
3. **时态增强**：stream-table 增强事件；用时态（as-of）join 以匹配正确的维度版本。
4. **运维痛点**：状态大小、故障下的 exactly-once、数据倾斜。

### 100. 设计端到端实时分析系统

**频率：** 高

**题目：** 请端到端设计一个实时分析平台（例如实时产品/用户事件分析），把摄取、处理、服务与治理串联起来。

**方案：**

1. **从需求出发**：从需求出发——延迟目标、查询模式、规模和正确性要求——然后逐层构建系统。
2. **摄取**：客户端向持久化日志（Kafka/Kinesis）发送事件，按实体键分区以保证顺序与并行，并用 schema registry 强制契约。
3. **处理**：流引擎（Flink/Spark Structured Streaming）做窗口聚合、stream-table 增强和去重，利用事件时间 + 水位线和 checkpoint 实现 exactly-once；把结果同时写入用于低延迟服务的在线存储和用于历史的数据湖。
4. **存储/服务**：实时 OLAP 存储（Druid/Pinot/ClickHouse）提供亚秒级看板/API 查询；湖仓（Iceberg/Delta）保存完整历史用于即席查询和 ML。
5. **架构选型**：相较于双份代码的 Lambda 架构，更推荐 **Kappa**（通过重放日志来重算）以避免维护两套代码库。
6. **横切关注点**：**feature store** 为在线 ML 供数，而治理——catalog、血缘、数据质量门禁、可观测性 SLA（新鲜度/体量）、加密/掩码和多租户隔离——贯穿每一层。
7. **点明权衡**：要点出权衡——延迟 vs 成本、exactly-once vs 吞吐、预聚合 vs 查询灵活性。

**演进：**

1. **先摄取处理**：先搭持久化分区日志 + 流引擎（事件时间、水位线、exactly-once）。
2. **双路服务**：再接实时 OLAP 提供低延迟服务、湖仓保存完整历史。
3. **Kappa+治理**：最终用 Kappa 避免双套代码，并把治理横切到每一层。

**面试追问：**

1. **Lambda vs Kappa**：为什么用 Kappa 重放而非 Lambda 维护两套代码？
2. **OLAP 选型**：Druid/Pinot/ClickHouse 在查询模式上如何取舍？
3. **预聚合权衡**：预聚合与查询灵活性之间如何平衡？

**要点：**

1. **分层**：持久化分区日志 → 流引擎（事件时间、水位线、exactly-once）→ 实时 OLAP + 湖仓。
2. **双路服务**：用 Druid/Pinot/ClickHouse 提供低延迟服务；用 Iceberg/Delta 保存完整历史供即席/ML。
3. **Kappa**：用 Kappa（重放）而非 Lambda 以避免双套代码库；feature store 桥接到在线 ML。
4. **横切治理**：治理是横切的：catalog、血缘、质量门禁、可观测性 SLA、加密、租户隔离。
5. **权衡**：点明权衡：延迟 vs 成本、exactly-once vs 吞吐、预聚合 vs 灵活性。
