100 道关于软件架构、分布式系统模式、可扩展性、可靠性、数据建模以及经典系统设计练习的高频题目。

---

### 1. 单体 vs 微服务 vs 模块化单体

**频率：** 高

**题目：** 请对比单体、微服务和模块化单体三种架构风格：分别说明它们的部署单元与优缺点，谈谈微服务在带来独立部署、多语言技术栈和按服务扩展的同时引入了哪些运维复杂度，模块化单体又是如何在单一部署下强制模块边界的。你会把哪种作为默认选择，以及在什么条件下（团队规模、部署节奏、扩展曲线、合规隔离）才值得拆分为微服务？

**答案：** 单体作为一个可部署单元发布；开发、部署和理解都简单，但会把团队速度和扩展能力耦合在一起。微服务按界限上下文拆分，允许独立部署、多语言技术栈以及按服务扩展，代价是运维复杂度（网络故障、分布式追踪、数据一致性、部署流水线）。模块化单体保留单一部署，但通过包/程序集结构与显式接口强制模块边界；既享有重构安全性，又不必承担分布式系统的"税"。默认选模块化单体，直到团队规模、部署节奏或体量倒逼拆分。当团队数量超过邓巴数量级、服务扩展曲线差异巨大或合规要求隔离时，微服务才划得来。

**要点：**
- 康威定律占主导：架构映射组织结构。
- 微服务带来延迟、部分失败、最终一致性。
- 模块化单体用单一部署获得大部分模块化收益。
- 拆分成本高；在拆之前先把接缝跑通。

### 2. 事件驱动架构

**频率：** 高

**题目：** 请阐述事件驱动架构：服务如何通过发布不可变事件而非同步调用来通信，由此带来的松耦合、时间解耦和扇出优势是什么？同时说明它的权衡（流程更难推理、最终一致性、需要幂等消费者、回放/DLQ 工具、schema 演化纪律）。请区分事件与命令，并说明什么场景适合选用 EDA、什么场景应当避免。

**答案：** 服务通过发布不可变事件来通信，而不是同步互相调用。生产者不知道消费者，从而实现松耦合、时间解耦（消费者按自己的节奏处理）以及面向新用例的便捷扇出。权衡：端到端流程更难推理、最终一致性、需要幂等消费者、需要回放/DLQ 工具，以及 schema 演化的纪律（Avro/Protobuf 配合 registry）。当工作流本质上是异步、需要对同一事实做多个下游反应，或希望把写路径与读模型解耦（CQRS）时选 EDA。需要强一致性和即时确认的简单请求/响应场景请避免使用。

**要点：**
- 事件是事实；命令是意图。
- 需要 schema registry、DLQ、幂等键。
- 默认支持 CQRS、事件溯源和审计。
- 跨跳追踪需要关联 ID 与 OpenTelemetry。

### 3. CQRS

**频率：** 高

**题目：** 请解释 CQRS：写模型与读模型如何拆分，写入如何打到规范化存储、再通过事件或 CDC 投影出反规范化的读模型（搜索索引、缓存、物化视图）。请说明它的好处（读写独立扩展、读侧更简单、读模型独立演化）与代价（两侧最终一致、组件更多、需要投影重建逻辑），并谈谈它与事件溯源的关系以及"读自己写"的 UX 隐患。

**答案：** 命令查询职责分离把写模型（变更状态的命令，按不变量校验）和读模型（针对特定视图优化的查询）拆开。写入打到规范化存储；事件或变更数据捕获把每种查询所需的反规范化读模型投影出来（搜索索引、缓存、物化视图）。好处：读写独立扩展、读侧代码更简单、读模型可以独立演化而不动写侧。代价：两侧之间最终一致、组件更多、需要投影重建逻辑。读写不对称大或查询形态众多时使用 CQRS；简单 CRUD 不要套。

**要点：**
- 两个模型，通常两套数据库。
- 读相对于写最终一致。
- 自然搭配事件溯源，但并非必须。
- 当心"读自己写"的 UX 问题。

### 4. 事件溯源

**频率：** 高

**题目：** 请解释事件溯源：状态如何以追加式领域事件日志持久化、当前状态如何通过折叠事件推导、聚合如何通过回放事件流（配合快照）来重建。它带来了哪些能力（完美审计、时间旅行、新增投影）？又面临哪些挑战（事件 schema/版本兼容、GDPR 删除的加密粉碎、复杂查询需要 CQRS、学习曲线）？请说明它最适合和应当避开的场景。

**答案：** 把状态以追加式领域事件日志的方式持久化；当前状态通过折叠事件推导。提供完美的审计、时间旅行以及从历史中新增投影的能力。聚合通过回放其事件流来重建（用快照提升性能）。挑战：事件 schema/版本要永远兼容、GDPR 删除（加密粉碎）、复杂查询（需要 CQRS 读模型）以及陡峭的学习曲线。最适合：历史本身是一等业务关注点的领域（金融、账本、合规），或者多个消费者需要相同事实。简单 CRUD 或团队运维成熟度不足时请避开。

**要点：**
- 事件不可变且仅追加。
- 快照加速聚合重建。
- GDPR 需要加密粉碎或墓碑。
- 几乎总是与 CQRS 结合。

### 5. DDD：界限上下文、聚合、通用语言

**频率：** 高

**题目：** 请解释领域驱动设计中的界限上下文、聚合和通用语言：(1) 通用语言如何让代码与业务词汇一致，同一个词在不同上下文里含义为何可以不同；(2) 聚合作为一致性/事务边界的含义，以及跨聚合为何是最终一致、通过领域事件实现；(3) 界限上下文与服务边界的关系；(4) 上下文映射图如何记录上下文间关系（共享内核、客户/供应商、防腐层）。也请谈谈 DDD 做成仪式后的风险。

**答案：** 领域驱动设计通过围绕业务建模来应对复杂性。界限上下文定义一条显式边界，在边界内某个模型及其通用语言保持一致——同一个词（Customer、Order）在不同上下文里含义可以不同。聚合是一致性边界：一个根实体加上必须在一个事务中共同维护不变量的对象。跨聚合一致性是最终的，通过领域事件实现。界限上下文常常映射到服务边界；上下文映射图记录上下文之间的关系（共享内核、客户/供应商、防腐层）。做得好时，DDD 让代码与对话对齐；做成仪式后，会产出贫血模型加一堆多余的类。

**要点：**
- 通用语言：代码与业务词汇一致。
- 聚合 = 事务/一致性边界。
- 界限上下文通常 = 服务边界。
- 上下文映射图记录上下文间关系。

### 6. Saga（编排 vs 编舞）

**频率：** 高

**题目：** 请解释 Saga 模式及其两种协调方式：Saga 如何把跨服务的长事务协调为一系列局部事务并在失败时执行补偿动作。请对比编排（orchestration，中心编排器显式调用每步并触发补偿）与编舞（choreography，各服务对事件反应并发出新事件）的耦合度、可调试性和可追踪性差异，说明各自适合的流程形态，以及为什么每一步的补偿动作都必须幂等。

**答案：** Saga 把跨服务的长事务协调为一系列局部事务，并在某步失败时执行补偿动作。编排（orchestration）：中心编排器（如 Temporal、Camunda）显式调用每一步并在失败时触发补偿——流程可见、易调试，但编排器是耦合点。编舞（choreography）：每个服务对事件作出反应并发出新事件——耦合松，但流程是隐式的，规模化后难以追踪。编排在带分支的复杂流程下扩展更好；编舞适合简单线性的扇出。两种情况下，每一步都需要幂等的补偿动作。

**要点：**
- 用补偿替代 2PC。
- 编排：中心大脑，更易调试。
- 编舞：只用事件，松散但不透明。
- 每一步都需要幂等的回退。

### 7. 无服务器 vs 容器 vs 虚拟机

**频率：** 高

**题目：** 请对比无服务器、容器与虚拟机三种运行模型：分别说明它们在隔离性、冷启动、运维开销、计费与扩展（如缩到零）方面的特点，无服务器的约束（冷启动、运行时上限、厂商锁定）是什么。请说明各自的最佳适用场景（无服务器适合尖峰/事件驱动/低流量，容器适合稳态服务，虚拟机适合遗留/GPU/强隔离合规），以及成本交叉点大致在什么利用率区间。

**答案：** 虚拟机提供完整的 OS 隔离、可预测的性能、最长的冷启动、最高的运维开销。容器打包应用 + 依赖，共享内核，启动快，密度高——是有状态或常驻工作负载的默认选择。无服务器（如 Lambda 的 FaaS 或基于容器的 Cloud Run）完全抽象掉服务器，可缩到零，按调用计费，但有冷启动、运行时上限和厂商锁定。无服务器适合尖峰、事件驱动或低流量场景，这里运维节省占主导。容器适合稳态服务，这里单位成本重要、需要完全掌控。虚拟机留给遗留、GPU 或需要强隔离的合规工作负载。

**要点：**
- 无服务器：按使用付费、冷启动、缩到零。
- 容器：密度与控制力最佳。
- 虚拟机：隔离最强，开销最高。
- 成本交叉点大约在 30-50% 利用率。

### 8. 水平扩展 vs 垂直扩展

**频率：** 高

**题目：** 请对比水平扩展与垂直扩展：垂直扩展（scale-up）的优点（简单、无需改代码）与局限（天花板、单点故障），水平扩展（scale-out）的优点（近乎无上限、容错）与要求（无状态或外置共享状态、协调开销）。为什么无状态服务放在负载均衡器后水平扩展是平凡的，而数据库历史上最难水平扩展、现代系统如何通过分片/共识实现？请谈谈垂直加水平的混合做法。

**答案：** 垂直（scale-up）给单节点加 CPU/RAM——简单、无需改代码，但有天花板且是单点故障。水平（scale-out）在负载均衡器后加节点——理论上无上限、容错，但要求无状态或把共享状态外置，并增加协调开销。大多数现代服务起步就把无状态服务放在 LB 后，所以水平扩展是平凡的。数据库历史上以垂直为主；现代系统（Cassandra、Spanner、CockroachDB）通过分片/共识做水平扩展。混合很常见：先垂直扩展直到成本或机型到顶，再分片。

**要点：**
- 垂直：简单、有天花板、单一故障域。
- 水平：需要无状态或外置状态。
- 数据库最难水平扩展——需要分片。
- 组合：更大节点 + 更多节点。

### 9. 无状态 vs 有状态

**频率：** 高

**题目：** 请对比无状态与有状态服务：为什么无状态服务能让水平扩展、滚动部署和故障恢复变得平凡，状态应放在哪里（数据库、缓存、对象存储）。有状态服务（Kafka broker、Elasticsearch 节点、游戏服、WebSocket 状态）为何需要粘性路由、扩缩时小心再平衡、恢复更慢？请说明理想目标（无状态应用层加托管有状态系统），以及必须有状态时的手段（一致性哈希、持久卷、pre-stop 钩子优雅排空）。

**答案：** 无状态服务不在本地保存会话/数据；任何实例都能服务任何请求，使水平扩展、滚动部署、故障恢复都变得平凡。状态放在数据库、缓存或对象存储里。有状态服务把状态保存在内存或本地磁盘（Kafka broker、Elasticsearch 节点、游戏服、WebSocket 连接状态），需要粘性路由、扩缩时小心再平衡、恢复更慢。目标：无状态应用层 + 把状态推到托管的有状态系统。当必须有状态时，使用一致性哈希、持久卷和 pre-stop 钩子优雅排空。

**要点：**
- 无状态 = 水平扩展平凡。
- 有状态需要粘性路由与再平衡。
- 尽量把状态推到托管存储。
- HTTP 的粘性会话是反模式。

### 10. 负载均衡（RR、最少连接、哈希、加权）

**频率：** 高

**题目：** 请对比常见负载均衡算法：(1) 轮询的适用与局限；(2) 最少连接为何更适合长连接或耗时可变的请求；(3) 一致性哈希如何按 key 路由以实现缓存/有状态亲和并在拓扑变化时最小化再洗牌；(4) 加权变体如何处理异构实例或 canary 切换；(5) power-of-two-choices 随机为何常在尾延迟上优于轮询。请说明如何按流量形态选择。

**答案：** 轮询（Round-robin）在请求均匀时分布均匀；便宜简单。最少连接路由到活跃连接数最少的实例——更适合长连接或耗时变化大的请求。一致性哈希按 key（用户 ID、租户）路由，让相同 key 持续命中相同后端——对缓存和有状态系统至关重要，拓扑变化时最小化再洗牌。加权变体可处理异构实例规格或 canary 流量切换。带"两个选择"的随机（power-of-two）通常在尾延迟上优于 RR。按流量形态选：均匀短请求 = RR、可变 = 最少连接、缓存亲和 = 哈希。

**要点：**
- RR：简单、假设请求均匀。
- 最少连接：处理可变时长。
- 一致性哈希：缓存与有状态亲和。
- power-of-two-choices 降低尾延迟。

### 11. CAP 与 PACELC 的实操

**频率：** 高

**题目：** 请结合实操解释 CAP 与 PACELC：CAP 为什么只在网络分区时要求在一致性与可用性之间取舍，PACELC 又如何补充说明即便没有分区时也要在延迟与一致性之间权衡。为什么真实系统要按操作而非按系统做选择（例如银行转账偏 CP、社交动态偏 AP）？请说明 Spanner 与 Dynamo 分别近似哪种取向，以及应把 CAP 当作分析框架而非打勾清单。

**答案：** CAP 说在网络分区时必须在一致性和可用性之间选。PACELC 扩展之：即便没有分区（Else），也要在延迟（Latency）和一致性之间权衡。真实系统按操作做选择：银行转账偏好 CP（分区时拒绝），社交动态偏好 AP（陈旧但可用）。许多"一致"系统是 PC/EL（任何时候强一致，正常时低延迟），如 Spanner；许多"可用"系统是 PA/EL（始终可用、快、最终一致），如 Dynamo。把 CAP 当作框架工具而非打勾——按工作负载、按操作分析。

**要点：**
- CAP 只在分区时适用。
- PACELC 增加正常情况下延迟 vs 一致性。
- 选择按操作，而非按系统。
- Spanner ≈ CP；Dynamo ≈ AP。

### 12. 最终一致性模式

**频率：** 高

**题目：** 请阐述最终一致性下的实用模式：(1) 读自己写（写后把读路由到主或带写 token）；(2) 单调读（粘性到同一副本）；(3) 因果一致（用矢量时钟或会话 token 跟踪 happens-before）；(4) 有界陈旧（如最多落后 N 秒或 M 操作）。请说明乐观 UI 如何对用户掩盖延迟、幂等写与 CRDT 如何消除合并冲突，以及为什么应按端点记录一致性契约。

**答案：** 用工具拥抱陈旧并将其掩盖：读自己写（写后把读路由到主或带写 token）、单调读（粘性会话到同一副本）、因果一致（用矢量时钟或会话 token 跟踪 happens-before）、有界陈旧（Cosmos DB 风格：最多落后 N 秒或 M 操作）。对 UX，乐观 UI（本地先应用，确认后协调）能掩盖延迟。对数据正确性，幂等写入和 CRDT 消除合并冲突。按端点记录一致性契约，让消费者不要假设强语义。

**要点：**
- 通过主路由或 token 实现读自己写。
- 有界陈旧提供可度量的 SLA。
- 乐观 UI 对用户隐藏延迟。
- 按 API 记录一致性契约。

### 13. 强一致性 vs 最终一致性 vs 因果一致性

**频率：** 高

**题目：** 请对比强一致性、最终一致性与因果一致性：(1) 强（线性化）如何保证每次读看到最新提交的写、代价是什么；(2) 最终一致的优点（便宜、可用）与风险（读可能陈旧或乱序）；(3) 因果一致如何保留 happens-before 关系而不要求全序，适合哪些应用。请说明顺序一致的位置，并举例说明为何应按操作而非按系统选择（账户余额、社交时间线、线程内聊天消息）。

**答案：** 强（线性化）：每次读看到最新提交的写；昂贵、需要共识、限制可用性与延迟。最终：副本在写停止后会收敛；最便宜、最可用，但读可能陈旧或乱序。因果：保留 happens-before 关系（若 A 引起 B，所有观察者都先看到 A 再看到 B）而不要求全序——协作应用和聊天的甜点。顺序一致介于强与因果之间。按操作选择：账户余额读 = 强；社交时间线 = 最终；线程内的聊天消息 = 因果。

**要点：**
- 强：线性化，昂贵。
- 最终：便宜，可能陈旧或乱序。
- 因果：保留因果序。
- 按操作选，而非按系统。

### 14. 分布式事务：2PC vs sagas

**频率：** 高

**题目：** 请对比分布式事务的两种方式：(1) 两阶段提交如何通过协调器（prepare/commit）跨资源保证原子性，以及它的问题（协调器失败时阻塞、扩展不佳、服务紧耦合）；(2) Saga 如何把事务拆为局部事务加补偿、在不加锁下提供最终原子性，为什么补偿必须幂等且语义有意义（如不能"取消扣款"而要执行真实退款）。请说明 2PC 与 saga 各自的适用边界。

**答案：** 两阶段提交通过协调器（prepare/commit）跨多个资源协调一个事务。保证原子性但在协调器失败时阻塞、扩展不佳、把服务紧紧耦合在一起——在微服务间很少用。Saga 把事务拆为局部事务加补偿：若第 3 步失败，对 1、2 步执行回退。在不加锁的情况下提供最终原子性、可扩展，但补偿必须幂等且语义有意义（你不能"取消扣款"，必须执行真实退款）。2PC 只在单个数据库集群或 XA 感知基础设施里使用；跨服务用 saga。

**要点：**
- 2PC：阻塞，跨服务不可扩展。
- Saga：局部事务 + 补偿。
- 补偿必须幂等且有意义。
- 编排式 saga 比编舞式更易调试。

- 范围：范围扫描，热点风险。

### 41. 服务网格（Istio/Linkerd）

**要点：**
- 数据面（sidecars）+ 控制面。
- 提供 mTLS、流量策略、遥测。
- Linkerd 更轻；Istio 更全。
- 用服务数量与团队容量来论证。

### 42. Outbox 模式

**频率：** 中

**题目：** 请解释 Outbox 模式如何解决数据库与消息 broker 之间的双写问题：服务如何在一个事务里把业务变更和出向事件写入同一数据库的 outbox 表，中继（轮询 worker 或 Debezium 这类 CDC 流）又如何读取并发布到 broker 再标记已发送。它在不使用分布式事务的前提下提供了怎样的投递保证？请说明其权衡（提交到发布的延迟、outbox 表增长需归档、消费者必须幂等去重）。

**答案：** 解决数据库与消息 broker 之间的双写问题。服务在一个事务中把业务变更和出向事件写入同一个数据库（"outbox"表）。一个中继（轮询 worker 或 Debezium 这类 CDC 流）读取 outbox 并发布到 broker，标记行已发送。在不需要分布式事务的前提下保证至少一次发布，让数据库与 broker 最终一致。权衡：提交到发布之间有微小延迟、outbox 表会增长（需归档），且消费者必须幂等。与事件驱动和 saga 架构配合良好。

- 中继（轮询或 CDC）向下游发布。
- 至少一次投递；消费者必须去重。
- 避免对 broker 的不可靠双写。

### 43. L4 vs L7 负载均衡

**频率：** 中

**题目：** 请对比 L4 与 L7 负载均衡：L4（TCP/UDP）在传输层做均衡的特点（快、协议无关、不检查载荷），L7（HTTP、gRPC）理解应用协议后能做什么（按 host/path/header 路由、终止 TLS、重试、粘性 cookie、限流、可观测性）。请说明二者在成本与延迟上的差异、常见的组合栈（L4 前置 L7 应对规模、DDoS），以及为什么服务网格本质上是分布式 L7 负载均衡。

**答案：** L4（TCP/UDP）在传输层做均衡——快、协议无关、不检查载荷（AWS NLB、HAProxy TCP 模式）。L7（HTTP、gRPC）理解应用协议——可按 host/path/header 路由、终止 TLS、做重试、粘性 cookie、限流和可观测性（Envoy、NGINX、ALB）。L4 更便宜、延迟更低；L7 更灵活，是当今多数现代 API 流量的栖息地。常见栈：L4 用于原始 TCP/UDP（游戏、数据库），L7 用于 HTTP API，L4 在 L7 集群前承担 DDoS 规模。服务网格本质上就是分布式 L7 LB。

**要点：**
- L4：TCP/UDP，最快，协议盲。
- L7：HTTP 感知，路由/策略丰富。
- L7 终止 TLS 并做重试。
- 常用 L4 前置 L7 以应对规模。

### 47. 法定人数与副本数

**频率：** 中

**题目：** 请解释法定人数与副本数：在 N 个副本、写需 W 个确认、读需 R 个回复的模型下，为什么 W + R > N 才能保证强一致，RF=3、W=2、R=2 为何是 Dynamo 经典甜点。降低 W 或 R 分别带来什么风险与收益？请说明提示交接（hinted handoff）与读修复（read-repair）如何异步修复不一致、更高 RF 的耐久性与成本影响，以及如何按读多/写多工作负载调优。

**答案：** N 个副本时，写需要 W 个确认，读取需要 R 个回复；强一致需要 W + R > N（重叠保证看到最新的写）。RF=3、W=2、R=2 是 Dynamo 经典：容忍一台故障且保强读。降低 W（=1）写更快但故障时有丢数据风险；降低 R（=1）读更快但可能错过最新写。提示交接（hinted handoff）和读修复（read-repair）异步修复不一致。更高 RF 提升耐久性但增加存储与写延迟。按工作负载调优：写多的系统降 W 并依赖读修复；读多的系统降 R。

**要点：**
- W + R > N 才能强一致。
- RF=3 配 W=R=2 是甜点。
- Hinted handoff 修复临时故障。
- 更高 RF = 更耐久、更高成本。

### 50. 舱壁（Bulkhead）

### 54. Exactly-once 语义

**频率：** 中

**题目：** 请解释 exactly-once 语义：为什么"恰好一次"通常指实际上一次（至少一次投递加幂等处理），真正的端到端 exactly-once 需要生产者、broker 和消费者如何共同参与（如 Kafka 事务加幂等生产者与事务性偏移，或 Flink 的两阶段提交 sink）。在实践中如何把消费者设计成幂等（按事件 ID 去重、按主键 upsert、HTTP 幂等键、保存已处理事件 ID 的 TTL 窗口）来统一处理 broker 重投、应用重试和网络重复？

**答案：** "Exactly once"通常指实际上一次：至少一次投递 + 幂等处理。真正的端到端 exactly-once 要求生产者、broker 和消费者都参与（Kafka 事务搭配幂等生产者和事务性消费者偏移，或 Flink 的两阶段提交 sink）。实践中把消费者设计成幂等：按事件 ID 去重、按主键 upsert、在 HTTP 中使用幂等键、保存已处理的事件 ID（TTL 窗口）以拒绝回放。这种方式统一处理 broker 重投、应用重试和网络重复。比追求真 exactly-once 更便宜、更可靠。

**要点：**
- 真 exactly-once 罕见且昂贵。
- 实际上一次 = 至少一次 + 幂等。
- 按事件 ID 去重或按主键 upsert。
- 每个入口都用幂等键。

- Kappa：纯流式，从日志回放。

### 100. 多人游戏服（匹配、状态同步）

**频率：** 低

**题目：** 请设计一个多人游戏服务器。需求：实时游戏玩法（60Hz tick）、按技能/区域/延迟匹配、反作弊、持久成长、百万并发。请说明关键组件（匹配器、会话服务器、状态同步、持久存储、语音/聊天、反作弊）并覆盖：(1) 匹配器如何按区域/模式分队列并基于技能桶（MMR）平衡公平与排队时间；(2) 会话服务器如何做权威模拟并由编排器（如 Agones）按需启动；(3) 状态同步如何用服务端权威 + 客户端预测与协调、UDP 上 delta、命中检测的延迟补偿；(4) 扩展与权衡，如区域集群、对局装箱、优雅排空，以及服务端权威耗 CPU、rollback netcode vs 客户端预测按品类不同、延迟补偿利射击手不利目标。

**答案：** 需求：实时游戏玩法（60Hz tick）、按技能/区域/延迟匹配、反作弊、持久成长、百万并发。组件：匹配器（按区域/模式分队列 + 基于技能桶——MMR；平衡公平与排队时间）、会话服务器（按对局专用进程；通过编排器如 Agones 按需启动；权威模拟）、状态同步（服务端权威带客户端预测 + 协调；UDP 上 delta；命中检测用延迟补偿）、持久存储（玩家档案、库存在 SQL；对局历史在 OLAP）、语音/聊天（独立服务）、反作弊（服务端校验 + 客户端检测）。扩展：区域集群降低延迟；把对局装箱到会话服务器；对局结束时优雅排空。权衡：服务端权威打败作弊但耗 CPU；rollback netcode（格斗）vs 客户端预测（FPS）按品类不同；延迟补偿利好射击手但不利目标。

**要点：**
- 权威服务器 + 客户端预测。
- 固定 tick 的 UDP delta。
- 匹配器平衡 MMR vs 排队时间。
- Agones 风格编排专用会话服务器。
