100 道关于软件架构、分布式系统模式、可扩展性、可靠性、数据建模以及经典系统设计练习的高频题目。

### 1. 单体 vs 微服务 vs 模块化单体

**频率：** 高

**题目：** 请对比单体、微服务和模块化单体。哪些信号才真正值得迁移到微服务？

**答案：** **单体**作为一个可部署单元发布：一份代码库、一个进程、一个数据库。它是开发、部署、端到端测试和理解都**最简单**的形态——一条堆栈跟踪就能贯穿整个请求。它的弱点是把**团队速度与扩展能力耦合**在一起：每个团队都部署同一个产物（发布火车、合并队列），而且即使只有一个端点是热点，你也得整体扩容。

**微服务**按**界限上下文（bounded context）**把系统拆成可独立部署的服务。这买来了**独立部署**（团队按自己的节奏发布）、**多语言**技术栈、**故障隔离**和**按服务扩展**（只扩图片处理服务而不动结账服务）。代价是沉重的**运维税**：网络调用会部分失败，你需要**分布式追踪**（OpenTelemetry + 关联 ID）才能跟踪一个请求，**数据一致性**变成最终一致（saga、outbox），而且每个服务都会成倍增加部署流水线、监控面板和 on-call 面。草率的拆分往往产出一个**分布式单体**——服务之间过于啰嗦且被绑在一起部署，付了分布式的税却没拿到独立性的好处。

**模块化单体**是务实的折中：**单一可部署单元**，但内部按模块划分并**强制边界**（独立的包/程序集、显式接口、禁止伸手去动别的模块的表）。你获得了重构安全性和清晰的接缝，却**不必**承担网络、部分失败和最终一致性的税——而这些模块边界就是你将来真要抽取时的服务边界。

**默认选模块化单体。** **康威定律**占主导——你的架构会映射你的组织结构——所以一个小团队不该跑 20 个服务。抽取成本很高，所以先**把接缝跑通**再说。真正值得抽取一个服务的具体信号：**团队数量**超过一份代码库能协调的规模（多个团队被同一次部署卡住）、某服务的**扩展曲线截然不同**（GPU 推理 vs CRUD）、**部署节奏**冲突（一部分要每小时发布，另一部分受监管且缓慢），或**合规**要求硬隔离（PCI、PII）。沿着这些接缝抽取，而不是投机式地拆。

**要点：**
- 康威定律占主导：架构映射组织结构。
- 微服务带来延迟、部分失败、最终一致性。
- 模块化单体用单一部署获得大部分模块化收益。
- 拆分成本高；在拆之前先把接缝跑通。

### 2. 事件驱动架构

**频率：** 高

**题目：** 什么是事件驱动架构？相比同步的请求/响应，什么时候该选它？

**答案：** 在**事件驱动架构（EDA）**中，服务通过向消息中间件（Kafka、SNS/SQS、RabbitMQ）**发布不可变事件**（"OrderPlaced"、"PaymentCaptured"）来通信，而不是同步互相调用。生产者**并不知道谁来消费**这个事件——它只是陈述"某个事实发生了"。这种反转正是关键所在：它带来**松耦合**（新增一个消费者无需改动生产者）、**时间解耦**（消费者按自己的节奏处理，用队列吸收峰值）以及便捷的**扇出**——同一个"OrderPlaced"事实可以独立地驱动库存、邮件、分析和风控。

**事件与命令的区别**很重要：**事件**是关于过去的事实（"UserSignedUp"），广播给所有关心它的人；**命令**是指向某个处理者的意图（"SendWelcomeEmail"）。把两者混为一谈（发布名义上是"事件"、实则是伪装成 RPC、只发给一个已知消费者的命令）会重新制造紧耦合。

权衡是实打实的。端到端流程变得**难以推理**——没有单一的调用栈，所以你需要**关联 ID**和分布式追踪来还原"订单 123 到底经历了什么"。你会继承**最终一致性**：读模型落后于写。消费者必须**幂等**（中间件是至少一次投递，同一事件可能到达两次——按事件 ID 去重）。你还需要运维工具：处理毒消息的**死信队列（DLQ）**、用于重新处理的**回放**，以及 **schema 演化**纪律（Avro/Protobuf + 带兼容规则的 schema registry，这样生产者的改动不会打断消费者）。

**当**工作流本质上异步、当许多下游系统必须对同一事实做出反应、或当你想把写路径与读模型解耦（它是 **CQRS** 和事件溯源的骨架）时，**选择 EDA**。而对于调用方需要**即时、强一致答案**的简单请求/响应（"这笔转账成功了吗？现在把余额给我"），**应避免**用它——那里同步 RPC 更简单也更正确。

**要点：**
- 事件是事实；命令是意图。
- 需要 schema registry、DLQ、幂等键。
- 默认支持 CQRS、事件溯源和审计。
- 跨跳追踪需要关联 ID 与 OpenTelemetry。

### 3. CQRS

**频率：** 高

**题目：** 什么是 CQRS？什么时候它才值得付出额外的复杂度？

**答案：** **命令查询职责分离（CQRS）**把**写模型**和**读模型**拆开。命令（CreateOrder、CancelOrder）变更状态，并按**业务不变量**校验；它们打到一个规范化、事务一致的存储。查询从不碰那个模型——取而代之的是，**事件或变更数据捕获（CDC）**投影出一个或多个**反规范化的读模型**，每个都为特定视图量身定制：全文检索用搜索索引、热点看板用 Redis 缓存、报表用物化 SQL 视图。

核心收益是两侧的**独立优化与扩展**。读通常以 100:1 压倒写，所以你可以扩展读副本（或边缘缓存）而完全不动写路径。读侧代码变得极其简单——没有联表、查询时不做聚合，只是"取出预先算好的形状"。而且你可以**自由地新增或演化读模型**：要个新视图？从同一条事件流里构建一个新投影即可，无需迁移写存储。

代价是两侧之间的**最终一致性**（读模型落后写模型一个投影延迟）、**更多的活动部件**（投影器、消息管道、要运维多套存储）以及**投影重建逻辑**——在出现 bug 或 schema 变更后，你必须能回放事件来重建读模型。一个经典的 UX 陷阱是**读自己写**：用户提交表单、被重定向到列表页，却还看不到自己刚做的改动。缓解办法是这一个请求从写模型读，或者在客户端乐观地先渲染改动。

**当**读写不对称很大、当你对同一份数据有许多**不同的查询形态**、或当你本来就在做事件溯源（两者天然搭配，尽管 CQRS 并不要求事件溯源）时，**采用 CQRS**。**不要**把它套在只有一种查询形态的简单 CRUD 上——那里它纯属额外开销：两个模型、两套存储，外加一个你本不需要的一致性缺口。

**要点：**
- 两个模型，通常两套数据库。
- 读相对于写最终一致。
- 自然搭配事件溯源，但并非必须。
- 当心"读自己写"的 UX 问题。

### 4. 事件溯源

**频率：** 高

**题目：** 什么是事件溯源？它适合哪里、又应当避开哪里？

**答案：** 不是存储当前状态并覆盖它，**事件溯源持久化一个追加式的领域事件日志**——"AccountOpened"、"MoneyDeposited(100)"、"MoneyWithdrawn(30)"——并通过**折叠（回放）**这些事件来推导当前状态。事件日志才是真相来源；当前余额（70）是一个计算出来的投影。

这给你三样其他方式难以获得的东西。一份**完美的审计轨迹**——你不是去重建历史，你本身*就是*历史，这对金融、账本和受监管领域是无价之宝。**时间旅行**——重建任意过去时刻的确切状态，用于调试或"截至某时"报表。以及**回溯式新增投影**的能力——一个新的业务问题（"去年有多少账户转为负额？"）只需把现有日志回放到一个新读模型中即可回答，无任何数据丢失。

聚合通过**回放其事件流**来重新水化（rehydrate）；对于长生命的聚合，你会定期写一个**快照**，这样只需回放自上次快照以来的事件，而不是从头回放成千上万条。

挑战很严峻。你得**永远为事件 schema 做版本兼容**——一条五年前的事件今天仍必须能反序列化，所以你需要 upcaster 和只做追加式变更。**GDPR/被遗忘权**与不可变日志相冲突：你不能删除一个事件，所以要么**加密粉碎（crypto-shred）**（PII 加密存储，销毁密钥），要么用墓碑。查询很别扭——你几乎总要在上面加**CQRS 读模型**，因为在原始事件日志上"列出所有活跃账户"十分不切实际。而且**学习曲线**陡峭；团队经常过度滥用它。

**最适合：** 历史是一等业务关注点的领域——金融、会计、订单/库存账本、一切受审计的东西——或者许多消费者需要相同的权威事实。**避开**简单 CRUD、缺乏运维成熟度去跑投影和回放的团队，或领域并不真正需要记住*如何*到达当前状态的场景。因为原始事件存储拙于查询，事件溯源**几乎总是与 CQRS 搭配**。

**要点：**
- 事件不可变且仅追加。
- 快照加速聚合重建。
- GDPR 需要加密粉碎或墓碑。
- 几乎总是与 CQRS 结合。

### 5. DDD：界限上下文、聚合、通用语言

**频率：** 高

**题目：** 请解释领域驱动设计中的界限上下文、聚合和通用语言：(1) 通用语言如何让代码与业务词汇一致，同一个词在不同上下文里含义为何可以不同；(2) 聚合作为一致性/事务边界的含义，以及跨聚合为何是最终一致、通过领域事件实现；(3) 界限上下文与服务边界的关系；(4) 上下文映射图如何记录上下文间关系（共享内核、客户/供应商、防腐层）。也请谈谈 DDD 做成仪式后的风险。

**答案：** 领域驱动设计通过围绕业务建模来应对复杂性。界限上下文定义一条显式边界，在边界内某个模型及其通用语言保持一致——同一个词（Customer、Order）在不同上下文里含义可以不同。聚合是一致性边界：一个根实体加上必须在一个事务中共同维护不变量的对象。跨聚合一致性是最终的，通过领域事件实现。界限上下文常常映射到服务边界；上下文映射图记录上下文之间的关系（共享内核、客户/供应商、防腐层）。做得好时，DDD 让代码与对话对齐；做成仪式后，会产出贫血模型加一堆多余的类。

**要点：**
- 通用语言：代码与业务词汇一致。
- 聚合 = 事务/一致性边界。
- 界限上下文通常 = 服务边界。
- 上下文映射图记录上下文间关系。

### 6. Saga（编排 vs 编舞）

**频率：** 高

**题目：** 请解释 Saga 模式，并对比编排与编舞。哪种适合带分支的复杂流程？

**答案：** **Saga** 用**一系列局部事务**（每个服务一个）加上每步的一个**补偿动作**（在后续步骤失败时撤销它），来替代分布式 ACID 事务（两阶段提交，既不扩展又会阻塞）。预订一次行程：预订机票 → 扣款 → 预订酒店。如果酒店预订失败，你就反向运行补偿——退款、释放机票。没有全局回滚；你通过为每个"做"显式设计"撤销"来获得**最终一致性**。

**编排（Orchestration）**使用一个**中心协调器**（Temporal、Camunda、AWS Step Functions 或你自己的状态机），它显式地调用每一步，并在失败时调用补偿。工作流住在**一个地方**，所以**可见且可调试**——你能看到一个卡住的 saga 到底卡在哪里、为什么。缺点：编排器是一个耦合点、也是另一个要运维的组件，而且服务必须暴露它能调用的命令。

**编舞（Choreography）**没有中心大脑——每个服务**监听事件并发出新事件**。"FlightReserved" 触发支付服务，其 "PaymentCaptured" 触发酒店服务。这保持了**松耦合**，但端到端流程是**隐式的**——它只作为跨服务的涌现式链条存在，一旦有了分支、重试和超时，就变得非常难以追踪、调试或修改。

**经验法则：** **简单的、线性的扇出用编舞**（步骤少、无分支），**带条件分支、并行步骤、超时和人工审批的复杂流程用编排**——中心化的全局视图值得那点耦合。**两种**风格中，每一步都需要一个**幂等的补偿动作**，因为至少一次投递和重试意味着补偿可能触发两次，不能重复退款。

**要点：**
- 用补偿替代 2PC。
- 编排：中心大脑，更易调试。
- 编舞：只用事件，松散但不透明。
- 每一步都需要幂等的回退。

### 7. 无服务器 vs 容器 vs 虚拟机

**频率：** 高

**题目：** 请对比无服务器、容器与虚拟机。各自适合什么工作负载，成本交叉点在哪里？

**答案：** 这三种部署模型在**隔离性、启动延迟、运维开销、装箱密度和成本**上权衡各异。

**虚拟机（VM）**虚拟化硬件，给每个工作负载一个**完整的客机 OS**。这是**最强的隔离**（独立内核）和最**可预测的性能**，但**冷启动最长**（启动一个 OS，几十秒）、**运维开销最高**（每个 OS 都要打补丁与管理）。适合：遗留应用、GPU/专用硬件，以及需要硬隔离的**受监管工作负载**。

**容器**打包应用加依赖，但**共享宿主内核**。启动**快**（几秒）、装箱**密集**（每节点多个容器），并对运行时有完全控制。这是**常驻、有状态或稳态服务的默认选择**，因为你在意**单位成本**并想要可移植性（Kubernetes、ECS）。隔离比 VM 弱（共享内核 = 攻击面更大），可用 namespace、cgroups、seccomp 以及 gVisor/Firecracker 来强化边界。

**无服务器/FaaS**（Lambda、Cloud Functions）——以及容器化无服务器（Cloud Run、Fargate）——**完全抽象掉服务器**。你部署代码；平台替你扩展，包括**缩到零**，而你**按调用/GB-秒计费**。代价：**冷启动**（请求峰时新实例必须启动）、**运行时上限**（执行时长、内存、包体积），以及通过专有触发器带来的**厂商锁定**。适合：**尖峰、事件驱动或低流量**工作负载——空闲时间占主导、运维节省占上风的场景：cron 任务、webhook、服务间粘合、不可预测的突发。

**成本交叉点：** 当**利用率低**时无服务器最便宜，因为空闲时你不付费；一旦服务**忙到能保持节点常热**，容器就占优。大致的盈亏平衡点在**约 30–50% 的持续利用率**——低于此，无服务器的按用付费加零运维通常胜出；高于此，常驻容器单位成本更低，而且你反正都在为一台预留的机器付费。

**要点：**
- 无服务器：按使用付费、冷启动、缩到零。
- 容器：密度与控制力最佳。
- 虚拟机：隔离最强，开销最高。
- 成本交叉点大约在 30-50% 利用率。

### 8. 水平扩展 vs 垂直扩展

**频率：** 高

**题目：** 请对比水平扩展与垂直扩展。为什么数据库是最难横向扩展的一层？

**答案：** **垂直扩展（scale-up）**意味着给**单个节点**更多资源——更多 CPU、内存、更快的磁盘。它**极其简单**：不改应用、无分布式系统问题，只是一台更大的机器。但它有个硬**天花板**（钱能买到的最大实例），顶端的成本曲线是**超线性**的，而且那一个节点是一个**单一故障域**——它一死，全部都死。

**水平扩展（scale-out）**意味着在负载均衡器后面**加更多节点**。它**理论上无上限**且**容错**（掉一个节点，其余继续干活）。难点在于它要求**无状态**（任何节点都能服务任何请求），或者你必须把共享状态**外置**（到 DB、缓存或对象存储）并付出**协调开销**（服务发现、领导选举、缓存一致性）。大多数现代应用层从第一天就设计为**无状态**，正是为了让横向扩展变得微不足道：加副本即可。

**数据库是难点**，因为它们*就是*共享状态，而且必须跨节点保持**一致性**。你不能只是加读/写节点就完事——你得决定如何**分区（分片）**数据、如何把查询**路由**到正确的分片、如何处理**跨分片联表与事务**（变得昂贵或不可能），以及如何在并发写入下保持副本**一致**（共识、法定人数）。这就是为什么数据库历史上以**垂直**扩展为主，以及为何横向扩展需要专门构建的系统——**Cassandra**（一致性哈希 + 可调法定人数）、**Spanner**（TrueTime + Paxos）、**CockroachDB**（Raft range）——把分片和复制内置到引擎里。

**实践中是混合的：** 把无状态应用层自由**横向**扩展，把数据库**垂直**扩展到碰到成本或机型上限，再**分片**——因为分片引入了你想尽可能推迟的真实复杂度。

**要点：**
- 垂直：简单、有天花板、单一故障域。
- 水平：需要无状态或外置状态。
- 数据库最难水平扩展——需要分片。
- 组合：更大节点 + 更多节点。

### 9. 无状态 vs 有状态

**频率：** 高

**题目：** 为什么无状态服务能如此轻松扩展？要把有状态服务跑好需要什么？

**答案：** **无状态服务在本地不保存任何客户特定状态**——没有内存会话、没有跨请求有意义的本地文件。任何实例都能服务任何请求，因为一切持久之物都住在**别处**：会话在 Redis、数据在 DB、上传在对象存储。这让三个最难的运维问题变得**平凡**。**水平扩展**：在 LB 后加副本即可，无需再平衡。**滚动部署**：随意杀掉并替换任何实例——没有人被绑在它上面。**故障恢复**：一个实例死了，LB 绕过它，什么都不会丢。这就是为什么标准模式是**无状态应用层**加上把所有状态**推到托管存储**。

**有状态服务把状态保存在内存或本地磁盘**上，而那状态*就是*它提供的价值——Kafka broker 拥有分区日志，Elasticsearch 节点拥有分片，游戏服拥有对局状态，WebSocket/gRPC 流服务器拥有活连接。这里每一件"简单事"都变难：

- **路由**必须**粘性**——一个持有 WebSocket 的客户必须持续抓到同一节点，所以你需要一致性哈希或会话亲和性路由，而不是轮询。
- **扩缩事件触发再平衡**——加/减节点意味着**移动数据/分区**（Kafka 重新分配分区，Elasticsearch 重定位分片），这会消耗带宽并可能在迁移期间退化性能。
- **恢复更慢**——死节点的状态必须先从副本或回放日志**重建**才能重新上线，所以你需要复制和重建路径。

**推荐的形态**是把应用层保持无状态，把状态委托给**专门构建的托管有状态系统**（RDS、Kafka、Elasticsearch），它们的团队已经解决了复制与再平衡。**当你必须自己拥有状态**时，工具是：**一致性哈希**（成员变化时最小化移动量）、**持久卷**（pod 重启不必完全重建）和 **pre-stop 排空钩子**（关机前完成在飞工作并优雅交接连接）。

**要点：**
- 无状态 = 水平扩展平凡。
- 有状态需要粘性路由与再平衡。
- 尽量把状态推到托管存储。
- HTTP 的粘性会话是反模式。

### 10. 负载均衡（RR、最少连接、哈希、加权）

**频率：** 高

**题目：** 请过一遍常见的负载均衡算法，以及如何按流量形态选择。

**答案：** 负载均衡器把请求分发给后端；在**非均匀**负载下，算法选择最关键。

**轮询（RR）**按轮次把请求发给后端。它**便宜且无状态**，在请求**短且均匀**（每个请求花销差不多）时很好用。盲点：它忽略每个后端实际有多忙，所以一个卡在慢请求上的节点仍会被喂新活。

**最少连接**路由到**活跃连接数最少**的后端，近似"最不忙"。它处理**长连接或耗时可变**的请求好得多——流式、上传，或花销相差 100 倍的端点。它需要 LB 跟踪连接数，但能自然地把活从挣扎的节点上引开。

**一致性哈希**按 **key**（用户 ID、租户、缓存 key）路由，让**相同 key 总落在同一后端**。这对**缓存亲和性**（最大化命中率——同一用户的数据缓在一个节点）和**有状态亲和性**（会话或分片住在特定节点）至关重要。它的关键性质是：加/减后端只**重洗约 1/N 的 key**而非全部，所以拓扑变化不会把每个缓存都冲掉。

**加权**变体（加权 RR / 加权最少连接）按比例把更多流量发给更大的实例，或**把受控百分比切到**新版本——这是 **canary** 和蓝绿流量爬升背后的机制。

一个微妙之处：**power-of-two-choices**（随机选两个后端，发给较不忙的那个）在大规模下常在**尾延迟上胜过普通 RR**，因为它避免了"群宁"问题——全局"最不忙"视图一陈旧，大家都扞到同一节点。**按流量形态选：**均匀+短 → RR；耗时可变 → 最少连接；缓存/有状态亲和性 → 一致性哈希；异构集群或 canary → 加权。

**要点：**
- RR：简单、假设请求均匀。
- 最少连接：处理可变时长。
- 一致性哈希：缓存与有状态亲和。
- power-of-two-choices 降低尾延迟。

### 11. CAP 与 PACELC 的实操

**频率：** 高

**题目：** 请解释 CAP 及其 PACELC 扩展。为什么这个选择实际上是按操作而非按系统的？

**答案：** **CAP** 说在**网络分区**（P）时——当节点互相无法通信——分布式系统必须在**一致性**（C：每次读都看到最新写）和**可用性**（A：每个请求都得到非错误响应）之间选择。*分区期间*不能两全，因为一个触不到同伴的节点要么**拒绝服务**（保一致、牺牲可用 = **CP**），要么**提供可能陈旧的数据**（保可用、牺牲一致 = **AP**）。常见误读是把 C/A/P 当成"总是选两个"——CAP 只在**分区期间**强制取舍，而分区很罕见。

**PACELC** 补全图景：**若分区（P），选 A 或 C；否则（Else，正常运行），选延迟（L）或一致性（C）**。这是日常更有用的透镜，因为分区罕见但**每个**请求都交延迟-一致性的税。一个强一致写必须在确认前抵达跨副本（可能跨区）的**法定人数**——那是你在正常路径上付的真实延迟。放松一致性，你就能从最近副本确认而更快。

关键洞察是选择**按操作**而非按系统。同一产品里，**银行转账/余额查询**想要 **CP**——分区期宁可拒绝也不双花；而同平台的**社交动态**想要 **AP**——略陈旧的时间线可以，宕机不行。真实系统两者混用。

分类举例：**Spanner** 实际上是 **CP / PC-EL**——它选一致性，用 TrueTime 和 Paxos 保持线性化，接受更高延迟并拒绝无法法定人数的写。**DynamoDB/Cassandra** 是 **AP / PA-EL**——始终可用且低延迟，最终收敛（用可调法定人数在需要时调向一致性）。**把 CAP/PACELC 当作分析框架**去推理每个工作负载的容忍度——而不是把整个数据库标上"CP"或"AP"的打勾。

**要点：**
- CAP 只在分区时适用。
- PACELC 增加正常情况下延迟 vs 一致性。
- 选择按操作，而非按系统。
- Spanner ≈ CP；Dynamo ≈ AP。

### 12. 最终一致性模式

**频率：** 高

**题目：** 哪些模式能让最终一致性对用户可容忍、对数据保正确？

**答案：** 最终一致性意味着副本**在写停止后收敛**，但期间读可能陈旧或乱序。工程任务是对用户**掩盖滞后**，同时保数据**正确**。一套一致性保证，各自叠在普通最终一致性之上：

**读自己写（read-your-writes）：** 用户必须总看到自己*自己*的更改。写后短时间内把该用户的读**路由到主**（或已追上的副本），或附上一个**写 token/版本**让读路径等待。没有它，用户编辑资料、刷新、看到旧值——典型的"是不是坏了"bug。

**单调读（monotonic reads）：** 用户绝不能看到时间**倒退**（先读到新值，因请求打到滞后副本又读到旧值）。通过会话亲和性把用户**钉在单一副本**，让读只向前。

**因果一致（causal consistency）：** 若 A 导致 B，人人都先看到 A 再看到 B。用矢量时钟或会话 token 跟踪 **happens-before**。对**聊天和评论**至关重要——你绝不能在看到被回复的消息之前先看到回复，即使全局总序被放松。

**有界陈旧（bounded staleness）：** 给一个**可度量的 SLA**——"读最多落后 N 秒或 M 个操作"（Cosmos DB 作为一个档位提供）。这把"最终"变成你能推理和告警的数字。

对 **UX**，**乐观 UI** 完全隐藏滞后：把更改**本地立即应用**，服务器确认后再协调（罕见失败时回滚）——点赞按钮瞬间变蓝。对**数据正确性**，使写**幂等**（至少一次投递下重试安全），并对在多处并发编辑的数据用 **CRDT**（无冲突复制数据类型），让合并**自动且无冲突**而非"后写覆盖"。

最后，**按端点记录一致性契约**——"此读最终一致，最多陈旧 ~2s"——让消费方不要默默假设强语义而在上面建竞态逻辑。

**要点：**
- 通过主路由或 token 实现读自己写。
- 有界陈旧提供可度量的 SLA。
- 乐观 UI 对用户隐藏延迟。
- 按 API 记录一致性契约。

### 13. 强一致性 vs 最终一致性 vs 因果一致性

**频率：** 高

**题目：** 请对比强一致、最终一致与因果一致，并举一个按操作选择的例子。

**答案：** 它们处在从"总是正确、总是昂贵"到"便宜、有时陈旧"的谱系上。

**强（线性化）一致性：** 每次读返回**最新已提交的写**，系统表现得就像只有单份数据、操作按单一全局顺序。这是最直觉的模型，但**昂贵**：需要**共识**（Raft/Paxos）或同步复制，增加延迟并**限制可用性**——分区期间强一致系统必须拒绝无法法定人数的写。用在正确性不可妥协之处：**账户余额、库存计数、唯一用户名抢占**。

**最终一致性：** 允许副本分歧，只在**写停止后收敛**。它**最便宜、最可用**——写从最近副本确认，系统在分区下保持在线——但读可能**陈旧或乱序**。完美适用于一点陈旧不可见或无害之处：**社交时间线、浏览量、商品目录、DNS**。

**因果一致性：** 中间的甜点。它**保留 happens-before**：若 A 导致 B（一条消息及其回复），**每个观察者都先看到 A 再看到 B**——但它*不*对无关事件强加全序。这正是**协作应用和聊天**所需：比强一致更便宜更可用，但绝不会在消息之前显示回复、或在帖子之前显示评论。**顺序一致性**紧在因果之上——尊重每个客户程序顺序的单一全局顺序，但不必是实时顺序。

实用教训：**按操作选，而非按系统**。同一消息应用里，**账户/计费**读是**强**，**"谁在线"列表**是**最终**，**线程内的消息**是**因果**。把每个操作的一致性与其实际业务容忍度匹配，才能在能承受之处买到可用性和延迟、只在必须之处花钱在一致性上。

**要点：**
- 强：线性化，昂贵。
- 最终：便宜，可能陈旧或乱序。
- 因果：保留因果序。
- 按操作选，而非按系统。

### 14. 分布式事务：2PC vs sagas

**频率：** 高

**题目：** 请对比分布式事务中的 2PC 与 saga。你何时用哪个？

**答案：** 两者都解决"让多个服务就一个全或全无的结果达成一致"，但方式大不相同。

**两阶段提交（2PC）**用一个**协调器**和两轮。**阶段 1（prepare）：**协调器问每个参与者"你能提交吗？"；每个干活、锁资源并投 yes/no。**阶段 2（commit/abort）：**若全投 yes，协调器告诉大家提交；否则全部回滚。这给出**真正的原子性**，但缺陷在大规模下致命：参与者在两阶段间**持锁**，吐吐量暴跌；若**协调器在 prepare 后崩溃**，参与者无限期**阻塞**持锁（经典阻塞问题）；而且它**把服务紧耦**并不容忍微服务网中正常的部分失败。所以 2PC 用在**单个数据库集群内或跨 XA 感知资源**（DB + 消息代理），**而非**跨独立微服务。

**Saga** 舍弃全局原子性，换取**最终原子性**。事务是**一系列局部事务**，各自独立提交，各配一个语义上撤销它的**补偿动作**。若第 3 步失败，就对第 2、1 步反向跑补偿。跨服务不持锁，所以它**可扩展**并容忍部分失败。难点是补偿必须**幂等**（重试可能触发两次）且**语义上有意义**——你不能字面上"取消扣款"，所以补偿是一笔**真实退款**，"取消发送"邮件不可能所以你发一封更正。还有个**可见性窗口**：在一步与其补偿之间，其他读者可能看到中间状态，所以有时需要语义锁或"待定"状态。

**选 2PC** 只在单个 DB 集群或 XA 基础设施内、需要强原子性且参与者受严格控制时。**跨服务边界选 saga**——并偏好**编排式**saga（中心协调器驱动各步）而非**编舞式**（服务互相响应事件），因为 saga 卡在中途时编排流程**可见且好调试得多**。

**要点：**
- 2PC：阻塞，跨服务不可扩展。
- Saga：局部事务 + 补偿。
- 补偿必须幂等且有意义。
- 编排式 saga 比编舞式更易调试。

### 15. 只读副本与复制延迟

**频率：** 高

**题目：** 只读副本如何工作，你如何管理复制延迟？为什么它们不能扩展写？

**答案：** **只读副本**是主库的一份拷贝，接收主库变更流并服务**只读**查询。把分析、仪表盘和非关键读指向 N 个副本，就**卸载了主库**，让它专注写——读密集工作负载的标准第一步。

难点是**复制延迟**——副本总稍微落后。延迟取决于复制模式：

- **异步复制：**主库提交并**立即**向客户确认，然后在后台把变更送到副本。它**快**（写不等副本）但读可能**陈旧**，且延迟在大量写、网络抖动或副本重启追赶时**飙升**。若主库在送出最近提交前死了，那些写就**丢了**。
- **半同步复制：**主库在提交前等**至少一个副本确认**收到。这把故障切换时的数据丢失限定（被提升的副本拥有最新已提交数据），代价是**写稍慢**。常见生产配置：一个半同步副本用于安全故障切换，加几个异步副本用于读扩展。

**运维上你必须测量延迟**，既看**落后主库多少秒**（多陈旧，为 UX）又看**落后多少字节/LSN**（多少积压，为容量），并在超阈值时**告警**（如 >5s），因为滞后副本会静静地服务越来越错的数据。为**读自己写**正确性，把**写后关键读路由到主库**（或通过写 token 确认已追上的副本）——例如用户刚更新资料后，从主库读其资料。

关键局限：**只读副本对写吞吐量毫无帮助。**每个写仍在主库执行*并*在每个副本上回放，所以加副本只加读容量而写天花板不变（且每个额外副本还加复制负载）。一旦**主库写速率**成为瓶颈，副本就帮不上忙——你必须**分片**（把数据分到多个主库）才能水平扩展写。

**要点：**
- 异步 = 快但陈旧；半同步 = 更安全。
- 同时监控延迟的秒数与字节数。
- 写后读路由到主。
- 副本不能扩写——之后分片。

### 16. 分片策略与再平衡

**频率：** 高

**题目：** 请对比主要分片策略。为什么再平衡是难点？

**答案：** 分片把数据分到多个数据库节点，让写（和存储）水平扩展。策略决定 key 如何映射到分片——各有不同取舍。

**哈希分片：** `shard = hash(key) mod N`。它把 key 铺得**均匀**、避免热点，但你**失去范围查询**（相邻 key 落在不同分片），而且——关键地——朴素的 `mod N` 在 N 变化时**几乎重洗一切**（加一个节点，几乎每个 key 都移动）。修法是**一致性哈希**（或**虚拟节点**），改变成员只移动约 1/N 的 key。

**范围分片：** 每个分片拥有一段**连续 key 范围**（如用户 A–F、G–M…）。这让**范围扫描和有序查询高效**，但**易热点**——时间戳或自增 ID 这样的顺序 key 全堆到最新分片（"热的最后一个分片"问题）。缓解方法：选分布良好的分片 key 或加盐。

**目录/查找分片：** 一个显式**分片映射**（"客户 42 → 分片 7"）给最大灵活性——任何 key 能放任何地方且可单独移动。代价：映射是额外一跳且是潜在**瓶颈与单点故障**，所以必须缓存并高可用。

**地理分片：** 按**地区**分，让数据住在用户附近（EU 用户在 EU 分片）。对**延迟和数据驻留/合规**很好，但跨区查询昂贵且负载可能按地理倾斜。

**再平衡是真正的难点。**当你加容量或某分片变热，你必须**无停机移动活数据**，即向旧新分片**双写**、**回填**历史行、验证，再**切换**读——全程系统仍在服务流量。做错会丢数据或重复数据。所以团队要么用**原生再平衡**的系统（Cassandra、Vitess、CockroachDB 自动移 range/token），要么**在上线前规划再分片**——最重要的是起步就选**高数量虚拟分片**（如 1024 个逻辑分片映射到几个物理节点），这样未来增长只需把虚拟分片重映射到新节点，而非重新哈希每个 key。

**要点：**
- 哈希：均匀但无范围查询。
- 范围：范围扫描，热点风险。
- 一致性哈希最小化重洗。
- 用大量虚拟分片便于再平衡。

### 17. 缓存层与失效

**频率：** 高

**题目：** 请过一遍缓存层与写策略。为什么失效是那个难题？

**答案：** 缓存存在于**多个层**，一个请求可能命中好几个：**浏览器缓存**（本地、每用户）、**CDN**（静态资源，全球边缘缓存）、**边缘/反向代理缓存**、**API 网关缓存**（整个响应）、**进程内应用缓存**（本地 map 或 Caffeine——最快，但每实例独立不共享）、Redis/Memcached 这样的**共享缓存**（跨实例共享，一次网络跳），最后是**数据库缓冲池**。规则是**每层都度量**——低 CDN 命中率和低 Redis 命中率需要截然不同的修法。

**写/读策略**决定缓存和数据库如何保持同步：

- **cache-aside（懒加载）：**应用查缓存，miss 时读 DB 并自己填缓存。简单、弹性（缓存宕机只是读变慢），是**通常默认**——但 miss 后首请求慢，陈旧条目在失效前滞留。
- **read-through：**缓存库 miss 时透明从 DB 取；应用代码更干净但把你耦到缓存提供方。
- **write-through：**每个写同步到缓存**和** DB——缓存总是新鲜，代价是写延迟及缓存了可能从不被读的数据。
- **write-behind（回写）：**写缓存，异步刷到 DB——写最快，但若缓存在刷前死了就**有数据丢失风险**。

**失效**是出名的难题（"只有两件难事…"）。选项在陈旧与耦合间权衡：**TTL** 最简单但接受有界陈旧；**写时显式失效**一致但把写方耦到每个缓存；**事件驱动**失效（通过 **CDC**/变更流）在 DB 变化时自动触发失效，把写方与缓存解耦。做错意味着用户看到陈旧数据，或更糟——跨层不一致的数据。

最后，防范**缓存雪崩**——一个热 key 过期时成千上万请求同时打 DB。用**请求合并**（只一个请求重算，其余等）、**拖动 TTL**（key 不同时过期）和 **stale-while-revalidate**（后台一个 worker 刷新时先供陈旧值）缓解。重要指标是**命中率**（每层）和**尾延迟**（p99），而非平均值。

**要点：**
- 层次众多——每一层都要度量。
- cache-aside 是默认。
- TTL + 抖动防止雪崩。
- 失效是难题。

### 18. 断路器

**频率：** 高

**题目：** 请解释断路器模式、它的三种状态，以及它如何防止级联失败。

**答案：** **断路器**包裹对远程依赖的调用并**跟踪失败率**，当依赖明显坏掉时就**停止调用它**而不是继续猫加。它借用电路隐喻，有**三种状态**：

- **关闭（Closed，正常）：**调用通过；断路器数失败。若失败率越阈，它**跳开**。
- **打开（Open，已跳）：**调用**立即快速失败**而不碰依赖。这是关键一招——它停止猛击已宕服务，给它恢复空间，并释放调用方资源。**冷却**后转半开。
- **半开（Half-open，探测）：**放**有限数量的试探请求**通过。若成功，依赖已恢复，断路器**关闭**；若失败，它**重新打开**并再等。

为什么重要：**级联失败**。没有断路器，当下游服务变慢或死亡，调用方堆积在**重试循环和阻塞线程**里，耗尽自己的线程池/连接——于是调用方也倒下，其调用方紧接着倒，直到整个系统因一个坏依赖而宕。断路器**限住爆炸半径**并**释放**否则会卡在等待的资源。

调优旋钮：**错误阈值**（如最近 100 请求 >50% 失败时跳——基于率而非原始计数，低流量不误跳）、**打开时长**（探测前等多久，如 10s）和**半开探测数**。同样重要的是断路时的**回退**：供**陈旧缓存**值、**默认/空响应**或**入队稍后处理**——优雅降级而非报错。

断路器**补充但不取代超时**——总先设激进超时（无限等待才是填满线程池的元凶），断路器坐在上面停止重试已知坏的依赖。实践中你从**库**（Resilience4j、Polly、Hystrix 的继任者）或**服务网格**（Istio/Envoy）获得它而非手写。跟踪断路器状态转换也是有价值的早期**健康信号**。

**要点：**
- 状态：关闭、打开、半开。
- 防级联并节省资源。
- 配合超时与回退。
- 库或网格提供。

### 19. 超时、重试、指数退避、抖动

**频率：** 高

**题目：** 请阐述远程调用中超时、重试、指数退避和抖动的纪律。

**答案：** 这四者合起来把脆弱的远程调用变成有韧性的——但只有在有纪律地应用时。

**超时：**每个远程调用**都必须**有一个，因为**无限等待会级联成故障**——一个挂起的下游调用占住一个线程/连接，足够多就耗尽池并把调用方拖垮。关键是把每个超时设得**比调用方的超时短**——这是**预算传播**：若面向用户的请求有 3s 预算，它发的下游调用应远低于 3s 超时，否则调用方先超时、工作白做。截止期应沿调用链向下流。

**重试——只对幂等操作。**重试 `GET` 或幂等 `PUT` 是安全的；盲目重试一个扣款的 `POST` 会**重复扣款**。所以只重试幂等操作（或用幂等 key 使其幂等），并**限制次数**——通常 3 次够了；无界重试只会放大负载。也只重试**对的失败**：**5xx 和网络/超时错误**值得重试（瞬时的）；**4xx 客户端错误**不值——请求畸形或未授权，重试它会永远同样失败。

**指数退避：**每次尝试间等更久（如 100ms、200ms、400ms）而非立即重试。故障期间立即重试造成**惊群**，让挣扎的服务持续宕机。

**抖动：**给退避加随机（**完全抖动** = 在 `[0, backoff]` 里取随机延迟）。没有抖动，同一瞬间失败的所有客户端会**重新同步**并步调一致地重试，产生反复的协同尖峰。抖动把它们打散、平滑负载。

最后，重试必须**与断路器结合**——依赖已坏还重试只会更糟，所以断路器**打开时你完全跳过重试**、快速失败。并把**重试率当作一等指标跟踪**：重试突然飙升往往是依赖劣化的**最早信号**，远早于它表现为面向用户的错误。

**要点：**
- 处处设超时；比父级短。
- 只对幂等操作重试，有上限。
- 完全抖动 > 无抖动以打散惊群。
- 断路打开时跳过重试。

### 20. SQL vs NoSQL 决策矩阵

**频率：** 高

**题目：** 你如何在 SQL 与各 NoSQL 家族间选择？为什么不该一上来就"为规模"用 NoSQL？

**答案：** 诚实的默认是**关系型 SQL**（Postgres、MySQL）：它给你**丰富的即席查询、ACID 事务、连接、约束、成熟生态**，以及在写时抓 bug 的严格 schema。你应该选它，**除非有具体理由排除它**，因为多数应用能在单个 Postgres 实例里舒服地跑好几年，而调优良好的 Postgres 能扛远超人们预期的负载。

NoSQL 家族各自优化一个**特定访问模式**，你按实际怎么查询而非按炒作来选：

- **文档存储（MongoDB、DynamoDB）：**存类 JSON 文档，**schema 灵活/多变**、**单文档原子性**。适合每条记录是自包含聚合、形态多变且你想要**高写吞吐**而无刚性迁移。弱在跨文档连接和多文档事务。
- **宽列（Cassandra、ScyllaDB）：**为**海量写吞吐**和**线性水平扩展**、**可调一致性**而建。对**时序、事件日志、写多**工作负载极佳——但你必须**提前围绕查询设计表**（查询优先建模），因为不支持即席查询。
- **键值（Redis、DynamoDB）：**按 key 极简 `get`/`put`，**亚毫秒延迟**。理想用于缓存、会话、计数器、排行榜、限流器——任何访问模式是直接 key 查找之处。
- **图（Neo4j）：**一等的**关系与遍历**。当核心查询是"朋友的朋友"、欺诈团伙或推荐路径——在 SQL 里会是痛苦自连接的多跳关系查询——图数据库大放异彩。

**按四个维度决定：****访问模式**（提前已知的查询偏向专用 NoSQL 建模；不可预测的查询偏向 SQL 的灵活性）、**一致性需求**、**规模**和**运维成熟度**（你的团队真能运维 Cassandra 集群吗？）。反模式是过早"为规模选 NoSQL"：你把连接、事务、查询灵活性——真实的每日成本——换掉，去解一个你还没有的扩展问题。**先证明 SQL 不够**；多语言持久化（SQL 存核心数据、Redis 做缓存、搜索引擎做全文）通常优于把一切押在一个非关系存储上。

**要点：**
- SQL 是默认，直到被证伪。
- NoSQL 的选择依赖访问模式。
- 大规模写多用宽列。
- 真正关系查询用图数据库。

### 21. 认证 vs 授权架构

**频率：** 高

**题目：** 请对比认证与授权。为什么在架构上把它们分开？

**答案：** **认证（AuthN）**回答**"你是谁？"**——通过登录、会话、MFA、无密码/passkey、社交登录验证身份。**授权（AuthZ）**回答**"你被允许做什么？"**——通过 RBAC（基于角色）、ABAC（基于属性）或 ReBAC（基于关系）规则评估*这个*身份是否可对*这个*资源做*这个*动作。它们是不同问题，**混为一谈是经典 bug 源**——检查了某人已登录但没检查他拥有正在编辑的记录（对象级授权失效，OWASP API 头号风险）。

**在架构上分开**有回报，因为它们独立扩展和演化：

- **把认证集中到身份提供方**（Auth0、Okta、Cognito 或内部 IdP）。一个地方拥有凭据、MFA、会话生命周期和锁定策略——你不想每个服务都重实现登录。它签发下游服务信任的 token（OIDC/JWT）。
- **授权可集中或分散。**一个**中央策略引擎**——**OPA/Rego、AWS Cedar 或 AuthZed/SpiceDB**（Google Zanzibar 式 ReBAC）——让你在一处编写、版本化和审计策略，并从任何服务查询它。或者，服务通过**共享库**本地评估策略以求更低延迟。趋势是把授权从应用代码外置，好让权限逻辑不散落在 `if user.role == "admin"` 检查里。

关键分工：**token（JWT/OIDC）携带身份、也许粗粒度角色**，但**细粒度、资源级决策（"Alice 能编辑文档 42 吗？"）应由策略引擎在请求时评估**，而非烤进 token——因为权限变化比 token 生命周期快，而把每个权限塞进 JWT 会让它臃肿并使撤销不可能。

最后，**审计每次授权决策**及完整上下文——**主体、动作、资源、决策（allow/deny）和原因/策略**——好让你在安全审查或事故时回答"谁访问了这个、为何被允许？"。那审计轨迹往往是合规要求，也对调试"为什么这个用户不能做 X？"极有价值。

**要点：**
- 认证 = 身份；授权 = 权限。
- 集中 IdP 做认证；引擎做授权。
- JWT 承载身份，不是细粒度权限。
- 带完整上下文审计决策。

### 22. OAuth 2.0 / OIDC 流程

**频率：** 高

**题目：** 请过一遍 OAuth 2.0 和 OIDC——主要流程、token 类型和安全实践。

**答案：** **OAuth 2.0** 是一个**委派授权**框架：它让应用获得一个**access token** 来*代表用户*调用 API，而从不见其密码。**OIDC（OpenID Connect）**在 OAuth 之上叠加**认证**，加了一个携带已验证身份声明的 **ID token**——所以 OAuth 回答"这应用能访问这 API 吗？"，OIDC 还回答"用户是谁？"。

**流程，以及各自何时用：**

- **Authorization Code + PKCE**——Web 应用、移动应用和 SPA 的**现代默认**。用户在 IdP 认证，IdP 通过重定向返回短时**授权码**；应用用该码（加 **PKCE** verifier）换 token。**PKCE**（Proof Key for Code Exchange）把码绑定到发起流程的客户端，所以被截获的码无用——对不能保守密钥的**公共客户端**（移动/SPA）至关重要。
- **Client Credentials**——**机器对机器**，无用户参与。后端服务用自己的 client ID/secret 认证以获得访问另一 API 的 access token。
- **Device Code**——用于**输入受限设备**如电视和 CLI：设备显示一个码，用户在手机/笔电上输入，设备轮询 token。

**已弃用流程：****Implicit** 流程（直接在 URL 片段返回 token——泄漏、无 PKCE）和 **Resource Owner Password**（应用处理原始密码——违背委派初衷）。新系统别用它们。

**Token 类型：****access token** **短时**（分钟级）并作为 bearer 凭据发给 API；**refresh token** **长时**，用于静默获取新 access token——必须安全存储并**每次使用时轮换**（轮换检测盗用：被重放的旧 refresh token 表明失陷）。**ID token**（OIDC，一个 JWT）携带身份声明（`sub`、`email`、`name`）供客户端建立会话。

**安全实践：**公共客户端始终用 **PKCE**；处处要求 **HTTPS**；**校验 `iss`**（签发方）、**`aud`**（受众——token 是给*你的* API 的）、**`exp`**（未过期）和 **`nonce`**（把 ID token 绑到你的请求，阻止重放）。把 refresh token 存在 **HTTP-only、Secure cookie** 或平台安全存储里——绝不放 `localStorage`（XSS 能偷它）——并**使用时轮换**。

**要点：**
- Authorization Code + PKCE 是默认。
- Access token 短，refresh token 轮换。
- OIDC 在 OAuth 之上加 ID token。
- 总是校验 iss/aud/exp/nonce。

### 23. Blue/Green vs Canary vs 滚动

**频率：** 高

**题目：** 请对比 blue/green、canary 和滚动部署。你如何按风险等级混用它们？

**答案：** 三者都把新版本发到生产；区别在**需多少额外容量**和**回滚多快多安全**。

**滚动：**每次替换 **N 个实例**——杀几个 v1 pod、拉起 v2 pod、重复直到全集群升级。它**便宜**（无额外容量——复用同一批节点），是 Kubernetes 默认。缺点：**回滚慢**（得每次 N 个地回），部署期间**两个版本都服务**流量所以必须兼容，且**坏版本立即触达真实用户**（一开始只一小部分，但无自动门控）。

**Blue/green：**在运行中的 v1（"蓝"）旁**立起整个 v2（"绿"）集群**，私下测试绿，然后**原子地切全部流量**（翻转负载均衡器/DNS/路由器）。**回滚瞬时**——翻回仍在运行的蓝。代价是切换期**约 2 倍容量**，且因为切换是全或全无，坏 v2 在你翻的那一刻命中**100% 用户**（切前用冒烟测试缓解）。它干净，适合**有状态或 DB 耦合的升级**，你想要一次果断切换。

**Canary：**把**一小百分比**流量路由到 v2（如 1% → 5% → 25% → 100%），每步**盯 SLO**（错误率、延迟、业务指标），并基于分析**自动爬升或回滚**（Flagger、Argo Rollouts、Spinnaker）。这给**最小爆炸半径**——坏版本在只影响 1% 用户时就被抓——但**需要强可观测性**和自动指标分析才安全，且完全展开更慢。

**按风险混用**是成熟做法：**风险变更用 canary**（新算法、大重构、任何面向用户且不确定的）以早捕回归；**常规低风险部署用滚动**（配置微调、小修复），canary 分析的开销不值；**有状态或数据库耦合的升级用 blue/green**，干净、可逆、一次性切换比两版本在同一数据上交错更安全。把仪式感匹配变更的爆炸半径。

**要点：**
- 滚动：便宜，回滚慢。
- Blue/green：瞬时回滚，2 倍容量。
- Canary：渐进，依赖可观测性。
- 按风险等级混用。

### 24. 日志 vs 指标 vs 链路追踪

**频率：** 高

**题目：** 请对比可观测性三支柱——日志、指标和链路追踪。它们如何协同工作？

**答案：** 日志、指标和追踪回答不同问题，成熟的可观测性三者并用而非只选一个。

**日志**是**离散、带时间戳、带丰富上下文的事件**——"用户 42 支付失败：卡被拒，码 XYZ"。它们是**调试具体事故**的最佳工具，因为携带细节。但它们**大规模存储贵**（高量、全文索引）且**难聚合**——靠扫日志回答"我的 p99 延迟是多少"又慢又贵。最佳实践是**结构化日志**（带字段的 JSON），至少让日志可查。

**指标**是**带标签的数值时间序列**——`http_requests_total{status="500", route="/checkout"}`。它们**便宜**（只是随时间的数字）、**可聚合**，完美用于**仪表盘、SLO 和告警**（"错误率 >1% 持续 5 分钟就 page 我"）。它们的硬约束是**基数**：每个唯一标签组合是一个单独序列，所以把**用户 ID 或请求 ID 这样的高基数字段放进标签会爆炸序列数**，能搞垮你的指标后端。保持标签**低基数**（status、route、region）——这是要盯的指标杀手。

**追踪**跟随**单个请求跨服务**，把它拆成带每-span 计时的 **span**。一个追踪显示一个慢结账在 API 花了 20ms、等支付服务 400ms、DB 30ms——对**延迟分析**和在分布式系统中建**服务依赖图**无价，因为没有单个日志或指标能展示端到端路径。因为追踪每个请求贵，你**采样**追踪（保留一定百分比）——**但你永不采样掉错误**：失败/慢请求总保留 100% 追踪，因为那正是你需要调试的。

**并用：****指标**告诉你*出了问题*并触发告警；**追踪**告诉你分布式调用图中*哪里*耗时或出错；**日志**告诉你那个具体 span *为什么*。**OpenTelemetry** 统一了埋点表面——三者用一套 SDK 和线格式，用**关联 ID** 把追踪链到其日志——所以你能从告警转到追踪再到具体日志行，同时自由选后端（Datadog、Honeycomb、Grafana/Loki/Tempo/Prometheus）。

**要点：**
- 指标做告警、日志做调试、追踪做流程。
- OpenTelemetry 标准化埋点。
- 基数是指标的杀手。
- 对追踪采样；永远不要采样错误。

### 25. SLI / SLO / SLA 与错误预算

**频率：** 高

**题目：** 请定义 SLI、SLO、SLA 和错误预算，并解释它们如何连起来治理部署风险。

**答案：** 这四个术语构成可靠性工程的词汇，它们从测量到契约到决策连成一链。

- **SLI（服务水平指标）：**一个**用户可见健康的可度量信号**——请求成功的比例、p99 延迟，或"300ms 内服务的请求"。是你实际测量的原始数字。
- **SLO（服务水平目标）：**对该 SLI 的**内部目标**——"滚动 30 天内 99.9% 请求成功"。是你对自己坚守的线。
- **SLA（服务水平协议）：**与客户的**对外契约**，违约带**罚则**（退款、抵扣）——"99.5% 可用否则抵扣账单"。SLA 有意设得**比 SLO 松**（你想通过 SLO 在内部远早于违反客户契约前抓到问题）。
- **错误预算 = 1 − SLO。**99.9% 的 SLO 允许 **0.1% 失败**——30 天里那是你*被允许*花掉的约 43 分钟停机。

**错误预算是枢纽思想**，因为它把"可靠性 vs 速度"从争论变成**量化政策**。当你**舒服地达到 SLO** 时，你有预算可*花*——发风险变更、跑实验、更快部署，因为你能承受些失败。当预算**耗尽**（用完了 43 分钟），你**冻结风险部署**并把精力转向可靠性直到预算恢复。这让开发和运维就一个数字对齐，而非开发抽象地推速度、运维抽象地推稳定。

两个重要细化。**SLI 必须以用户为中心**——测量"用户请求是否成功且快速返回？"，**而非** CPU 或内存这样的基础设施代理。高 CPU 但用户满意没问题；低 CPU 但用户报错才是问题——基础设施指标用于调试，不用于定义可靠性。**告警用多窗口、多燃烧率**逻辑：**快燃**（一小时内耗尽整月预算）立即 page，**慢燃**（几天渐进走势）开工单。结合短窗口和长窗口既防**短暂抖动的告警疲劳**又防**漏掉缓慢稳定的劣化**——你只对真正威胁预算的东西 page。

**要点：**
- SLI 度量、SLO 目标、SLA 契约。
- 错误预算治理部署风险。
- 用户为中心的 SLI 优于基础设施。
- 多窗口燃烧率告警。

### 26. 短链接（bit.ly）

**频率：** 高

**题目：** 请设计一个像 bit.ly 的短链接服务。覆盖码生成、存储和 301-vs-302 权衡。

**答案：** **需求：**把长 URL 缩短为短码，`GET /:code` 时重定向，跟踪点击，并处理规模——比如 **1000 亿 + 链接**、**约 10 万读 QPS**、读写比约 **10:1**（重定向远多于创建）。这是**读密集、写轻**系统，塑造了每个决策。

**组件：**一个 **API 服务**（`POST /shorten` 创建、`GET /:code` 重定向）、一个**码生成器**、存 code→URL 映射的 **KV 存储**，以及点击的**分析管道**。

**码生成。**干净的做法是取一个**全局唯一 64 位 ID** 并 **base62 编码**（`[a-zA-Z0-9]`，7 字符 ≈ 3.5 万亿码）。ID 来自**分片/分段计数器**（每个应用服务器抓一段 ID 范围以免每请求协调）或 **Snowflake 式**生成器（时间戳 + 机器 + 序号）。另一种——**哈希 URL**（如 MD5 取前缀）——需要**冲突处理**（用盐重试）且能让相同 URL 去重，但随空间填满有冲突风险。

**为读调优的存储层。**前面放 **CDN/边缘缓存**让热重定向不碰源站；最热码放 **Redis 缓存**；一个**耐久、可水平扩展的 KV 存储**（Cassandra 或 DynamoDB，按 `short_code` 哈希分片）作为事实来源。因为 code→URL 映射**不可变**，它缓存得极好。

**数据模型：**`{ short_code (PK), long_url, owner, created_at, expires_at, click_count }`。

**301-vs-302 权衡是经典陷阱。****301（永久）**重定向被浏览器和 CDN 永远缓存——利于卸载流量（后续命中永不到你）但它**杀死分析**（你永不见重复点击）并使**撤销/过期困难**（缓存的重定向持续）。**302（临时）**重定向意味着**每次点击都回到你的服务**，所以你能**计点击**并**撤销/过期**链接——代价是更高负载。**分析或撤销重要时选 302**，原始重定向吞吐最重要时选 301。

**扩展与安全：**按码哈希分片 KV，在每个边缘本地缓存最热码，并异步流点击（`click → Kafka → ClickHouse`）让分析永不拖慢重定向路径。注意**基于计数器的码是顺序且可猜的**——公链没问题，但对私链是**安全/枚举风险**，那里应用**随机或哈希**码让人无法遍历 ID 空间。

**要点：**
- 来自分片计数器或 Snowflake 的 base62。
- CDN + Redis + 耐久 KV。
- 需要点击分析则用 302。
- 本地缓存热码吸收峰值。

### 27. Twitter 时间线（写时扇出 vs 读时扇出）

**频率：** 高

**题目：** 请设计 Twitter 主页时间线。对比写时扇出与读时扇出，并描述混合方案。

**答案：** **需求：**用户发推并看到其关注者的**主页时间线**，按时间或排序。规模是全部挑战——**约 5 亿用户**、严重的**读写偏斜**（人们浏览远多于发帖）、以及**带 1 亿 + 粉丝的名人**。核心问题是*何时*组装每个用户的时间线。

**写时扇出（push）：**用户发推时，**立即把该推推入每个粉丝的预计算时间线**——每用户一个 **Redis 列表（"收件箱"）**。于是读极快：时间线读只是"返回我的收件箱列表"，O(1)。代价是**写放大**：普通用户一推扇出到几百收件箱（没问题），但**带 1 亿粉丝的名人一推触发 1 亿次收件箱写**——巨大、尖峰的写风暴，跟不上。

**读时扇出（pull）：**推存一次，**读时查询你关注的所有人的最近推并合并**。写便宜（一次插入），但**读贵**——组装时间线意味着每次浏览都扇出到几百个被关注者并归并排序其推，在 5 亿用户时很慢。

**混合才是真正答案：****普通用户写时扇出**（便宜、给 99% 快读），但对**名人不扇出**——把其推放单独存储并在**读时合并**。所以用户时间线 = 其预计算收件箱（来自普通被关注者）**∪** 对其关注的少数名人的实时拉取，合并并排序。这限住写放大（无 1 亿写风暴）同时对几乎所有人保持快读。

**组件：**一个 **Tweet 服务**（耐久存储——Manhattan/Cassandra）、一个 **Timeline 服务**（Redis 收件箱）、由 **Kafka** 驱动的**扇出 worker**（把发帖与昂贵扇出解耦，推瞬时返回而分发异步进行）、一个**排序服务**（ML 模型按预测参与度而非严格时序重排合并时间线）和一个**媒体服务**（S3 + CDN）。关键取舍：混合**平衡写放大与读延迟**，Kafka **吸收扇出尖峰**，**排序最终取代纯时序**——它本身又在合并之上加了延迟和复杂度。

**要点：**
- 混合扇出：普通写、名人读。
- 每用户 Redis 列表作收件箱。
- Kafka 把发推与扇出解耦。
- 在时间线合并之上加排序模型。

### 28. WhatsApp / 聊天

**频率：** 高

**题目：** 请设计 WhatsApp/一个聊天系统。覆盖连接、消息路由、在线状态和 E2E 加密。

**答案：** **需求：**1:1 和群聊、**在线状态**、**送达和已读回执**、**端到端加密**、**离线消息排队**（接收方重连时送达），超大规模——比如**每天 1000 亿条消息**。聊天本质在于**维持百万活连接**并在它们之间可靠路由小消息。

**组件：**
- **连接服务：**持有**长连 WebSocket**——用事件驱动/actor 运行时可能**单节点百万连接**（WhatsApp 著名地用 Erlang，其轻量进程擅长海量并发）。每个已连用户**钉在特定连接节点**。
- **消息服务：**持久化**每会话追加日志**（Cassandra 或自研存储），让消息存活并可重送。
- **状态服务：**用**带短 TTL 的 Redis 键**跟踪在线/离线和"最后上线"——心跳刷新键，过期即离线。状态高流动，所以单独且瞬时。
- **推送服务：**接收方离线时，交给 **APNs/FCM** 让其手机唤醒并拉取排队消息。
- **媒体服务：**大附件作为（E2E 加密）blob 进 **S3 + CDN**，不走消息路径。

**路由：**每个用户通过**一致性哈希**映射到其连接节点（一个用户→节点注册表）。送一条消息时，发送方节点**查接收方节点并转发**到那里；那节点把它推下接收方的 WebSocket。若接收方离线，消息在日志里**排队**并发**推送通知**；重连时客户端拉取漏接的。**送达/已读回执**只是同样回流的小控制消息（sent → delivered → read）。

**端到端加密：**用 **Signal 协议**——**X3DH** 做初始密钥协商、**Double Ratchet** 做每消息前向保密密钥。关键地，**服务器只存储和转发密文**，无法读消息。密钥住在设备上，这就是为什么"此消息已加密"以及新设备必须重建会话。

**扩展：****按用户分片**、把每个用户**地理路由**到最近接入点以降延迟，并对**群聊异步扇出**（通过消息服务送给 N 成员而非阻塞发送方）——群消息是同一路由问题按成员重复，所以通过队列解耦。

**要点：**
- 每用户 WebSocket；一致性哈希到节点。
- Signal 协议做 E2E（X3DH + Double Ratchet）。
- 按会话日志存 Cassandra。
- APNs/FCM 做离线送达。

### 29. Uber / 网约车调度

**频率：** 高

**题目：** 请设计 Uber 式网约车调度。覆盖地理索引、匹配和扩展模型。

**答案：** **需求：**在**数秒内把乘客匹配到附近可用司机**、跟踪百万司机的**实时位置**、计算**定价/加价和 ETA**，规模——比如 **1000 万+活跃司机**。系统核心是在持续位置更新洪流下的**地理空间匹配**问题。

**组件：**
- **位置服务：**每个司机**每几秒 ping 一次 GPS**。不能每次查询扫全部司机，所以把他们索引在**地理空间结构**里——**Google S2 cell** 或 **Uber 的 H3 六边形**——把地球划分为层次化 cell。"找乘客附近司机"就变成"查乘客所在 cell 及邻居 cell"，把全局搜索变成**局部 cell 查找**。
- **调度服务：**维护**每 cell 的可用司机索引**并跑**匹配算法**——通常**最小化接驾 ETA**（考虑路网和路况而非直线距离）同时加入**公平性**（把单均匀分给司机）并避免抖动。
- **定价/加价服务：**从实时**供需比**计算**每 cell 加价**——某 cell 内司机少 + 请求多 → 提高倍数以拉供给并配额需求。
- **行程服务：**一个**状态机**——`requested → matched → en_route → in_progress → completed`——保证每个行程正确且恰好一次地推进，外加**支付**和**通知**服务挂在状态转换上。

**扩展：****按城市/区域地理分片**——因为**几乎每笔行程都是本地**，苝加哥的乘客永远不需东京的司机，所以**每区域独立调度服务**干净横向扩展。**位置更新流**巨大（1000 万司机×每几秒一 ping），通过 **Kafka** 作为 firehose 流入**内存地理索引**而非每 ping 就砌数据库。

**关键取舍——贪婪 vs 全局匹配：**简单做法把每个请求立即匹配到**最近可用司机**（快、简单、局部最优）。**全局/批优化**等一会把*一批*乘客和司机一起匹配，最小化所有人总等待——全局更优但延迟更高且难造得多。加价是另一个取舍：它实际上**平衡供需**且经济上合理，但**政治敏感**（紧急时用户讨厌价格飙升），所以需要封顶和精心 UX。

**要点：**
- 用 S2/H3 cell 做地理索引。
- 每区域调度分片。
- 行程状态机保证正确性。
- 通过 Kafka 接位置流 firehose。

### 30. Google Drive / Dropbox（文件同步）

**频率：** 高

**题目：** 请设计 Dropbox/Google Drive 文件同步。覆盖分块、去重、冲突解决，以及去重与加密的权衡。

**答案：** **需求：**跨设备同步文件、解决**冲突**、支持**分享**、**版本**和**离线编辑**，**PB 级**规模。决定性洞见是**绝不同步整文件**——只同步**最小变更块集**。

**组件：**
- **块存储：**把每个文件切成**块**（约 4MB）、按其**哈希内容寻址**、存进对象存储（S3）。内容寻址带来**自动去重**——两个用户（或两个版本）拥有同一块只存**一次**，同步一个已编辑文件只传**变更的块**。
- **元数据服务：****一致性点**——持有文件树、每文件的有序**块哈希列表**、**版本历史**和 **ACL**，按用户/团队分片。文件本质上 = 元数据（块哈希的食谱）+ 它引用的块。
- **同步客户端：**监听本地文件系统、**计算 delta**（rsync 风格哪些块变了）、**只上传新块**，然后把新块列表提交给元数据服务。下载反向——拉新元数据，只取尚无的块。
- **通知服务：**推送**远端变更事件**（长轮询或 WebSocket）让其他设备及时同步而非轮询。
- **分享服务：**ACL 加带作用域（查看/编辑、过期）的**可分享链接 token**。

**同步流：**客户端检测到变更 → 对块哈希 → 只上传新块到块存储 → **原子更新文件元数据**（新版本 = 新块列表）。因为元数据更新**每文件原子**，读者总看到一致版本，绝不会是写一半的文件。

**冲突解决：**两设备离线编辑后都同步时，常见策略是**最后写入获胜 + 保留双方**——系统保留一个作为文件、另一个存为**"冲突副本"**，不静默丢失任何编辑。对**实时协作编辑**（Google Docs）还不够——用**操作变换（OT）**或 **CRDT** 自动合并字符级并发编辑。

**去重与加密的权衡：**跨用户去重要求服务器能识别两用户传了**同一块**——意味着块不能用**每用户密钥**加密（否则去重失效，因为相同明文会产生不同密文）。**收敛加密**（密钥从内容哈希派生）部分弥合但会泄露"其他人有这个一模一样的文件"。所以你选：**最大去重**（服务端密钥、隐私差）或**真正每用户 E2E 加密**（隐私好但失去跨用户去重和大部分存储节省）。

**要点：**
- 内容寻址的块做去重。
- 元数据服务是一致性点。
- 客户端算 delta；只上传新块。
- 冲突解决：LWW + 双副本，或 OT。

### 31. 分布式限流器

**频率：** 高

**题目：** 请设计一个分布式限流器。对比算法，以及跨边缘节点的精度 vs 延迟权衡。

**答案：** **需求：**在 **N 个全球分布的边缘节点**上强制**每用户/每 key 请求上限**（如 100 req/s），每请求**低开销**，容忍**分区期间轻微超限**（这里的正确性是"大致对且快"，而非"精确且慢"）。

**算法：**
- **令牌桶：**桶最多装 B 个令牌、**按 R 令牌/秒补充**；每请求消耗一个，空桶拒绝。它**允许爆发**到 B（好——真实流量是突发的）同时强制平均速率 R。这是 API 限流的**实用默认**。
- **滑窗日志：**存**每个请求的时间戳**并数落在最近窗口内的数量。**精确**（无边界伪影）但**内存重**——每 key 保留每个时间戳，扩展不到百万 key。
- **滑窗计数器：**每固定窗口一个计数器、用上一窗口的计数在边界处**插值**。**近似**但**便宜**（每 key 两个整数），且平滑了朴素固定窗口计数器"边界双爆发"缺陷。

**实现：**最简单正确版是**集中式 Redis**——对 key `INCR` 加 `EXPIRE`，超上限时拒绝。为让检查-递减**原子**（避免并发请求间竞态），用 **Lua 脚本**在 Redis 上跑，使读-改-写在服务端一步完成。代价是每请求打中心 Redis 加了**网络往返**延迟且是瓶颈/单点。

**分布式挑战与分层答案：**有 N 个边缘节点时，每请求调中心 Redis 太慢。标准模式是**分层**：每节点在**内存里强制本地软上限**（快、无往返）并**周期性同步**计数到中心存储由其强制**全局硬上限**。这让热路径保持本地、只偶尔全局对账。

**核心取舍是精度 vs 延迟。**完美精确的全局上限要求每请求都协调（慢）；快速本地上限会略微**超出**因为节点不实时看到彼此计数。既然多几个请求少有影响，你**故意允许小超量**以避免往返。对最终一致的**跨区域**计数，**CRDT PN-counter** 让每区域本地递增并无冲突合并——用临时超量换可用性和低延迟。

**要点：**
- 令牌桶是实用默认。
- Redis + Lua 做原子 check-and-decrement。
- 本地软上限 + 全局硬上限以降延迟。
- 允许小超限以省往返。

### 32. Typeahead / 自动补全

**频率：** 高

**题目：** 请设计一个 typeahead/自动补全系统。如何提供 100ms 以下建议并融合流行度与个性化？

**答案：** **需求：**每次按键在 **100ms 以下**返回建议、融合**流行**查询与**个性化**查询、支持**多语言**，**数十亿查询**。主导约束是延迟预算——每次按键发一个请求，所以每个必须极便宜。

**索引——离线构建、内存服务。**你不从原始日志实时算建议。而是**离线作业挖掘查询日志**产出带**分数**（频率、新鲜度）的顶查询，构建**Trie**或更紧凑的 **FST（有限状态转换器）**，把前缀映射到其顶补全。这结构**每小时/每天刷新**并**完全放在**建议节点内存里——前缀查找走几个节点就返回预计算的 top-K，这就是它快的原因。

**查询服务：**每次按键发一个轻量请求；节点走到前缀返回**按频率 + 新鲜度 + 个性化排序的 top-K 补全**。K 小且排序预计算，使每请求工作量极小。

**个性化：**把**全局建议**与**用户自己历史**（最近搜索、点击结果）混合——或服务端从小的每用户索引合并、或客户端从浏览器缓存历史应用。总搜"react hooks"的用户应看到它排在全局"react native"之上。

**扩展：****按前缀分片索引**（所有"ap..."在一个节点）或简单**只读复制索引**到多节点（它小且中心重建，复制便宜）。**CDN 缓存**最常见短前缀（单/双字母）结果，**客户端 debounce**（约 200ms）避免每次急促按键都发请求——批处理大幅削减后端负载。

**权衡：****新鲜度 vs 构建成本**——更频繁重建索引更快浮现热门查询但更耗算力；**流行度偏置**——纯按历史频率排序会**埋没新/长尾查询**并形成富者愈富循环，所以**从实时流混入新鲜查询**让新词在积累历史前就能突围。

**要点：**
- Trie/FST 离线由日志构建。
- 分片或只读复制索引。
- Debounce + 客户端缓存。
- 混合流行 + 新鲜 + 个性化。

### 34. 支付系统（幂等、账本、对账）

**频率：** 高

**题目：** 请设计一个以正确性为中心的支付系统。为什么幂等键是唯一最重要的元素？

**答案：** **需求：**在**重试和部分失败下正确**处理支付、**绝不重复扣款**、保持**精确记账**和完整**审计轨迹**、并满足 **PCI 合规**。不像大多系统丢失或重复请求只是烦人，这里是**钱**——所以正确性主导每个决策。

**组件：**
- **支付 API：**每个变更请求携带客户端生成的**幂等键**。服务器把键**连同其结果**存储；若同键再次到达（超时后重试、双击、网络抖动），就**返回存储的响应而非再扣款**。这是整个设计的核心（见下）。
- **账本服务：****复式记账**——每笔事务跨账户记录**相等的借方和贷方**，条目**仅追加/不可变**（绝不编辑；发一条更正分录）。这使账目总平衡并给出完美审计轨迹。
- **提供方适配器：**与 Stripe/Adyen 等集成，包在**断路器和重试**里，使不稳的提供方不级联。
- **对账作业：****每日比对你的账本与提供方流水**并标记任何差异——捕捉在系统间"消失"资金的安全网。
- **Webhook 处理器：**提供方通知异步事件（支付结算、争议）；处理器必须**幂等**（webhook 会重送）且**验签**（使攻击者无法伪造"支付成功"）。
- 加 **KYC/AML** 检查和**结算**。

**数据模型：****账户 + 条目**——每笔事务是一组引用账户的借/贷条目，一经入账不可变。

**扩展：****按账户分片账本**；因条目不可变，分片容易（无跨分片更新可变余额——你求和条目）。

**同步 vs 异步取舍：****同步确认**（持住请求直到扣款完成）更简单但更慢且占用连接；**异步**（接受、返回 pending、通过 webhook/轮询确认）更可扩展且容忍慢提供方，代价是客户端处理更复杂。

**为何幂等键最重要：**支付请求**一定**会被重试——客户端超时、用户双击、网络在扣款成功后丢了响应。没有幂等，每次重试都是**一笔新扣款** → 客户被扣两次。幂等键使重试**可证安全**：无论发多少次，操作**恰好执行一次**。其余一切（账本、对账、webhook）都保护正确性，但幂等键防的是唯一最坏的失败——**重复扣款**——所以它是你首先设计、永不妥协的一个。

**要点：**
- 每个变更请求都带幂等键。
- 复式账本，仅追加。
- 对账作业捕捉漂移。
- Webhook 幂等且签名。

### 35. SOA vs 微服务

**频率：** 中

**题目：** SOA 与微服务都基于"服务"抽象，它们有何不同？

**答案：** 两者都把系统组织为**服务**，但来自不同时代并反转了若干关键默认值——真正的区别是**文化性**的（谁拥有数据、逻辑放哪），而非标签。

**SOA** 在 **2000 年代**围绕**企业集成**兴起。其标志是重型 **企业服务总线（ESB）**集中了路由、转换和编排；全组织共享的**规范化 XML schema** 和 **WS-*** 契约（WSDL、SOAP、WS-Security）；以及服务间常见的**共享数据库**。ESB 是"智能"的——业务逻辑和集成流程住在*总线里*。

**微服务**借用服务抽象但翻转默认值：
- **智能端点、笨管道：**逻辑住在**服务里**，传输（HTTP、消息 broker）只是简单管道——与智能 ESB 模型**相反**。无中心编排总线。
- **去中心化数据所有权：**每个服务**拥有自己的数据库**；无共享 schema、不伸手另一服务的表。这是最大的实际差异——SOA 常**共享数据**，微服务**禁止**。
- **轻量契约：****HTTP/JSON 或 gRPC** 而非 WS-*/规范 XML，按服务演进而非中心治理。
- **持续交付 + 容器编排：**微服务**假设**独立、自动部署（CI/CD、Kubernetes）——那种运维模型内建在风格里。

**各自优化什么：**SOA 优化**企业级复用与治理**（一个规范客户模型、中心控制）；微服务优化**团队自治与部署速度**（每团队独立发布）。

**界限模糊处：**给微服务加**服务网格**（Istio）或 **API 网关**，你就重新引入了看似 ESB 的中心路由/策略；反之轻量 SOA 也可能像微服务。所以标签不如**耦合度**重要：若服务**共享数据库或规范 schema 且不能独立部署**，无论叫什么都是 SOA 式耦合；若它们**拥有自己的数据并按自己节奏部署**，那就是微服务的自治。关注耦合，不是营销术语。

**要点：**
- ESB vs 笨管道是架构分叉点。
- SOA 共享数据；微服务按服务拥有数据。
- 微服务假设有 CD 和容器编排。
- 二者都可做好或做砸；标签远不如耦合度重要。

### 36. 六边形/端口与适配器

**频率：** 中

**题目：** 请解释六边形（端口与适配器）架构。何时值得用、何时是过度？

**答案：** 在**六边形架构**（又称**端口与适配器**）中，**应用核心**——你的领域逻辑——位于中心并定义**端口**：它从外部世界所需一切的接口（`UserRepository` 端口、`PaymentGateway` 端口、`EventPublisher` 端口）。**适配器**位于外部并为具体技术**实现**那些端口（仓储的 Postgres 适配器、支付的 Stripe 适配器、事件的 Kafka 适配器）。关键规则：**依赖指向内部**——核心不知道框架、HTTP 或 SQL；只知道其端口。

有两种适配器。**驱动（主）适配器***调入*核心——HTTP 控制器、CLI 命令、队列消费者——它们驱动应用。**被驱动（次）适配器**是核心通过端口*调用*的——数据库、消息总线、外部 API。同一核心可被 HTTP 请求、CLI 调用或队列消息驱动而**不改一行领域逻辑**，因为三者都只是插入同一用例的驱动适配器。

最大回报是**可测试性与可互换性**。因核心只依赖接口，你用**内存适配器**（假的内存仓储）单测它——**无数据库、无 HTTP、无框架**，所以测试快且确定。你还能通过写新适配器**互换技术**（Postgres → DynamoDB、REST → gRPC）而不动核心。

**权衡：**它增加**样板**（每个外部依赖一个接口 + 至少一个实现）和**间接层**（顺端口才找到真实代码），且容易**过度抽象**——为只会有一个实现的东西发明端口，无益地加仪式。

**何时值得：****领域逻辑丰富、生命周期长**的系统（复杂业务规则值得隔离的快测试）或真需**多种投递通道**（同逻辑同时通过 HTTP *和*队列消费者 *和* CLI 暴露）。**何时过度：**基本是"校验 → 保存 → 返回"的**薄 CRUD 服务**——那里端口适配器只把框架包在额外层里毫无收益，所以用框架默认并略去仪式。

**要点：**
- 领域核心与框架无关。
- 驱动方（HTTP、CLI）与被驱动方（数据库、broker）适配器。
- 用内存适配器实现快速测试。
- 易过度工程；视领域价值再用。

### 37. 整洁架构（Uncle Bob）

**频率：** 中

**题目：** 请阐述整洁架构的层级与依赖规则。它与六边形如何比较、何处变重？

**答案：** **整洁架构**（Robert C. Martin）把代码排列在**同心圆层**里，从中心最稳定/抽象到边缘最易变/具体：

- **实体**（最内）：**企业级业务规则**——即使没有这个应用也存在的核心领域对象和不变式。
- **用例**（应用规则）：**编排实体**以完成特定应用动作（"下单" = 加载购物车实体、校验、创建订单、请求支付）。包含应用特定逻辑但无框架细节。
- **接口适配器：****控制器、展示器、网关**，在用例形状与外部世界形状间**翻译**（HTTP 请求 → 用例输入；实体 → 视图模型）。
- **框架与驱动**（最外）：Web 框架、数据库、UI、外部服务——可替换细节。

**依赖规则**是重点：**源码依赖只能向内**。外层可依赖内层，**绝不反向**——实体不知道用例，用例不知道控制器或数据库。这通过**依赖反转**实现：内层定义**接口**、外层实现它们，所以数据库"插入"用例而非用例依赖数据库。

**对比六边形：**两者同神（隔离领域逻辑、把依赖反转向接口），但整洁架构**对分层更规定**——它命名四个同心环和严格流向，而六边形只说"核心 + 端口 + 适配器"不强制内部分层。实践中六边形常是"整洁架构、少些仪式"。

**优点：**业务规则**被隔离且快测**（无需框架），**且替换/升级框架/数据库不往内波及**——你重写外层适配器而非领域。**缺点：**严格分层滋生**到处的 DTO 和映射器**——同一数据在每个边界被重新表示和拷贝（实体 → 用例 DTO → 视图模型），是真实样板；**小服务被**围绕本质上是 CRUD 的四层间接**撞肿**。

**选择性应用：**保留**依赖规则**（几乎总是好的——依赖抽象、指向领域），但当领域薄且分层只增噪而非保护真复杂度时，**丢掉严格的四层模板**。

**要点：**
- 依赖规则：只能向内。
- 用例编排实体；适配器做翻译。
- DTO 和映射器泛滥——注意成本。
- 适合复杂、长生命周期的领域逻辑。

### 38. 绞杀者无花果迁移

**频率：** 中

**题目：** 请解释绞杀者无花果迁移模式。如何支撑它并跟踪进度？

**答案：** **绞杀者无花果**模式（得名于缠绕大树并逐渐取代它的藤蔓）是**增量替换遗留系统**而非冒险的"大爆炸重写"的策略。你在遗留系统前放一个 **facade 或代理**（通常是 **API 网关或反向代理**），它**按请求**决定路由到**老系统**还是接管了那块功能的**新服务**。随时间一次迁一个能力；当每块都迁完，遗留被完全"绞杀"，你**删掉它**。

**为何胜出：**你**持续交付价值**（每个迁好的切片独立上线）、**大幅降风险**（大爆炸重写是单一巨大切换，要么成功要么搞垮业务；绞杀是几十个小、可逆切换）、并得到**按切片回滚**——若新"结账"服务失常，把那条路由翻回遗留而不动其他。

**难点：****拉长的双跑**——你同时运行两套系统数月甚至数年，付双倍维护和认知负载，所以真正完成至关重要。**数据同步**——两系统都活时可能共享数据，需新旧存储保持一致（通过谨慎的**双写**，或更好的 **CDC/变更数据捕获**单向流变更）。**业务规则漂移**——遗留里编码的微妙行为在重写时被遗漏，新切片行为*几乎*像老的但不完全。

**如何支撑：**用**特性开关**控制路由并启用瞬时回滚；用 **CDC 或双写**跨迁移边界保数据一致；为每模块设**显式下线里程碑**（带硬日期拆除遗留件，使双跑不无休止拖延）；并跟踪**"绞杀百分比"指标**——新系统服务的流量/功能占比——作为迁移进度的**先导指标**，使努力可见且按计划推进。

**要点：**
- 代理增量切流量。
- 避免大爆炸重写风险。
- 需要数据同步策略（双写或 CDC）。
- 设定显式的下线里程碑。

### 39. BFF 模式

**频率：** 中

**题目：** 请阐述 BFF（Backend-for-Frontend）模式：为什么要为每种客户端类型放一个专属 API 层，各 BFF 如何聚合下游微服务、按客户端塑形负载、处理客户端特定的认证流程，从而避免"一个 API 包打天下"的妥协。理想的归属团队是谁？请说明它的权衡（更多服务、BFF 间逻辑重复、与客户端发布节奏耦合），以及 GraphQL 在何种场景下可作为替代。

**答案：** Backend-for-Frontend 为每种客户端类型（Web、iOS、Android、合作伙伴）放置一个专属 API 层。每个 BFF 聚合下游微服务、按客户端需要塑形负载、处理客户端特定的认证流程，避免那种"一个 API 包打天下"的妥协（导致载荷臃肿、移动端变慢）。理想情况下由拥有该客户端的同一团队负责。权衡：要运维更多服务、各 BFF 间可能存在逻辑重复（抽公共库/服务）、BFF 与客户端发布节奏的耦合更紧。GraphQL 在某些场景下可让客户端按需投影字段，从而替代 BFF。

**要点：**
- 每种客户端体验对应一套后端。
- 减少过度获取与往返。
- 由客户端团队拥有。
- GraphQL 在部分场景可作为替代。

### 40. Sidecar 模式

**频率：** 中

**题目：** 请解释 Sidecar 模式、其常见用途与代价。何时需求应放回应用内？

**答案：** **sidecar** 是在同一单元（同一 Kubernetes pod 或主机）中**与主应用并列部署的辅助进程**，它**共享应用的生命周期和网络命名空间**（一同启/停、看到同一 `localhost`）。思路是把**横切基础设施关注**从应用移到同位的伙伴，使应用专注于纯**业务逻辑**。

**常见用途：**
- **服务网格代理**（Envoy、linkerd-proxy）：sidecar 拦截应用所有入/出流量以加 mTLS、重试和遥测——经典例子。
- **日志投递**（Fluent Bit）：tail 应用日志并转发到中心存储。
- **配置重载器：**监听配置变更并信号应用重载。
- **密钥获取**（Vault agent）：取回并刷新密钥，本地暴露给应用。

**最大收益**是这些关注**与语言无关且可独立升级**：你可通过全队更新 sidecar 推出新 mTLS 策略或日志格式而**不动或重部署任何应用代码**，且同一 sidecar 对 Java 服务和 Go 服务同样有效。

**代价：****每 pod 资源开销**——每个 pod 现跑额外容器消耗 CPU/内存，乘以成千 pod 很可观；**部署复杂度**——两个容器要版本化、配置、保同步；**调试歒义**——请求异常时你得判断是**应用还是 sidecar** 处理的，因为代理隐形地坐在路径中。

**何时值得 vs 属于应用：**当辅助物**在多服务间可复用**且由**基础设施/平台团队**拥有（网格代理、日志投递、密钥）时用 sidecar——开销被全队一致性和独立升级证明合理。对**单一服务特有的一次性需求**请**避免**——那里应用**内部**的库或一点代码比跑和调试独立进程的运维成本更简单。

**要点：**
- 同位部署的辅助进程。
- 与主容器共享网络/存储。
- 支撑服务网格、日志投递、密钥。
- 每个 pod 都增加开销——要度量。

### 41. 服务网格（Istio/Linkerd）

**频率：** 中

**题目：** 什么是服务网格、它如何工作？何时采用而非基于库的弹性？

**答案：** **服务网格**（Istio、Linkerd）是**透明管理服务间通信的基础设施层**，使弹性、安全和可观测性由平台处理而非编进每个服务。它有两部分：
- **数据面：**注入到每个服务实例旁的 **sidecar 代理**（Istio 用 Envoy、Linkerd 用 Rust 微代理）。**服务所有入出流量都流经其代理**，实际工作（mTLS、重试、路由）就在那里发生。
- **控制面：**中心组件**配置所有代理**——你声明一次策略（"canary 5% 到 v2"、"处处 mTLS"、"重试 3 次、100ms 超时"），控制面推送到每个 sidecar。

**零应用代码改动就能得到：****mTLS**（所有服务间自动双向 TLS 加密与身份）、**流量切移**（按百分比路由做 canary/blue-green）、代理层的**重试、超时、断路**、**细粒度授权**（服务 A 可调 B 的 `/read` 但不可 `/admin`）和**丰富、统一的遥测**（每跳延迟、错误率、流量）。魅力在于这**跨语言一致**——Python 和 Java 服务得到同样 mTLS 和重试而无需各自实现。

**权衡：****显著运维复杂度**（网格是你现在要跑、升级、调试的分布式系统）、**每跳延迟开销**（每代理加约 1–5ms）、**每 pod 资源成本**和出问题时**又多一层要调试**（"是应用、代理还是控制面？"）。

**Istio vs Linkerd：****Istio** 功能**丰富但重且复杂**（基于 Envoy、旋钮多、学习曲线陡）；**Linkerd** **更精简、更简单、基于 Rust**，优先低开销和易运维而非功能广度。

**何时采用：**当你有**多服务、多语言、且有专职平台团队**运维时网格回本——全队一致性和免费 mTLS/遥测证明成本合理。**何时跳过：**只有**少数服务**或单语言时，**基于库的弹性**（gRPC 内置重试/截止时间、Resilience4j/Polly 做断路、OpenTelemetry SDK 做追踪）给你大部分好处而**无需**跑整个网格——在服务数和多语言需求真正需要前不要背那运维负担。

**要点：**
- 数据面（sidecars）+ 控制面。
- 提供 mTLS、流量策略、遥测。
- Linkerd 更轻；Istio 更全。
- 用服务数量与团队容量来论证。

### 42. Outbox 模式

**频率：** 中

**题目：** 请解释 Outbox 模式及它解决的双写问题。它的保证与权衡是什么？

**答案：** **双写问题：**服务常需**原子地做两件事**——更新其数据库 *并* 向消息 broker 发布事件（如保存订单 *并* 发出 "OrderPlaced"）。但数据库和 broker 是**无共享事务的独立系统**。若先写数据库再发布而发布失败（或中间进程崩溃），你提交了状态变更但**丢了事件**——下游永不知道该订单。先发布有镜像问题：事件发了但数据库写失败，消费者对未发生的事反应。不用分布式事务（2PC）就**无法**使两独立系统原子，而 2PC 正是你想避免的。

**Outbox 模式解决它**，把两写变成**一个本地事务**。服务在**单个 ACID 事务**中把**业务变更**和代表**出向事件**的一行写入**同一数据库的 "outbox" 表**。要么都提交要么都不——无部分状态。事件现在与数据一同被耐久捕获。

一个单独的**中继**再把那些事件投递到 broker。它读未发送的 outbox 行并发布，随后标每行**已发送**。中继要么是**轮询 worker**（周期 `SELECT` 未发行——简单、略有延迟），要么是 **CDC 流**（Debezium tail 数据库事务日志——更低延迟、无轮询负载，且 outbox 插入一提交就捕获）。

**保证：**你得到**无分布式事务的至少一次发布**——事件因与数据原子提交而永不丢失，中继重试直到 broker ack。数据库和 broker 变得**最终一致**（事件在提交后不久落地）。

**权衡：**有**小的提交到发布延迟**（中继轮询间隔或 CDC 滞后）；**outbox 表会增长**需**归档/清理**已发行；因投递是**至少一次**，中继可能发同事件两次（发布后、标已发送前崩溃），所以**消费者必须幂等**（按事件 ID 去重）。该模式**与事件驱动和 saga 架构天然搭配**，在那里从服务自己的事务中可靠地发出事件正是所需。

**要点：**
- 状态与事件原子写入数据库。
- 中继（轮询或 CDC）向下游发布。
- 至少一次投递；消费者必须去重。
- 避免对 broker 的不可靠双写。

### 43. L4 vs L7 负载均衡

**频率：** 中

**题目：** 请对比 L4 与 L7 负载均衡。为何栈常把 L4 放在 L7 前面？

**答案：** 区别在于均衡器工作在网络栈的**哪一层**，这决定了它对流量的理解程度。

**L4（传输层）负载均衡**工作在 **TCP/UDP**。它按 **IP 和端口**路由、简单**转发包/连接**而不看内部。因**不检查载荷**——不解析 HTTP、不终止 TLS——它**极快、低延迟、协议无关**（均衡任何东西：HTTP、数据库协议、游戏 UDP 流）。例子：**AWS NLB、HAProxy TCP 模式**。局限是它"盲"——不能按 URL 路径或 header 路由、不能重试失败的 HTTP 请求、不能加 HTTP 级可观测性。

**L7（应用层）负载均衡**理解**应用协议（HTTP、gRPC）**。因它解析请求，能做得多：**按 host/path/header 路由**（`/api` 到一集群、`/images` 到另一个）、**终止 TLS**（在 LB 解密）、**重试**、**粘性 cookie**、**限流**和**丰富 HTTP 级遥测**（每路由延迟、状态码）。例子：**Envoy、NGINX、AWS ALB**。代价是**更高延迟和 CPU**（解密和解析每个请求）且**协议特定**。

**权衡：**L4 **更便宜更快**但**不灵活**；L7 **更丰富**但**更重**，且是多数现代 API 流量的栖息地因路由、TLS、重试在那里至关重要。你把层匹配负载——**原始 TCP/UDP 用 L4**（数据库、游戏、任何非 HTTP）、**HTTP/gRPC API 用 L7**。

**为何 L4 前置 L7：**常见高规模栈把 **L4 均衡器放在边缘**便宜地吸收原始连接量和 **DDoS 规模流量**（L4 能处理极大包速而无解析开销），再**分发到一群做智能 HTTP 路由的 L7 均衡器**。L4 层在前门给你**巨大、便宜的水平扩展和弹性**；L7 层在后给你**应用感知路由**。相关地，**服务网格本质上是分布式 L7 负载均衡器**——每个 sidecar 代理都在为其服务流量做 L7 均衡。

**要点：**
- L4：TCP/UDP，最快，协议盲。
- L7：HTTP 感知，路由/策略丰富。
- L7 终止 TLS 并做重试。
- 常用 L4 前置 L7 以应对规模。

### 44. 粘性会话

**频率：** 中

**题目：** 请解释粘性会话——为何它便宜地补了无状态缺口却制造问题，以及用什么替代。

**答案：** **粘性会话（会话亲和）**让负载均衡器**把给定客户端钉到某个特定后端**——通过 LB 设的 **cookie** 或**哈希客户端 IP**——使该客户端每个请求都落到**同一实例**。目的是让**内存会话状态能用**而不外置：实例把用户会话放 RAM，粘性保证用户一直命中那实例所以状态在。

它是**便宜修补**——无外部会话存储、无代码改动——但**削弱了负载均衡本身的好处**：

- **负载不均：**流量按客户端钉而非按容量，所以一些实例发烫而其他空闲。几个重用户在一节点可把它压垮而同伴闲置。
- **破坏滚动部署：**部署时杀实例，**其会话消失**——被钉用户登出或丢状态——除非你先小心**排空**连接，而那复杂了每次发布。
- **热点与差 failover：**热门节点持续过载，若它死，其所有用户一下子丢会话。

**更好的替代**都归结为**让应用无状态**，使任何实例能服任何请求：
- **外置会话状态**到 **Redis/Memcached**——会话住共享存储，实例可互换，保持干净的负载均衡和发布。
- **签名 JWT**——会话是客户端携带的**自包含签名 token**；任何实例可本地**验证**而无需查询，无物可钉。
- **SPA + token 鉴权**——客户端持 token 每次调用携带；后端完全无状态。

**仍有狭义合理用途。****WebSocket（和其他长连）连接天生粘性**——TCP 套接字本身在连接生命期绑到一台服务器，所以那里的"粘性"只是物理而非设计异味。某些**遗留应用**确实无法外置状态。注意**面向缓存亲和的一致性哈希路由与粘性不同**——它按*key* 路由以最大化缓存命中率（且拓扑变化时优雅重洗），而非按*客户端* 保留每会话内存；混淆二者是常见错误。

**要点：**
- 通过 cookie/IP 把客户端绑定到后端。
- 破坏均匀负载与干净发布。
- 优先外置会话或 JWT。
- WebSocket 天然粘性。

### 45. 自动扩缩触发器

**频率：** 中

**题目：** 请阐述自动扩缩触发器与最佳实践。为何优先基于工作量的信号而非 CPU、且快扩慢缩？

**答案：** 自动扩缩调整实例数以匹配负载；艺术在于**选对触发器**和**调好动态**，使其响应而不抖动或超支。

**反应式扩缩**响应**当前指标**——CPU、内存、请求率、**队列深度**或 **p95 延迟**——跨阈值。简单、无需预测，但**对尖峰滞后几分钟**：等 CPU 爬升、警报触发、新实例启动并预热，流量浪潮可能已伤用户。**预测式扩缩**在**需求之前**扩——按**计划**（早 9 点高峰前拉起）或通过负载曲线的 **ML 预测**。它优雅处理**已知模式**但**错过意外**（突发病毒式尖峰不在预测里）。**最佳实践是两者结合**：预测/计划扩缩为已知高峰预供给，加反应式扩缩作为意外的安全网。

**优先基于工作量的信号而非 CPU。**CPU 是 **I/O 密集型负载的差代理**——等数据库或外部 API 的服务可能在 **20% CPU 就已满载（所有请求槽繁忙）**，所以基于 CPU 的扩缩即使延迟爆炸也从不触发。**基于工作量的信号**量真实需求：**每副本 RPS**（"每实例处理约 200 req/s，扩容保持在那"）或**队列深度**（"消息堆积，加消费者"），直接反映容量够不够。

**快扩慢缩。****激进扩容**吸收尖峰——短暂略超配是对丢流量的便宜保险。**保守缩容**带**冷却/稳定窗口**，因为负载一降就拆实例会导致**抖动**（抖动）——小降拆实例、负载回来、你又匆忙加回，反复。非对称速度使你响应而不振荡。

最后，**封最大值**以**界定成本**——bug、反馈循环（或重试风暴）否则可驱动失控扩容和巨额账单——并用**现实坡度压测针对 SLO 验证扩缩**。稳态测试不能证明系统扩得*够快*；你需确认现实尖峰下自动扩缩保住延迟/错误 SLO。

**要点：**
- 优先用基于工作量（RPS、队列深度）的信号而非 CPU。
- 扩缩容要快扩慢缩（缩容设冷却）。
- 反应式 + 计划预测式相结合。
- 设上限以约束成本。

### 46. 领导者选举（Raft 基础、etcd/ZK）

**频率：** 中

**题目：** 请解释领导者选举与 etcd/ZooKeeper 的角色。Raft 如何工作、这类系统不应用于什么？

**答案：** 很多分布式系统需**恰好一个节点负责**某职责——持权威配置、授分布式锁、分配单调序列、或协调谁做什么。无单一领导者就会脑裂（两节点都以为自己当家，损坏状态）。**领导者选举**是**安全商定一个领导者**并在其失败时**重选**的协议。

**Raft** 使它易懂。每节点是 follower、candidate 或 leader。**选举：**每个 follower 等一个**随机超时**；若听不到 leader 心跳，它变 **candidate** 并请求投票。节点赢得**多数票**即成 leader。随机超时使两 candidate 并列可能性很低，所以选举快速解决。**日志复制：**leader 接受写、追加到其**日志**、复制给 follower；条目在**多数确认后提交**。这个多数（**法定人数**）要求是为何这些系统需**奇数节点**（3 或 5）并容忍 `(N-1)/2` 个失败。

**etcd 和 Consul 用 Raft；ZooKeeper 用 ZAB**（类似的基于 leader 的原子广播协议，保证相当）。均提供小型、强一致、高可用的协调存储。

**读/写路由：****写进 leader**（只有它能提交）。**读**可两种方式——从 **follower 带有界陈旧**（快、可能稍落后）或**经 leader 线性化**（保证最新、代价是 leader 往返）。你按能否容忍陈旧逐读选择。

**故障切换**约**几百毫秒到数秒**——检测死 leader（漏心跳）并跑选举的时间——期间写暂停。

**宜用 vs 不宜：**这些是**协调存储**——完美适合**服务发现、领导者选举、分布式锁和配置**。它们**不是通用数据库**：每写都过共识（慢）、整个数据集必须舒适装入内存、吞吐按 DB 标准很低。把应用数据或大量状态存 etcd/ZooKeeper 是经典误用会垮——只留给小、关键的**协调元数据**。

**要点：**
- Raft = 领导者 + 日志复制 + 多数派提交。
- etcd、Consul 用 Raft；ZK 用 ZAB。
- 用于锁、发现、配置——不用于数据。
- 故障切换以秒计；需要法定人数。

### 47. 法定人数与副本数

**频率：** 中

**题目：** 请解释法定人数与副本数：为什么 W + R > N 才能强一致？如何按读多/写多工作负载调优 W、R、RF？

**答案：** 在 **N 个副本**下，一次写要 **W 个副本确认**、一次读要向 **R 个副本查询**。**W + R > N 保证强一致**，靠的是**鸽巢原理**：任意写集合与任意读集合必**至少有一个副本重叠**，因此读一定能看到最新的已确认写。举例 N=3、W=2、R=2：2+2=4>3，写落在的两个副本与读的两个副本必然相交。

**RF=3、W=2、R=2 是 Dynamo 经典甜点**：容忍**一台副本故障**仍能读写（W=2 和 R=2 都还凑得齐），同时保强读。

**调低旋钮的取舍：**
- **W=1**（写只等一个确认）：写延迟低、吞吐高，但**耐久性弱**——那一台写完立刻挂就丢了这条写。
- **R=1**（读只查一个副本）：读延迟低，但**可能读到旧值**，错过刚提交的写。

**异步收敛：****提示交接（hinted handoff）**——目标副本临时不可达时，另一节点代存并在其恢复后转交；**读修复（read-repair）**——读时发现某副本落后就顺手把最新值写回。二者让副本最终收敛而无需每次都强一致。

**更高 RF** 提升**耐久性与读可用性**（更多副本能挺过故障），但代价是**更多存储**和**更高写延迟**（要触达更多副本）。

**按工作负载调优：****写多**系统调**低 W**（甚至 W=1）换快速摄入，靠提示交接+读修复收敛；**读多**系统调**低 R**（R=1）换快速读，把一致性压到写侧（高 W）。像 Cassandra 这类系统旋钮是**逐操作**的，你甚至能给关键读选强一致、给廉价读选最终一致。

**要点：**
- W + R > N 才能强一致。
- RF=3 配 W=R=2 是甜点。
- Hinted handoff 修复临时故障。
- 更高 RF = 更耐久、更高成本。

### 48. 热点 key 问题

**频率：** 中

**题目：** 请解释热点 key 问题，以及读侧和写侧分别如何缓解。

**答案：** **热点 key 问题**是指**单个 key 吸走不成比例的流量**——名人账号、爆款商品、病毒推文、黑五秒杀商品。因为该 key 落在**一个分片**（并映射到**一个缓存条目**），它的全部负载压在**单个节点**上，把该节点**打饱**，而集群其余空闲。分片把*数据*均匀铺开了，但流量偏斜到一个 key，所以*数据*均匀不等于*负载*均匀。

**先检测：**你需要**每 key 指标**或**采样请求追踪**才能真正看出哪个 key 热——否则只观察到"一个节点着火"却不知为何。好系统持续跟踪按请求率排名的 top-N key。

**修复热读：**
- **请求合并 / singleflight：**大量并发请求同一 key 且缓存未命中时，让**一个**请求去取，其余**等这个结果**，而不是全部涌向后端（避免缓存击穿踩踏）。
- **短 TTL 本地缓存：**把热值缓存**在每个应用实例内存**几秒——哪怕 1 秒 TTL，也能把每实例每秒上千次后端命中变成一次。
- **key 拆分 / 扇出：**把热 key 复制成 **N 个带后缀变体**（`key#1`…`key#N`）分散到各分片；读时随机挑一个再**聚合**，把一个 key 的读负载摊到 N 个节点。
- **专门的热 key 缓存层或只读副本**专服务该 key。

**修复热写**（更难，因写必须持久、不能一缓了之）：
- **批量与异步聚合：**别把每次自增同步写到一行。经典手法是**分片计数器**——每次自增随机写到 **N 个副本行之一**，**读时对 N 行求和**。把写竞争摊到 N 行而非串行在一行上，代价是读要扇出。

**元教训：****在爆红之前就为热 key 做规划，而非之后。**等热 key 已经在呼叫 on-call 时，你已在生产里救火一个饱和分片。提前内建每 key 监控、请求合并和计数器分片策略，能让系统在某物不可避免地走红时优雅降级。

**要点：**
- 通过每 key 指标、采样 trace 检测。
- Singleflight 与本地 TTL 缓存吸收读。
- key 扇出（分片计数器）用于写。
- 在爆红之前规划，而不是事后。

### 49. 背压与边缘限流

**频率：** 中

**题目：** 请解释背压与边缘限流并区分二者，为什么两者都需要？

**答案：** 二者都保护系统免于过载，但防的是**不同威胁**、作用在**不同位置**。

**背压**是关于**不接受超过自身处理能力的工作**——把"慢下来"从过载组件反向传播回其生产者。**没有它**，慢消费者会让**队列无限膨胀**：内存耗尽、**延迟飙升**（请求在越来越长的队列里等待），最终进程**OOM 崩溃**——负载下经典的级联崩塌。修法是在**每个边界都设界**：
- **有界 channel/队列**在满时**阻塞或丢弃**，而非无限增长。满队列示意生产者慢下来（阻塞）或卸载（丢弃），而不是吞掉无限内存。
- **最大在途信号量**——限制并发处理的请求数；超限的新工作等待或被拒。
- **每后端并发上限**——绝不给下游依赖超过它能吸收的并发调用，免得把*它*推入过载。

**边缘限流**是关于**限定每个客户端/租户能发多少**，施加在**边缘**（网关/LB）。它用**按客户端或租户的令牌桶**，客户端超配额时得到 **429 Too Many Requests** 加 **`Retry-After`** 头（客户端应带**抖动**退避）。这防**滥用和吵闹邻居**——一个行为不端的客户端不能吃光容量而饿死其他人。

**自适应并发限流器**有益地模糊了界线：不用静态并发上限，而是**按观测到的延迟动态调整限制**（AIMD 风格，类似 TCP 拥塞控制——Netflix 的 concurrency-limits）。延迟一升，它自动调低允许的并发，让系统自我调节到当前真实容量而非拍脑袋的常数。

**关键区别：****限流保护你免于滥用**（外部、按客户端配额——"你发得太多了"），而**背压保护你免于过载**（内部、基于容量——"*我*现在跟不上了，不管是谁在请求"）。二者互补，你要**同时用**——边缘限流公平配给访问，内部处处背压使任何单个慢组件都无法撑爆内存拖垮全系统。

**要点：**
- 队列处处有界；永远不要无界。
- 边缘按租户使用令牌桶。
- 429 + Retry-After + 抖动。
- 自适应并发限制优于静态。

### 50. 舱壁（Bulkhead）

**频率：** 中

**题目：** 请解释舱壁（Bulkhead）模式、它在不同层级的形式及其权衡。

**答案：** **舱壁模式**得名于船的水密隔舱：一个隔舱进水时，舱壁**拦住水**使整船不沉。用到软件上，你**分区资源**，使一处的故障或过载**不能吐光共享资源而拖垮其余一切**。

它防的典型故障：你的服务通过**单个共享线程池（或连接池）**调多个依赖。一个依赖——比如**慢的第三方 API**——开始挂起，它的调用**堆积并占完共享池的所有线程**。现在到你*健康*端点的请求也拿不到线程，于是**整个服务因一个慢依赖而宕机**。这正是舱壁阻止的级联。

**不同层级的形式：**
- **每依赖池（最常见）：**给**每个下游依赖自己的线程池或连接池**。慢的第三方 API 耗尽*它自己*的池时，调它的请求失败/排队，但你的数据库调用和其他端点保留自己的线程保持健康，故障**被拘在那一个依赖**。
- **服务层：****每租户隔离池**（吐闹租户不能饿死其他）或**按优先级队列**（关键流量有专留通道）。
- **基础设施层：****为关键工作负载分集群**，使失控批处理作业不能偷走面向客户 API 的容量。

**权衡**是**最大利用率降低**：因切片**不能共享**其预留容量，每分区都留些空闲余量——单个共享池本可用。你用一点效率换**缩小爆炸半径**。对任何**延迟特征多样**（快慢依赖混合）或**关键 vs 尽力交付**流量划分的系统，这明显值得。

舱壁**与断路器天然组合**：**舱壁拦住**损害（隔离池使故障不扩散），而**断路器停止**反复锤打失败依赖（一旦它明显宕机就快速失败）。二者共同**限制**爆炸半径并**加速恢复**。

**要点：**
- 每依赖线程/连接池隔离。
- 限制单点故障的爆炸半径。
- 利用率降低，韧性提升。
- 与断路器组合使用。

### 51. 多语言持久化

**频率：** 中

**题目：** 请解释多语言持久化——它的收益、代价，以及如何明智地采纳。

**答案：** **多语言持久化**指**在一个系统内为不同需求用不同存储技术**，把每种工作负载匹配到最适合的存储，而非强行完叔一个库。典型配置：**Postgres** 存事务核心数据、**Redis** 做缓存与队列、**Elasticsearch** 做全文搜索、**S3** 存 blob/媒体、**ClickHouse**（或其他列式库）做分析、**Neo4j** 做图/关系查询。

**收益**直白：每种工作负载都用上它真正擅长的工具。Postgres 用 `LIKE` 做全文搜索又慢又弱；Elasticsearch 原生支持。对十亿行做分析聚合会压垓 OLTP 行式库，但在列式库上飞快。从关系库服务大文件很浪费；对象存储专为此而生。每种访问模式都用对工具，每个工作负载的性能和开发体验都好得多。

**代价真实且常被低估：**
- **运维负担按存储数翻倍**——每个都需自己的**备份、升级、监控、安全加固、容量规划**。五个存储就是五倍运维面。
- **数据同步**——同一数据现在存于多处（订单在 Postgres、索引在 Elasticsearch、缓存在 Redis），保一致需 **CDC 或双写**，增加复杂度与最终一致滞后。
- **团队专长被摊薄**——没人能同时精通运维 Postgres *和* Cassandra *和* Elasticsearch *和* ClickHouse；每个都有自己的故障模式与调优。
- **跨存储事务难/不可能**——你做不了跨 Postgres 和 Elasticsearch 的 ACID 事务，只能退回 saga 与最终一致。

**明智采纳路径：****从单一存储起步**——调好的 Postgres 处理事务、JSON、全文、甚至基本分析，能撑得比人们预期久得多。**只在某个清晰、痛苦的访问模式真正证明必要时才加新存储**（搜索确实慢、分析确实压垓 OLTP）。关键地，**把每个次级存储视为真相记录的投影**——指定一个存储为**真相源**，其余从它派生（经 CDC/事件），这样你总能从权威数据**重建**搜索索引或缓存，使不一致可恢复而非灾难性。抵住过早过度碎片化的诱惑——每加一个存储都是永久的运维税。

**要点：**
- 按访问模式选对工具。
- 每种存储都加运维负担。
- 通过 CDC/事件从真相源同步。
- 抵制过早过度碎片化。

### 52. CDC 与下游扇出

**频率：** 中

**题目：** 请解释变更数据捕获（CDC）与下游扇出。何时你会首选 CDC 而非 outbox 模式？

**答案：** **变更数据捕获**接入数据库的**复制日志**——Postgres 的 **WAL**、MySQL 的 **binlog**——把**每一个行级变更**（插入/更新/删除）作为事件发到流上。像 **Debezium** 这样的工具读日志并发布到 **Kafka**，下游**消费者把这些变更投影**到**搜索索引、缓存、数据湖、分析仓或其他服务**——全部**无需修改应用代码**。应用照常写库；CDC 从日志观察那些写并扇出。

**优点：**
- **应用保持简单**——无需显式发事件，只做普通库写。CDC 对它隐形。
- **捕获可靠、一个不漏。**因读的是**已提交日志**，即使应用**提交后立刻崩溃**也能捕获每个变更——不存在"写了库却忘发布"的缺口，因为日志*就是*提交的记录。
- **获得可回放日志**——重置消费者偏移就能从历史重建投影（如把一切重新索引到新 Elasticsearch 集群）。

**缺点：**
- **事件暴露物理 schema。**CDC 发**原始表/行变更**，消费者**被耦合到你数据库的内部列与布局**，而非干净的领域契约。一次列重命名或表重构可**保每个下游消费者**。
- **顺序与 exactly-once 需小心**——必须保每 key 顺序（按主键分区）并用幂等消费者处理至少一次投递。
- **schema 变更脆弱**——DDL 变更会波及读物理列的消费者。

**CDC vs outbox 模式：**二者以不同方式解重叠问题。**outbox** 让**应用有意把语义领域事件**（"OrderShipped"）写入事务内的 outbox 表——事件是**干净、有意的业务事实**，与物理 schema 解耦。**CDC** 捕获**底层物理行变更**，应用零参与。

**选 CDC**：想要**底层数据同步/复制**（保搜索索引、缓存、数据湖与表同步）且不想动应用时。**选 outbox**：想要其他限界上下文消费的**语义领域事件**作为**稳定契约**、与内部 schema 隔离时。常见混合：在 outbox 表上用 CDC——应用写干净领域事件到 outbox，CDC 可靠发送，兼得语义事件与日志级可靠。

**要点：**
- 读 WAL/binlog；无需改应用。
- 可靠：应用崩溃不会漏。
- 把消费者耦合到物理 schema。
- CDC 做数据同步，outbox 做领域事件。

### 53. Broker 选择：Kafka vs RabbitMQ vs SQS vs Pulsar

**频率：** 中

**题目：** 请对比 Kafka、RabbitMQ、SQS 与 Pulsar。如何根据回放、路由与运维胃口选型？

**答案：** 这四个都是"消息中间件"但处不同类别——**日志** vs **broker** vs **托管队列** vs **混合**——选型取决于你是否需回放、复杂路由或极少运维。

**Kafka** 是**耐久、分区、只追加的日志**。消息消费后不删，而是**保留**，消费者自行跟踪**偏移**，所以能**回放**历史（重处理一周事件、新增一个从头读的消费者）。通过把 topic 分区到多 broker 实现**极高吞吐**。最适合**事件流、CDC 管道、分析、事件源**。代价：自营运维重（有托管方案），对简单任务队列是杀鸡用牛刀。

**RabbitMQ** 是**经典 broker**，带**丰富路由**——交换机、topic/direct/fanout 绑定、headers——能表达复杂的"按规则把消息路由到这些消费者"逻辑。消息通常 **ack 后删除**（队列语义，非保留日志——无回放）。吞吐**低于 Kafka**。最适合**带复杂路由的任务队列与工作流**。

**SQS** 是 **AWS 完全托管**队列：**几乎无限扩展、极简、无服务器可运维**。标准 SQS 是**至少一次、无顺序**；**FIFO 变体**加顺序与 exactly-once 但**吞吐受限**。最适合**零运维、不需回放/顺序的云原生任务队列**。代价：功能少（无丰富路由、保留有限）且 AWS 锁定。

**Pulsar** 是**日志 + 队列混合**：兼支流（像 Kafka）与队列语义，内建**多租户、地理复制、分层存储**（冷段卸到对象存储）——对大型多租户部署可说运维模型优于 Kafka。坑在**生态与社区比 Kafka 小**，工具与会用的人都少。

**选型：**
- 需**回放 / 事件流 / 高吞吐** → **Kafka**（若同时要多租户与地理复制则 **Pulsar**）。
- 需**复杂路由 / 经典任务队列** → **RabbitMQ**。
- 要**托管简单、零运维、在 AWS** → **SQS**。
- 决定性轴：**回放需求**（Kafka/Pulsar 保留；Rabbit/SQS 消费即删）、**路由复杂度**（Rabbit 胜）与**运维胃口**（SQS=零；Kafka/Pulsar=除非托管否则是真正的平台投入）。

**要点：**
- Kafka：日志、回放、高吞吐。
- Rabbit：路由丰富的任务队列。
- SQS：托管、简单、无运维。
- Pulsar：日志 + 队列，多租户。

### 54. Exactly-once 语义

**频率：** 中

**题目：** 请解释消息中的 exactly-once 语义。为何"effectively-once（实际上一次）"才是实用答案？

**答案：** 真正的 **exactly-once 投递**——每条消息端到端恰好处理一次且仅一次——在分布式系统里出了名的难，因为网络总可能在工作*完成后*丢掉确认，逼你二选：重试（冒重复风险→**至少一次**）或不重试（冒丢失风险→**至多一次**）。你无法让消息及其 ack 在不可靠网络上完美原子。

所以**实践中的"exactly once"通常指"effectively-once"**：**至少一次投递 + 幂等处理**。你接受消息可能**被投递多次**（broker 重投、生产者重试、网络重复），转而把**处理**做成处理重复**无额外效果**。可观察结果是"如同恰好处理一次"，靠的是让重复无害而非不可能。

**真的端到端 exactly-once** *确*可在特定系统内实现，但需**生产者、broker、消费者都在一个事务里协作**。**Kafka** 靠**幂等生产者**（用序列号去重重试）加**事务**（原子提交输出消息**和**消费者偏移）——"读→处理→写→提交偏移"是一个原子单元。**Flink** 靠**两阶段提交 sink**把检查点与外部提交对齐。能用，但仅在其封闭生态内且有真实吞吐/复杂度代价。

**实用、可移植的做法是把消费者做成幂等**，它**统一处理** broker 重投、应用重试、网络重复，不拘 broker：
- **按事件 ID 去重**——给每事件带唯一 ID；存已处理 ID 并**拒绝回放**（放在 **TTL 窗口**里，窗口大小覆盖最大可能重投延迟，使去重存不无限增长）。
- **按主键 upsert**——"插入或冲突时更新"，重处理同事件只重写同行（天然幂等）。
- **HTTP 幂等键**——同键返回已存响应而非重执行。

这比追真 exactly-once **更便宜、更健壮**：不需特殊 broker 或事务性 sink，跨异构系统都能用、优雅降级。口诀：**假定重复一定会发生，把处理设计成重复也无所谓。**

**要点：**
- 真 exactly-once 罕见且昂贵。
- 实际上一次 = 至少一次 + 幂等。
- 按事件 ID 去重或按主键 upsert。
- 每个入口都用幂等键。

### 55. 物化视图与读模型

**频率：** 中

**题目：** 请解释物化视图与读模型。为何必须把它们设计成可重建？

**答案：** **物化视图**（或**读模型**）是**预计算、反规范化的查询结果**，存下来使读**快且便宜**——不在每次请求跑昂贵的 join/聚合，而是算一次并服务存下的答案。它用**写时开销与存储**换**读时速度**，对读多工作负载非常划算。

同一思路体现为两种机制：
- **SQL 数据库**（Postgres、Snowflake、Oracle）中，物化视图是一等对象，按**计划刷新**（每晚 `REFRESH MATERIALIZED VIEW`）或**提交时增量刷新**（部分引擎随基表变化维护）。写一次查询，引擎缓存其结果。
- **事件驱动系统**中，**投影**消费**事件**流并写**按查询定制的反规范化读模型**——一个投影建"用户仪表盘"表，另一个建"搜索索引"，同源事件嗂养。机制不同、目标相同：预计算读形态。

**权衡：**
- **写放大**——每个源变更必须更新依赖它的每个视图/投影，写做更多活且要同步的东西更多。
- **相对源最终一致**——视图按刷新间隔或投影延迟**落后**底层数据，读可能略旧。
- **重建成本**——重算大型物化视图或回放百万事件重建投影又贵又慢。

**为何可重建不可妥协：**投影与视图**必定**需重建——bug 損坏投影、你改读 schema、加新字段、对历史数据开新视图。若**不能重建**，一个投影 bug 就成**永久数据損坏**无法恢复。所以要提前设计：
- **使投影可回放**——可从**原始事件或真相源数据库**重建，绝不持有*仅*存于投影的状态。
- **为投影 schema 版本化**，以便演进读形态。
- **事件（或源数据）保留足够久以重建**——日志剪得太狠就丢了重建能力。
- **切换期新投影与旧并行跑**——并行建 v2、校验一致、再切读，使重建是**零停机、可逆**操作而非冒险大爆炸。把读模型当作**派生、可弃、可重建**的——绝不当真相源——才能保这个模式安全。

**要点：**
- 预计算、反规范化的读形态。
- 相对源最终一致。
- 可从事件重建是不可妥协的。
- 为 schema 变更对投影做版本化。

### 56. 全文搜索（把 Elasticsearch 当投影）

**频率：** 中

**题目：** 如何把 Elasticsearch 当作投影来做全文搜索？何时 Postgres FTS 就够？

**答案：** 搜索引擎（Elasticsearch、OpenSearch、Solr、Meilisearch）提供 **SQL LIKE 做不到**的能力：**倒排索引、分词、analyzer（词干提取、同义词）、faceting、相关性打分、聚合**。Postgres 用 `LIKE '%x%'` 既慢又无法排序。

**把搜索当作投影**：**真相源是数据库**，由**事件或 CDC 保持索引更新**。**别把 ES 当主存**——它并非设计为在所有故障模式下提供强一致或耐久性。把它当可从真相源重建的反规范化读模型。

**必须规划的运维事项：**
- **重建管道**——这是**必备**不是可选。ES 的 analyzer、schema 或 mapping 变更常**无法就地应用**；你必须**建新索引并切换别名**。从第一天就设计好由真相源驱动的重建路径。
- **Ingest 背压**——洪水般的更新（批量导入、CDC 追赶）能冲垮索引；需有界队列与限速，使索引不塔下、不饿死搜索查询。
- **资源隔离**——**搜索与索引争**同集群 CPU/IO。重索引会拖慢查询延迟，故隔离二者（分节点/分层、限速索引）以保护读路径。

**Postgres 全文搜索何时就够：**对**中小规模**，Postgres 内建 **`tsvector`/`tsquery`** FTS（配 GIN 索引）能处理词干、排序、短语搜索，**无需新增第二个存储**，而且白拿事务一致（索引与数据同事务更新）。加 **pgvector** 甚至能在同库做语义/向量搜索。**只在长出 Postgres FTS 时**才上专用引擎——超大语料库、苛刻的相关性调优、重 faceting/聚合、或通用库满足不了的延迟。在需求明确前避开单独搜索集群的运维成本。

**要点：**
- 倒排索引、analyzer、faceting。
- 当作投影，而非真相源。
- 重建索引管道是必备。
- Postgres FTS 适合中小规模。

### 57. 向量数据库与 RAG

**频率：** 中

**题目：** 向量数据库与 RAG 管道如何工作？何时用 pgvector 而非专用向量库？

**答案：** **向量数据库**（Pinecone、Weaviate、Qdrant、Milvus 与 Postgres 内的 **pgvector**）存**高维嵌入**——常 768–3072 维、捕捉文本/图像*语义*的向量——并回答**近似最近邻（ANN）**查询："找与这个最接近的向量"。对百万高维向量做精确最近邻太慢，故用 **ANN 索引**——**HNSW**（可导航小世界图，常见默认，召回/延迟优）或 **IVF**（聚类后只搜最近簇）——用少许召回换巨大提速。

**RAG（检索增强生成）**用它把 LLM 锚定到你自己的数据。**离线：**把文档**分块**、每块**嵌入**、**存**向量。**查询时：嵌入用户问题**、经 ANN 检回**最相似的 top-K 块**、**塞入 LLM 提示**作为上下文，使它从*你的*文档作答而非从训练数据幻觉。

**决定 RAG 成败的架构关切：**
- **分块策略**——块太大检索不精（无关文本稀释匹配）；太小丢上下文。重叠与语义边界很重要。
- **嵌入模型版本化**——查询与存块**必须用同一嵌入模型**；换模型就要**重嵌入整个语料库**，故要版本化并规划迁移。
- **混合搜索**——向量相似 + **关键词 BM25**。纯向量错过精确词（产品码、名称、缩写）；BM25 能捕捉。融合二者（如 RRF）稳定**优于纯向量**。
- **重排**——检回更大候选集，再用**交叉编码器重排**（同读 query+块给精准相关分），把真正最优的块放到前面再入提示。
- **新鲜度**——**文档更新时重嵌入**，否则答案陈旧。
- **访问控制过滤**——按**用户权限**过滤检索，使 RAG 绝不抛出用户无权看的块（忽视则是真实泄密风险）。

**pgvector vs 专用：**对**多数应用**，**Postgres 内的 pgvector** 是务实选择——避免新增存储，向量与关系数据（及其 ACL）**事务一致**，百万向量也胜任。只在**极高规模**（亿级到十亿向量）、需该规模下**极低延迟**、或需高级特性（分布分片、大规模元数据过滤、托管运维）时才上**专用向量库**（Pinecone/Qdrant/Milvus）。从 pgvector 起步，真长出时再升专用库。

**要点：**
- ANN 索引：HNSW 常见。
- RAG = 检索 top-K + LLM 提示。
- 混合（向量 + BM25）优于纯向量。
- pgvector 适合中小规模。

### 58. 多租户隔离策略

**频率：** 中

**题目：** 请描述 silo、pool、bridge 三种多租户隔离策略及分层模型如何用它们。什么能控住吵闹邻居？

**答案：** 多租户是用共享基础设施服务多客户；隔离策略决定它们**共享多少**，用**成本换隔离与合规**。

- **Silo（每租户一库或一集群）：**每租户得**专用基础设施**。**隔离最强**——无跨租户泄露可能、爆炸半径按租户拘住、**最易满足合规**（受监管企业可指*自己的*库）。代价是**成本与运维开销最高**——运维、备份、打补丁、监控 N 个库，新租户供给很重。
- **Pool（共享一库，每行带 `tenant_id`）：**所有租户同表，以 **`tenant_id` 列**区分。**最便宜、最可扩展**（一库、加租户只需新 ID），但**最难隔离**：一个漏写的 `WHERE tenant_id = ?` 就把一租户数据泄给另一个（灾难性 bug），且共享资源有**吵闹邻居风险**。
- **Bridge（共享基础设施，每租户一 schema）：**中间地带——一个库实例、每租户**独立 schema（命名空间）**（Postgres 里很自然）。比 pool 隔离好（schema 级分隔、每租户备份/导出更易），成本低于 silo，但过百租户后 schema 泛滥难管。

**分层模型**把策略映射到客户价值：**pool** 给**免费/自助/SMB**（便宜、高密度、配额下隔离可接受），**bridge** 给**付费**租户（更强分隔），**silo** 给**企业**租户（常*合同要求*专用基础设施与合规保证，也愿为此付费）。一个系统跑三层，按租户规模与合规需求选。

**控住吵闹邻居**（pool/bridge 共享资源时必备）：
- **每个查询带 `tenant_id`、结构性强制**——绝不依赖开发者记得。用**中间件**注入过滤、ORM scope 或数据库**行级安全（RLS）**使数据库自身拒绝跨租户访问。这是最重要的单一保障。
- **每租户限速与配额**——限每租户请求率、存储、算力，使一租户不能垄断共享容量而饿死其余。
- **每租户可观测**——按租户跟踪指标与成本，以便发现吵闹/滥用租户、归属成本、在伤及邻居前执行限制。

**要点：**
- silo、pool、bridge：成本 vs 隔离。
- 分层模型：自助用 pool，企业用 silo。
- 每行 tenant_id + 中间件强制。
- 每租户配额防邻居噪音。

### 59. 地理分布的数据

**频率：** 中

**题目：** 你如何为低延迟与数据驻留合规架构地理分布的数据？从哪里起步？

**答案：** 地理分布服两个目标：**延迟**（把数据放用户附近，使东京的请求不跨太平洋）和**数据驻留**（GDPR 等法律要求 EU 公民数据物理留在 EU）。难处在于跨区复制把**一致性 vs 延迟权衡**全球化地重新引入。

**从最简到最难的模式：**
- **读本地 / 写全局：**数据有**主区域**接所有**写**，但**读**由每区的**本地副本**服务。到处读快；坑在离主区远的用户每次写都付**跨区往返**。简单一致，读主导、写容延时好。
- **本区域（按用户钉定）：**每**用户钉到一个区域**拥有其数据（EU 用户数据在 EU），并**复制到另一区做灾备**。因用户多与自己数据交互，读写都**本地很快**，驻留天然满足。因多数工作负载按用户/租户干净分区，这是**常见默认**。
- **Active-active 多主：**每区都**接受写**，用 **CRDT 或冲突解决**调和并发写。给**最低延迟与最高可用**（处处可写）但**最难**——必须处理写冲突，多主间强一致要么不可能要么极贵。

**数据库区别：****Spanner** 用 **TrueTime**（GPS/原子钟同步、不确定性有界）提供**全球强、外部一致**事务——代价是提交延迟系于钟不确定窗口。**CockroachDB** 用 Raft range 提供类似全球 SQL。**Cosmos DB** 暴露**可调一致级别**（强→有界陈旧→会话→最终）。**Cassandra** 给最终一致 active-active 加可调法定人数。

**核心权衡**总是**一致性 vs 写延迟 vs 复杂度**，权衡本地化/驻留收益。全球强一致（Spanner）赔写延迟；active-active 低延迟赔一致性与复杂度。

**从哪起步：**从**每用户本区域**起——它交付大部分延迟收益并对常见情况满足驻留，无 active-active 的冲突解决噩梦。**只在延迟或合规需求推动时才加复杂度**——转向全球强一致（Spanner/CockroachDB）或处处可写可用（带 CRDT 的 active-active）。在具体需求逼你之前别上多主。

**要点：**
- 每用户钉本区域是常见默认。
- Spanner/CockroachDB 用于全球 SQL。
- Cassandra/Cosmos 用于可调 AP。
- 驻留规则把数据钉到司法管辖区。

### 60. Token：不透明 vs JWT；撤销

**频率：** 中

**题目：** 请比较不透明 token 与 JWT，尤其围绕撤销。你何时选哪个，混合方案是什么？

**答案：** 二者都是客户端出示以证明授权的 bearer token；区别在**状态住哪里**，因而决定校验与撤销如何工作。

**不透明 token** 是**随机、无意义的字符串**——token 本身不携信息。所有状态（哪个用户、什么 scope、过期）住在签发方**服务端**。校验它需**内省**——调签发方（或共享存储）查"这 token 有效吗、授予什么"。好处：**即时撤销**——删服务端记录，token 立刻到处失效。坏处：**每次 API 调用都需查找/往返**，增延迟与耦合。

**JWT** 是**自包含的签名声明**——token *就是*数据（用户 ID、scope、过期）加签名。任何服务可用签发方公钥**本地校验**——**无往返、完全无状态**，快且扩展好。坏处是不透明优势的镜像：**过期前难以撤销** JWT——因校验本地离线，无中央"是否仍有效"检查，被盗或应撤销的 JWT 仍有效到其 `exp`。

**JWT 撤销的缓解：**
- **短 TTL（5–15 分）+ refresh token**——访问 JWT 快速过期（拘住损害窗口），较长命、可撤销的 refresh token 铸新的。撤 refresh token，访问几分内死。
- **`jti` 黑名单**——用于**强制/应急撤销**，维小列已撤销 ID（`jti`）供服务查。重引一次查找，但仅对罕见的已撤销情况。
- **密钥轮换**——轮换签名密钥使旧密钥签的所有 token 失效（一刀切式全局撤销）。
- **受众限定（`aud`）**——限每 token 到特定服务，使泄露 token 爆炸半径更小。

**选型：**对**B2B/内部**且流量适中的 API，**不透明 + 缓存**常更简单安全（即时撤销、内省成本可控/可缓存）。对**高流量公共 API 与微服务网格**，**JWT** 在性能上胜——无状态本地校验避免百万调用中每一次都查找。**混合**常见且务实：**快速路径用 JWT**（多数请求本地校验），但**对敏感操作加黑名单/内省检查**（转账、权限变更）——大流量享 JWT 速度，关键处享即时撤销安全。

**要点：**
- JWT：无状态、快、难撤销。
- 不透明：有状态、易撤销、需查找。
- 短 TTL + refresh 缓解 JWT 撤销。
- 黑名单用于紧急撤销。

### 61. 大规模密钥管理

**频率：** 中

**题目：** 你如何大规模管理密钥，又如何避免引导密钥问题？

**答案：** 核心规则：**密钥（数据库密码、API key、私钥）绝不能写入代码、容器镜像或提交到仓库的环境变量**——git 历史或镜像层里的东西对任何有访问权的人都等于永久公开，且无法真正轮换。

**集中到密钥管理器**——**HashiCorp Vault、AWS Secrets Manager 或 GCP Secret Manager**。应用**在启动或运行时从存储获取**密钥而非内嵌；存储处理**自动轮换**（改数据库密码，客户端拾取新的）和**审计访问**（每次读密钥都记录——谁、何时取了什么——对合规与泄露调查关键）。

**引导问题——"乌龟驮乌龟"：**若应用需要一个密钥去*向密钥管理器认证*，*那个*密钥住哪？不能存管理器里（先有鸡先有蛋），放镜像又重现原问题。解法是 **workload identity**：应用用平台背书的身份证明*它是什么*，**无预共享密钥**：
- **云 IAM 角色**——AWS EC2 实例/EKS pod 承担 **IAM 角色**；AWS 自身证明身份并授予 Secrets Manager 访问。无存储凭证。
- **SPIFFE/SPIRE**——从平台属性证明签发密码学**工作负载身份**。
- **Vault 认证方法**——Kubernetes、IAM 或云原生认证让 pod 用其服务账号 token/实例身份向 Vault 认证。

这打破递归：*第一个*密钥来自**平台证明**，而非另一个存储密钥。

**投递与加固：**
- **Sidecar 或 CSI 驱动注入**——**Vault Agent sidecar** 或 **Secrets Store CSI driver** 取密钥并挂进 pod（文件或环境变量），应用甚至不实现获取逻辑，密钥从不碰镜像。
- **短命动态密钥优于静态**——不是一个长命数据库密码永久共享，Vault 可**生成每会话数据库凭证**并**自动过期**（如有效 1 小时）。泄露的凭证几分钟后无用，轮换自动。
- **CI 扫描泄露**——在 CI 中对**仓库和镜像**跑密钥扫描器（gitleaks、truffleHog），在合并/发布*前*抓住误提交的密钥。

**要点：**
- 集中存储，代码无密钥。
- Workload identity 优于引导密钥。
- 尽量用短时动态密钥。
- CI 扫描防意外泄露。

### 62. 纵深防御

**频率：** 中

**题目：** 请解释纵深防御：有哪些层，什么使它们真正有效而非仅仅存在？

**答案：** **纵深防御**指绝不依赖任何**单一安全控制**，因任一控制*终将*失效（防火墙配错、凭证泄露、依赖有 CVE）。而是叠加**独立层**，使一层被破时其余仍拘住攻击者。每层**假设其他层可能已失效**（这也是"假设已被攻破"心态）。

**各层与其归属：**
- **网络**——**防火墙、网络分段**（使被攻陷的 web 服务器够不到数据库子网）、服务间 **mTLS**（加密并双向认证内部流量）。限制横向移动。
- **身份**——**MFA**（单靠盗来的密码不够）、**SSO**（集中控制）、**最小权限**（每身份得所需最小访问）。拘住被攻陷账号能做什么。
- **应用**——**输入校验、输出编码**（挡 XSS）、**参数化查询**（挡 SQL 注入）、**依赖扫描**（抓有漏洞的库）。阻止应用成为入口。
- **数据**——**静态与传输加密**、**tokenization**（把卡号等敏感值换成 token）、**密钥管理**。即便数据被窃也不可读。
- **监控**——**审计日志、异常检测、SIEM**。看不到的就无法响应；此层检测进行中的破坏并提供取证。
- **流程**——**代码评审、威胁建模（STRIDE——欺骗、篡改、否认、信息泄露、拒绝服务、权限提升）、事件响应**。人/组织层，在代码发布前抓设计级缺陷并在出事时协调反应。

**什么使层*有效*而非仅存在**是围绕它们的运营纪律：**及时打补丁**（未打补丁的层就是洞）、**持续扫描**（漂移与新 CVE 每日出现）、用 STRIDE **对新特性做威胁建模**（在设计时找弱点，并**假设内部威胁**而非只是外部攻击者）、**演练事件响应**（没人练过的 runbook 在压力下失灵）。纸面存在但陈旧、无监控或从未测试的控制给假信心——各层必须被**维护与演练**，而非仅仅部署。

**要点：**
- 假设任意单点控制失效。
- 分层网络、身份、应用、数据、监控。
- 对新特性做威胁建模。
- 演练事件响应；别只写 runbook。

### 63. 限流与滥用检测架构

**频率：** 中

**题目：** 请设计限流与滥用检测的架构。每一层执行什么，滥用检测如何融入？

**答案：** 限流不是一处一物——它是**分层防御**，每层在尽可能便宜的点抓住不同类别的问题。

**各层：**
- **边缘（CDN/WAF）：**最外层执行**粗糙的 IP 级上限并吸收 DDoS/容量攻击**（Cloudflare、AWS Shield/WAF）。粗（IP 粒度、无应用上下文）但在洪水**触及你基础设施之前**就挡住——那是唯一能经济地吸收大规模攻击的地方。
- **API 网关：**用**令牌桶**（允许突发到桶大小、稳定速率回填——适合突发的正当流量）或**滑动窗口**（更平滑、移动时窗内更准）执行**按 API key/按用户请求率**。这是*身份感知*上限所在。
- **按服务：**贴近资源的细粒度上限，由 **Redis 分布式计数器**支撑，使上限**跨水平扩展服务的所有实例**执行（进程内计数器只对单实例有效，用户打不同 pod 就能超限）。

**差异化上限：**按**用户类别**（匿名 < 免费 < 付费——付费客户得更多余量）和**按端点**（廉价读给高上限；昂贵的 `login` 或搜索端点给紧上限，因它们是滥用目标）施加不同上限。

**滥用检测**超越静态上限。把**异常信号**——突发 **RPS 尖峰**、**登录失败**爆发、**撞库**模式（多用户名一 IP，或一用户名多 IP）——喂入**行为系统**按比例响应：下发**挑战（CAPTCHA）**、要求**阶梯认证**或**临时封禁**。这抓住那些停在原始速率上限*之下*却行为异常的攻击者。

**始终返回 `429 Too Many Requests` 加 `Retry-After` 头**，使良好客户端确知何时重试（而非猛捶），并**公开你的上限**使集成方围绕它们设计。

**要点：**
- 分层：边缘、网关、服务。
- 令牌桶或滑窗 + Redis。
- 按用户类别与端点分级。
- 配合异常检测与挑战。

### 64. RBAC vs ABAC

**频率：** 中

**题目：** 请比较 RBAC、ABAC 与 ReBAC。你何时用哪个，真实系统如何混合？

**答案：** 这三种都回答"此主体能否对此资源执行此动作？"——区别在**基于什么推理**。

**RBAC（基于角色）：**把**用户分配到角色**，**角色对资源*类型*授权**（`editor` 可改文章、`admin` 可删用户）。**简单、直观、易审计**——可列出谁有何角色、授予什么。弱点：**当权限随单个资源变化时爆炸**。若访问取决于*哪个*文档或租户，单靠类型无法表达，就会滋生上千超具体角色（`editor-of-doc-123`）——"角色爆炸"反模式。

**ABAC（基于属性）：**决策由**评估关于主体、资源、动作、环境属性的策略**做出——如 `subject.department == 'engineering' AND resource.owner == subject.id AND env.time in business_hours`。**细粒度、灵活**，无角色爆炸地扩到每资源与上下文规则。代价：策略**更难推理与审计**——"谁能访问 X？"变成对属性组合的查询而非角色列表，复杂策略可能有意外交互。

**ReBAC（基于关系）：**访问由主体与资源间的**关系图**推导（`用户属于组；组是文件夹的 editor；文件夹含 doc → 用户可编辑 doc`）。这是 **Zanzibar 模型**（Google 的系统，由 **SpiceDB** 实现），**优雅处理"分享给我"场景**——正是破 RBAC 的每对象、传递共享权限（Google Docs 分享、GitHub 仓访问）。

**真实系统如何混合：**用 **RBAC 做粗粒度、组织级访问**（是否 admin/editor/viewer），叠**ABAC 做资源范围与上下文**（…*且*他拥有此记录、*且*在其租户内）。当产品本质就是**用户间分享对象**时采用 **ReBAC（SpiceDB/Zanzibar）**。现代策略引擎——**OPA、AWS Cedar、SpiceDB**——支持这些模型，使你把授权从应用代码中外部化。

**要点：**
- RBAC：角色、简单、粒度细时扩展差。
- ABAC：基于属性策略、灵活、复杂。
- ReBAC（Zanzibar）适合关系分享。
- 多数系统混用 RBAC + ABAC。

### 65. 十二要素应用

**频率：** 中

**题目：** 什么是十二要素应用方法论，为何它是云原生基线，部分要素如何演化？

**答案：** **十二要素应用**是一套原则（来自 Heroku），用于构建在**容器与 PaaS** 上干净运行的应用——可移植、可丢弃、可水平扩展。它是**基线**，因遵它才能使应用在 Kubernetes、自动扩缩、滚动部署下"开箱即用"。

**十二要素：**
1. **代码库**——每应用一个版控代码库，多个部署。
2. **依赖**——**显式声明**（lockfile），绝不依赖系统级包。
3. **配置**——存于**环境**（env vars）而非代码，使同一构建跑 dev/staging/prod。
4. **后端服务**——把数据库、队列、缓存当**附加资源**，可按 URL 替换，零代码改动就能改指。
5. **构建、发布、运行**——**严格分离**三阶段（构不可变制品、与配置合成发布、运行），保可复现与易回滚。
6. **进程**——以**无状态进程**运行；状态入后端服务，任何实例可处理任何请求、实例可丢弃。
7. **端口绑定**——应用**通过端口导出自身**，自包含而非依赖注入的 web 服务器。
8. **并发**——**通过进程模型横向扩展**（跑更多相同进程）而非把单进程变大。
9. **可处置性**——**快启动与优雅关停**，使实例可自由创建/杀死（对自动扩缩与滚动部署关键）。
10. **开发/生产对等**——环境**尽量相似**以消除"在我机器上能跑"。
11. **日志**——当作**写到 stdout 的事件流**；平台处理路由/聚合。
12. **管理进程**——把一次性管理任务（迁移、脚本）当**一次性进程**在同环境跑。

**部分如何演化：****配置**现在是 env vars **加密钥管理器**（原始 env vars 存密钥不安全——见 Q61）；**日志**常**经 sidecar/agent（Fluent Bit）发送**而非应用知道日志管道。但**核心思想——无状态、显式配置/依赖、可处置、构建/发布/运行分离——仍成立**，支撑每个云原生平台。

**要点：**
- 配置在环境变量，密钥通过管理器。
- 无状态进程，按数量扩展。
- 日志输出到 stdout；收集器负责路由。
- 严格分离构建/发布/运行。

### 66. 特性开关解耦部署与发布

**频率：** 中

**题目：** 特性开关如何把部署与发布解耦、解锁什么、要求什么纪律？为何它不是配置的替代？

**答案：** **部署**（把代码上生产服务器）与**发布**（对用户启用特性）传统上是同一事件——这使每次部署都冒险。**特性开关**把它们拆开：你**发布"暗"代码**（已部署但裹在 `if (flag.enabled)` 里），稍后通过无需重部署的**运行时开关**为特定用户或群体**启用**（**LaunchDarkly、Unleash、Flagsmith** 或自研）。部署变**频繁且低风险**；发布变**独立做出的业务决策**。

**解锁什么：**
- **基于分群的 canary 发布**——为 1% → 10% → 100% 用户或仅内部员工启用特性，监控指标后再扩大。
- **A/B 测试**——给一群体发 A、另一群 B，度量对比。
- **事件 kill switch**——无需回滚部署即可**瞬间关掉出问题的特性**（秒级而非分钟）。
- **主干开发**——把未完成工作藏在禁用开关后合并，避免长命特性分支与痛苦合并。

**代价与所需纪律：**
- **开关债**——超期旧开关堆积；你**必须清理**否则腐烂。
- **条件逻辑爆炸**——开关嵌开关产生缠绕分支。
- **组合无法全测**——N 个开关意味 2^N 状态，**不可能测每个组合**，bug 藏在罕见组合里。
- 规则：**每个开关都有 owner、过期日期与移除任务**，使临时开关真正被移除。

**为何不是配置的替代：**开关用于**在途特性与运维切换**——本就**临时**、最终归于"常开"（然后删掉）或"常关"。**永久、结构性设置**（超时、连接串、层级上限）属于**配置管理**——当开关用意味永久条件分支与永久开关债。

**要点：**
- 把部署与发布解耦。
- 支持定向 canary、A/B、kill switch。
- 开关债真实存在——过期并移除。
- 不是配置管理的替代。

### 67. CD 中的数据库迁移

**频率：** 中

**题目：** 在持续交付与滚动部署下你如何安全地跑数据库迁移？走一遍 expand-migrate-contract。

**答案：** **滚动部署**期间，新旧应用版本会**同时运行**一段时间（pod 逐个替换）。这意味每个 schema 变更都**必须向后兼容**——旧代码必须能继续对新 schema 工作，否则仍在跑的旧实例就坏了。你**不能**一步做破坏性变更（重命名/删列）。安全手法是 **expand-migrate-contract**，跨多次部署铺开：

1. **扩展（Expand）**——只做**可加性**变更：加新列/表、加可空列、加新索引。新旧代码都能工作因它们依赖的东西都未被移除。（把 `name` 重命名为 `full_name` 变成：*加* `full_name`。）
2. **迁移（Migrate）**——部署**使用新 schema** 的应用代码。若过渡期新旧列均需同步，让应用**双写**（同写 `name` 与 `full_name`）并**回填**现有行。本次部署完成后，所有实例用新 schema，旧列不再被读。
3. **收缩（Contract）**——在**更晚**的部署中，确信**无运行实例引用旧列/表**后，**移除**它。现在安全，因无物依赖它。

**运维要领：**
- **大表上避免阻塞型 DDL**——天真的 `ALTER TABLE` 在大表上可能拿锁几分钟卡住全部流量。用**在线 schema 变更工具**——**pt-online-schema-change** 或 **gh-ost**（MySQL）或数据库**原生在线 DDL**——在影子副本上应用变更而无长锁。
- **把迁移当应用部署*前*的独立 CI/CD 步骤**跑，绝不**在应用启动时**——启动迁移在多实例同时启动并并发迁移时引发竞态。
- **在 staging 用 prod 形状数据（现实大小与分布）预演**，在触及生产*前*抓住慢迁移与锁意外。

**要点：**
- expand-migrate-contract 保证向后兼容。
- 大规模使用在线 schema 变更工具。
- 作为独立 CI 步骤运行，而非应用启动时。
- 用真实量级数据预演。

### 68. liveness/readiness/startup 探针

**频率：** 中

**题目：** 请解释 Kubernetes 三种探针及各自正确配置。为何探针配错是可避免事故的头号原因？

**答案：** Kubernetes 用三种探针管理 pod 健康，它们回答**不同问题**、带**不同后果**——混淆它们正是导致事故的原因。

- **liveness 探针——"进程活着/没卡住吗？"**失败会**重启 pod**。因惩罚是重启，保持它**廉价且自包含**（简单进程/心跳检查）。关键规则：**绝不因下游依赖失败 liveness**（数据库、另一服务）。若数据库抖一下且每个 pod 的 liveness 都查数据库，Kubernetes 会**同时重启每个 pod**——把瞬时抖动变成完整**级联事故**。liveness 只回答"*此进程*坏了、值得重启吗？"，仅此而已。
- **readiness 探针——"此 pod 现在能服务流量吗？"**失败会**把 pod 从负载均衡器摘除**（但**不**重启）。这里你**确实检查阻塞请求的依赖**——数据库连接已建立、缓存已预热、下游可达。不能服务的 pod 被拉出轮转、恢复后放回，无需重启。
- **startup 探针——"这个慢应用启动完了吗？"**它为启动很慢的应用（JVM 预热、大缓存）**门控 liveness 探针**。没有它，liveness 会在慢启动期触发并**在应用起来前杀掉它**，永远重启循环。startup 探针一旦通过，liveness 接管。

**为何配错导致事故：**两个经典失败模式是 (1) **查依赖的 liveness** → 一次下游抖动同时重启每个 pod（级联失败），(2) **readiness/liveness 过严或过快** → 健康 pod 在正常负载尖峰下被拉出或重启循环。探针看似简单却控制整个生命周期，把*语义*搞错就可靠地制造自伤事故。

**要点：**
- liveness：进程活着；便宜；不要级联。
- readiness：能服务；查依赖。
- startup：保护慢启动。
- 探针配错引发事故。

### 69. 优雅关停与连接排空

**频率：** 中

**题目：** 你如何实现优雅关停与连接排空？SIGTERM 上应发生什么，缺了它会坏什么？

**答案：** 当实例被告知停止（部署、缩容、节点排空），它通常正**处理在途**的真实请求。**优雅关停**确保它干净收尾而非丢弃这些请求。**SIGTERM** 上的顺序：

1. **标记实例未就绪**——让 readiness 探针失败，使**负载均衡器停止把新请求路由**给它。这必须*先*发生，否则新活儿在你试图关停时不断到达。
2. **排空在途请求**——让已在进行的请求在**宽限期内完成**，而非直接切断。
3. **关闭空闲连接**——拆掉无活跃请求的 keep-alive/池连接。
4. **flush 缓冲**——推出任何缓冲的**日志、指标、事件**，避免丢失可观测数据或已发出的事件。
5. 干净**退出**。

**Kubernetes 如何驱动：**它发 **SIGTERM**，然后等最多 **`terminationGracePeriodSeconds`（默认 30 秒）**再发 **SIGKILL**（强制、无清理）。按你最长合理请求调它。有个微妙竞态：端点移除（LB 更新）与 SIGTERM 几乎同时发生，所以 LB 可能在你刚开始关停时仍发几个请求。修法是在进程开始关停*前*加一个**短 sleep（5-10 秒）的 `preStop` 钩子**——给 LB/端点控制器时间真正注意到 pod 已消失，再停止接受流量。

**有状态服务需要更多：**退出前它们必须**重新分配分区/领导权**（交出 Kafka 分区、退位 Raft leader、转移分片所有权），使集群不至于该数据无主。

**缺少优雅关停：**每次部署（替换每个 pod）都**丢弃一小部分在途请求**，表现为**每次滚动发布期间错误率尖峰**——一个自伤、反复的可靠性问题，优雅关停能彻底消除。

**要点：**
- SIGTERM、排空、再退出避免 SIGKILL。
- Pre-stop 钩子给 LB 反应时间。
- 按工作负载调 terminationGracePeriod。
- 有状态服务必须移交领导权。

### 70. DR：RTO vs RPO

**频率：** 中

**题目：** 请解释 RTO 与 RPO 及它们如何驱动灾难恢复架构与成本。为何未演练的 DR 等于没有 DR？

**答案：** **RTO（恢复时间目标）**是你的**停机预算**——灾后服务可*停机*多久才到不可接受。**RPO（恢复点目标）**是你的**数据丢失预算**——你能承受*丢失*多少最近数据（以时间计："最多 15 分钟写入"）。这两个数字是决定 DR 架构、并直接决定其成本的**主要杠杆**——越紧的目标要求越贵、始终热备的基础设施。

**目标如何映射到架构（从贵到便宜）：**
- **RTO=分钟、RPO=零** → **同步复制的 active-active 多区域**。每次写在多区域提交后才确认，故无数据丢失、另一区域几乎瞬间接管。成本最高（双份基础设施、跨区写延迟）。
- **RTO=小时、RPO=15 分钟** → **异步复制的 pilot-light 或 warm-standby**。DR 区域跑一个最小（pilot-light）或缩小（warm）副本、异步复制。灾时扩容并重指流量——更便宜，但接受一些停机（扩容+切换）与一小窗未复制数据。
- 再宽松些 → **备份恢复**（冷）：仅从备份恢复，最便宜但最慢。

**按服务分层：**别对全组织套一个目标——**支付系统**需紧 RTO/RPO（active-active），而**分析仪表板**可容忍数小时停机与一天数据丢失（warm standby 或备份）。层级匹配业务关键性**避免在不需要的服务上巨额超支**。

**为何未演练 DR = 没 DR：**从未*执行*过的 DR 计划是假设而非能力。备份会静默损坏、恢复流程有缺失步骤、故障切换自动化有陈旧配置、runbook 假设一个已离职的人。团队常在*真实灾难中*才发现备份恢复不了或切换切不过去。你必须**用现实数据至少每季度演练整条路径（备份、runbook、故障切换自动化）**，否则你没有真正的 DR——你只有它存在的*信念*，那更糟。

**要点：**
- RTO = 停机预算；RPO = 数据丢失预算。
- 驱动复制与成本。
- 按服务分层避免过度花费。
- 没演练 = 没 DR。

### 71. 备份与恢复

**频率：** 中

**题目：** 请描述稳健的备份与恢复策略。为何没有测过的恢复，备份就无用？

**答案：** 指导原则：**你拥有的不是备份，而是*恢复***——未测过的备份是猜测。以下一切都服务于**可证明可恢复**的系统这一目标。

**备份组合（做时间点恢复）：**
- **定期全备**（如每周）——完整快照，恢复基线。
- 全备间的**增量**——只备变化的，保持存储与备份窗口小。
- **持续归档的 WAL/binlog**——数据库的预写日志/二进制日志持续流出，实现**时间点恢复**：恢复最后全备+增量，再**回放日志到精确时刻**（如坏 `DELETE` *前*一秒），而非只能恢复到昨晚。

**存储与保护：**
- **异地、不同区域**——使摧毁主区域的灾难不会同时摧毁其备份。
- **加密**——备份含你全部数据；至少与生产同等保护。
- **不可变/一次写入**加严格访问控制——这是关键的**勒索软件防御**：攻击者（或被攻陷的管理员）**无法删除或加密不可变备份**，故你总能恢复。

**测试与正确性：**
- **每季度用现实数据量测试恢复**——这验证**完整性**（备份确实能恢复）*并***测量 RTO**（5 TB 的全量恢复可能耗费你没预算的数小时）。这是团队跳过并后悔的步骤。
- **按法规需要保留**——如金融记录常要求 **7 年**；保留期对齐合规而非便利。
- 数据库要**应用一致备份**——静默/快照使备份是连贯事务状态，**而非崩溃一致**（后者可能捕获撕裂的、写到一半的数据，恢复成损坏）。
- **捕获备份元数据**——随每次备份记录 **schema 版本与应用版本**，使你恢复到**兼容运行时**（在新代码下恢复旧 schema、或反之，可能失败或损坏）。

**要点：**
- 全量 + 增量 + 持续 WAL。
- 异地、加密、不可变。
- 每季度测恢复。
- 数据库要应用一致备份。

### 72. on-call、runbook、无指责事后复盘

**频率：** 中

**题目：** 你如何有效地组织 on-call、runbook 与无指责事后复盘？

**答案：** 这三种实践把事故从反复救火变成稳步改善可靠性的**学习系统**。

**on-call：**在团队内**轮值** on-call。轮值**传播运维知识**（人人都学会系统如何失败，而非只有一个英雄）并**防倦怠**（没有单人被永久拴住）。关键是**限制每班 pager 次数**——若 on-call 被不断呼叫，**告警疲劳**就来了：工程师开始忽略或反射性静音告警，而*真正*那条被漏掉。吵闹的 pager 是可靠性风险，故调告警使之可执行且稀少。

**runbook：****每个告警都必须有 runbook**——一份具体文档，列出**诊断步骤**（查什么、哪些仪表板、哪些查询）与**处置步骤**（如何修复或缓解）。这让即使经验较少的 on-call 值班者也能在凌晨 3 点无需深厚部落知识就快速行动。更好的是**尽量自动化** runbook（自动修复、一键脚本），使响应快速且一致。没有 runbook 的告警是没人知道如何处理的告警。

**无指责事后复盘：**事故后写一份**无指责**复盘——聚焦**系统与流程失败，而非个人**。这至关重要：若人们怕被追责，就会隐瞒信息，你便失去学习能力。记录**时间线**、**根因**、**贡献因素**、**有指定 owner 与截止日期的行动项**。最常被跳过的一步是**跟踪行动项到完成**——若从不做完，**相同事故会重现**。**广泛分享复盘**使整个组织从一个团队的事故中学习。

**事件指挥：**对严重事故，**演练明确角色**——一名协调并决策的**事件指挥官（IC）**、一名让干系人知情的**通讯负责人**、一名记录时间线的**记录员**。演练这些角色（game day）意味在真实高压事故中协调是**自动的**而非混乱的。

**要点：**
- 每告警一份 runbook；尽可能自动化。
- 限制 pager 数量以防疲劳。
- 复盘无指责且行动项被跟踪。
- 演练事件指挥角色。

### 73. 多区域 active-active vs active-passive

**频率：** 中

**题目：** 请比较多区域部署的 active-active 与 active-passive 两种模式。请说明：(1) active-passive——一个区域服务、另一个温备做故障切换，简单、无写冲突，但切换耗分钟、备用容量浪费；(2) active-active——两个区域都服务，用户延迟更低、满负载利用，但写需要冲突解决（CRDT、最后写入获胜或区域亲和），一致性更棘手；(3) 本区域路由（每用户为写钉到一个区域、本地读）为什么常是甜点。请谈谈全球应用与合规驱动 DR 的选型差异，以及为什么故障切换自动化必须演练。

**题目：** 请比较多区域 active-active 与 active-passive 部署及本区域混合。你何时选哪个，为何切换必须演练？

**答案：** 两者都跑在多区域，区别在**第二区域是否服务实时流量**，这驱动其他一切。

**active-passive：****一个区域服务全部流量**；另一个是随时待命的**温备**（复制数据、缩小或空闲的计算），纯为**故障切换**。它**更简单**：因只有一个区域接受写，**无写冲突**、一致性直接。缺点：**切换耗分钟**（检测事故、提升备用、重指 DNS/流量），且**被动区域容量闲置**——你为一个灾难来临前什么都不服务的第二区域付费。

**active-active：****两个区域同时服务流量**。这带来**更低延迟**（用户命中最近区域）与**满容量利用**（你为两个区域付费*并使用*两个）。难点是**写**：两区域都接受对同一数据的写时，并发冲突写必须被**调和**——用 **CRDT**（无冲突合并）、**最后写入获胜**（简单但可能丢数据）或**区域亲和**（把每记录的写路由到一个拥有区域）。**一致性确实更棘手**，冲突解决搞错会导致静默数据损坏。

**混合——本区域路由——通常是甜点：**每个**用户为写钉到一个本区域**（故其写永不冲突——只有一个区域拥有它们），而**读在每个区域从副本本地服务**。你获得 active-active 的大部分延迟与利用优势，**却没有**通用多主冲突问题，因写按用户分区。

**何时选哪个：**为**真正全球的应用**选 **active-active（或本区域混合）**，那里全球用户需要低延迟且你想用尽全部容量。为**合规驱动的 DR** 选 **active-passive**，那里切换**不频繁**、工作负载是区域性的、简单性/一致性比利用率更重要。

**为何演练切换：**尤其在 active-passive，**切换只在真实灾难中被行使**——恰是你最输不起它失败之时。未演练的切换自动化常坏（陈旧配置、缺 IAM 权限、DNS TTL 过长、备用数据滞后）。若你不**定期演练切换**，会在最糟时刻发现它坏了。

**要点：**
- Active-passive：简单，温备容量浪费。
- Active-active：满利用，写冲突。
- 本区域路由是常见甜点。
- 故障切换自动化必须演练。

### 74. Pastebin

**频率：** 中

**题目：** 请设计一个 Pastebin（任意文本最多约 10MB、短 URL、过期、可见性、约 1 万写/天、10 倍读）。为何把内容卸到 S3 而非数据库？

**答案：** **需求：**存任意文本最多**约 10MB**、生成**短 URL**、支持**过期**与**私有/未列出/公开**可见性、**语法高亮**、约**每天 1 万写、约 10 倍读**（规模适中、读多）。

**组件：**
- **API + Web 层**——`POST /paste`（创建）与 `GET /:id`（获取）。生成短 ID（计数器的 base62，或随机 7-8 字符 slug）。
- **对象存储（S3）存粘贴内容**——S3 便宜、极耐久（11 个 9）、支持**范围读**，故 10MB 粘贴可流式/部分获取而无需全载入应用内存。
- **元数据库（Postgres）**——每粘贴一小行：`{id, owner, visibility, expiry, mime/language, size, s3_key, created_at}`。
- **搜索索引（Elasticsearch）**——仅对**公开**粘贴，使其可被发现；私有/未列出永不索引。

**数据模型——关键切分：**Postgres 中一**小元数据行**（有索引、可查询、便宜）通过 `s3_key` 指向 **S3 中的大内容 blob**。数据库存粘贴的*事实*；S3 存*字节*。

**扩展：**在公开粘贴前放 **CDN**——因内容按 ID 不可变，公开读在边缘完美缓存、永不触及源站。为热粘贴元数据加 **KV 缓存（Redis）**。鉴于读多画像，缓存吸收几乎全部流量。

**过期：**最干净的做法是 **S3 生命周期策略**——给对象打过期标签、让 S3 自动删除——或**定时清理任务**扫过期行与其对象。语法高亮在**客户端**做以省服务端 CPU。

**为何用 S3 而非数据库内联：**把 10MB blob **内联存 Postgres** 在演示里能跑但**规模化时严重退化**——它膨胀表大小、拖慢备份/vacuum、把 buffer cache 浪费在 blob 上、使复制沉重。**从第一天就把内容卸到 S3** 保持数据库小而快（仅元数据），给你便宜耐久、支持 CDN/范围读的存储，并干净分离可查询元数据与批量字节。

**要点：**
- 元数据在 SQL，内容在 S3。
- 公开读用 CDN。
- 生命周期策略处理过期。
- 客户端做语法高亮省服务端。

- 图片转码管道 + CDN。

- 混合时间线扇出。
- 点赞用分片计数器。

- **幂等键防重复发送**——重试或重投的队列消息不得把同一通知发两次；以幂等键为键的去重存储使送达**至少一次但实际只被见一次**。

**要点：**
- 渠道网关后接队列。
- 偏好引擎控制送达。
- 幂等键去重。
- 按用户聚合防疲劳。

### 77. YouTube

**频率：** 中

**题目：** 请设计 YouTube（上传、转码到多分辨率/编解码、全球自适应码率流式播放、评论、推荐）。覆盖组件与关键权衡。

**答案：** **需求：****上传**视频、**转码**到多分辨率/编解码、**用自适应码率（HLS/DASH）全球流式播放**、**评论**、**推荐**，规模**数十亿小时观看**。系统由**视频存储与分发成本**主导。

**组件：**
- **上传服务**——**断点续传、分块**上传，使大文件断连时续传而非重来。
- **转码管道**——**队列驱动的并行 worker** 产出**分辨率/码率阶梯**（240p→4K）跨编解码（**AV1/VP9/H.264**），使每个设备/网络得到兼容、大小高效的流。视频切块并行转码以提速。
- **存储**——带**冷层**的**对象存储**：热门内容留热；**长尾**（多数视频、罕看）移到更便宜的冷存储。
- **CDN**——**多层带边缘缓存的 CDN** 分发实际视频段；带宽（与成本）在此。
- **元数据库（Vitess/Spanner）**——可扩展存视频元数据、观看数等。
- **推荐服务**——基于观看历史的 ML 驱动下一视频与主页。
- **评论**——**独立写多存储**（评论的访问模式与视频大不相同）。

**扩展：****把热门内容预放近边缘**（主动把趋势视频推到边缘缓存）；从更少的地区缓存或源站服务**长尾**，因把每个罕看视频到处缓存不经济。

**权衡：**
- **存储成本 vs CDN 成本**——存更多编码/层耗存储但改善缓存/分发效率；你在两者间平衡。
- **转码成本 vs 编码质量**——昂贵的 **per-shot/per-title 编码**（逐场景优化码率）**仅对**会被看数百万次的**热门内容**值得以摊销成本；长尾用更便宜的通用编码。

**要点：**
- 断点续传 + 队列驱动转码。
- 自适应码率（HLS/DASH）。
- 多层 CDN；冷热存储分层。
- 爆款视频用 per-shot 编码。

### 78. Netflix

**频率：** 中

**题目：** 请设计 Netflix 的流式架构（预编码目录、数百万并发观看者、个性化、全球版权）。为何 Open Connect 与 per-title 编码是关键？

### 80. Google Maps

**频率：** 中

**题目：** 请设计 Google Maps（瓦片、搜索/POI、含实时交通的路由、导航）。覆盖组件与新鲜度 vs 预计算权衡。

**答案：** **需求：****渲染地图瓦片**、**搜索/POI** 查找、含**交通**的驾车/公交/步行**路由**、逐向**导航**，规模**数十亿用户**。工作负载分为便宜可缓存的读（瓦片）与昂贵的计算（路由）。

**组件：**
- **瓦片服务**——通过 **CDN** 在多**缩放层级**服务**预渲染的栅格与矢量瓦片**。瓦片按区域/缩放静态，故达 **90%+ CDN 缓存命中**——大部分流量永不触及源站。
- **搜索/地理编码**——类 Elasticsearch 索引，带**地址规范化**（"1600 Amphitheatre Pkwy" → 坐标）与结果的 **ML 排序**。
- **路由服务**——难点。把道路网络建模为**加权段的图**（权重=行程时间）。在洲际图上朴素 Dijkstra 太慢，故用**分层算法——Contraction Hierarchies（CH）或 Customizable Route Planning（CRP）**——**预计算捷径**，使查询只触及图的极小部分、毫秒返回。**实时交通调整边权重**使路线反映当前状况。
- **交通采集**——来自数百万设备的**匿名 GPS ping** 流入**流处理器**估计每段当前速度——众包交通。
- **POI 数据库**——地点、营业时间、评论。
- **影像管道**——卫星/街景处理。

**扩展：****瓦片对 CDN 友好**并几乎全卸到边缘；**路由 CPU 重**并**按区域分片**，使每个路由集群处理一个地理区域。

**新鲜度 vs 预计算权衡：**最快的路由来自**重度预计算**（CH 捷径），但预计算结构**不反映实时交通**——若你完全预计算路线，它们会失新。反之，用新鲜交通**实时重算一切**在查询时**太慢**，若没有分层捷径。解法是 **CRP 式**：一次预计算*结构*，再在其上**便宜地重新施加实时交通权重**——同时得到速度*与*新鲜度。

**要点：**
- 预渲染瓦片 + CDN。
- Contraction Hierarchies 做快速路由。
- 通过众包 GPS 做实时交通。
- 按区域分片的路由服务。

### 81. 分布式缓存（类 Redis）

**频率：** 中

**题目：** 请设计一个类 Redis 的分布式缓存（低延迟 KV、水平扩展、复制、淘汰、每秒数十亿 op）。覆盖分片、HA 与关键权衡。

**答案：** **需求：**一个**低延迟内存 KV 存储**、**可水平扩展**、带可选**复制**、**淘汰策略**，规模**每秒数十亿 op**。内存意味每个设计选择都朝保持操作 O(1) 与网络跳数最小弯折。

**组件：**
- **分片**——通过**一致性哈希**或**固定分区槽**把键空间跨节点分区。**Redis Cluster 用 16384 个哈希槽**：每个 key（经 CRC16 mod 16384）映射到一个槽，槽分配给节点。固定槽使**再平衡**干净——你在节点间移动整个槽而非重哈希一切。
- **复制**——每个分片有一**主 + 一或多副本**，**异步**（快、小数据丢失窗口）或**半同步**（更安全、更慢）复制。副本服务读并随时待晋升。
- **客户端**——**槽感知**（知道哪个节点拥有每个槽、直接路由）与**流水线**（每次往返批处理多条命令——对吞吐至关重要，因延迟由网络往返主导）。
- **淘汰**——内存满时按策略淘汰：**LRU**（最近最少使用）、**LFU**（最不频繁使用）、**allkeys-random** 或**基于 TTL** 的过期。按工作负载选（偏斜热集用 LFU，近因驱动用 LRU）。

**故障处理：**节点跑 **gossip 协议**检测死对等；主死时，**副本被自动晋升**。为持久，通过 **AOF**（写的追加日志）或 **RDB**（时间点快照）持久化。

**在线扩展：****实时加分片**——槽迁移到新节点，命中旧节点的客户端得到指向新拥有者的 **MOVED/ASK 重定向**，故无停机。

**权衡：****异步复制在故障切换时可能丢最后几个写**（缓存可接受；不能则用半同步）；**大 key 造成热分片**（巨值或热 key 压垮单节点——拆 key 或客户端分片）；**流水线 + 连接池是必备**才能真正达到每秒数十亿 op。

**要点：**
- 一致性哈希或固定槽数。
- 异步复制；可能小数据丢失。
- Gossip + 自动晋升做 HA。
- 按工作负载选淘汰策略。

### 82. 指标/监控（类 Prometheus）

**频率：** 中

**题目：** 请设计一个类 Prometheus 的指标/监控系统（抓取数千服务、标签查询、告警、分层保留）。覆盖组件与拉 vs 推权衡。

**答案：** **需求：**从数千服务**采集指标**、**按标签查询**、**按条件告警**、**保留高精度短期 + 低精度长期**数据。核心挑战是**基数**（唯一标签组合的数量），它主导成本。

**组件：**
- **抓取器**——Prometheus 按间隔**拉**每个服务的 `/metrics` HTTP 端点。对**短生命周期任务**（在抓取前就死的批任务）它接受**经 Pushgateway 的推送**。
- **TSDB（时序数据库）**——**列式且按时间分区**，带**标签索引**（标签→序列的倒排索引），使 `http_requests{status="500", service="api"}` 快速解析。列式布局对时间戳/值序列极佳压缩。
- **查询引擎（PromQL）**——标签感知的查询语言，用于切片、聚合、在序列上计算速率。
- **告警管理**——**评估告警规则**、**去重**（许多 pod 触发同一告警 → 一条通知）、分组、并**路由到 PagerDuty/Slack**，带静默/抑制。
- **长期存储（Thanos、Cortex、Mimir）**——加**HA、多租户、便宜的对象存储支撑的历史**（S3 上降采样的老数据），因单个 Prometheus 无法保留多年高精度数据。

**扩展：**按区域**联邦**抓取器（区域 Prometheus 经 remote-write 喂全局视图）、**降采样**老数据（保 1 天的 1s 精度、1 年的 5m）、**控制基数**——**在 ingest 时丢弃或重打高基数标签**（永不把用户 ID 或请求 ID 放标签；那是炸掉 TSDB 最快的方式）。

**拉 vs 推权衡：****拉**（Prometheus）使**服务发现与健康简单**——抓取器精确知道哪些目标存在，失败的抓取*就是*健康信号——但**难处理短生命周期任务**与 NAT/防火墙后的目标（需 Pushgateway）。**推**（StatsD、OTLP）天然处理临时任务但需要**网关且失去内建活性信号**。无论哪种模型，**基数是头号杀手**——不受控的标签爆炸会 OOM 系统。

**要点：**
- 拉（Prom）vs 推（StatsD/OTLP）权衡。
- TSDB 列式 + 标签索引。
- 联邦 + 远程写做全局视图。
- ingest 阶段控制基数必备。

### 83. 防腐层

**频率：** 低

**题目：** 什么是防腐层，它何时关键，你如何按每个集成判断它是否值得？

**答案：** **防腐层（ACL）**是**你的界限上下文与外部或遗留模型之间的翻译层**，其职责是**防止外来模型渗入你的领域**。没有它，一个混乱的第三方 API 的概念、命名与怪癖会渗入你的核心代码，逐渐**腐蚀你干净的领域模型**，直到你的业务逻辑与别人的数据结构纠缠不清。

**如何构建：**作为一组坐在边界的**适配器与翻译器**，**把外部概念映射到你的通用语言**（并反向）。你的领域代码永远只看到*你*的干净模型；ACL 吸收阻抗失配。例如支付提供方的 `txn_status: "S"` 在边界被翻译成你领域的 `PaymentStatus.Succeeded`，故下游无人知道或关心提供方的隐晦编码。

**它何时关键：**
- 集成模型陈旧或别扭的**遗留系统**。
- 消费你不控制（且可能变化）的**第三方 API**。
- 与另一团队拥有、约定不同的**界限上下文**对话。
- 在**绞杀者无花果迁移**（Q38）的边缘——ACL 在你增量替换时保护新系统免受旧系统模型侵染。

**它的代价：**要写与维护的**额外映射代码**、一些**性能开销**（每次调用翻译）、以及**外部模型变更时的维护负担**（你更新 ACL，但*只*更新 ACL——这正是关键）。

**按每个集成判断：**权衡外部模型的**混乱度/不稳定度/异质度**与映射成本。对小、稳定、设计良好的集成**跳过 ACL**（翻译开销不值得）。当外部模型**混乱、频繁变化或与你文化迥异**时**采用它**——那里 ACL 通过把混乱围堵在一个明确定义的边界而非任其扩散，物有所值。

**要点：**
- 保护领域纯洁性，隔离外来模型。
- 通过适配器与翻译器实现。
- 遗留迁移期不可或缺。
- 维护有成本——按每个集成单独评估。

### 84. Ambassador 模式

**频率：** 低

**题目：** 什么是 Ambassador 模式，它与通用 sidecar 有何不同，权衡是什么？

**答案：** **Ambassador 模式**是一个**与客户端同位**（通常作为 **sidecar** 容器）的代理，代表应用处理**出向网络关注点**：**服务发现、重试、断路、TLS、可观测性**。应用只**与 `localhost` 对话**，ambassador 处理混乱的网络现实——找到目标服务、失败时重试、宕机时断路、加密连接、发出指标/追踪。

**为何有用：**它**把网络行为与应用代码解耦**。你可以通过更新 ambassador 来**升级重试逻辑、加 mTLS 或改发现**，而**无需触碰或重部署应用**。它对**无法修改的遗留客户端**尤其有价值（一个只会调 `localhost` 的老应用突然免费获得现代韧性与安全），也对**多语言舰队**有价值（在 ambassador 里实现一次网络逻辑，而非在每种语言的客户端库里）。

**vs 通用 sidecar：****sidecar** 是*任何*与主应用同位的辅助容器（日志发送器、配置重载器、代理等）的广义模式。**ambassador 是特定*种类*的 sidecar**——特指**出向调用的网络代理**。故每个 ambassador 都是 sidecar，但非每个 sidecar 都是 ambassador。**服务网格数据面**（Istio/Linkerd 中的 Envoy）**将 ambassador 一般化**——它们本质是全舰队部署、由中央控制面管理的 ambassador。

**权衡：****多一网络跳**（应用 → ambassador → 目标）增加少许延迟；**调试更难**因失败现在可能源自代理而非仅应用；且**需要平台投入**（到处部署、配置、维护 sidecar）。当你有许多服务需要一致网络行为时值得；对单个简单服务是过度设计。

**要点：**
- 与客户端同位的出向代理。
- 处理重试、TLS、发现。
- 把网络与应用代码解耦。
- 服务网格将其一般化。

### 85. 协作状态的 CRDT

**频率：** 低

**题目：** 什么是 CRDT，基于状态与基于操作的变体有何不同，用在哪，权衡是什么？

**答案：** **CRDT（Conflict-free Replicated Data Types，无冲突复制数据类型）**是**设计成使多个副本的并发更新确定性合并——无需协调**、总收敛到同一结果的数据结构。这给出**强最终一致**：副本可独立接受写（离线、在不同区域），一旦交换更新，就**保证到达同一状态**而无需中央权威或锁。收敛由合并操作的属性（交换律、结合律、幂等）**数学保证**。

**例子：****G-Counter**（只增计数器——每副本增自己的槽，合并取每槽的 max）、**PN-Counter**（经两个 G-Counter 实现增*与*减）、**OR-Set**（经唯一标签正确处理并发加+删的加/删集合）、**LWW-Register**（按时间戳最后写入获胜），以及用于**协作文本**的 **RGA/Yjs/Automerge**（对字符排序使并发插入合理合并）。

**基于状态 vs 基于操作：**
- **基于状态（CvRDT）：**副本**发送完整状态**，一个 **join/merge 函数**合并两个状态（如 G-Counter 的逐元素 max）。对网络问题稳健（合并幂等，故重复/乱序消息无妨）但**随数据增长发送完整状态昂贵**。
- **基于操作（CmRDT）：**副本在**可靠因果广播**通道上**发送单个操作**（每 op 送一次、按因果序）。消息小得多，但**要求传输更强的送达保证**。

**用在哪：****协作编辑器**（Figma、Linear、Notion 的本地优先同步）、**离线优先应用**（离线编辑、重连时合并）、以及需要无冲突 active-active 写的**多区域数据库**（Riak、Redis Enterprise）。

**权衡：****元数据开销增长**（已删元素的墓碑、每副本计数器——频繁变动的 OR-Set 会积累大量簿记）；**合并遵循数学而非意图**，故确定性结果可能**对人意外**（两人编辑同一词可能合成谁都不想要的东西）；且**并非每个问题都映射到 CRDT**——像"余额永不为负"这样的约束根本需要协调、无法无冲突表达。

**要点：**
- 数学上保证收敛。
- 无需协调，无需中心权威。
- Yjs/Automerge 在协作文本中流行。
- 元数据开销可能很大。

### 86. Lambda 架构 vs Kappa 架构

**频率：** 低

**题目：** 请对比 Lambda 与 Kappa 数据架构。你何时默认 Kappa、何时保留 Lambda？

**答案：** 两者都解决同一问题——同时提供流数据的**实时**与**准确/完整**视图——但区别在你跑**多少条流水线**。

**Lambda 架构**跑**两条并行流水线**：
- **批处理层**——**慢但准**，周期性**从完整原始数据集重算结果**。它是真相源、处理迟到数据、可重处理一切。
- **速度层**——**快但近似**，处理实时流得到**近实时**结果，填补到下次批处理运行前的空隙。
- **服务层**合并两侧，使查询现在看到实时数据、批处理追上后看到准确数据。

**优点：**干净**处理迟到数据与完整重算**（只需重跑批处理层）。**缺点：**你维护**两套代码与两套系统**实现*同一逻辑*两次——它们不可避免**漂移失同步**（批处理修了但速度层没修的 bug 产生分歧结果），且运维沉重。

**Kappa 架构**消除批处理层：在**持久、可回放的日志**（如带长保留的 **Kafka**）上跑**单一流式管道**。只有**一套代码**。需要重算（bug 修复、新派生视图）时，你**从头回放日志**过一个新的流任务实例——日志*就是*你的重处理机制，故你无需单独批处理系统就获得批处理的重算能力。**现代流引擎（Flink、Spark Structured Streaming）**足够好地处理事件时间、窗口、迟到数据，使单靠流式覆盖了过去需要批处理的多数情形——**模糊了 Lambda/Kappa 界线**。

**何时选：**当你的 **broker 能持久保留并回放历史**时（带足够保留的 Kafka）**默认 Kappa**——一套代码、无同步漂移、更简单运维。仅当**批处理工具对大型冷重算明显更便宜**时（如重处理 PB 级数据，便宜存储上的 Spark 批任务远胜回放流），或当法规/精度要求单独权威批重算时才**保留 Lambda**。

**要点：**
- Lambda：批 + 速度层，逻辑重复。
- Kappa：纯流式，从日志回放。
- Kappa 需要持久且可回放的日志（Kafka）。
- 现代引擎减少了这种二分。

### 87. 管道-过滤器 vs 编排工作流

**频率：** 低

**题目：** 请对比管道-过滤器与编排工作流。你如何选择，它们如何共存？

**答案：** 两者都从更小的步骤组合出更大的流程，但区别在**谁持有控制流与状态**。

**管道-过滤器：****独立、常无状态的阶段**（过滤器）由**流或队列**（管道）连接。每个过滤器**读输入、变换、把输出写**到下一管道，对周围阶段一无所知。控制隐式流动——数据流经管道*就是*协调。它**擅长高吞吐数据变换**：**ETL、媒体/转码管道、日志处理**。优势：**阶段独立扩展**（为慢过滤器加更多实例），且你可**插入/移除/重排过滤器**而不碰其他。

**编排工作流：**一个**中央工作流引擎**（**Temporal、Airflow、AWS Step Functions**）把流程显式定义为**带重试、分支、定时器与人工介入**等待的**步骤**，并**持有**每个在途执行的状态。它**擅长需要正确性与可见性的有状态、长时长业务流程**——如一个订单履约流程：扣卡、等仓库确认（可能数小时）、按库存分支、重试失败步骤、可等数天人工审批。编排器给你**每个执行在哪的持久记录**并保证每步完成。

**如何选——按延迟、状态、可见性：**
- **高吞吐、无状态、流式变换** → **管道-过滤器**（低延迟、简单、独立可扩展）。
- **有状态、分支、需可审计的长时长协调** → **编排工作流**（正确性与可见性优于原始吞吐）。

**共存：**两者自然组合——**编排工作流的单个步骤本身可以是管道-过滤器管道**（如工作流的"处理上传视频"步骤启动一条转码管道），或管道阶段可调用工作流。你用编排器做**业务级、有状态的骨架**，用管道-过滤器做内部的**数据处理肌肉**。

**要点：**
- 管道：流式、无状态阶段。
- 编排器：有状态、分支、长跑。
- 两者可在同一系统并存。
- 按延迟、状态与可见性需求选择。

### 88. Outbox vs CDC 做事件

**频率：** 低

**题目：** 请对比 Outbox 模式与 CDC 两种产生事件的方式。你何时用哪个？

**答案：** 两者都解决**双写问题**——如何在改数据库状态时可靠地发布事件、而不让两者失同步——但它们产生**非常不同种类的事件**。

**Outbox 模式：**你把一个**语义有意义、应用定义的领域事件**（如 `OrderPlaced` 带消费者关心的字段）写入一个**与状态变更*同一数据库事务*中**的 outbox 表。因两个写在一个事务里，它们**原子地一起成功或失败**——无双写不一致。一个独立的**中继**随后读 outbox 并把事件**发布**到 broker。事件是**应用编写、稳定、与你的物理 schema 解耦的**——消费者得到干净的业务事件（`OrderPlaced`），你可重构表而不破坏它们。

**CDC（Change Data Capture）：**像 **Debezium** 这样的工具跟踪数据库的**事务日志（WAL/binlog）**并**发出低层行变更**（`UPDATE orders SET status='paid' WHERE id=42`）。**无应用代码、无额外表**——它纯在数据库层工作，甚至在你无法修改的系统上。代价：消费者看到**原始物理 schema**（列名、行差异）并必须从中**重建业务意图**（"status 变成 'paid'——那意味订单被支付了"）。且 schema 变更（重命名列）**破坏每个消费者**，因它们耦合于你的表结构。

**何时用哪个：**
- **Outbox**——当你**掌控生产者**并想要与 schema 解耦的**稳定、有意义的领域事件**。最适合你有意发布业务契约的**跨服务集成**。
- **CDC**——当你**无法改生产者**（遗留应用或另一团队拥有的数据库），或当你特意想要**数据级复制/同步**而非语义事件——如把表变更流入**搜索索引、数据湖或缓存**。

**两者都是至少一次**，故中继重试或 CDC 重投可能发一事件两次——**消费者必须幂等/按事件 ID 去重**。

**要点：**
- Outbox：领域事件、schema 稳定。
- CDC：行级、无需应用改动。
- Outbox 需要中继；CDC 需要 Debezium。
- 两者都是至少一次；消费者必须去重。

### 89. 流处理（Flink、Kafka Streams、Spark）

**频率：** 低

**题目：** 请对比 Flink、Kafka Streams 与 Spark Structured Streaming。你如何选，事件时间、水印、检查点是什么意思？

**答案：** 三者都用**窗口、连接、聚合、有状态算子**处理**无界事件流**，但在架构、延迟、运维模型上不同。

- **Apache Flink**——**真正逐事件流式**，**最低延迟**（毫秒）与**最精妙的事件时间语义**。它提供**基于检查点的 exactly-once** 状态，是**复杂有状态管道**（大键控状态、精细窗口、CEP）的**最佳选择**。代价是运维复杂——它是一个要运行的完整分布式系统。
- **Kafka Streams**——不是集群而是**直接嵌入你应用的库**。它**运维简单得多**（无独立处理集群——它就是你的应用、像任何服务一样部署）、**随 Kafka 分区扩展**（加实例、分区再平衡），并用 Kafka 事务给出 exactly-once。权衡：它**紧绑 Kafka**（进和出），最适合**嵌入的、每服务的流逻辑**而非巨型中央化管道。
- **Spark Structured Streaming**——流式 API 下的**微批**（每几百毫秒处理小批），故比 Flink**延迟更高**，但它**对已在 Spark 上的团队极佳**——统一批+流代码、成熟生态、擅长 **ETL**。

**如何选：**按**延迟**（需毫秒与重状态 → **Flink**）、**团队熟悉度**（已是 Spark/ETL 店 → **Spark Structured Streaming**）、**复杂度/部署**（想把流逻辑以最小运维嵌入微服务 → **Kafka Streams**）。

**三者都要面对的关键概念：**
- **事件时间 vs 处理时间**——**事件时间**是事件*实际发生*时（内嵌时间戳）；**处理时间**是你系统*看到*它时。正确的分析（如"每小时点击"）必须用**事件时间**，因事件迟到且乱序到达。
- **水印**——一个启发式，说"我大概已见到直到时间 T 的所有事件"；它让引擎**决定何时关闭窗口**、等**迟到数据**多久（以及对水印后到达的掉队者怎么办）。
- **检查点**——周期性快照算子状态，使失败时任务**恢复状态并继续**，支撑 **exactly-once** 处理（状态跨重启不被重复计数或丢失）。

**要点：**
- 事件时间 vs 处理时间很重要。
- 水印处理迟到数据。
- Checkpoint 用于 exactly-once 状态。
- Flink 适合最难的有状态工作负载。

### 90. 时序存储

**频率：** 低

**题目：** 时序存储为什么优化、有哪些关键特性与可选方案，为何基数是隐形杀手？

**答案：** **时序数据库**为带时间戳数据的独特形状而生：**按时间戳排序的追加写**（你几乎从不更新旧点）、**在时间窗口上聚合**（每 5 分钟桶的平均 CPU）、**保留/降采样**（原始数据留短暂、汇总留长久）。用于指标、监控、IoT 传感器、金融 tick。

**代表方案：****InfluxDB**（专用 TSDB）、**TimescaleDB**（Postgres 扩展——SQL 熟悉度 + 时序优化）、**Prometheus**（拉、监控向、临时本地存储）、**VictoriaMetrics**（高性能、Prometheus 兼容）、**ClickHouse**（通用列式 OLAP，对时序与即席分析也极佳）。

**使其快的关键特性：**
- **列式存储**——时间戳与值按列存储，极佳压缩（相似值的长序列），并使只扫你需要的列快速。
- **按时间分区 chunk**——数据分成时间界定的块，故"最近一小时"的查询触及一个小块、老块可整体丢弃。
- **自动降采样/上卷**——把原始点预聚合成更粗汇总（1s → 1m → 1h），使长范围查询读紧凑上卷。
- **基于 TTL 的保留**——按策略自动过期老数据。
- 在时间维度上的**快速范围扫描**。

**为何行存 SQL 数据库规模大了不合适：**通用行存不为数十亿带时间戳的行而建——其**索引膨胀**（数十亿行上的 B 树巨大且维护慢）、写争用、**范围/聚合查询慢到爬**。TSDB 的列式、按时间分区设计才使这些工作负载可行。

**基数——隐形杀手：**在指标系统中，**基数是唯一序列的数量** = 所有标签值组合的乘积（`metric × service × instance × endpoint × …`）。每个唯一组合是一个独立序列、有自己的索引项与内存占用。加一个**高基数标签**（**用户 ID、请求 ID 或邮箱**——数百万不同值）会**把序列乘到百万或十亿**，耗尽内存并使查询停滞。你必须**明确预算基数**并**在 ingest 时拒绝/重打高基数标签**——永不把无界标识符放标签。这是 TSDB 事故的头号原因。

**要点：**
- 列式 + 按时间分区 chunk。
- 内置降采样与保留。
- 基数是失败模式。
- ClickHouse 适合即席分析。

### 91. 租户分区

**频率：** 低

**题目：** 在 pool 型多租户系统中，你如何跨分片分区租户使吵闹邻居不级联，你如何迁移一个租户？

**答案：** 在 **pool 型**系统（共享基础设施、行上带 `tenant_id`——Q58），你仍把租户跨**多个分片**分散，使一个重租户的负载只命中**它的分片**、而非整个舰队——控制**吵闹邻居的爆炸半径**。

**路由策略（租户 → 分片）：**
- **`tenant_id` 的哈希**——`shard = hash(tenant_id) % N`。简单且给出**均匀分布**，但它**僵硬**：你无法把某个大租户从热分片移走，且重分片有破坏性。
- **查找表**——一个显式的 `tenant_id → 分片`映射。最大**灵活**：你可通过更新一行**重定位任何租户**（把巨鲸移到自己的分片）。代价是维护并查询映射。
- **混合（常见答案）**——**哈希多数租户**（便宜、均匀）但经查找表把**最大的 top-N 租户钉到专用分片**。这处理租户大小**高度偏斜**的现实（几个巨头、一条小尾巴）——巨头得隔离、大众用简单哈希。

**迁移一个租户**（在分片间移动一个）必须**零停机**：
1. **批量导出**租户数据到目标分片（初始复制）。
2. **双写窗口**——在复制追上期间把新变更**同时**写老与新分片，故无丢失。
3. **切换**——把路由翻（更新查找表）到新分片、验证，然后停止写老分片并清理。

**额外防御：****每分片容量上限**（单租户不得填满分片——在它做到前触发迁移）、**按租户按分片可观测性**（尽早发现热租户*及它在哪个分片上*）、加**按租户限流与断路器**。分区是抵御多租户过载的**主要结构防御**；限流/断路器是战术后盾。

**要点：**
- 哈希、查找或混合分片路由。
- 把大租户钉到独立分片。
- 提前规划租户迁移。
- 每租户可观测性是必备。

### 92. GDPR / 数据驻留

**频率：** 低

**题目：** GDPR 与数据驻留要求如何塑造系统架构？为何在事件溯源系统中墓碑不满足删除权？

**答案：** **GDPR** 授予个人你的架构必须主动支持的权利：处理的**合法依据**，以及**访问**（导出其全部数据）、**更正**（改正它）、**删除**（"被遗忘权"——删除它）、**可移植**（以机器可读形式获取）的权利。**数据驻留**法（在**欧盟、中国、俄罗斯、印度**等）额外要求某些数据**物理留在国内/区内**。

**这些如何塑造设计：**
1. **按区域存储或假名化**——为满足驻留，**每个驻留区跑独立存储/环境**使欧盟数据留欧盟、中国数据留中国等（见地理分布 Q59）。可行处**假名化**以最小化可识别数据。
2. **静态加密加按租户（或按用户）密钥 → 加密粉碎**——这是**删除**的优雅机制：把每个主体的数据用**专用密钥**加密，要"删除"他们只需**销毁密钥**。密文瞬间变成无密钥不可恢复的垃圾，无需物理追踪并删除每个副本（备份、副本、归档）——当数据散布在许多存储时极有价值。
3. **事件溯源系统需要特殊处理——墓碑不满足删除。**在事件溯源（Q4）中，事件日志是**不可变、只追加的**——那是重点。追加一个**墓碑**（"用户 X 已删"）**不**移除仍含用户 PII 的早期事件，故数据**仍在**、GDPR **未**满足。你必须**重写/压实日志以物理移除带 PII 的事件**，或（更好）**加密粉碎**：在事件中按用户加密存 PII 并删密钥，使那些历史事件不可读而保持日志结构完整。
4. **PII 分类、血缘、目录与 DPIA**——你无法保护你找不到的，故**在 ingest 时分类 PII**、维护**数据血缘**（追踪每块 PII 流向哪）、保持**数据目录**、对新特性跑 **DPIA（数据保护影响评估）**流程。这些治理实践对向监管者证明合规是**不可妥协的**。

**要点：**
- 按区域存储以满足驻留。
- 事件溯源用加密粉碎实现删除。
- 按租户密钥支持选择性删除。
- PII 分类与血缘必备。

### 93. 零信任网络

**频率：** 低

**题目：** 请解释零信任网络模型。它的构建块是什么，相比 VPN 的成本/收益如何？

**答案：** **零信任**用**"永不信任、始终校验"**取代旧的"城堡与护城河"模型——后者对网络边界*内部*任何东西隐式信任。**不存在基于网络位置的隐式信任**：在公司 LAN 上或集群内**什么都不给**你。**每一个请求——包括东西向（服务到服务）流量——都被认证、授权、加密**，就像它来自开放互联网。前提是边界*终将*被攻破，故进入内部的攻击者应发现**没有柔软的内里**可穿行。

**构建块：**
1. **服务身份（SPIFFE/SVID、workload identity）**——每个工作负载有它证明的**密码学身份**，而非仅 IP 地址（IP 可伪造、会重分配）。
2. **服务间 mTLS**——双向 TLS 使**两端都认证**且所有内部流量**加密**（见 Q94）。
3. **面向用户的身份感知代理（Google 的 BeyondCorp）**——用户访问按请求由**身份 + 设备态势**门控，而非"你在 VPN 上吗？"。
4. **短时凭证（Vault、IAM 角色）**——无长命静态密钥；凭证快过期，缩小泄露一个后可用的窗口。
5. **每请求策略（OPA、服务网格策略）**——对**每个**请求做授权决策（"服务 A 可否调服务 B 的端点 X？"），中央一致地评估。

**相比 VPN：**它**取代 VPN 模型**——VPN 一旦你"进入"就授予广泛网络访问，正是零信任拒绝的平坦信任问题；BeyondCorp 让用户从任何地方按请求门控地访问特定应用而无需 VPN。

**成本/收益：****成本**是**巨大的平台投入与复杂度**（身份基础设施、网格、策略引擎）加**额外每请求检查带来的延迟**。**收益**巨大：**泄露的爆炸半径骤减**——被攻陷的服务无法自由漫游因每跳都被重新校验——且**内部威胁与横向移动变得难得多**。对有许多服务的成熟组织，安全收益证明投入合理。

**要点：**
- 网络无隐式信任。
- mTLS + 服务身份 + 每请求策略。
- 取代 VPN（BeyondCorp 模型）。
- 平台投入巨大，安全收益大。

### 94. 网格中的 mTLS

**频率：** 低

**题目：** 服务网格中的 mTLS 如何工作、为何重要、成本是什么？

**答案：** **常规 TLS** 只认证**服务端**（客户端验证它确实在与 `bank.com` 对话）；服务端对*客户端是谁*无密码学证明。**双向 TLS（mTLS）**加上反向：**客户端与服务端都出示证书并互相验证**，故**每次服务到服务调用都密码学地证明双方身份**。结合加密，这意味服务*确切*知道哪个服务在调它（而非仅"某 IP"），且它们之间所有流量机密且防篡改。

**为何服务网格使其可行：**手工实现 mTLS——在每个服务、每种语言中签发、分发、轮换、校验证书——痛苦且易错。**网格（Istio、Linkerd）**通过 **sidecar 代理完全自动化**：一个**内部证书颁发机构（CA）**签发**短时证书**（每 24 小时或更短轮换），sidecar 代表应用**透明处理 mTLS 握手**。应用代码**完全不含 TLS 逻辑**——它对 `localhost` 做普通调用，sidecar 把它升级为已认证、加密的 mTLS。

**为何重要：**mTLS 是集群*内部***零信任的基础**（Q93）。它**加密所有东西向流量**（故网络嗅探者什么都看不到）并提供**强、可验证的服务身份**——正是**授权**策略决定"服务 A 可否调服务 B？"所需。没有可信身份，集群内授权毫无意义。

**成本：**
- **CA 管理**——你现在跑一个内部 CA 并必须保护其根密钥（CA 被攻陷破坏一切）。网格处理大部分，但它是真实基础设施。
- **每握手延迟**——双向握手增加少许延迟，**由会话恢复/keep-alive 缓解**使它罕付而非每请求。
- **调试被拒请求**——"为什么这个调用被拒？"（证书过期？身份不匹配？策略拒绝？）需要网格里**良好的策略/可观测性工具**，否则变不透明。

对有许多服务的成熟平台，mTLS 本质是**基本门槛**——安全内部通信的基线。

**要点：**
- 双方都用证书认证。
- Sidecar 透明地处理轮换。
- 零信任 + 授权的基础。
- 内部 CA 是关键。

### 95. WAF 放在哪里

**频率：** 低

**题目：** 什么是 Web 应用防火墙，它应放在哪，为何它不是安全编码的替代？

**答案：** **Web 应用防火墙（WAF）**检查**进入的 HTTP 流量**并阻断匹配已知**攻击模式**的请求——**OWASP 式**经典：**SQL 注入（SQLi）、跨站脚本（XSS）、远程代码执行（RCE）、路径穿越**，以及已知漏洞签名。它坐在**第 7 层**，理解 HTTP 语义（头、参数、体），不同于网络防火墙。

**放置——在边缘：**尽量往外部署——**Cloudflare、AWS WAF、Akamai**——使它在恶意流量**触及你的基础设施前就检查并丢弃**。这在边缘（你有海量容量处）**便宜地吸收 bot 与已知漏洞扫描**，把垃圾挡在源站服务器与应用之外。边缘也是你有规模处理攻击流量之处。

**权衡：**
- **误报**——过于激进的规则可能**阻断合法流量**（一个恰好看着像注入的有效请求），故 WAF **必须按应用调优**——先在监控/日志模式起步，再强制。
- **按应用调优**——通用规则不适合每个应用；每个都需自己的调优在保护 vs 误报间平衡。
- **托管规则滞后新型漏洞**——基于签名的规则只抓**已知**攻击；**零日**或新型漏洞在规则写出前直接穿过。

**为何必要但不充分：**WAF 是纵深防御（Q62）中的一**层**，非全部防御。**配合限流、bot 管理、RASP（运行时应用自保护）**。关键是，它**不是安全编码与依赖卫生的替代**——WAF 是你应用**前的过滤器**，但**真正的防御是一开始就不脆弱的代码**：参数化查询（不靠 WAF 抓 SQLi）、输出编码、输入校验、依赖保持打补丁。把 WAF 当主要防御是虚假安全感——它买时间、挡明显的，但坚决的攻击者会找到它漏掉的。

**要点：**
- 放在边缘（CDN/WAF 服务）。
- 阻断 OWASP 类攻击。
- 调优以避免误报。
- 不能替代安全代码。

### 96. 混沌工程

**频率：** 低

**题目：** 什么是混沌工程，成熟度进程如何，为何文化比工具更重要？

**答案：** **混沌工程**是**故意注入故障**——**杀 pod、隔离网络、慢盘、耗 CPU/内存、加延迟**——到类生产或**生产**环境的实践，以**在真实事故之前发现弱点**。逻辑是分布式系统以你无法完全预测的方式失败，故与其*希望*你的冗余与故障切换有效，不如在受控条件下**经验性地证明它**。每个实验都是**假设驱动**："我们相信杀这个 pod 不影响用户——让我们验证"，一个*意外*就是你按自己方式发现的 bug。

**成熟度进程**（爬 → 走 → 跑）：
1. **staging 的 game day**——从小起步：在**非生产**环境有计划、手动的故障注入演练，团队观察。低风险，建立信心与可观测性。
2. **限制爆炸半径的受控生产实验**——毕业到**生产**但**控制损害**：瞄准小 canary 切片、在工作时间由工程师待命跑、能瞬间中止。生产是*真正*弱点所在。
3. **持续混沌（Chaos Monkey 风格）**——成熟端：生产中**自动、持续**的随机故障注入，使韧性被持续验证、而非仅在计划事件时。

**前置条件（别跳过）：****扎实的可观测性**（你必须*看到*影响才能学到任何东西）、**SLO/错误预算**（知道多少破坏可接受）、**自动回滚**（实验一超爆炸半径就中止）。无这些跑混沌只是制造事故。

**工具：****Chaos Mesh、LitmusChaos、Gremlin、Pumba**（及原始的 Netflix Chaos Monkey）。

**为何文化比工具更重要：**工具是容易的部分。混沌工程只在**无指责、面向学习的文化**中有效——发现的弱点是**待修的胜利**、非要追责的人；实验是**假设驱动**（你学到系统是否如所信行为）；**事后复盘被当学习而非惩罚**读。在追责文化里，没人敢注入故障、发现被隐瞒、实践消亡。思维转变——把失败当老师拥抱——才使它成功。

**要点：**
- 注入故障以发现弱点。
- 从 staging 开始，逐步到生产。
- 可观测性与回滚是前置条件。
- 文化比工具更重要。

### 97. 成本可观测性与单位经济

**频率：** 低

**题目：** 什么是云系统的成本可观测性与单位经济，为何把成本当一等非功能性需求？

**答案：** **成本可观测性**意味**度量你的云开销实际去哪**——**按特性、按租户、按请求**——而非盯着单张月账单。不度量这个的团队会被**打个措手不及**：账单跳 40% 而没人能说*为什么*，或一个"免费"特性悄悄花得比赚得多。**单位经济**把它降到可行动的比率：**每用户金额、每请求金额、每 GB 存储金额**——使你知道增长的边际成本、以及一个特性/租户是否盈利。

**如何获得可见性：****给一切打标签**（服务、团队、环境、特性）使每个资源的成本**可归因**；用**成本分摊报表**按这些标签切开销；把**单位成本**作为跟踪的 **KPI**、像任何其他指标一样随时间观察。

**FinOps 实践：**
- **showback/chargeback**——展示每个团队*它们*花了什么（showback），或实际计入其预算（chargeback），驱动主人翁意识。
- **定期成本评审**——把成本当经常性工程关注、而非年度财务惊吓。
- **花费异常告警**——对**日**花费尖峰告警，使失控任务或错配在数小时内被抓、而非月末。
- **自动 rightsizing**——缩小超配实例/卷的建议。

**架构选择有"成本形态"：**
- **无服务器 vs 容器**——无服务器（Lambda）在**低/尖峰流量**便宜（按调用付费）但在**稳态高量**常**更贵**，那里常开容器更便宜。交叉点很重要。
- **多 AZ/跨区数据传输**——**出口与 AZ 间传输费**悄悄累加，对多话系统可远超计算成本。
- **日志——隐形预算杀手**——规模化的冗长日志（摄入+存储+索引）常在无人注意中膨胀成最大项目之一。

**为何一等：**成本是**对业务的真实约束**，恰如延迟或可用性。若你只为性能优化而忽略成本，你造出能跑但**经济上不可行**的系统。把成本当**一等非功能性需求**——为其设计、度量、评审——使系统随扩展保持可持续，并把权衡（花更多换低延迟？更便宜存储换慢查询？）作为**显式工程决策**而非意外浮现。

**要点：**
- 一切打标签；按团队/特性可见。
- 单位成本（每用户/请求）作为 KPI。
- 对日花费异常告警。
- 日志和出口流量是隐形杀手。

### 98. 边缘计算（Workers、Lambda@Edge）

**频率：** 低

**题目：** 什么是边缘计算（Cloudflare Workers、Lambda@Edge），它的约束是什么，边缘+源站模式是什么？

**答案：** **边缘计算**在 **CDN 存在点（PoP）**运行你的代码——数百个物理靠近用户的位置——而非在中央源站。平台：**Cloudflare Workers、Lambda@Edge、Fastly Compute、Deno Deploy**。回报是**超低延迟**：代码在离用户 **10-50ms** 处跑、对比到远源站的 **100-300ms**，因计算离你几网络跳。

**用例**（值得就在边缘做的事）：
- **A/B 路由**——在请求走远前决定用户得哪个变体。
- **边缘鉴权**——校验 token/JWT 并拒绝未授权请求，无需往返源站。
- **个性化与地理路由**——按用户位置即时定制或路由。
- **图片变换**——在边缘缩放/优化图片。
- **带自定义逻辑的 API 缓存**——用比普通 CDN 更精妙的规则缓存。

**约束（边缘是受限环境）：**
- **极小运行时**——**V8 isolate 或 WebAssembly**，非完整容器，故启动即时但环境受限。
- **短 CPU 预算**——通常每请求 **~50-500ms** CPU；无长运行或重计算。
- **有限库**——受限 API，非完整 Node/OS 环境。
- **存储是最终一致 KV**——边缘 KV 存储**高读复制但低写吞吐且最终一致**；边缘无强一致数据库。

**架构模式：****边缘处理薄逻辑+缓存；源站处理重逻辑+写。**把**延迟敏感、轻量、读多**的工作（鉴权检查、路由、缓存服务、小变换）推到边缘，把**重计算、事务性写、强一致数据**留源站。这给全球用户对常见路径**敏捷的响应**、同时把复杂/一致的工作中央化。它对**受众地理分布的读多工作负载**大放异彩。

**要点：**
- 代码运行在 CDN PoP；50ms 以下延迟。
- V8 isolate/Wasm；CPU 预算短。
- 存储是最终一致 KV。
- 边缘做薄逻辑；源站做重逻辑。

### 99. 日志聚合（类 Splunk/ELK）

**频率：** 低

**题目：** 请设计一个类 ELK/Splunk 的日志聚合系统（每天 TB 摄入、近期快速搜索、长期归档、告警）。对比 Loki vs Elasticsearch 并覆盖扩展。

**答案：** **需求：**从许多服务摄入**每天 TB** 级**结构化与非结构化**日志、提供**近期数据的快速搜索**、保持**长期归档**、**对模式告警**。日志体量巨大且尖峰，故设计关乎**缓冲、便宜存储层、控制体量**。

**组件（流水线）：**
1. **收集器**——轻量 agent（**Fluent Bit、Vector、OpenTelemetry sidecar**）跑在服务旁、**送出日志**，可在源头解析/富化/采样。
2. **缓冲（Kafka）**——坐在收集器与索引器之间**吸收尖峰**。日志体量突发（一个事故产生洪流）；Kafka 把摄入与索引解耦，使激增缓冲而非压垮或丢弃。
3. **索引器**——**Elasticsearch/OpenSearch、Loki 或 ClickHouse** 构建**可搜索索引**。成本/能力权衡在此（下方）。
4. **对象存储（S3）**——便宜地放**原始日志与冷归档**做长保留/合规，与热的可搜索索引分离。
5. **查询 UI**——**Kibana**（对 ES）或 **Grafana**（对 Loki）做搜索、仪表板、告警。

**Loki vs Elasticsearch——关键选择：**
- **Elasticsearch** **索引一切**（所有字段全文）→ **丰富、快速的任意查询**，但规模化**贵**（完整索引大且吃资源）。
- **Loki** **只索引标签**（服务、级别等）并把日志*体*作为压缩块存对象存储 → **便宜得多**，但**全文搜索更慢**（它按标签过滤、再 grep 块）。当你需要强大即席搜索且能付费时选 **ES**；当你主要按标签过滤且想低成本时选 **Loki**。

**扩展：**
- **按时间分片索引**——每时间窗一个索引（每天），故老索引可整体关闭/丢弃、"最近一小时"查询触及一个小索引。
- **热/温/冷层**——近期数据在快（贵）存储、老数据在更便宜/慢节点、最老作为 S3 原始归档。这个分层是主要成本杠杆。
- **在源头采样与结构化**——最大胜利：**强制结构化日志**、**生产丢弃 debug 日志**、在**收集器**处**采样噪音服务**，在它们触及流水线前。因日志体量是成本驱动，上游削减胜过扩展后端。

**要点：**
- Kafka 在收集器与索引器之间吸收峰值。
- ES = 查询丰富，贵；Loki = 仅标签，便宜。
- 热/温/冷分层降成本。
- 源头采样并结构化。

### 100. 多人游戏服（匹配、状态同步）

**频率：** 低

**题目：** 请设计一个多人游戏服务器（60Hz、匹配、反作弊、百万并发）。覆盖状态同步与延迟补偿。

**答案：** **需求：**实时游戏玩法（**60Hz tick**——每秒 60 次模拟更新）、按**技能/区域/延迟**匹配、**反作弊**、**持久成长**、**百万并发**。核心张力是**实时响应 vs 一致公平**跨不可靠网络。

**组件：**
- **匹配器**——按**区域/模式**分**队列**（低延迟与公平对局需要），用**基于技能的 MMR 桶**配对相近水平玩家。有**公平 vs 排队时间**张力：太严的技能匹配意味长等待，故**随时间放宽窗口**——先要紧对局，等久了扩大可接受范围。
- **会话服务器**——**每对局的专用进程**跑**权威模拟**（服务器、非客户端，是真相）。**通过 Agones on Kubernetes 按需启动**、对局结束**拆除**。
- **状态同步**——**服务端权威 + 客户端预测/协调**：客户端本地预测运动使输入感觉即时，服务器校正分歧。**UDP 上 delta**（只发变化、UDP 因速度而非可靠——过时状态无用）。**命中检测的延迟补偿**：服务器把世界**回退到射击手看到目标时的视图**，故高延迟玩家仍能命中他们*看到*的。
- **持久存储**——**玩家档案/库存在 SQL**（事务、一致），**对局历史在 OLAP**（分析、排行榜）。
- **语音/聊天**——**独立服务**，与游戏模拟解耦。
- **反作弊**——**服务端校验**（服务器拒绝不可能的移动/动作，因它是权威）+ **客户端检测**（抓已知作弊程序）。

**扩展：**
- **区域集群**——把玩家路由到最近区域降延迟。
- **对局装箱**——高效把对局打包到会话服务器最大化利用。
- **优雅排空**——对局结束时优雅拆除会话服务器（不打断进行中的对局）。

**权衡：**
- **服务端权威**打败作弊（服务器是唯一真相源）但**耗 CPU**（服务器模拟每对局）。
- **rollback netcode**（格斗游戏——回退并重放输入）vs **客户端预测/插值**（FPS）——不同品类不同技术。
- **延迟补偿利好射击手**（他们命中所见）但**不利目标**——产生"我明明躲到掩体后了还被打中"，因服务器为射击手回退了时间。这是不可避免的公平权衡。

**要点：**
- 权威服务器 + 客户端预测。
- 固定 tick 的 UDP delta。
- 匹配器平衡 MMR vs 排队时间。
- Agones 风格编排专用会话服务器。
